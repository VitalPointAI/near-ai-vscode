<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| External wallet ↔ extension/webview | An external signer authorizes a public account and may return a transaction outcome through a browser callback; private keys remain in the wallet. |
| Verified staking configuration ↔ transaction builder | Network, RPC, validator/pool, method, and entitlement endpoint data determine where a value-changing action could execute. |
| Read-only RPC/entitlement responses ↔ status/history | Untrusted remote data becomes user-visible balances, credits, and audit facts. |
| Extension host ↔ webview/model/profile stores | Wallet status and previews cross into presentation code but must not enter model context, API-key profiles, or project attribution. |

## Least-Privilege Constraints

- The wallet bridge may authorize one selected public account and submit one immutable, user-confirmed preview; it has no local filesystem credential reader and no private-key API.
- Only verified release configuration may supply a validator/pool receiver, supported contract methods, network, RPC, and entitlement endpoint; user input can select an operation/amount but cannot choose an arbitrary receiver.
- Status reads are read-only and must cross-check account, network, validator, response shape, numeric bounds, and freshness before display.
- Approval and preview fingerprints bind signer, receiver, method, arguments, amount, gas, attached deposit, network, validator, config digest, and expiry; any change invalidates the preview.
- Wallet audit/history stores only bounded operational facts; API keys, refresh tokens, seeds, private keys, signed payloads, prompts, context, commands, and unrestricted paths are excluded.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-05-09 | Spoofing | wallet account/network binding | high | mitigate | Bind the public account to the wallet session and verify the wallet/network identity against the verified configuration before reads or writes. |
| T-05-10 | Tampering | validator/configuration and transaction builder | critical | mitigate | Use only verified configuration, canonical preview hashing, receiver/method allowlists, expiry, and immediate pre-submit revalidation. |
| T-05-11 | Elevation of privilege | approval-to-wallet submission | critical | mitigate | Require fresh existing network approval plus an explicit preview confirmation; keep the wallet call unreachable from refresh/read-only/status paths and test call counts. |
| T-05-12 | Information disclosure | wallet bridge, webview, model context, profiles | critical | mitigate | Keep signing material external, use allowlisted DTOs, reject credential-shaped fields, and test API-key/profile/seed/prompt/context leakage. |
| T-05-13 | Repudiation | callback and transaction history | high | mitigate | Bind callback state to preview/account/expiry, reject replay, record non-sensitive transaction ID/outcome, and poll authoritative status after redirect. |
| T-05-14 | Tampering | balance/credit status | high | mitigate | Validate response account/network/validator, numeric ranges, source, and freshness; reject forged or mismatched responses instead of displaying them. |
| T-05-15 | Denial of service | RPC/entitlement refresh and history | medium | mitigate | Bound response sizes, event/history counts, polling attempts, callback lifetime, and retry behavior; preserve stale/unavailable recovery. |
| T-05-16 | Information disclosure | local audit/history/export | high | mitigate | Reuse bounded `AuditStore` redaction and add wallet-specific allowlists that retain only account/network/validator/amount/transaction/outcome facts. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installation is planned; the external wallet is an injected bridge, and any later dependency adoption must pass the official package-legitimacy gate. |
</threat_model>
