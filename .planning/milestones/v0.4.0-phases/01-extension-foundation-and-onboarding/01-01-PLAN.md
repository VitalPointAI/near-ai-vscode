# Plan 01-01: Extension Walking Skeleton and Packaging

## Objective

Create a maintainable TypeScript VS Code extension that activates reliably, exposes the initial Near AI/Open-GSD commands, and can be packaged as an installable VSIX.

## Requirements covered

PKG-01, TEST-01, GSD-02, GSD-03, GSD-04, GSD-05

## Design note

The branded reasoning/thinking animation is intentionally scheduled for Phase 3 with the chat surface, where its state machine can represent actual provider/agent lifecycle events. It should be implemented as a lightweight code-native/vector UI asset rather than a raster dependency, with `prefers-reduced-motion` behavior and an accessible live status label.

## Tasks

### 1. Scaffold the extension

- Add `package.json` with VS Code engine compatibility, activation events, commands, configuration contributions, scripts, and development dependencies.
- Add TypeScript compiler/linter/test configuration with strict settings and source-to-dist output.
- Add the extension entry point and a small dependency-free service composition root.
- Add a README with local development, launch, test, and VSIX installation instructions.

### 2. Define stable extension boundaries

- Create interfaces for provider configuration, authentication status, onboarding state, action policy, and workspace/GSD state.
- Keep VS Code API calls at adapters so core policy/configuration logic can be unit tested without an extension host.
- Register placeholder commands for setup, status, open chat, and GSD progress; return useful status when later phases are not yet installed.

### 3. Add packaging and quality gates

- Add build, lint, unit-test, and package scripts.
- Add ignore files so generated output, secrets, and local state cannot enter the workspace.
- Verify `vsce package` produces a VSIX and that the extension manifest contains only intended commands/settings.

### 4. Add Open-GSD release synchronization

- Add a startup coordinator that checks the stable `@opengsd/gsd-core@latest` metadata on every activation and schedules a recurring check at least every 24 hours for long-lived extension hosts.
- Detect the installed Open-GSD version and installation scope, compare semver safely, and report the current/latest versions.
- When behind, invoke the official Open-GSD update/install contract (`npx @opengsd/gsd-core@latest` with the supported runtime/scope) rather than copying package files directly.
- Synchronize the active project through the Open-GSD installer/update path, preserving user-added files and surfacing any migration or conflict result.
- Restrict package/channel/registry inputs, redact command output, serialize updates with a lock, support cancellation, and write a durable last-result record for recovery/status.
- Verify Open-GSD's context-monitor/checkpoint hooks are enabled for the active runtime after installation; configure warning at 35% remaining and critical at 25% remaining, then provide a fallback handoff/checkpoint path for runtimes without native context hooks.

## Verification

- TypeScript build completes with strict checking.
- Lint and unit tests pass.
- Extension host smoke test activates the extension and registers all Phase 1 commands.
- VSIX packaging succeeds and the generated package excludes source secrets, test fixtures, and `.planning` internals unless explicitly intended.
- Startup updater tests verify latest-version checks, no-op when current, update invocation when stale, daily timer behavior, official-package restrictions, cancellation, and failure recovery.
- Continuity tests verify warning/critical thresholds, checkpoint-before-compaction behavior, handoff restore, and safe degradation when runtime context metrics are unavailable.

## Done when

An independent developer can clone the repository, install dependencies, launch the extension in an Extension Development Host, run the setup/status commands, and install the generated VSIX.
