# Plan 01-02: Onboarding, Authentication, and Safe Defaults

## Objective

Give a new user a clear first-run setup flow that configures NEAR AI access without leaking credentials and makes the default action policy visible and predictable.

## Requirements covered

ONB-01, AUTH-01, AUTH-02, SAFE-01, PRIV-01, TEST-01

## Tasks

### 1. Implement secure configuration storage

- Store API keys only through `ExtensionContext.secrets`.
- Store non-sensitive preferences through VS Code configuration with explicit defaults for provider URL, selected auth mode, model preference, and action policy.
- Ensure logs and error messages redact bearer tokens, refresh tokens, and key-like values.

### 2. Build onboarding and status flows

- Add a first-run command/view that explains TEE-backed inference, what context may be sent, authentication choices, and approval defaults.
- Support API-key setup, validation, replacement, and removal without ever echoing the secret.
- Add a NEAR sign-in adapter contract with a clear “not configured/needs validation” status until the exact supported exchange is implemented.
- Provide a status command that reports auth mode, configured endpoint, selected model (if any), policy mode, and verification availability without exposing secrets.

### 3. Implement action policy defaults

- Define policy capabilities for read/inspect, plan, workspace write, shell, network, and git mutation.
- Default read/inspect and planning to allowed; default writes, shell, network, and git mutation to approval-required.
- Make policy changes explicit, persisted, and visible in the status/onboarding UI.
- Expose an emergency-stop state that later agent execution can consume.

### 4. Test security and onboarding behavior

- Unit test configuration serialization, default policy, secret redaction, and auth-state transitions.
- Test setup cancellation, invalid credentials, replacement, removal, and re-opening onboarding.
- Add an extension-host smoke path proving secrets are stored through SecretStorage and not workspace files.

## Verification

- No API key or token appears in tracked files, workspace settings, output channels, or thrown error text.
- A fresh install reaches a usable status screen without requiring undocumented manual edits.
- Risky actions are approval-required on first run.
- API-key setup and removal work end-to-end with a mocked provider validation endpoint.
- The NEAR sign-in boundary is documented with an explicit pending capability rather than a misleading success state.

## Done when

A new user can install the VSIX, run onboarding, configure either supported authentication path as available, inspect the active privacy/safety state, and trust that credentials and risky action defaults are handled safely.
