<objective>
Durable per-person secrets and long-term keys that never enter the session (P3, P4; D-04, D-15 to D-21, D-25, D-36, D-37, D-43; FND-T-03, FND-T-04): every secret saved through Theia's key store goes to the person's own OpenBao path (or the OS keyring on a single machine, or fails visibly), and signing and key wrapping happen inside OpenBao Transit, with signing refused without a fresh hardware-key or passkey sign-in.

Purpose: success criteria 3 and 4.
Output: the path encoding and stores (Theia-free, unit tested), the rebind with the keyring override and the "secrets unavailable" notice, the KeyService and its RPC, and a real KV and Transit test against the dev OpenBao.

Planning choices (discretion, reported in the summary):
1. Segment encoding `u` + base64url (never empty, never `.` or `..`, no `/`, reversible for `keys()` and `findCredentials()`), research Pattern 2. `deletePassword` deletes metadata (all versions). Rating costly: free to change until the first site stores secrets; after that a change needs a per-site KV path migration, so it is in the Phase 47 contract.
2. The KeyService RPC exposes `sign` and `generateWrappedDataKey` only; `unwrapDataKey` stays a backend call for Phase 33's backend code. Rating reversible.
3. The secret store status is its own small RPC (`/services/sterling-secret-store`) so the browser can say "Secrets are unavailable" at start, not only when a save fails. Rating reversible.
</objective>
