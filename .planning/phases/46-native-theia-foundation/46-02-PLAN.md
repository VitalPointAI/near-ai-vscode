<objective>
Session identity (P5): the backend knows who signed in from the forwarded sign-in token and `THEIACLOUD_SESSION_USER`, logs in to OpenBao with jwt auth, renews and revokes its token with the session, shows `failed` with a reason and Retry, and can start a step-up sign-in (D-03, D-05, D-21 to D-25, D-37, D-38; FND-T-05).

Purpose: secrets (46-07) and long-term keys (46-07) need the person's OpenBao token and entity id; this plan is their only source.
Output: a Theia-free OpenBao client and identity state machine with unit tests, their Theia wiring and status in the browser, and a real login against a dev-mode OpenBao.

Planning choices (discretion, reported in the summary):
1. `IDENTITY_TIMEOUT_MS` = 60 s, a constant (no new setting). A `failed` state whose reason is "no sign-in reached this session" returns to `identity` by itself when a token arrives, because a person can open the page after the timer; every other `failed` leaves only by Retry. Rating reversible.
2. `STERLING_OPENBAO_ADDR` accepts `http:` only for a loopback address (an OpenBao agent in the pod; also how the tests reach the dev server); anything else must be `https:`. Recorded for the Phase 47 contract in 46-08. Rating costly.
3. An invalid hosted setting (bad address, mount name, step-up window) stops the backend at start with one sentence naming the setting; it is not a `failed` state, because Retry cannot fix configuration. Rating reversible.
4. The person check compares emails (`THEIACLOUD_SESSION_USER`, `X-Auth-Request-Email`, the token's `email` claim when present); `X-Auth-Request-User` is kept for the status only. The token's signature is checked by OpenBao's jwt login, never locally (research Pattern 3). Rating reversible.
</objective>
