Planning choices (discretion, reported in the summary):
1. The job runs on every PR and every push (like `hub`) rather than on a path filter, because the engine bundle reads `src/` and a filter would miss those changes. Rating reversible.
2. The signing job verifies with the public key derived from the private key in the same job (`cosign public-key --key env://COSIGN_PRIVATE_KEY`) and uploads it with the digest; publishing the public key for sites belongs to the release cutover and Phase 47's key ceremony. Rating reversible.
3. The image the container suite tests is the one scanned and, on main, saved and signed: the job builds `sterling-workbench:ci` once and passes `WORKBENCH_TEST_IMAGE` to the suite. Rating reversible.

Gate files and tools needing the owner's approval in the integration PR: `.github/workflows/ci.yml`, `scripts/test/workflow-files.test.mjs`, and the new cosign tool pin (the TOOLS.md precedent; CONTEXT owner items 2d and 6).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| PR code to CI runner | untrusted PR code runs the build and tests |
| CI to signing key | the protected environment's secret meets the image |
| CI to registry | the signed image becomes the artifact sites trust |
