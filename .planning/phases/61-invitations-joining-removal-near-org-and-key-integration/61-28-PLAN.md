The core of "Ask to join" (G-61-9, owner design 2026-11-04 item 2): an invite in reverse. The requester's computer makes the single-use code and keeps it; the request carries only the public key derived from it; the lead's accept writes a normal invitation for that key; the requester's computer then joins by itself with the existing proof. export const JOIN_REQUEST_PREFIX = 'near-ai-join-request-v1.';
export interface JoinRequest { v: 1; team: string; ref: string; member: string; name: string; email?: string; key: string; sig: string }
export class JoinRequestError extends Error {}
export function parseJoinRequest(text: string): JoinRequest;                  // checks shape, size (at most 2048 bytes), patterns, no secret shape in any field, and sig over the canonical body without sig with the purpose 'near-ai.team.join-request'
export function requestCheckCode(request: JoinRequest): string;               // 8 characters in two groups, from a hash of the canonical request, shown to both people
export async function createJoinRequest(input: { secrets: SecretStorageLike; teamFile: TeamFile; name: string; email?: string }): Promise<{ text: string; checkCode: string; memberId: string }>;
// stores { memberId, code (text), name, email? } under SecretStorage key nearAi.team.joinRequest.<teamId>; returns the stored request again when one exists
export async function readPendingRequest(secrets: SecretStorageLike, teamId: string): Promise<{ text: string; checkCode: string; memberId: string; name: string } | undefined>;
export async function cancelJoinRequest(secrets: SecretStorageLike, teamId: string): Promise<void>;
export async function acceptJoinRequest(input: Omit<InviteInput, 'name' | 'email'> & { request: JoinRequest; email: string }): Promise<{ ok: true; memberId: string; nearInvitation: 'sent' | 'already-member' | 'queued' | 'not-applicable'; notice?: string } | { ok: false; code: 'refused' | 'conflict' | 'offline'; message: string }>;
// records { memberId, name, invitedEvent } in accepted-requests.json in the team's storage folder (no email, no key)
export async function wasAcceptedHere(storageDir: string, memberId: string): Promise<boolean>;
export type CompleteOutcome = { kind: 'none' } | { kind: 'not-yet' } | { kind: 'joined'; result: Extract<JoinResult, { ok: true }> } | { kind: 'expired' | 'cancelled' | 'used' | 'failed'; message: string };
export async function completeJoinRequest(input: Omit<JoinInput, 'bundle' | 'displayName'> & { state: TeamState }): Promise<CompleteOutcome>;
// none: no stored request; not-yet: no matching invitation in state; joined: joinTeam ran with a bundle built from the stored code, the stored request is deleted

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| requester -> lead (chat or email) | The request text travels in the open |
| request text -> lead's computer | Hostile pasted text |
| lead's accept -> team record | A signed invitation bound to the requester's public key |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-61-109 | Spoofing | someone sends a request in another person's name | medium | mitigate | The request can only be completed by the computer holding its code, so a forged request lets in only the forger; the lead sees name, email and the check code and the 61-29 accept dialog asks them to check it with the person; the lead still confirms (or the accepting computer confirms on the lead's behalf, 61-29) |
| T-61-110 | Tampering | name or email changed in transit | low | mitigate | Self-signature by the derived key over the canonical request; tests refuse a changed field |
| T-61-111 | Information disclosure | the code or a key in the request, log or files | high | mitigate | The code stays in the requester's SecretStorage; the request carries the derived public key only; canary test over every place |
| T-61-112 | Elevation of privilege | a non-manager accepts, or a request is accepted twice | medium | mitigate | member.invite permission through the log's write-side checks; a member id already on the record is refused |
| T-61-113 | Denial of service | a large or malformed request | low | mitigate | 2048-byte cap and strict parsing before any work |
| T-61-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan |
</threat_model>
