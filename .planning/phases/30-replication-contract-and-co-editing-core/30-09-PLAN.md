<objective>
Ordering, finality and incremental folding: the deterministic total order proven against a topological reference, the checkpoint format with its order tip, the rule that checkpointed order is final, incremental application with refold on late concurrent entries, and the transport interface as types (MUS-01; D-08, D-10, D-14, D-15, D-36).

Purpose: a machine that folds entries as they arrive must reach the same state as one that folds them all at once (DESIGN 4.4 step 3); the hub (Phase 32) signs checkpoints in this format and the transports (Phases 33 and 34) implement this interface.
Output: order.ts and fold.ts extended, digest.ts adjusted, checkpoint.ts and transport.ts, a fake transport, two test files.

File ownership in wave 3: order.ts, checkpoint.ts, fold.ts, digest.ts, transport.ts, src/test/helpers/replicaFakeTransport.ts and the two test files. Changes to `FoldResult` are additive (new `checkpoint` field; `digests` keeps its `Record<stream, string>` shape because other wave-3 plans compare it). Tests use the text reducer only; the convergence property over every family is 30-12's.

Recorded planning choices:
- Checkpoints carry `count` and `orderTip` per stream (D-36); `orderTip_k = sha256(orderTip_(k-1) || entryHash_k)` from 64 zeros over the stream's covered entries in final order.
- Successive checkpoints nest: final order is sort(C1), then sort(C2 minus C1), and so on, then sort(rest). The fold uses the longest chain of nested, verified checkpoints from the caller; a checkpoint that does not nest is reported as a conflict, not used.
- Checkpoints are signed with the same `staff-replica` purpose as headers (D-05: one purpose); the `type` field and the closed key list keep a checkpoint from ever verifying as a header and the reverse.
- The digest caveat (research): two machines holding the same entries but different checkpoints may number versions differently, so `FoldResult.checkpoint` names the checkpoint used and comparisons are made only between equal values.
</objective>
