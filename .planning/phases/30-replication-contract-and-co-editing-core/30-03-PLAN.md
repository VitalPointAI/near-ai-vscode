<objective>
Run the CRDT spike WP-R0 asks for (D-22): measure Yjs update sizes, full-state size and garbage collection over a simulated 30-page product with many authors, check convergence and attribution under the workload, and write the numbers to the phase folder.

Purpose: confirm that a garbage-collection-off fold document (needed for versions and deletion records, 30-RESEARCH "Yjs facts" item 9) and compaction blobs are affordable before Phase 33 puts real people on it; name the Loro fallback if not. Runs in wave 2 beside the tracer because it needs only the vendored bundle.
Output: one script and one report.

Recorded planning choices:
- The spike is its own plan (CONTEXT, Claude's Discretion) so it runs in parallel with the tracer.
- The script lives under `scripts/` (not shipped: `.vscodeignore` excludes `scripts/**`) and loads the vendored bundle directly. D-17's "nothing outside doc.ts imports Yjs" governs `src/domain/replica/`; a measurement script is not product code.
- Thresholds (planner's, reversible): a size problem is a gc-off full state above 8 bytes per character of final text, or a compaction plus 500 later updates taking over 500 ms to load on this machine, or heap above 256 MB for the workload. Research's preliminary measure was about 3.6 bytes per character and 73 ms to apply 8000 updates.
</objective>

  <action>
Write `scripts/crdt-spike.mjs` (ES module, Node built-ins only, `createRequire` to load `vendor/yjs/yjs.cjs` from the repository root) per D-22. A seeded generator (the xorshift pattern from `src/test/stateMerge.test.ts`) drives a workload: each author (person or agent run) has a local Y.Doc with its own client id and a Y.Text named body; authors take turns of typing batches (1 to 40 characters at a random position, one update per batch, as a 500 ms batch would produce), occasional deletions, paste blocks (500 to 3000 characters) and rewrites (delete a paragraph, type a replacement); each author's updates are captured from the update event, and other authors receive them with random delays so edits are genuinely concurrent. The script records which client produced each inserted character (authorship) for the attribution check.

Measurements: per pattern the update byte sizes (median, p95, p99, max), the total of all updates, final text length, full state (`Y.encodeStateAsUpdate`) of a doc with gc off and of one with gc on, the compaction size (full state from the gc-off doc), time to apply all updates to a fresh gc-off doc, time to load the compaction plus the last 500 updates into a fresh doc, time to walk `getText('body')._start` following `right` for attribution, and `process.memoryUsage().heapUsed` after the run. Checks: convergence (two fresh gc-off docs fed all updates in two different shuffled orders, each with duplicates, end with equal text and equal state vector) and attribution (walking the final doc, each non-deleted character's item client id equals the recorded author of that character). Either check failing prints the seed and exits with code 1.

`report(results)` writes markdown to `--out`: method, environment (Node version, yjs and lib0 versions, the output sha256 from `scripts/crdt-vendor.json`), options and seed, a table per measurement, the thresholds from this plan's objective, a verdict line ("No size or garbage collection problem found" or which threshold was crossed), and when a threshold is crossed one sentence naming Loro behind `src/domain/replica/doc.ts` as the fallback (D-17). Plain words, no em-dashes.

Run it once on a small workload (`--pages 1 --persons 2 --agents 1 --seed 1`) writing the report, to prove the path end to end.
  </action>
