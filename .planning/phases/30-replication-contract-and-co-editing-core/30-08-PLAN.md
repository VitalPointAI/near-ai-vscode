<objective>
Products and their versions on the replica layer: a product has a working text and frozen versions; a proposal must pin text that really was in the document; numbering, concurrent proposals and "N changes since" are fold outputs; and the release gate chain up to awaiting-decision runs per version through today's release.ts (MUS-03; DESIGN 6.1 to 6.3, 15.4 rows 1 to 5).

Purpose: versions are what people decide on; the check that a version is text from the document is the base of every later decision (15.4 forbidden act "proposal of text never in the document").
Output: versions.ts (reducer and version hash), the versions-family schemas, one test file.

File ownership in wave 3: versions.ts, kindSchemas/versions.ts, replicaVersions.test.ts. `release.ts` is reused, never copied or edited, and `src/test/staffRelease.test.ts` must still pass unchanged (D-24). Tests pass reducer lists explicitly (`[textReducer, versionsReducer]`); 30-12 registers versionsReducer. `kindSchemas/versions.ts` is a hub-side module (see 30-02): it may import `src/domain/staff/doctrine.ts` for `STAFF_SECTION_IDS` but never `versions.ts`, `doc.ts` or any fold-side replica file.

Split with 30-10 (wave 4): this plan validates and records every version act kind (verdict, submit, withdraw, decide, release, supersede) and derives states up to awaiting-decision; 30-10 adds the decision algebra (30-07) to that derivation, the rows from awaiting-decision on, the forbidden decision acts and the per-version attribution summary.

Recorded planning choices:
- The version blob's plaintext is canonical JSON `{ text, header }` (D-23 "the exact text and header"); the hash covers text and pins (`replicaVersionHash`, the construction of today's `productHash` with `product@hash` pins, D-37); the header is kept for the Phase 31 and 33 projections.
- Per-version state is derived in `finish` from the version's set of acts, applied through `transition()` in a fixed canonical sequence (tradecraft verdict, guard verdict, submit), so it never depends on arrival order.
- Owner side: an agent act passes `transition()` as itself; a person authorised by the roster for an owner-side act (propose, submit, withdraw) is presented to `transition()` as the owner seat (or the section lead seat), as research's adapter proposes; an agent is never presented as a person.
- Concurrent submits naming different decision_for roles leave the version guard-checked with a `submitConflict` flag (a conservative reading; the design names one decision_for per submission).
</objective>
