<objective>
Make per-writer chains tamper-evident and fork-proof: equivocation produces a portable proof and quarantine on every machine whatever the arrival order, a changed old entry breaks only its writer's chain, withholding is reported, and the lamport, roster-citation and future-time rules hold (MUS-01; ROADMAP Phase 30 success criterion 2).

Purpose: the fold's convergence is meaningless if one device can show two histories, or if a peer can hide or alter entries unnoticed (DESIGN 4.5, threat model rows "Cloned device key", "Replay", "Clock manipulation").
Output: chain.ts completed, equivocation.ts, the integrity family (schema and reducer), a fork helper, two test files.

File ownership in wave 3: chain.ts, equivocation.ts, kindSchemas/integrity.ts, integrityFold.ts, src/test/helpers/replicaForks.ts and the two test files. `fold.ts` already reads `excluded`, `quarantined` and `proofs` from `ChainResult` (30-02) and is not edited here; shared types only gain fields. Tests pass reducer lists explicitly; plan 30-12 registers `integrityReducer`. chain.ts, equivocation.ts and kindSchemas/integrity.ts are hub-side modules (see 30-02): they never import integrityFold.ts, fold.ts, reducers.ts, doc.ts or any other fold-side replica file.

Recorded planning choice (D-12 leaves the cross-stream extent open): "folds nothing from that device after the fork point" is read as: in the forked stream, every entry of that writer from the fork seq on (both branches); in other streams, every entry of that writer whose causal past contains a forked entry. This is a pure function of the entry set (so it is the same on every machine and in every order) and never depends on wall time.
</objective>
