# Phase 33.1 Plan 03: Turning positions on safely Summary

The lead turns positions on once: one roster.require with positions@1 (and verified-clearance@1 when your organization's rules carry a credentials@1 section), then one signed project.mode. Every member's computer and your organization's server fold the same mode and settings. A computer or server that does not fold positions@1 stops with the update sentence and keeps every entry. No positions kind applies before positions@1 is required. Every 33.1 roster kind and both personnel kinds need the person key: a session key's attempt is refused at the fold and at the server, while the same session key's typing still folds.

## Deviations from Plan

1. **[Base] No `defence-team` mode on this base.** The Defence Team row (32.1-22) is not merged here; the mode table holds military, public-service, corporate and capital. The tests use `military`, an assignment mode. The fold's rules read the mode's `joiningModel`, so the Defence Team row works on its own once it lands.
2. **[Rule 2] Every positions kind waits for positions@1, not only project.mode.** 33.1-01 left the position kinds ungated and handed the gate to this plan. Without it, a project could hold postings before an older build is stopped. This changes the premise of two tests:
   - `hub/test/positionsTracer.test.ts` now requires positions@1 before it creates a position;
   - `hub/test/require.test.ts`, `hub/test/liveReplicator.test.ts`, `staffRequireGate.test.ts`, `replicaFeatures.test.ts` and `replicaRosterRequire.test.ts` used positions@1 as "a feature this build does not know". Now that the build knows it, they use `later@1`. Their assertions are unchanged.
   - The exact-list tests (`replicaFeatures`, hub `session`) read the new registry.
3. **[Rule 1] Refused at the authority step, not when applied.** A plain invitation refused in `applyOne` still counted as a roster candidate, so a later entry by the same lead at the same head made a split. Both refusals now run at the authority step, where a refused entry never splits the roster. A test shows a device invitation folding right after a refused plain one.
4. **[Frozen size] membership.ts.** The architecture test froze `membership.ts` at 1,537 lines. The invitation check is one line, and its sentence lives in `multiUser.ts`, whose import line already existed. One comment line was shortened, so the file stays at 1,537.
5. **"Hub fixture that lacks positions@1".** The hub's features come from one module-level probe with no injection point, and adding a test-only seam to hub code was not worth it. Two tests cover it instead:
   - the hub's needs-update for a feature it lacks stays covered by `require.test.ts`'s tracer (now with `later@1`);
   - `positionsRequire.test.ts` adds a session from a build without positions@1, refused needs-update with the update sentence.
6. **Personnel kinds at the server.** The server cannot open the personnel key group, so it cannot refuse a session key's `posting.unable` or `posting.reference` there. The fold does (`person-key-required`, tested for `posting.reference`). The server refuses all six 33.1 roster kinds the plan names.
7. **The acceptance grep for `'posting.report'` in sessionKeys.ts gives 0.** The list is read by family from the kinds registry (33-21's design), and the registry test asserts every roster-family and personnel kind is in it, so a later kind cannot be left off.
8. **Not wired at genesis yet (D-26).** `turnOnPositions` works right after genesis, and the test shows it. Calling it when a folder is shared needs your organization's rules from `nearAi.organizationPeople` (33.1-15), which is not built yet. This hand-off goes to 33.1-15, or to whichever plan supplies the rules to the Share flow.
