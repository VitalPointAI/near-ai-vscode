## 2. Why every component sits on every control

- `compliance/src/dashboard.ts`, `buildDashboard`: for every level, every control and every component in `level.components`, a component with no implemented requirement is assessed with its family's responsibility. The comment says so on purpose: "An in-scope component that says nothing about the control is not skipped... A component the control does not apply to needs a reviewed tailoring record".
- `compliance/responsibility/families.json` makes AC, AU, CM, CP, IA, IR, PL, RA, SA, SC, SI and SR `shared`, so `computeStatus` returns Not met with `no-statement` for each silent component.
- No component-level Not applicable exists today: `compliance/tailoring/*.json` are all empty, and Phase 48 (Pitfall 5, T-48-27) forbids bulk tailoring of hosted levels, rightly, because tailoring removes a control from a level or marks a row Not applicable.
- So the dashboard cannot say "the HSM has no part in account management" except as Not met. That is the defect: a missing concept (component scope), not missing work.

## 3. What the catalogue says each component is

Inputs read: the 19 component definitions (`compliance/components/*.json` descriptions), `compliance/resources.json` (141 entries: component, role, architecture area, controls), `compliance/architecture-areas.json` (8 areas), `compliance/hosted/exchanges.json` (15 exchanges with from, to, data and controls), `compliance/levels.json` (which components each level assesses), the Section 10 conditions table in `docs/security/hosted-verification-records.md`, and the Phase 46 to 48.1 plans.

The draft below turns that into facets: short facts about a component ("keeps accounts for people or services") that a control needs before a component can have a part in it. A component either carries a facet as `implements` (it provides the mechanism), as `supports` (it contributes a part another component leads) or not at all. A control lists the facets that give a component a part. A component with none of them has no part in the control, and the reason names the missing facet and which components carry it. Enhancements inherit their base control unless listed.

## 7. Facts the plans rely on

- **Reported tests.** Only these CI jobs write a per-test report the bundle reads: `test` (root `npm test`: `src/test`, `scripts/test`), `relay` (`relay/test`), `hub` (`hub/test`), `workbench` (`workbench/test`) and `deploy` (`deploy/test`), as `test-report-<job>.ndjson`. The `compliance` job and `docs-site/test` write none, so a rule that names a test there never gets a result (48.1-VALIDATION makes the same point).
- **Existing rules** name tests in `src/test`, `scripts/test`, `hub/test`, `relay/test` and `deploy/test`, plus observation rules; none names a `compliance/test` file today.
- **Component and rule files are one-line JSON** (all component files except `model-endpoints.json`). Two branches that edit the same file always conflict on that line, so one plan writes a component file at a time, and a later branch re-applies its implemented requirements onto main's file by control id rather than resolving the line by hand.
- **Gate paths.** `compliance/src/`, `compliance/components/`, `compliance/evidence-rules/`, `compliance/responsibility/`, `compliance/tailoring/`, `compliance/levels.json`, `scripts/test/`, `scripts/lib/`, `.github/` and `SECURITY.md` need the owner's gate approval (`scripts/lib/workflow.mjs` GATE_PATHS, `.github/CODEOWNERS`). A new `compliance/applicability/` and `compliance/coverage/` must be added to both.
- **The docs job is required and Node-only today.** It runs `node compliance/src/cli.ts hosted-docs --check` without installing the compliance package; a check that loads components or profiles needs `npm --prefix compliance ci --ignore-scripts` first, because `validate.ts` imports ajv.
- **The SSP** (`compliance/src/oscalSsp.ts`) writes a by-component entry for every component on every control with "No product statement is available yet." A component that has no part must instead say why, with implementation status not-applicable.
- **The docs drawer** (`docs-site/src/components/accreditation/ControlDrawer.jsx`) prints `component.statement ?? row.reasonText` and neither the component's name nor its state, so a component's own reason never shows. The workbench Compliance view (`workbench/extension/src/browser/sterling-compliance-module.ts`) already shows each component's name, state and `reasonText`, and its parser accepts extra fields.
- **No-status rule.** No source file may use a key named `status`, `state` or `met` (`test/noStatus.test.ts`); the new source files use `applicability` and `class`.
- **Word lint.** New reason texts go through `compliance/src/wordLint.ts` (no compliance claims).

## 8. Pitfalls

1. **Bulk tailoring in disguise.** A map that marks pairs Not applicable to lift a level's numbers is what Phase 48 Pitfall 5 forbids. The map must be derived from what each component is, reviewed, and unable to remove a row or turn one Not applicable.
2. **Gaming the ratchet.** If the coverage check only counted applicable cells without a statement, widening Not applicable would lower it. The map's own changes therefore need sign-off before they take effect, and Not applicable counts are reported beside the ratchet.
3. **A catch-all gap.** `44.1-02-TRIAGE.md` already found that a generic triage reference is not an accountable work item. New gaps name specific controls and a plan.
4. **Anticipatory statements.** A pair whose behaviour is not built gets a link to the phase that builds it, never a statement (48 D-12, `compliance/README.md`).
5. **Evidence nobody reports.** A rule on a `compliance/test` file never gets a result; the check must refuse it at source time.
6. **Same-file parallel edits.** One-line JSON makes any two writers of one component file conflict; plans in one wave never share a component file, `gaps.json`, `SECURITY.md` or the crypto inventory.
