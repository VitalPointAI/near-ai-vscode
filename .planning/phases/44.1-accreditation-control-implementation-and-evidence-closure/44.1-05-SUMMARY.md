# Phase 44.1 Plan 05: Applicability tracer Summary

The status engine can now say "Not applicable to this component" with a reason built from the applicability rules. It does so only while a stage review lists that component with its current section hash. Unsigned, the same cell reads Not met, and a row that no component has a part in reads your organization's responsibility, never Not applicable.

## What was built

- **Engine reasons** (`compliance/src/model.ts`, appended), as written:
  - `component-not-applicable`: "Not applicable to this component: {reason}"
  - `component-not-applicable-unreviewed`: "The applicability map says this component has no part in this control, but your organization has not signed off the current map for this level, so it counts as not met."
  - `no-component-applies`: "No component in this level's scope has a part in this control, so your organization carries it; each component's reason is listed."
- **The {reason} text** (`notApplicableReason` in `applicability.ts`): "this control needs a component that {facet words} (facet {id}); {carriers} carry that here, and this component does not." With no facet on the control: "the applicability rules give no component a part in this control, so your organization carries it." For example, hsm in ac-02 reads: "Not applicable to this component: this control needs a component that keeps accounts for people or services (facet accounts); hub, keycloak and rke2 carry that here, and this component does not."
- **`computeStatus`** reads the optional `applicability` record (class, reason, reviewed) after the your-organization and inherited checks and before tailoring. It stays pure.
- **`applicability.ts`**: source types, `classify` (an override wins; implements beats supports; not-applicable with a reason; undefined when no rule covers the control or the component has no entry), `controlRule` (an enhancement falls back to its base control), `componentSection`, `buildApplicabilityIndex`, `isReviewed`, `applicabilityFor` and `loadApplicability`.
- **The section hash function**: `componentSection(rules, component)` builds `{ component, facets, controls }`. `facets` holds the component's facets with class and basis. `controls` holds `[control, class, reason]` for every control in `rules.controls` plus every control the component's overrides name, sorted. It returns the SHA-256 (hex) of `canonicalJson(section)`, which is JSON with every object's keys sorted. Statements are never part of it. A changed facet, rule, override or reason (including another component newly carrying the facet) changes the hash.
- **`buildDashboard`** asks the index only for a component without an implemented requirement (D-08). A signed exclusion's responsibility reads `not-applicable`. The `applicability` class is added to the component row whenever a rule covers the pair. In `controlState`, a row whose every component reads `component-not-applicable` returns `your-organizations-responsibility` with `no-component-applies`.
- **Schemas**: `applicability.schema.json` (strict; the rules, lock and reviews files chosen by `kind`) and `dashboard.schema.json`, which gains the three reasons and the optional `applicability` enum. `schemaVersion` stays 1.
- **Bundle**: `commands/bundle.ts` loads `compliance/applicability/` (exported `loadDashboardSources`). A missing folder leaves the dashboard as it was. `loadApplicability` refuses invalid files, undefined facets, duplicate overrides, duplicate stage ids and unknown review levels.
- **Source folder**: `rules.json` holds the `accounts` facet, carried by keycloak, hub and rke2 with a basis each, hsm with no facets, and the ac-02 rule. `reviews.json` has no stages.
