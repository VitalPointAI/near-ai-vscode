<domain>
## Phase Boundary

Every cell of the Compliance dashboard (level x control x component) ends with an honest statement and its evidence, or an honest reason it has none:

1. **Applicability first.** A generated, reviewable map of which controls each component implements, supports or has no part in, derived by rules from the component catalogue and the control families. A component with no part shows "Not applicable to this component" with its reason, not Not met. Your organization signs the map off in the repository; a test stops any cell from changing class without that sign-off.
2. **Statements.** For every applicable pair, a statement of what the built code does, cross-referenced with the plans that already write statements, so nothing is written twice.
3. **Evidence.** Every statement is tied to an evidence rule backed by a test a CI job reports, a CI artefact collector or a site collector. A statement without evidence is never Met.
4. **Order.** Unclassified and Protected A first, then Protected B, then the Classified appliance and the overlays.
5. **A coverage measure CI tracks**: counts per state and component, generated, with a check that the number of applicable cells without a statement only goes down.

Not in this amendment (owned elsewhere, referenced only):
- Evidence freshness, collection cadence and the Stale display: Phase 48.2 (Live compliance evidence in the workbench), planned on `docs/live-compliance-evidence-plan` (gap block G475 to G479).
- The statements of the sibling plans in `44.1-RESEARCH.md` section 6. Their pairs are reserved in `44.1-HANDOFFS.md`; 44.1 never edits or replaces their statements.
- The behaviour itself. Where a pair's behaviour is not built, the delivery phase builds it (for example the relay's messaging, Phases 75 to 84); 44.1 links the pair to that phase.
- Level tailoring (`compliance/tailoring/`), which stays the only way to remove a control from a level.
- The appliance's own statements, which wait for the appliance scope that 44.1-03 obtains from the sponsor.
</domain>

<decisions>
## Implementation Decisions

### The owner's brief (locked)
- **D-01 (owner):** Applicability comes first: a generated, reviewable per-component map of which controls each component implements, supports or does not touch, derived from the component catalogue (role, architecture area, data flows, the exchange register) and the control families by rules, not by editing cells. "Not applicable to this component" always carries a reason and shows as such, not as Not met. Your organization reviews the map; changes are signed off in the repository and tested, so no cell can silently disappear.
- **D-02 (owner):** Statements: every applicable (component, control) pair gets a statement of what the built code does. The existing plans are cross-referenced so nothing is written twice (48-07, 48-08, 48.1-18, 48.1-19, 44.1-01 to 44.1-03, 45.2-08, 74.1-16, 74.3-14), and uncovered pairs get new plans.
- **D-03 (owner):** Evidence: every statement is tied to an evidence rule backed by a real test, CI artefact or site collector; a statement without evidence is never Met. Freshness follows Phase 48.2 (Live compliance evidence); 44.1 links to it and does not duplicate it.
- **D-04 (owner):** Order: Unclassified and Protected A first, then Protected B, the Classified appliance and the overlays.
- **D-05 (owner):** A coverage measure CI tracks: counts per state and component, generated, with a check that the no-statement count for applicable cells only goes down and never silently up.

### Applicability (D-01)
- **D-06 (not tailoring):** Applicability is a fact about a (component, control) pair and is the same at every level. It lives in its own source folder, `compliance/applicability/`, never in `compliance/tailoring/`, so Phase 48's rule that no tailoring names a hosted level (T-48-27) still holds. It cannot remove a row, mark a row Not applicable or change any responsibility. Every cell stays on the dashboard: an excluded component keeps its row in every control, so 48-08's "every hosted row lists all fifteen components" still holds.
- **D-07 (three classes):** `implements` (the component provides the mechanism), `supports` (it contributes a part another component leads) and `not-applicable` (with a reason). Both `implements` and `supports` need a statement and evidence before they can be Met.
- **D-08 (rules, from the catalogue):** The rule source `compliance/applicability/rules.json` has three parts: facets (a short fact about a component with the words its reason uses), each component's facets as `implements` or `supports`, each citing where the catalogue says so (its component definition, `resources.json` roles and architecture area, the exchanges it is party to), and each control's facets (an enhancement inherits its base control unless listed). A component has a part in a control when it carries one of the control's facets. Per-pair overrides exist only with a reason, a reviewer and a date. A component that has a statement for a control has a part in it whatever the rules say; the generator lists those pairs for review. `44.1-RESEARCH.md` section 3 is the draft to start from.
- **D-09 (every control classified):** Every control of every level's profile must be covered by a rule. A profile import or catalogue change that adds a control the rules do not cover fails the generator, so new controls cannot arrive as unexplained cells.
- **D-10 (generated, committed, drift-checked):** The generator writes `compliance/applicability/map.lock.json` (one line per component, class and reason, with a SHA-256 per component section) and the readable `docs/security/component-applicability.md` (per component: what it implements, supports and has no part in, with reasons; per level: the controls no component has a part in). Both are committed and checked for drift in the required `docs` job, as `hosted-docs --check` is.
- **D-11 (sign-off and the no-silent-change invariant):** `compliance/applicability/reviews.json` holds one record per review stage: the levels it covers, the reviewer's role and name, the date, and the SHA-256 of each component's lock section as reviewed. The sign-off is the reviewer's own answer at the plan's review checkpoint, recorded in that file, plus the owner's gate approval of the pull request that carries it (GitHub records who approved, and the reviews collector already reads gate approvals). A component's Not applicable cells take effect at a level only while that level's stage review lists the component with its current section hash. When a section changes without a new review, its cells read "awaiting sign-off" and count as Not met, never Not applicable, and the docs job fails until the stage is signed again. No cell can change class unseen.
- **D-12 (stages):** Stage 1: Unclassified, Protected A and hosted Protected A. Stage 2: Protected B and hosted Protected B. Stage 3: the Classified appliance and the overlays (ITSP.10.171, CPCSC Level 1, Controlled Goods, ITAR), whose requirements reach components through the existing mappings in `compliance/mappings/`. Each stage is signed separately and in this order (D-04).
- **D-13 (engine):** Three new reasons, filled by `computeStatus` and the dashboard builder, which stay pure: `component-not-applicable` ("Not applicable to this component: {reason}"), `component-not-applicable-unreviewed` (the map says the component has no part but the current map is not signed off for this level, so it counts as not met) and `no-component-applies` for a row whose every component has no part at that level, which then reads "Your organization's responsibility", never Not applicable. Component rows gain an optional `applicability` field; the dashboard schema stays version 1. An excluded cell's responsibility reads `not-applicable`. This amends the mechanism of Phase 44 D-18 (Not applicable needs a reviewed record): a reviewed applicability record is that record for one component in one control (owner question O-1, accepted "yes" on 2026-11-25).

### Statements (D-02)
- **D-14 (only what is built):** A statement says what code on main does, in plain words, as its evidence proves it (48 D-12, `compliance/README.md`). A pair whose behaviour is not built gets no statement: its plan links it to the existing gap and delivery phase, or names the gap it needs, in its summary. 44.1-22 files any new gaps from the block the session assigns at that time.
- **D-15 (one mechanism for the supply-chain controls):** CM-2 (with .02 and .03), CM-8 (with .01, .04 and .06), RA-5 (with .02), SA-5, SA-22, SI-2 (with .02), SI-7 (with .01), SR-3 and SR-11 describe the same release and import path for every component. 44.1-09 generates those statements for each component from the resource register and `compliance/src/inventory.ts` (its images by digest, the signature, the SBOM, the scan, the import refusals), with that component's own evidence subjects, into the component files under statement ids ending `.inventory`, drift-checked. Hand-written statements for the same control and the sibling plans' statements are left as they are. About 275 pairs need no hand-writing.
- **D-16 (clusters and file ownership):** Hand-written statements are planned per component cluster (44.1-10 to 44.1-21). One plan writes a component file at a time. New rules go in one rule file per component (`compliance/evidence-rules/<component>.json`, already the convention for the product components), so plans in one wave share no file. Cluster plans do not edit `compliance/gaps.json`, `SECURITY.md` or `docs/security/crypto-inventory.md`; a statement that needs a new Known limitations row or crypto row waits in the plan's summary and lands in 44.1-22, the single writer of those files.
- **D-17 (sibling pairs):** The pairs in `44.1-HANDOFFS.md` are reserved for their plans. Work lists skip them; if a sibling plan is cancelled, its pairs return to the cluster plan through a ledger update.

### Evidence (D-03)
- **D-18 (what counts as evidence):** A statement's rule is one of: a test rule on a test in a job that writes a per-test report (`src/test`, `scripts/test`, `relay/test`, `hub/test`, `workbench/test`, `deploy/test`), an observation rule on a CI artefact collector (ci, tests, audit, sbom, secret scan, crypto, settings, reviews, code scanning, release, attestations, documents) or on the site collector (`deployment`). The coverage check refuses, at source time, a statement with no rule and a test rule outside those folders; the appliance (claim false at every level) is exempt and keeps its no-rules row. The freshness of each kind is Phase 48.2 (Live compliance evidence)'s (D-03); 44.1 adds no window or collector.

### Coverage measure (D-05)
- **D-19 (the measure and the ratchet):** `node compliance/src/cli.ts coverage` computes, from sources only, per level and component: applicable cells with a statement, applicable cells without one, Not applicable (signed), Not applicable awaiting sign-off, your organization's (family), and statements without an acceptable rule. With a bundle it adds counts per state and component. One file per component, `compliance/coverage/<component>.json`, holds that component's number of applicable cells without a statement and its number of Not applicable cells awaiting sign-off, counted over every level the map covers, so it stays non-zero while stage 2 is unsigned (one file each, so plans that own different components never edit the same file). `coverage --check` fails when either count rises above its baseline (so a map change that moves cells out of the applicable count cannot pass as progress before your organization signs it), when a count falls and the baseline was not lowered with it (`coverage --write`), and when any statement lacks an acceptable rule. The baseline is a gate path, so a rise can only land with the owner's approval and shows in the diff. The check runs in the required `docs` job; the `compliance` job's summary prints the counts per state and component with the change since the previous main bundle. Evidence drops stay report-only as Phase 44 D-07 decided.

### Display, order and delivery
- **D-20 (display):** The docs drawer shows each component's name, state, applicability and its own reason; the assessor SSP gives an excluded component its reason and implementation status not-applicable; the workbench Compliance view already shows each component's state and reason and needs no change here; Phase 48.2 rebuilds that view (48.2-10) and keeps each cell's applicability and reason (44.1-HANDOFFS.md H-13).
- **D-21 (order inside every work list):** Unclassified controls first, then the rest of Protected A. Protected B rows gain the same statements at once, because the two profiles select the same controls; 44.1-23 checks each against Protected B's expectations (validated cryptography, hardened bases) and signs stage 2. The appliance's 126 cells stay as they are until 44.1-24.
- **D-22 (pull requests and gates):** Plans 44.1-05 to 44.1-08 land as one integration pull request with one owner gate approval (44.1-07); your organization reviews the stage 1 map in 44.1-06 and 44.1-07 records that sign-off. 44.1-09 is its own pull request. The cluster plans merge into two integration branches, `feat/phase-44.1-statements-product` (44.1-10 to 44.1-13) and `feat/phase-44.1-statements-hosted` (44.1-14 to 44.1-21), each landing as one pull request with one gate approval in 44.1-22. While a gate pull request waits on the owner, nothing else merges.
- **D-23 (gaps):** This planning files G490 to G494 (its block). Executors file gaps only from blocks the session assigns at execution, and only in 44.1-22.
- **D-24 (requirements):** COVR-01 to COVR-05 in `REQUIREMENTS.md` trace the five brief points; ACCR-03, ACCR-04, ACCR-06, ACCR-07 and ACCR-10 are the Phase 44 requirements this extends.
