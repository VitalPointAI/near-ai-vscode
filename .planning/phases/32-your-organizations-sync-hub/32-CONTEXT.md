## Phase Boundary

Phase 32 is the design's WP-HUB, preceded by two prerequisite parts the owner placed at its start (owner, 2026-11-20). It is part of drop A (Phases 30 to 33); drop A is released after Phase 33.

**Part A: the PR #130 review findings carried over** (plans 32-01 to 32-07). Each fixed with a regression test that fails on today's code.

**Part B: labelled products in shared projects** (plans 32-08 to 32-13). Each product lives in the label cell for its label, so only members cleared for that label hold its key and receive its plaintext. Make This Staff Project Multi-User then converts real projects (products default to org/Internal), and preview projects shared under 0.4.35 can move their products out of the base cell.

**Part C: the hub** (plans 32-14 to 32-28). A `hub/` workspace beside `relay/`, its image, its Compose service and profile, its required CI job, append checks against the roster and each cell's access list, sessions bound to TLS, catch-up, blobs, server-sent events for live heads and presence, signed checkpoints, join requests with invitation secrets, the client side that talks to it (a transport and a one-shot sync, no UI), the malicious-hub harness, the restore drill, a ciphertext-only byte capture, and the operator section.

### Part A: review findings carried over (each with a regression test)
- **D-03 (MAJOR, store.ts startAgain):** Start Again becomes resumable. It writes a small intent record (`.planning/staff/replica.start-again.json`: set-aside folder name, temporary folder name, the carried writer and counts) before the first rename, fsyncs the parent folder after each rename, and on every open checks for the intent: temporary folder present and store absent means finish the second rename; store absent and a set-aside folder named by the intent present means build again from the set-aside folder (never an empty store); both renames done but the mark not written means write the mark. A store folder deleted while this device's mark remains is no longer treated as "start empty": Start Again looks for the newest `replica.set-aside-*` folder whose own-writer entries verify and carries from it, and says which folder it used. Each crash point gets a test with a crash-injecting child process.
- **D-04:** The Remove list carries the member id (and the device writer for a device item) in each quick pick item and matches by id, never by label or description; a test with two members of the same declared name removes the one picked.
- **D-05:** Join refuses a flow result that is ok but has no file ("The join request was not made. Nothing was saved. Run Join Staff Project again."), and saves nothing.
- **D-06:** Every rename that must survive a power cut is followed by an fsync of its folder: marks.ts after the lists file rename, saveSecretFile in the commands after the secret file rename, and the Start Again renames (D-03). A shared helper `syncFolder(dir)` lives in `src/staff/staffFiles.ts` beside `writeIfUnchanged` (one copy, used by all three).
- **D-07 (singleCopy.ts):** The copy's signed head mark is stored before the staging folder is renamed into place, under the target's key; if the rename then fails, the mark is removed again (it names a copy that does not exist). A copy found in place without a mark (a crash from an older version) is refused as today's host refuses a ledger without a mark, and the message says to make the copy again into a new folder. Tested at both crash points.
- **D-08 (membership.ts):** updateMember's removal of the lead role gets a test that proves the fold refuses a member.update that takes away the lead's own lead role and that the host never writes one; if the host can write one today, it refuses first. describeRosterBranches reads only the roster entries and the two branch heads it shows, not a whole welcome file. The "no secret in a result" test asserts on the invitation text and the join request text too.
- **D-09 (staffHost.ts):** openShared caches by the store's identity (the store folder's inode and the mark's head hash); Start Again and Make a Single-Machine Copy call `invalidateShared()`, and a cache entry whose identity no longer matches is reopened. A test runs Start Again while the host holds a cached project.
- **D-10:** staffReplicaParity runs its module swaps in a forked child (the decodeHost pattern) and never mutates `require.cache` in the test process.
- **D-11:** The teamSignedPayload exemption test gains a case whose random field contains a real token shape (for example a `ghp_` or `sk-` prefix followed by the right length) that must still pass as a Phase 31 random field, and a case where the same shape outside an exempt field is refused.
- **D-12:** Brittle whole-sentence assertions in the Phase 31 tests are changed to match key phrases (the refusal id plus two or three load-bearing words); each plan does this only in the test files it owns, and 32-06 covers the rest. No assertion is weakened: the refusal id is always asserted exactly.
- **D-13:** 31-CONTEXT.md D-05 gets a dated amendment line: decoding runs in a forked child process with its own heap cap (decodeHost.ts), not `node:worker_threads`, because the worker's heap watch could not fire during a synchronous decode (PR #130 review). The original text stays.
- **D-14 (MAX_MARK_LISTED):** The signed mark stays small and bounded before the hub can deliver floods. Held and waiting lists move out of the signed record into the content-addressed lists file the record commits to by hash (already the MJ-06 shape), and are bounded: at most 1,000 refused outside entries per writer per stream and 10,000 per store. Past a writer's bound the store stops accepting that writer's outside entries, records one `flooded` line for it, and keeps the mark advancing for everyone else; the Staff Room text (Phase 33) is "Too many refused changes arrived from one device. They were not kept." SECURITY.md's "a few hundred bytes" sentence is corrected to state the bound.

### Part B: labelled products in shared projects
- **D-15:** Every product lives in the cell for its label. The base cell (stream id = project id) carries the roster and project-level entries only. A label cell is created on demand for each distinct label in use (`cell.create` with the label sealed inside the grant, `labelSealed`), with grants to every device whose member's declared clearance dominates the label at that roster (the Phase 31 `clearedFor` rule) and to no hub unless the lead grants it (owner: no default hub cell grants).
- **D-16:** org/Public products also live in their own cell (the "Public" cell), not the base cell, so granting the hub the base cell (D-40) never exposes product text.
- **D-17:** Products default to org/Internal when converted or created with no label in their header (today's host default). A product's label is fixed for the life of the product in a shared project; relabelling a product is a new product in another cell, made by a person, with a note (DESIGN 8.1 rule 5, "downgrading is a person's act"). Relabel flows are Phase 33 UI; Phase 32 refuses a label change.
- **D-18:** The write-down rule holds across products: a version may pin a product in a cell its own cell's label dominates; a pin to a higher or incomparable cell is refused by the fold (`pin-above-cell`) and by the host before writing. Within one cell nothing changes.
- **D-19:** The lead cannot create a cell for a label the lead's own declared clearance does not dominate. Conversion is refused with a sentence naming those products ("You are not declared cleared for SECRET//REL, so this computer cannot hold that part of the project. Ask the staff lead to declare a clearance that covers it, or keep this project on one machine."). The deputy rule from MN-05 stands.
- **D-20 (migration, legacy imports):** No legacy file is sealed into a cell that someone not cleared for its contents receives. The whole legacy product ledger and the whole decision log go into a lead-only "legacy" cell (grants to the lead's devices and to the deputy's devices only when the deputy's clearance dominates every label in the ledger), so the legacy chains stay verifiable by those who held them. Each label cell gets its own `project.import` carrying only the ledger lines for its products (each line is an individually signed envelope and still verifies on its own) with the legacy head hash, so its readers see their products' history. The calculator and wargame ledgers name no product and go into the org/Internal cell. The `project.import` schema gains an optional `scope` (`whole` or `cell`) and `lines` count; an import with no scope reads as `whole` (Phase 31 imports).
- **D-21:** The `label-above-base` refusal is removed; `BASE_CELL_LABEL` becomes the label of the base cell only for the roster. Conversion still refuses a broken ledger, a changed product file and D-19.
- **D-22 (preview projects, revised during planning):** Projects made shared under 0.4.35 (preview, off by default) hold their products in the base cell. Moving them out cannot help the hub: every old product entry stays sealed under the base cell's earlier epoch keys, and the hub needs those same keys to fold the roster from the genesis, so a hub given the base cell could still read every product written there. So nothing is moved. Such a project keeps working as it does today (the fold and the host still read base-cell products), and the only change is that connecting it to a hub (D-41) is refused with: "This project was made shared by an earlier preview, and its products sit in the part of the project the hub must read. Make a single-machine copy and make that copy multi-user again; the new shared project keeps each product in its own part." The pure helper `baseCellHeldProducts` (32-08) says whether the base stream ever held a product-family entry. Make Multi-User run on a single-machine copy is the way forward (it is a new genesis). There is no `product.moved` kind, no `movedFrom` field and no Move Products command.
- **D-23:** Each machine folds only the streams it holds; a member below a cell never receives its grant, its stream or its blobs (the welcome file, grants and store carry nothing for it), and cannot tell a product exists (DESIGN 8.1 rule 6). Make a Single-Machine Copy carries every cell this device holds and lists what it could not carry ("Parts of this project you are not cleared for were not copied.").
- **D-24:** The leak test (32-13) uses two compartments and two members each cleared for one: no grant, wrap, stream file, blob, welcome file or single-machine copy of one reaches the other, checked by byte search for canaries placed in product text, product names, labels and decision reasons.

### Part C: the hub service (MUS-07)
- **D-25 (owner):** The hub is its own service in the relay's Compose stack (`relay/compose.yaml`), under its own profile `hub`, with its own volume `hub-state` and its own secret files; either service runs without the other.
- **D-26:** `hub/` is built like `relay/`: Node 26.13.1 pinned in `engines` with the relay's guard, esbuild to `dist/bin.mjs` and `dist/app.mjs`, `node:sqlite` in WAL mode, **no runtime dependencies at all** (the relay has one, `jose`; the hub has none), distroless nodejs26 image as uid 65532 with no shell, secrets only from files, a redacting logger as the only output, `/healthz`, a kill -9 drill, a container hardening test.
- **D-27:** The hub reuses the extension's pure, hub-side replica modules (the `HUB_SIDE` list in `src/test/replicaBoundaries.test.ts`) through the `@ext/*` alias at bundle time; it copies nothing from them. `hub/test/workspace.test.ts` refuses any hub source import outside `hub/` except the hub-side closure, and refuses `vscode`, Yjs and any package. Test files under `hub/test/` may also import extension client modules that never import `vscode` (for real-hub client tests, D-52).
- **D-28:** Small relay modules the hub needs (Node version guard, config reader, secret file loader, state directory checks, redacting logger, health registry) are copied into `hub/src/` and adapted, not imported from `relay/`, so the two services never couple; each copied file says where it came from.
- **D-29:** The hub ends TLS itself (`node:https`, TLS 1.3 only) with a certificate and key from secret files, so a device challenge can bind to the TLS session. The certificate pin is the sha256 of the certificate's SubjectPublicKeyInfo, so renewing a certificate with the same key keeps the pin. The operator brings the certificate (your organization's CA, or a self-signed one made with the `openssl` command in the operator section); the hub does not generate certificates.
- **D-30:** The hub's Ed25519 signing key and X25519 encryption key are secret files outside the state volume (DESIGN 16, "keys outside the state volume"). `node /app/bin.mjs --generate-key signing|encryption` prints a new key file to stdout for the operator to save with mode 0400; the hub never writes its own keys.
- **D-31:** Compose publishes the hub's TLS port on an interface the operator chooses (`NEAR_AI_HUB_PUBLISH_ADDRESS`, default `127.0.0.1`, so nothing is exposed until the operator says so), port 8443 by default. A reverse proxy, if any, passes TCP through.
- **D-32:** CI gets an eighth job, `hub`, built like `relay` (Node 26.13.1, `npm ci --ignore-scripts`, `npm audit --omit=dev`, lint, tests, image build and hardening check, the same hotfix skip rule keyed on `hub/package.json`). The owner adds `hub` to main's branch protection after the phase merges (owner action, as D-19 of Phase 68 did for `relay`).
- **D-33:** `verify:release` refuses a VSIX holding anything from `hub/`; `.vscodeignore` leaves `hub/` out; `.dockerignore` (an allow-list) lets in `hub/` sources and the hub-side closure under `src/` and nothing else.

### Hub protocol (MUS-07)
- **D-34:** HTTPS plus server-sent events, version prefix `/v1`: `POST /v1/session`, `GET /v1/projects/:p/heads`, `POST /v1/projects/:p/append`, `GET /v1/projects/:p/entries`, `PUT` and `GET /v1/blobs/:hash`, `GET /v1/projects/:p/events` (SSE), `POST /v1/projects/:p/presence`, `POST /v1/projects/:p/checkpoint` (ask for one), `POST /v1/enrol`, `POST /v1/projects/:p/invites`, `POST /v1/join`, `GET /v1/projects/:p/join-requests`, `GET /healthz` (DESIGN 10.4 plus enrolment and invitation registration).
- **D-35 (session):** `POST /v1/session` returns a fresh challenge; the device answers with a signed payload (new purpose `staff-hub-session`) over the hub's writer id, the project, the challenge and 32 bytes of TLS keying material (`exportKeyingMaterial(32, 'near-ai-hub-session/v1')`), so the answer works only on that TLS connection to that hub for that project. The hub accepts a device admitted, not revoked and not quarantined at its roster head, and returns a bearer token (32 random bytes, kept only in memory, 15 minutes, bound to the TLS session's keying material, so a token copied to another connection is refused). The authentication deadline is 10 seconds from connect.
- **D-36 (catch-up):** The client asserts its heads (per stream, per writer: seq and hash); the hub returns what it lacks, per writer in seq order, at most 1,000 entries or 4 MiB per response, with `more: true` and the heads reached, never a silent partial answer. Every response names the project and stream, and carries the hub's latest checkpoint. The client checks each `prev` against its stored head (so a reordered, gapped or injected entry fails locally).
- **D-37 (SSE):** One event stream per device per project, events `heads`, `presence`, `checkpoint`, `roster`, `equivocation`, `join-request` (to lead and deputy devices only), and `resync`. Event ids are a per-connection counter for gap detection only; after any reconnect or `resync` the client runs heads-based catch-up, so `Last-Event-ID` never decides correctness. A comment line every 15 seconds keeps proxies open; `retry:` carries a jittered delay; revoked or expired access gets HTTP 204 so the browser-style client stops. Each connection has a 1 MiB unsent budget: past it the hub sends `resync` and closes (never queues without bound; Node's `write()` returning false is honoured with `drain`). At most 4 streams per device and 32 per address.
- **D-38 (presence):** Heartbeat every 5 seconds, time to live 30 seconds, an explicit leave, never written to disk, fanned out only to devices on the access list of the cell named, coalesced to at most one presence frame per cell per 250 ms keeping the latest per device. The body is sealed under the cell key by the client (Phase 33 defines its plaintext); the hub learns only "device D is active in cell C". Bounded at 2 KiB per heartbeat.
- **D-39 (limits):** Header 4 KiB, inline body 16 KiB plus seal overhead, blob 8 MiB (the Phase 30 limits); token buckets per writer (50 entries per second, burst 200) and per address for unauthenticated calls (session: 120 per minute, because a whole site may sit behind one address; join and enrol: 10 per minute), checked before signature verification; `429` with `Retry-After`. Targets from DESIGN 10.9 (10 projects, 400 devices, 300 event streams, 50 entries per second) are the load test's figures, not hard caps.

### Append checks (MUS-07)
- **D-40:** The hub holds the base cell key through an ordinary cell grant to its X25519 key, written by the lead when admitting the hub (`hub.admit` followed by the base cell grant). That is the only cell the hub reads unless the lead grants more (`hub.grant`, with the trade-off sentence from DESIGN 10.2). The hub folds the roster stream with the hub-side roster fold to know who may write; after D-16 the base cell holds no product text.
- **D-41:** The hub accepts a project through enrolment: the operator runs `--hub-file <days>` (default 7), which prints a `.near-staff-hub` file signed by the hub's key (new purpose `staff-hub-file`): hub id, address, certificate pin, Ed25519 and X25519 public keys, an enrolment id and a one-time enrolment secret, and expiry; the hub keeps only the secret's hash. The lead's device enrols a project with `POST /v1/enrol`: the genesis and roster entries up to and including `hub.admit` for this hub's key and pin and the base cell grant to it, plus an HMAC under the enrolment secret. The hub refuses a project whose roster does not admit its own key and pin, a used or expired enrolment, and a second project for one enrolment. Without enrolment nobody can create projects on the hub.
- **D-42:** Per entry the hub checks (DESIGN 10.7): header shape and size, signature by the writer's key at the hub's roster head, writer admitted and neither revoked nor quarantined, writer on the stream's access list (the grantees of the stream's cell at the head, from the roster fold's grant records; the hub reads writer ids from grants, never labels), `seq` next and `prev` matching, rate and size limits, and for the roster stream: a lead or deputy device and `rosterPrev` at the head. It cannot check bodies of cells it does not hold; clients do.
- **D-43:** A second signed header at a used `(stream, writer, seq)` is stored as an equivocation proof (both headers), pushed as an `equivocation` event, and that writer is refused until the roster records `device.release` or `device.revoke`. The first entry at that seq stays the hub's entry.
- **D-44:** Entries and blobs are kept for the life of the project. Blobs are content-addressed by the hash of their ciphertext, checked on `PUT`; a blob nobody's entry references within 24 hours of upload is removed by the hub (upload-before-entry is allowed, abandoned uploads are not kept).

### Checkpoints (MUS-07, MUS-08)
- **D-45:** The hub signs checkpoint format version 2 (Phase 31, unchanged; no new fields) with its own key: at most once every 60 seconds while entries arrive, debounced 2 seconds, and when a client asks (at most once per 10 seconds per project). Every checkpoint is kept as evidence. Digests are left out in Phase 32 because computing them needs the full fold with Yjs, which the hub does not load; granted-cell digests come with hub watches in Phase 35.
- **D-46:** Clients keep the newest checkpoint per hub per project and refuse a checkpoint whose heads fall below it for any writer (rollback) or that conflicts with one they hold over the same prefix (`checkpointConflict`, a hub equivocation proof). No change to the checkpoint format is needed; the research's chained checkpoints were considered and left out (see 32-RESEARCH.md).

### Join through the hub (MUS-07)
- **D-47:** The invitation payload gains an optional `hub` field (address, certificate pin, hub writer id). Invitations without it work by file as in Phase 31.
- **D-48:** The hub never holds a join secret. When the lead makes an invitation for a project on a hub, the lead's device registers it with the hub over its session (`POST /v1/projects/:p/invites`): invite id, expiry and a hub check key `HKDF-SHA256(secret, info 'near-ai/hub-join/v1' || invite id)`. The joiner's request posted to `POST /v1/join` carries the Phase 31 MAC plus a second MAC under the hub check key. The hub checks the second MAC, refuses expired, used, unknown or locked invitations (locked after 5 failed MACs), stores the request, and sends a `join-request` event to the lead's and deputy's devices; the lead's device still checks the Phase 31 MAC with the real secret before Admit, as today. Accepted requests are kept 7 days, then removed.

### Client side in Phase 32 (MUS-08)
- **D-49:** Phase 32 builds the client pieces the harness needs, with no UI and no scheduling: `src/staff/replica/hubTransport.ts` (implements `ReplicaTransport` over pinned TLS, the session, catch-up, append, blobs, the SSE reader) and `src/staff/replica/hubSync.ts` (one-shot exchange: heads, pull, verify, store, push what the hub lacks, re-push after a hub rollback). Phase 33 builds the live replicator, sync status and commands around them.
- **D-50:** A pure client module `src/domain/replica/hubWitness.ts` names every malicious-hub finding: `withheld` (a dep or checkpoint head never delivered after a grace period), `delayed` (own entries not covered by a checkpoint for more than 5 minutes while connected), `rolled-back` (heads or checkpoint below what this device saw), `forked-view` (two conflicting checkpoints), `injected` (an entry that fails verification), `corrupt-blob` (hash mismatch), `wrong-project` (a response naming another project or stream), `replayed` (an entry already held, harmless and counted). Each finding has one plain sentence (DESIGN 10.8 and 19 wording).
- **D-51:** Hub pins come from the hub file and the roster (`hub.admit.certPin`); system certificate authorities are not trusted for the hub unless your organization's CA is pinned instead (DESIGN 9 table).
- **D-52:** Tests that need a real hub process live in `hub/test/` and run in the `hub` CI job on Node 26 (they may import the client modules, D-27). The extension's own tests use a fake server for the transport.

### Harness, restore, byte capture, docs (MUS-08)
- **D-53:** The malicious-hub harness wraps the real hub in a fault proxy with these faults: withhold, delay, replay, reorder, roll back (serve a backup copy of the database), fork the view (two databases, two clients), inject a forged entry, corrupt a blob, refuse appends selectively, serve another project's stream, end a catch-up early with `more: false`. Each is detected and named by the client (D-50) or shown harmless, table-driven with a seeded random order.
- **D-54:** Restore drill test: back up the hub's state, write more, restore the old backup, start the hub; clients refuse the shorter history, re-push, and the next checkpoint covers every client's heads.
- **D-55:** Byte capture: every byte the hub writes to its database and blob folder, every byte it sends and receives at the application layer, and its logs are searched for canaries from cells not granted to it (text, product names, labels, decision reasons); none appear. Cells granted to the hub are the positive control (their canaries are readable by the hub's fold in memory, never logged).
- **D-56:** The operator section goes into `relay/README.md` as "Your organization's sync hub" (certificates and pins, secret files and modes, the hub file and enrolment, backups, the restore drill, upgrades, what the hub can read), with `hub/README.md` pointing there. SECURITY.md gains a "Your organization's sync hub" section; CHANGELOG gets plain bullets under "Military staff teams". README text for multi-user projects waits for Phase 33 (the feature is not usable from the editor until then).

## Amendments from planning (2026-11-20, on the owner's behalf; these refine the decisions above and win where they differ)

- **D-63 (refines D-45, D-50, D-54):** Version 2 checkpoint heads carry each head entry's lamport and newest roster, and both live inside sealed bodies. So the hub can checkpoint only the cells it can open: the base cell and cells granted with `hub.grant`. Coverage is the largest causally closed set of entries the hub can open. For every other cell, rollback and withholding are detected by the clients' high-water marks and by deps citing entries never delivered, and `delayed` applies to covered cells only. The restore drill asserts "the next checkpoint covers every client's heads" for covered cells; for other cells it asserts that clients re-push and the hub's heads then equal theirs. Members below a hub-granted cell see that cell's writer ids and entry counts in checkpoints (metadata only; stated in SECURITY.md).
- **D-64 (refines D-40):** Admitting the hub writes `hub.admit`, then `hub.grant` for the base cell, then the base cell grants to the hub's X25519 key. The roster then lists the base cell among the hub's cells, so every later base cell rekey (a member removed, a device revoked) still wraps the new epoch to the hub. The hub may never be granted the lead-only legacy cell (D-20).
- **D-65 (refines D-07):** Today's host records a missing head mark on first read, because marks live in each computer's own secret storage. So the unmarked-copy refusal lives in the copy flow, not in the host.
- **D-66 (refines D-08, D-11):** The lead and deputy roles are not stored in a member's roles, so `member.update` already cannot remove them. The D-08 and D-11 tests pin behaviour that is already right. Each plan proves the test has teeth with a stated mutation (break the rule and the test fails), instead of a test that fails on today's code.
- **D-67 (refines D-18):** Once a project has a cell order, a pin to a product@hash the fold cannot place in a cell counts as "above" and is refused. Machines holding different cells must decide the same way, and the host never writes such a pin.
- **D-68 (refines D-19):** A founding lead with no declared clearance may create only the org/Public cell, as Phase 31 allowed. Make Multi-User asks the lead to declare a clearance whenever a product needs a higher label.
- **D-69 (refines D-34, D-36):** Wire details settled in 32-20:
  - Grants travel inside append (`grants`) and in heads (grant hashes the device may fetch), and are fetched through the blob route.
  - Append declares the `blobRefs` an entry uses, because the hub cannot read sealed bodies. The 24-hour sweep (D-44) depends on these.
  - Catch-up is `GET /entries?stream&writer&from` per writer, with `more` and the heads reached.
  - A session is bound to one TLS connection, so a client keeps one keep-alive connection per session.
  - A refused session answer is 403 `session-refused`.
- **D-70 (refines D-49):** The client hands back checkpoints it holds that the hub lost after a restore. Without this, an honest restore with late concurrent entries could look like a fork. The harness has an "honest chain" control row to catch false fork findings from `checkpointConflict`.
- **D-71:** Adding the `hub` CI job also changes `scripts/lib/workflow.mjs` (CI_CHECKS) and `docs/development-workflow.md`, as ci.yml's header requires. Those are gate paths, so the integration PR needs the owner's gate approval.
</amendments>
