## Phase Boundary

Every tool call and every model request goes through one gate:

- one versioned capability vocabulary and label format in `src/domain` (no `vscode` import), refusing unknown verbs, fields, scales and levels;
- a capability manifest for every built-in tool and every MCP server tool, and a test that fails if any registered tool or execution path lacks one or reaches execution without the gate;
- one gate that decides from the actor, the capability, the context, the labels and the signed local policy bundle, with a floor no mode, setting or delegation can override;
- a local policy bundle signed by the person's device identity through Phase 69's signer, working with no network, failing closed to the floor plus read and plan, and self-signed on a fresh install;
- classification labels on projects, folders, files, chats and tool output, clearance dominance, a session high-water mark, and routing of every model request by the session's label;
- an OCSF-shaped decision record for every gate decision;
- SECURITY.md and README updated in the same phase so they describe the floor and the labels as the code does.

Not in this phase: DIDs, verifiable credentials, delegation chains and grants (Phase 71); execution backends and the sandbox (Phase 72); the credential broker (Phase 73); run contracts and run admission (Phase 74, OFFL-04); request-bound signed approvals (Phase 80); chain anchoring, status lists and the per-level maximum offline age as live checks (milestones L4 and L5). This phase only reserves their fields.

## Implementation Decisions

### Where the code lives and how the relay shares it (research flag 3)
- **D-01:** The pure parts live in a new folder `src/domain/gate/` (vocabulary, manifests, labels and scales, dominance, routing tiers, policy bundle format and validation, the decision function, the decision record shape), with no `vscode` import and no runtime dependency, like `src/domain/team/`. The parts that touch files, SecretStorage or VS Code live in `src/gate/` (bundle store, label map store, decision log) and the VS Code adapters in `src/services/` beside today's `policyGate.ts`. An import boundary test (the Phase 69 pattern) proves `src/domain/gate/*` imports neither `vscode` nor anything outside `src/domain`. *Undo: cheap (folder names).*
- **D-02:** The relay does not change in this phase. When the relay runs tools (Phase 77) it reaches the vocabulary the same way it reaches the agent core, through `relay/src/runner` and the existing `@ext/*` alias; the types are not copied into `relay/`. The relay workspace test stays as it is. *Undo: cheap.*

### Capability vocabulary (GATE-01, research flag 1)
- **D-03:** The vocabulary is version 1 (`gateVocabulary: 1`) and is closed: a capability is `{verb, ...constraints}` where the verb is one of `read{paths}`, `plan`, `workspaceWrite{paths}`, `shell{cwd}`, `network{hosts}`, `mcp{server, tools}`, `send{channel}`, `publish{target}`, `destroy{paths}`, `spawn{agent}`, `schedule`, `skill.write{scope}`, `spend{usd}`, `useSecret{handle}`, `infer{tier, provider, model}`, and the reserved `gpu{device}`. `publish`, `destroy` and `spawn` are added to the requirement's examples because the floor (D-16, D-17) and the execution-path test (D-08) need them by name; `infer` is defined and used for routing in this phase (D-31); `gpu` is reserved: known to the parser, always refused until a later phase defines it. An unknown verb, an unknown field, a wrong type or a version the build does not know is refused with a plain reason. Starting points: IronClaw's manifest fields and Hermes' grammar in the research folder; research confirms the field list. *Undo: costly once released (edge devices and anchored policy hashes commit to it); a new version can be added beside v1, never edited in place.*
- **D-04:** Today's `ActionCapability` (`src/domain/policy.ts`: `read`, `plan`, `workspaceWrite`, `shell`, `network`, `sharedWrite` and the rest) stays as the internal shorthand the UI and settings use, and maps one way into vocabulary verbs (for example `sharedWrite` becomes `workspaceWrite` on a shared path plus the floor's ask). The gate decides only on vocabulary capabilities. *Undo: cheap.*

### Manifests (GATE-02, GATE-03)
- **D-05:** A built-in tool's manifest is declared next to the tool's definition (a `manifest` field on the tool object in `src/agent/tools.ts`, `extraTools.ts` and the other tool files), not in a separate table, so a tool cannot be added without one. A manifest lists the effects (vocabulary verbs with constraints, which may name the tool's input fields that fill them), network hosts, credential handles, and the contexts it may run in (`interactive`, `unattended`, `relay`, `routine`). *Undo: cheap.*
- **D-06:** An MCP server's manifest is stored with the server's existing config (`McpServerConfig` in `src/services/mcpRegistry.ts`): declared effects per tool, allowed hosts and credential handles. A tool the manifest does not declare gets the most restrictive effects (`shell`, `network{*}`, `workspaceWrite{*}`, `destroy{*}`), so it asks in every mode and never runs unattended. Today's per-server `approval` and `readOnly` settings map into manifests with the same behaviour (a server marked read-only declares `read` for its tools). A stdio server's manifest says plainly that it runs on this machine with the person's own permissions, and it never runs in `unattended`, `relay` or `routine` contexts unless the person names it for that context. *Undo: medium (stored manifests need a migration if the format changes).*
- **D-07:** The Tools page and team member cards show each manifest in plain words ("Can change files in this project", "Connects to api.github.com", "Runs on this machine with your permissions") built from one function in `src/domain/gate/`, so the words and the gate never disagree. *Undo: cheap.*

### One gate for every execution path (GATE-04)
- **D-08:** One function, `decide(request, bundle, context)`, in `src/domain/gate/` returns `allow`, `ask` (with whether "always allow" may be offered), or `deny`, plus the rule that decided. Every execution path calls it: the agent loop's tool calls (file tools, Bash, web tools, knowledge, graphics, cyber tools), MCP tool calls, sub-agent spawns, routines and unattended runs, and every model request (D-31). Today's `decidePermission`/`decidePermissionAsync` (`src/agent/permissions.ts`), `forbidden`/`sensitive`/`risky` hooks (`src/agent/loop.ts` around line 620), `policyGate.ts`, `approvalPolicy.ts` and the unattended rules (`src/agent/unattended.ts`) become inputs to or parts of the gate, not separate deciders. A test enumerates every registered tool and every execution path and fails if one lacks a manifest or reaches execution without a recorded gate decision. *Undo: medium.*
- **D-09:** Approval cards are only a transport: the card carries the gate's question to the person and the answer back into the gate, which records it and re-decides. A card never decides on its own and cannot offer "always allow" when the gate says the action is on the floor. *Undo: cheap.*
- **D-10:** Migration keeps behaviour except the floor (research flag 2): every approval mode, auto-allow switch, allow rule, deny rule, protected path rule, held-after-outside-content rule and unattended rule decides as it does today when expressed through the gate. The existing tests of those rules stay green unchanged in meaning; the only tests that change are the ones that pin fully-autonomous behaviour the floor now overrides (D-19). *Undo: not applicable (a rule).*

### Policy bundle and its relation to settings (OFFL-01, OFFL-02, OFFL-03)
- **D-11:** The signed policy bundle is the ceiling; settings narrow inside it. The bundle holds what may happen at all: the highest approval mode allowed per context, the contexts each capability may run in, allowed MCP servers for unattended contexts, the label scales, the person's clearances, the cross-scale mappings and the routing tiers. The person's day-to-day preferences (approval mode, allow and deny rules, auto-allow switches, MCP approval settings) stay in VS Code settings and are applied by the gate inside the bundle's ceiling; a setting can never widen past the bundle. A fresh install's bundle allows everything today's settings can allow, so nothing changes for anyone until a bundle narrows it. *Undo: medium (moving preferences into the bundle later is a migration, not a format change).*
- **D-12:** The bundle is a JSON document signed with Phase 69's `signPayload` under the existing purpose `policy-bundle` (it is already in `PAYLOAD_PURPOSES`), stored per install in extension global storage (`<globalStorage>/gate/policy-bundle.json`), and verified with `verifyPayload` against the local key status (`localKeyStatus`). Its fields: `bundleVersion: 1`, `vocabulary: 1`, `issuer` (the device fingerprint and public key now; a slot for a DID from Phase 71), `issuedAt`, `expiresAt`, `ceiling`, `scales`, `mappings`, `clearances`, `routing`, `defaultLabel`, and reserved, empty-by-default fields `anchorRoots` (each a root with an inclusion proof), `statusLists` (references) and `maxOfflineAge` (per scale and level). Reserved fields are validated for shape but not used. An unknown field is refused. No second signer is added (Phase 69 D-10). *Undo: costly once released (same as D-03).*
- **D-13:** Failing closed (OFFL-02): a missing, unparseable, unsigned, tampered, wrong-purpose, revoked-key or expired bundle leaves only the floor plus `read` and `plan`, every other capability is refused with one plain sentence naming the cause and the fix (for example "Your policy file was changed outside NEAR AI. Run NEAR AI: Reset Policy to Defaults to sign a fresh one."), and a status bar item and the setup view show the same. Nothing waits on the network (OFFL-01); a test runs every decision with network access stubbed to throw. *Undo: cheap.*
- **D-14:** Fresh install and renewal: on activation, when no bundle exists, the extension creates the device identity if needed (Phase 69's `createDeviceIdentity`, created on first need) and signs a default bundle. A self-signed bundle expires after 365 days and is re-signed automatically on activation in its last 30 days, but only while it still verifies; a tampered bundle is never re-signed silently, only through the person's "Reset Policy to Defaults" command, which is recorded. If SecretStorage cannot hold the key (for example a code-server host with no keyring), the gate fails closed as D-13 says with a plain explanation; research checks how code-server and the Linux keyring fallback behave so this does not break the extension for people who use it today. *Undo: cheap (durations are bundle values).*
- **D-15:** Device clocks (identity research risk 8): expiry compares against the later of the wall clock and the last time this install saw a valid bundle, kept in SecretStorage, so turning the clock back does not revive an expired bundle. *Undo: cheap.*

### The floor (GATE-05, GATE-06)
- **D-16:** Refused in every mode, with no card: the project key folder (today's `STATE_KEYS_PATH` rule, unchanged), this extension's identity and policy files in global storage, the person's NEAR key folder in their home folder (`~/.near-credentials`), and well-known credential stores (SSH private keys, cloud and registry credential files such as `~/.aws/credentials`, `~/.config/gcloud`, `~/.azure`, `~/.docker/config.json`, `~/.netrc`, `~/.git-credentials`, and commands that read the OS keychain such as `security find-generic-password` or `secret-tool lookup`). Detection follows the honest text heuristic of `namesStateKeys` and says what it cannot see. Research settles the exact list. *Undo: cheap (a list), but widening it later breaks fewer workflows than narrowing it would expose.*
- **D-17:** Asks a person in every mode, fully-autonomous included, with no "always allow" and no run-wide grant: writes into `.git/` (any `.git` segment, as `PROTECTED_WRITE` does today), `.planning/.near-ai/` and `.near-ai/` state (everything `PROTECTED_WRITE` covers); publishing (`publish`: `git push`, package and extension publishing, release creation, container image push, deploy commands, and `send` to a channel); and destruction (`destroy`: recursive deletes outside the agent's scratch folders, `git reset --hard`, `git clean -f`, force pushes, branch and tag deletion, history rewrites). The owner accepted this floor. In a context with no person present (unattended, routine, relay) a floor ask becomes a refusal with a plain reason, recorded. *Undo: medium (behaviour people get used to).*
- **D-18:** Workspace credential-file reads (`.env`, private key files inside the project) keep today's behaviour: they ask in every mode except fully-autonomous. They are not added to the floor because the owner's accepted floor does not name them; this is listed as an open question for the owner. *Undo: cheap.*
- **D-19:** Fully-autonomous becomes "no approval needed within the policy's grant", never "gate off" (GATE-06). In code this removes the `policy.mode !== 'fully-autonomous'` exemption for floor actions in `src/agent/loop.ts` (around line 631) and the fully-autonomous shortcuts in `src/agent/permissions.ts` (around lines 213 and 222) for floor actions only. The test in `src/test/protectedPaths.test.ts` that pins today's behaviour ("fully-autonomous reads credential files and writes into .git/, .planning/.near-ai/ and .near-ai/ without asking; the other modes ask", around line 304) is changed deliberately in the same plan: writes into `.git/`, `.planning/.near-ai/` and `.near-ai/` now ask in fully-autonomous with no "always allow", and the credential-file read part stays as D-18 says. SECURITY.md (the "What the agent can do without asking" section and the Known limitations row "Under `fully-autonomous`, the agent ... writes protected files ... without asking") and README (the `nearAi.actionPolicy` row) are updated in the same plan so the docs never describe code that is not there. *Undo: medium.*

### Decision records (GATE-07)
- **D-20:** Every gate decision (tool calls, model routing, label changes, declassification, bundle load failures, read and plan included) produces one record shaped after OCSF: class and activity ids, time, actor (person, agent session, sub-agent, with the device fingerprint), the capability in vocabulary form, the resource, the outcome (`allowed`, `asked`, `approved`, `denied`, `refused-by-floor`), the rule that decided (a stable rule id such as `floor.git-write`, `bundle.ceiling.mode`, `settings.allowRule`, `label.dominance`, `route.local-only`), the bundle's hash and the session's label. Research picks the OCSF classes (for example Authorization or API Activity) and maps fields. Records carry `recordVersion: 1` so the later audit chain can sign and anchor them without a shape change. *Undo: medium (records outlive a change; versioned).*
- **D-21:** Records go to a local append-only JSON Lines file per project in extension global storage (`<globalStorage>/gate/decisions/<project key>.jsonl`), rotated at a size cap, never into the workspace, transcripts or synced state, with secrets redacted by `src/domain/redaction.ts` before writing. Writing a record never blocks or fails a decision; a write failure is reported once. Today's `auditStore` keeps its job; the decision log is separate. *Undo: cheap.*

### Labels and scales (CLAS-01, CLAS-02)
- **D-22:** A label is `{scale, level, compartments, releasability, handling}` exactly as decision 11 and CLAS-01 say, with `level` as the level's name (validated against the scale's ordered list), not an integer, so a label reads plainly in files and records. Unknown scale, level, compartment syntax or field is refused. Labels are vocabulary v1 (D-03). *Undo: costly once released.*
- **D-23:** The bundle ships four presets, each an ordered list: `org` (Public < Internal < Confidential < Restricted; the default scale), `ca-protected` (Protected A < Protected B < Protected C), `ca-classified` (Confidential < Secret < Top Secret) and `nato` (NATO Unclassified < NATO Restricted < NATO Confidential < NATO Secret < Cosmic Top Secret). A clearance on one scale covers another only through a mapping in the bundle; none ships by default. The NATO list comes from secondary copies only and the two-scale reading of the Canadian families is the plan's reading: the label settings and SECURITY.md say so, and your organization's security officer confirms both before relying on them (research flag 5). *Undo: costly once released (preset ids are in labels).*
- **D-24:** The default label of an unlabelled project on a fresh install is `org` Public, which routes to any cloud, so a fresh install routes exactly as it does today (research flag 4). Labels are opt in. *Undo: cheap (a bundle value), but changing the default later changes routing for every unlabelled project.*
- **D-25:** Where labels live: one label map per project at `.planning/.near-ai/labels.json` (committed with the project so labels travel with it), keyed by project-relative path for folders and files plus a project entry; never file attributes. The map is signed with Phase 69's signer under a new purpose `label-map` (added to `PAYLOAD_PURPOSES`). An unlabelled file takes its nearest labelled folder's label, then the project's, then the bundle's default (CLAS-01). Because a label only restricts, a map that does not verify (tampered, unknown signer such as a teammate's device before Phase 71) is applied only where it raises a label above what the verified sources say, never where it lowers one, and the person is told. Writes to the map by an agent are on the floor (it is under `.planning/.near-ai/`). *Undo: medium (the file location and purpose name are in projects people share).*
- **D-26:** Labels follow files: a rename or move through the agent's file tools or the extension moves the map entry; a copy made by the agent carries the session's high-water mark (D-29); a rename outside the extension loses the file's own entry but keeps its folder's label, which the label settings say plainly. Phase 72's copy-and-apply calls the same map update. Chats and tool output carry their session's mark as their label. *Undo: cheap.*

### Clearance, dominance and the high-water mark (CLAS-03, CLAS-04)
- **D-27 (must-carry, PR #60 review on CLAS-03):** Until Phase 71, a clearance comes from the person's own device-signed policy bundle, so it is self-asserted: the person declares their own clearance and signs it with their own key. It is not an enforced clearance boundary and must not be described as one. The label settings, the bundle's clearance editor text and SECURITY.md say this plainly. From Phase 71 the clearance comes from verified credentials (VCRD-07). A fresh install's bundle gives the person `org` Restricted (the whole commercial scale) and no clearance on the government or NATO scales; a person who labels content Protected B must first add a matching clearance to their own bundle, which is recorded. *Undo: cheap (text and a default).*
- **D-28:** Dominance is a small hand-written evaluator in `src/domain/gate/` with no runtime dependency: same scale or a bundle mapping, level at least the label's, every label compartment held, releasability met, nothing expired. A property test (generated labels and clearances with `node:test`, no new dependency) shows no access without dominance. Agents and sub-agents act with the session person's clearance in this phase; narrowing per agent is Phase 71. *Undo: cheap.*
- **D-29:** Each agent session carries a high-water mark: the highest label it has read (files, folders, tool output, MCP results, attachments, a parent's mark). Sub-agents start at their parent's mark. Anything the session writes takes the mark as its label (the label map is raised, never lowered), messages it sends and summaries it makes carry it, and the chat shows it. Labels on different scales with no mapping make the mark the set of both, and routing takes the strictest tier. The mark goes down only by a person's "Lower this chat's label" action, which asks for a reason and is recorded as a decision record. Network-effect tools (`network`, `send`, `publish`, MCP tools with network effects) at a mark whose tier is `local-only` or `deny` are refused, because content would leave the machine. *Undo: medium.*

### Routing by label (CLAS-05, CLAS-06, CLAS-07)
- **D-30:** The bundle maps each level (and the routing handling flag `local-only`; per D-47 the v1 handling flags are `local-only` and `no-agent-tools`, only `local-only` routes, and no flag can relax a tier) to a tier: `any-cloud`, `attested-cloud`, `local-only` or `deny`, with the CLAS-05 defaults: Public any cloud; Internal, Confidential and Protected A attested cloud; Restricted, Protected B, Protected C and every classified and NATO level above NATO Unclassified local only (NATO Unclassified attested cloud); `deny` available per compartment. Protected B stays local only unless your organization changes its bundle, because no CCCS Medium assessment of NEAR AI Cloud was found. *Undo: cheap (bundle values).*
- **D-31:** One route check before every model request, wherever it starts: the main chat (`src/services/chat.ts`, which uses `clientFor` and `privateRouteFor` from `src/services/providerCache.ts` and `providerFactory.ts`), sub-agents, the auto mode safety model, image and multimodal requests, research and summary calls. It decides `infer{tier, provider, model}` from the session's mark: `attested-cloud` allows only NEAR AI Cloud models whose attestation and response signature verified for this request (`src/services/attestation.ts`), `local-only` allows only the local or hybrid profile's on-device models, `deny` refuses. A request that needs `local-only` with no local model configured is refused with a plain explanation and never sent (CLAS-06). A test enumerates every model request site and fails if one skips the check. If the mark rises during a run so the current model is no longer allowed, the next request is refused with the explanation rather than silently switching models. *Undo: medium.*
- **D-32:** CLAS-07 wording, used where labels are set and in SECURITY.md: "Labels and routing are an organizational control that helps prevent mistakes. They do not make this device accredited for classified information, and until verified credentials arrive your clearance is what you declared yourself." Research flag 6: the plan checks each sentence of the wording against what the gate actually guarantees. *Undo: cheap.*

### UI
- **D-33:** Minimum UI in this phase, built on today's views, no new webview framework: the Tools page and member cards show manifests (D-07); a status bar item shows the policy state (valid, renewing, failed closed with the fix) and the session's label; commands "NEAR AI: Set Label" (file, folder, project, from the Explorer context menu and the Command Palette), "NEAR AI: Lower This Chat's Label", "NEAR AI: Show Policy" and "NEAR AI: Reset Policy to Defaults"; the chat shows its label and why a request was refused. A clearance and mapping editor beyond editing through "Show Policy" is not in this phase. A UI-SPEC is not required: the gate's UI is text in existing surfaces. *Undo: cheap.*

### Release and process
- **D-34:** Stage 1 phases ship in 0.4.x as plans land (owner decision). The phase lands as reviewed PRs into `main`, each under the agent review's diff budget (keep each PR diff under 950,000 bytes, as Phase 69 did), each leaving the extension usable and `main` green; because the plans are large, a planning-only PR goes first (as Phase 69's did). The floor change (D-17, D-19) and its documentation land together in one PR, never split, so no release ships code and docs that disagree. Repo rules for every plan: tests on every change; every test command uses the memory cap `systemd-run --user --scope -q -p MemoryMax=4G -p MemorySwapMax=0 choom -n 1000 -- timeout 900 env NODE_OPTIONS=--max-old-space-size=1536 <cmd>` (full suite and e2e: MemoryMax=6G, timeout 1800), one heavy run at a time; e2e only under xvfb with Wayland variables stripped; plain language, no em-dashes, "your organization" never "NEAR organization"; no new runtime dependencies; no local machine paths in repo files. *Undo: not applicable.*

### Amendments from research (2026-11-16, made on the owner's behalf; these refine the decisions above and win where they differ)
- **D-35 (refines D-03):** `spend` uses whole numbers of nano-USD: `spend{nanoUsdPerRun, nanoUsdPerDay}`, because Phase 69's canonical JSON accepts safe integers only (`src/domain/team/canonical.ts`, `signedPayload.ts` tells callers to use nano-USD). Every number in the vocabulary, bundle, labels and records is an integer. *Undo: costly after release, free now.*
- **D-36 (refines D-31, D-30; changes CLAS-05's wording):** `attested-cloud` is decided before sending from what can be known before sending: the model is a TEE model (`privacyBoundary === 'tee'`) on NEAR AI Cloud's own endpoint. After each response the attestation and response signature are verified (`src/services/attestation.ts`), the result is recorded, and a failed verification stops further requests at that tier for the session with a plain explanation. Today's attestation is on demand, after the fact and networked (`agentSession.ts` around 696-701), so "verified for this request" cannot be true before the request. REQUIREMENTS.md CLAS-05 is reworded to match. *Undo: medium.*
- **D-37 (refines D-31):** `local-only` allows only a local runtime on a loopback address, or a host your organization names in the bundle's `routing.localHosts` (empty by default), because the local runtime prompt accepts any `https://` URL today (`src/extension.ts` around 294). A LAN host counts as local only when the bundle names it. *Undo: cheap (bundle value).*
- **D-38 (refines D-06):** MCP servers configured before this phase get `toolDefaults: "legacy"` manifests that decide exactly as today (absent means legacy; no data migration). "Most restrictive" applies to servers added after this phase and to tools a declared manifest leaves out. *Undo: cheap.*
- **D-39 (refines D-14):** A missing bundle is self-signed only on a true fresh install (no SecretStorage marker `nearAi.gate.lastValid` yet). Once an install has had a valid bundle, a deleted or unverifiable bundle fails closed (D-13) and only "Reset Policy to Defaults" re-signs, recorded, so deleting the file never resets a narrowed policy. A lost device key (for example code-server, where secrets live in the browser) re-signs automatically only when the bundle was never customised; otherwise the person is told to reset. *Undo: cheap.*
- **D-40 (refines D-32):** The CLAS-07 wording also says the checks cover what NEAR AI sends to models and its own file and tool calls, not everything a shell command or an add-on server does inside itself, and that a declared clearance is not an enforced boundary. The exact text is in 70-RESEARCH.md section 12. *Undo: cheap.*
- **D-41 (refines D-33):** "NEAR AI: Edit Policy" writes an unsigned draft in global storage, validates it with plain errors, and signs and records it on Apply; "Show Policy" is read-only. This is how a person adds a clearance or mapping (D-27). *Undo: cheap.*
- **D-42 (refines D-26):** There is no agent rename tool, so labels follow renames through VS Code's `onDidRenameFiles`, the shell's `mv` and `git mv` when the gate sees them, and a report of label entries whose path no longer exists. *Undo: cheap.*
- **D-43 (refines D-17):** The gate carries `presence: 'person' | 'none'`. Sub-agents of a person's run are `interactive` with a person present (their cards queue for the person) even though they carry the PERF-01 unattended flag; a floor ask from a sub-agent stays a card with no grant, and a late approval is one-shot. Only runs with no person present (unattended, routine, relay) turn floor asks into refusals. *Undo: medium.*
- **D-44 (refines D-17):** The floor keeps today's exemption for `.planning/.near-ai/team.md` (`tools.ts` around 126, SECURITY.md). `labels.json` gets no exemption. *Undo: cheap.*
- **D-45 (refines D-17; research open question 2):** Discarding uncommitted work (`git checkout -- <paths>`, `git restore` of the worktree, `git stash drop`, `git stash clear`) is destruction and on the floor, the same class as `git reset --hard`. *Undo: cheap.*
- **D-46 (refines D-17; research open question 3):** Publishing on the floor: `git push` (any), package and extension publishing (`npm publish`, `vsce publish`, `ovsx publish`), release creation (`gh release create|upload|edit`), container image push, and deploy commands the research lists. Other GitHub writes (`gh pr create`, `gh pr merge`, `gh issue comment`) stay with today's settings layer and are an open question for the owner. *Undo: cheap.*
