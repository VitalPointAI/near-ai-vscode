<objective>
Put the owner's trust badge (CLAS-08) on every cloud answer: three plain states chosen by one pure function from checks that actually ran (plan 25's after-answer check and pre-send connection fact), a click that explains the state and shows the full attestation on request, a state that settles even offline, and colours that read in every theme. It ships last, after PR 4d, so its meaning never changes between releases (D-51).

Purpose: PR 4e (D-49). CLAS-08 (owner, 2026-11-16) and the visible half of CLAS-05's amplification: a person can see whether an answer's connection was proven private. OFFL-01: every check is out of band and a badge never waits forever (D-56). Plan 27 replays the badges when a chat reloads, adds the end-to-end check and the documentation.
Output: `src/domain/gate/trustBadge.ts`, `media/chat/trustBadge.js`, the badge in the chat page and its styles, the automatic check with its timeout and Check again in the session, the details request, `gateTrustBadge.test.ts`.

Owner's decision (2026-11-16, PROJECT.md Platform direction decision 16; named in the 4e PR body): every cloud answer from a TEE model is checked once automatically, because a badge that only ever says "Not verified" until someone clicks would tell people nothing; the cost is one signature request per answer and the attestation report reused for 10 minutes, and an answer that cannot be checked (offline) says so.

Corrections from the 2026-11-17 audit, applied here: the check map by chat id and the 10-minute report cache are built in plan 25 (PR 4d) and reused here; a check that does not settle times out to Not verified (D-56); the badge is on the lead agent's answers only, and says so (D-56); it replaces plan 25's Check again button in the old row, keeping its effect on the chat's stop.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| check results -> the words a person trusts | a badge that overstates privacy leads a person to share what they should not |
| the attestation report -> the page and the editor | the report comes from the network and is shown to the person |
| the page -> the host (trust-details, verify-response) | messages from the webview are untrusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
