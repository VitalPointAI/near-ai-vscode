<objective>
Put the owner's trust badge (CLAS-08) on every cloud answer: three plain states chosen by one pure function from checks that actually ran (the post-response attestation and signature check from plan 24 and the pre-send connection fact from plan 25), a click that explains the state and shows the full attestation on request, and colours that read in every theme.

Purpose: CLAS-08 (owner, 2026-11-16) and the visible half of CLAS-05's amplification: a person can see whether an answer's connection was proven private. Plan 27 replays the badges when a chat reloads, adds the end-to-end check and the documentation.
Output: `src/domain/gate/trustBadge.ts`, `media/chat/trustBadge.js`, the badge in the chat page and its styles, the automatic check and Check again in the session, the details request, `gateTrustBadge.test.ts`.

Recorded planning choice (visible, for the PR 4 body): every cloud answer from a TEE model is checked once automatically, because a badge that only ever says "Not verified" until someone clicks would tell people nothing; the cost is one signature request per answer and the attestation report reused for 10 minutes, and an answer that cannot be checked (offline) says so. Answers from forwarded models are never checked, since no attestation exists for them.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| check results -> the words a person trusts | a badge that overstates privacy leads a person to share what they should not |
| the attestation report -> the page and the editor | the report comes from the network and is shown to the person |
| the page -> the host (trust-details, verify-response) | messages from the webview are untrusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-70-95 | Repudiation | a badge claiming more than the checks proved | high | mitigate | one pure trustBadgeFor, exhaustive never-stronger test, pending and failed checks are Not verified (Tasks 1, 2) |
| T-70-96 | Tampering | report text injected into the page as markup | medium | mitigate | textContent only, checked by a grep gate; the full report opens as a JSON document, never in the page (Task 3) |
| T-70-97 | Tampering | a forged trust-details or verify-response message | low | mitigate | parseChatWebviewMessage accepts only the run id shape and the known fields (Task 3) |
| T-70-98 | Information disclosure | the attestation details written into the workspace or synced | low | mitigate | an untitled JSON document, nothing written to disk (Task 3) |
| T-70-SC | Tampering | npm installs | high | mitigate | No package is added |
</threat_model>
