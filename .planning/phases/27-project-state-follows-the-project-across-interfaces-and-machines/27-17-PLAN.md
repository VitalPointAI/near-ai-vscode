<objective>
Give a project with no online home one (D-14, SYNC-09): on the person's click, git init if needed, sign in to GitHub through VS Code, ask public or private each time with plain notes, create the repository, add the remote and hand over to the turn-on flow that pushes the sync branch. Offer pushing the person's own code separately, behind a check that shows the files and blocks likely secrets. Fall back to the gh CLI or a pasted empty-repository URL when VS Code's GitHub sign-in is missing. Report every error plainly and resume a half-done setup.

Purpose: D-14 supersedes the earlier "no remote: say so and never add one" choice (CONTEXT Claude's Discretion Q3). Without an online home there is nothing to sync to.
Output: a pure onlineHome domain module, a fetch-injected GitHub API client, the flow (no vscode), the code-push check, thin vscode adapters, and two test files that use fakes for GitHub and auth with no network.
Canon-referral breadcrumb (not minted as a prohibition): repository-name injection into URLs, JSON and git arguments is handled by strict validation, JSON serialisation and array arguments (canon injection).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| extension -> the person's GitHub account | repository creation and pushes act on the account with a broad 'repo' scope |
| project files -> public internet | a public repository exposes every pushed file |
| GitHub API, gh output and pasted URLs -> extension | names, URLs and errors from outside |
| person's folder name and typed name -> URL, JSON body, git arguments | untrusted strings reach requests and commands |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-74 | Information disclosure | accidental public exposure of the project's code | high | mitigate | visibility asked every time with no preselection and plain notes; code push is a separate offer naming the visibility (Tasks 1, 3) |
| T-27-75 | Information disclosure | secrets pushed with the code | high | mitigate | file list shown first; secret file names (ported repo rules) and content (scanSecrets, SECRET_TOKENS) block the push; values never echoed (Task 3) |
| T-27-76 | Information disclosure | OAuth or gh token in arguments, files, logs or messages | high | mitigate | token held in memory; API header and child-environment git config only; progress file token-free; spy tests over arguments, files, messages and console (Task 2) |
| T-27-77 | Tampering | repository-name or login injection into URL, JSON or git arguments | medium | mitigate | validateRepoName and validateLogin before use; JSON.stringify bodies; array arguments; clone_url must equal expectedCloneUrl (Tasks 1, 2) |
| T-27-78 | Elevation of privilege | acting on the account without consent | high | mitigate | modal start confirmation; each irreversible step behind its own click; declining writes nothing (Task 1) |
| T-27-79 | Tampering | pasted URL with a helper transport or a non-empty repository | medium | mitigate | validateRemote refuses '::' transports; ls-remote must show no refs (Task 2) |
| T-27-80 | Spoofing | a different gh binary or an unauthenticated gh | low | accept | gh is taken from PATH like git; it must report signed in; its token is used only for github.com |
| T-27-81 | Denial of service / integrity | a half-done setup or a duplicate repository | medium | mitigate | progress saved per step; resume checks getRepo before creating (Task 2) |
