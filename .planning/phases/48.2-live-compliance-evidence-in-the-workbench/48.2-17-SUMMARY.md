# Phase 48.2 Plan 17: Only the install identity writes the trust anchor; every session gets the site key admission uses Summary

The trust anchor is now protected twice: a Kyverno policy, failing closed, lets only `sterling-evidence-install` create, change or delete `sterling-evidence-trust` and `sterling-release-evidence` (DELETE alone also by the namespace controller, so a namespace can be deleted), and every session gets your organization's site key as `STERLING_ORGANIZATION_PUBLIC_KEY`, rendered from the same site value admission verifies images with, which 48.2-04's check compares `organization.pub` against.

## Rendered write policy (for the wave 3 gate; namespace theia-cloud)

```yaml
apiVersion: policies.kyverno.io/v1
kind: ValidatingPolicy
metadata:
  name: sterling-evidence-trust-writes
spec:
  validationActions: [Deny]
  failurePolicy: Fail
  evaluation:
    background:
      enabled: false
  matchConstraints:
    resourceRules:
      - apiGroups: [""]
        apiVersions: [v1]
        operations: [CREATE, UPDATE, DELETE]
        resources: [configmaps]
    namespaceSelector:
      matchLabels:
        kubernetes.io/metadata.name: theia-cloud
  matchConditions:
    - name: evidence-trust-anchor
      expression: "(object != null ? object.metadata.name : oldObject.metadata.name) in ['sterling-evidence-trust', 'sterling-release-evidence']"
  validations:
    - expression: "request.userInfo.username == 'system:serviceaccount:theia-cloud:sterling-evidence-install' || (request.operation == 'DELETE' && request.userInfo.username == 'system:serviceaccount:kube-system:namespace-controller')"
      message: "Only the install identity sterling-evidence-install may write the evidence trust anchor."
```
