    - Parity "refuse": a changed byte in the manifest, a second key pair's public key, a changed signature and a changed message digest are each refused by both.
    - The service, given a folder whose `manifest.json` that bundle signs, with the public key at `<STERLING_EVIDENCE_DIR>/supplier.pub` and the bundle at `<STERLING_EVIDENCE_DIR>/release-<version>.sigstore.json`, reports the release layer `verified` with anchor `supplier`.

Per D-17, D-18 and D-19. Write the parity test first. `verifySigstoreBundle(content, bundle, publicKeyPem)`: accept only the key-mode form (a `messageSignature` with a SHA-256 `messageDigest` and a signature, a public key hint, no certificate); check the digest equals SHA-256 of the content, then `crypto.verify('sha256', content, key, signature)` with an ECDSA P-256 key (refuse any other key type); return `{ ok, reason }`, never throw for a bad input. Re-export it from `compliance-entry.ts`. The service reads anchors only from `STERLING_EVIDENCE_DIR` (default `/etc/sterling/evidence`): `organization.pub` (role `organization`) and, only when no `organization.pub` exists, `supplier.pub` (role `supplier`); it never reads a key from `/opt/sterling/evidence` or from any bundle.
