<domain>
## Phase Boundary

A Sterling Sovereign AI (SovAI) workbench, fresh from install or from a plain `docker run`, opens the Compliance view on the release's own evidence, verified, with every state and freshness judged against the current time; at a site, the site's own evidence arrives live on top of it; nothing that cannot be verified is shown as passing.

In this phase:
1. Release (product) evidence inside every release image, under a manifest the release key signs.
2. Verification at start and on every change, with trust anchors from configuration only.
3. Real-time re-judging by the one status engine, with a freshness policy (current, ageing, out of date).
4. Live site evidence: a scheduled site collector, operator-signed site files (the site evidence export, the offline rescan, the exchange agreements), delivered to every session through a read-only mount.
5. The Compliance view: release then site layers; source, as-of time, freshness and verification on every cell.
6. The confirmed `compliance:refresh` file-mode bug.
7. The statements, evidence rules, documents and gap rows these obligations need.

Not in this phase:
- HQ's organization view of its edge sites (48.1-04's strategy: edges report by signed file; the view here shows its own site).
- SI-2 remediation timeliness judged from findings (findings are shown, not judged; G479 records it).
- Any change to 46-09's release file format `sterling-release/1`, or to any `.planning/phases/46-*`, `47-*`, `48-*` or `48.1-*` file: the cross-phase items are in "Hand-offs".

## Implementation Decisions

### The owner's direction (locked)
- **D-01 (owner, 2026-11-25):** The evidence shown is always a real-time understanding of the product's compliance status. Every state and every freshness label on screen is computed from evidence times against the current time when shown, never taken as recorded at build time.
- **D-02 (owner, 2026-11-24):** Each release image carries its own product evidence, read-only: the SBOM, the vulnerability scan results, the signature and attestations, the product's SSP control statements, the OSCAL package, the gap register and the road-to-production page. It is verified at start against the release's signed manifest and shown with its as-of time, the release build.
- **D-03 (owner):** Product evidence that depends on time never goes silently stale. Vulnerability scans show their age and flip to out of date past a threshold set in policy; the site can rescan offline with the Grype database on signed media (47-26 registers the tools; 47-29 builds the rescan).
- **D-04 (owner):** After install, the site's own evidence is layered on top: the site's collectors (Phase 48's deployment collector and its signed site evidence export; 48.1's hosted documents, alerting and exchange register), continuous or scheduled, each item with its own collection time and freshness rule, pushed to the Compliance view live the way other live state reaches sessions (47-32's site record ConfigMap pattern, or the hub), and never cached as if current.
- **D-05 (owner):** The view layers product evidence, then site evidence. Every control or state cell shows its source, as-of time, freshness (current, ageing, out of date) and verification status. "Authorization is your organization's decision" stays. In Restricted Mode, and with no site evidence, it shows the product evidence, clearly labelled.
- **D-06 (owner):** Evidence is verified (signatures and manifest) before display. A tampered or unverifiable bundle shows as not verified, never as passing. Zero trust: no evidence is trusted for where it is found.
- **D-07 (owner, confirmed bug):** `npm --prefix docs-site run compliance:refresh` writes the public dashboard projection with mode 0600, so the workbench (uid 10001) cannot read the README's own read-only bind mount (EACCES). Public projection files are 0644; a test covers it.
- **D-08 (owner):** Air-gapped and disconnected edge sites work: no outside fetch; freshness is judged from local signed sources.
- **D-09 (owner):** UI in the original theme with lifted cards, codicons and Theia variables only (memory "original UI design"); a UI design contract (`48.2-UI-SPEC.md`, `/gsd-ui-phase 48.2`) precedes the view plan; the product is named Sterling Sovereign AI, short SovAI.
- **D-10 (owner):** Gap ids only from this phase's reserved block, G475 to G479. Every caveat found goes into `compliance/gaps.json` with `appliesAt` and `blocksProduction` (memory "capture considerations").

### Release evidence and the one engine
- **D-11: One engine, judged now.** The bundle writes `dashboard/judgement.json` beside `dashboard.json`: for each level, control and component, the status engine's inputs (responsibility, statements, rules by statement, rule results with `collectedAt`, `commit` and `window`, tailoring, limitation, unsettled, self-signed, risk acceptance, head) and the presentation fields (label, title, gap, text file), but no clock and no state. `rejudge(judgement, { now, observations, policy })` in `compliance/src/judgement.ts` re-runs `computeStatus` and `aggregateControl` and the reason texts. The session runs it from the engine bundle (`workbench/tools/build-engine.mjs`, a new `compliance-entry.ts`, `engine/compliance.cjs`), never a copy. A parity test proves `rejudge` at the bundle's own `generatedAt` reproduces every row of `dashboard.json` exactly. The row rule (today's `controlState` in `dashboard.ts`) moves into `judgement.ts` and both call it, so they can never differ; from 44.1-05 on, each component's applicability is one more carried input (H-11). The browser never computes a state. Risk acceptances that expire and evidence windows that lapse change the view on their own.
- **D-12: Freshness labels.** Each rule result has a freshness from its `collectedAt`, its window kind and the policy: **Current** (age within the ageing threshold), **Ageing** (past the ageing threshold, within the out-of-date threshold), **Out of date** (past the out-of-date threshold, which is the engine window, so an out-of-date result is exactly the engine's Stale). `head` evidence (tests, CI checks, the SBOM) is about the release commit and stays current while the session runs that release. A cell's freshness is the worst of its results; a cell with no evidence has none. The state word "Stale" stays (docs site parity); its explanation says "evidence out of date".
- **D-13: Freshness policy (owner question 1, default).** The release's defaults are compiled into the engine: `FRESHNESS` (the out-of-date thresholds, unchanged for the existing kinds) and a new `AGEING` table, plus two new kinds, `vulnerability` (the scan's evidence time is its database build date, not the scan time) and `live` (site collector facts). Your organization may only tighten them, in the site trust document signed with your site key (D-17). A looser value is clamped to the release default and reported; a missing or unverifiable trust document means the release defaults and a plain note. Default table (owner question 2):

  | Kind | Ageing after | Out of date after | Used by |
  |---|---|---|---|
  | head | never by time | when the session no longer runs the release the evidence is for | tests, CI checks, SBOM, secret scan |
  | audit | 18 hours | 24 hours (unchanged) | audits |
  | settings | 5 days | 7 days (unchanged) | repository settings, the site evidence export |
  | harness | 23 days | 30 days (unchanged) | harness scans |
  | document | 335 days | 365 days (unchanged) | documents, hosted documents, site agreements |
  | attestation | 335 days | 365 days (unchanged) | signed attestations |
  | vulnerability (new) | 7 days | 30 days | release scan and site rescans, from the database build date |
  | live (new) | 30 minutes | 2 hours | site collector facts |

- **D-14: Clock honesty.** A session clock earlier than the release build time (a `builtAt` in the future) is the clock case: rows are shown, every freshness is "Unknown: this computer's clock is earlier than the release build", nothing is Met, and the release layer keeps its verification. Only a rule result, observation, site file or fact group dated more than 5 minutes in the future (`FUTURE_TOLERANCE_MS`) is Did not verify (`future-dated`), and it is not used. (Revised 2026-11-25 after the plan check.) At air-gapped sites the clock comes from the on-site time source (47-22) and clock-error alerts (48.1-23) reach the view as site evidence.
- **D-15: Release evidence layout.** `/opt/sterling/evidence/`, owned by root, files 0644, folders 0755: `manifest.json` (format `sterling-evidence/1`: `release`, `commit`, `builtAt`, `subject` = the software image ID the SBOM and scan describe, `bundle` and `package` (each `included` or `none`), and `files` with path, SHA-256 and size; no symlink, no file outside the list; one definition, `checkEvidenceManifest` in `compliance/src/judgement.ts`); every release has a folder: one with no compliance package says `package: none`, and with no bundle as well `bundle: none`, and still holds the SBOM and scan; `bundle/` (the release's verified evidence bundle, with `dashboard/judgement.json`); `package/` (the compliance package tarball and its checksum); `sbom/` (the image's CycloneDX SBOM); `scan/` (the Grype JSON and `grype db status` with the database build date, schema and checksum); `documents/` (the road-to-production page and the gap register as published). The scan becomes an `image-scan` observation (subject `sterling-image`, window `vulnerability`, `collectedAt` = the database build date, counts by severity).
- **D-16: Build order (the image cannot hold its own signature).** The image job builds the software image S (target `release-software`, today's `release`), takes its SBOM and scan, assembles the evidence, sets the folder's modes (files 0644, folders 0755), then builds R (target `release`) = S plus exactly one data-only layer holding `/opt/sterling/evidence`, copied with `COPY --chown=0:0` and no octal `--chmod`, never a `RUN chmod` layer. One script, `workbench/tools/check-evidence-layer.mjs`, run by both the container test and the release workflow, proves it: R's RootFS diff IDs are S's plus one, and that layer's tar holds only `opt/sterling/evidence/**` (with its two parent folders), no whiteout, files 0644 and folders 0755 owned by root, and exactly the manifest's files plus `manifest.json`; so the SBOM describes every program in R. Every release does this, hotfixes included: with no compliance package the image job runs `release-evidence --no-package` (and `--no-bundle` when it has no bundle) and the manifest is signed the same way; a tree without the compliance tooling fails the job rather than ship an image without evidence. Smoke, egress and Get Started tests run on R. Publish pushes R, signs it and attests the SBOM as today, checks that the `container-release` key is a cosign ECDSA P-256 key (cosign's default type, the only one the session verifier accepts), and signs the evidence manifest with that supplier release key in cosign key mode (empty signing config, never keyless), publishing `sterling-evidence-<version>.json`, its `.sigstore.json` and the release public key `sterling-release-cosign.pub` as release assets. The image signature and SBOM attestation are made after the image exists, so the view shows them as "checked by your site's admission policy when this session started" with the `cosign verify` command, not re-checked in the session (G477). The GitHub attestations of the installer and the compliance package are keyless and need the public Sigstore service, so the view lists them as "not checked here; verify on a connected computer with gh attestation verify" (G476).

### Trust and integrity
- **D-17: Trust anchors from configuration only.** Sessions trust only public keys that come from configuration, never one found beside evidence. At a site: your organization's site key (`organizationPublicKey`, the site's one root, 48.1-17 "sites trust only the site key"), rendered at install into the ConfigMap `sterling-evidence-trust`. The site key signs (a) each release's evidence manifest, re-signed by the bundle build after it verifies the supplier signature (48.1-17's re-signing), and (b) the site trust document `sterling-evidence-trust/1`: the site's evidence signer keys (the collector's Transit key and the operators' keys), each with its purposes and validity dates, and the site's freshness tightening (D-13). On a single computer without a site, the person may mount the supplier release public key and the release's evidence signature (README); without them the release evidence is Not verified (owner question 6). The anchor is protected twice (revised 2026-11-25 after the plan check; 48.2-17): (1) a Kyverno policy lets only the install identity, service account `sterling-evidence-install` (which the operator's kubeconfig impersonates), create, change or delete `sterling-evidence-trust` and `sterling-release-evidence` (the one exception: the namespace controller, `system:serviceaccount:kube-system:namespace-controller`, may DELETE them and nothing else, so uninstalling or rebuilding a site never leaves the namespace stuck Terminating); no Role names them for anyone else; the operator publish identity `sterling-evidence-publish` and the collector can change only their own ConfigMaps; the chart itself never creates the two; (2) every session gets the site file's `organizationPublicKey`, the same value admission checks every image against, as `STERLING_ORGANIZATION_PUBLIC_KEY` through `sterling-site-env`, and compares `organization.pub`'s fingerprint with it: a mismatch is Did not verify (`anchor-mismatch`) for release and site evidence alike, and `organization.pub` without the variable is Not verified (`anchor-unconfirmed`).
- **D-18: Three verification outcomes** (glossary: Verified, Not verified). **Verified**: every hash and size matches the manifest and a configured key's signature verifies for the right purpose and time. **Not verified**: no configured key, no signature for this release, or an expired signer entry; the content is shown, every cell shows "Not verified" in place of a passing state, and nothing counts as Met. **Did not verify**: a hash, size, missing, extra or symlinked file, a bad signature, a wrong purpose, an unknown format, an anchor that differs from the site's key, or a future-dated result, observation, site file or fact group (a future `builtAt` is the clock case of D-14 instead); nothing from that source is shown, only one plain message with the reason. A cell's verification is the worst of its sources.
- **D-19: Verifiers in Node, no cosign in the session.** A dependency-free verifier for cosign key-mode Sigstore bundles (ECDSA P-256 with SHA-256, the message digest checked against the file) in the workbench backend, held equal to the pinned cosign 3.1.4 by a parity test in the `deploy` job (it accepts what cosign accepts and refuses a changed byte, another key, a changed bundle and any key type but P-256). The supplier release key in `container-release` and your organization's site key must therefore be ECDSA P-256 cosign keys; 48.2-07's publish job checks the release key's type before signing. Site files use the extension's signed-payload envelope (`compliance/src/signed.ts`, Ed25519, purpose-bound) with new purposes.

### Live site evidence
- **D-20: The live feed.** Format `sterling-site-evidence/1`: site id, `generatedAt`, and fact groups, each with its own `collectedAt` (a group not refreshed in a run keeps its original time and is never re-dated); no pass field, because the session's checks decide (48-02's principle). Purpose `site-evidence-live`. Signed with OpenBao Transit key `site-evidence` (ed25519, not exportable, HSM-backed where the seal is), signing allowed only to the collector's service account through the Kubernetes auth mount (48.1-15), with the role bound to that account, its namespace and the projected token's audience. Key rotation (revised 2026-11-25): the trust document lists each allowed key version with its public key; the collector reads the trust document and signs with the newest listed version, passing `key_version` explicitly and recording `keyVersion` in the signed feed; a session verifies with that version's listed key, and an unlisted version is Not verified; the runbook (48.2-13) orders a rotation so sessions never lose site evidence. The residual risk that a key held in OpenBao signs facts about OpenBao is G475; the weekly operator-signed export stays the independent check (owner question 5).
- **D-21: The site collector.** A CronJob running the signed workbench image with `node /app/bin/collect-site-evidence.mjs` (no new image, no new fit entry), every 15 minutes by default (site setting `evidence.collectIntervalMinutes`, 5 to 60; owner question 4), `concurrencyPolicy: Forbid`, a read-only service account. It reads: Prometheus rules and alerts (48.1's alerting), Kyverno ClusterPolicies and PolicyReports (image admission enforcing, refused images), the node count, OpenBao `sys/seal-status` (no token), and the release record (47-32) against the AppDefinition image. It reads `sterling-evidence-trust` (get only) to choose its key version, and writes only ConfigMap `sterling-site-evidence-live` (a Role scoped by `resourceNames`). Checks on facts it shares with the deployment export reuse the deployment collector's thresholds.
- **D-22: Delivery to sessions (the 47-32 pattern).** One projected volume at `/etc/sterling/evidence`, read-only, without `subPath`, each source `optional: true` so a missing one never blocks a start, from four ConfigMaps: `sterling-evidence-trust` (install), `sterling-release-evidence` (install: the site-key signatures of the evidence manifests of the releases the site holds, current and previous), `sterling-site-evidence-live` (the collector), `sterling-site-evidence-operator` (operator files, D-23). The chart creates only the live and operator ConfigMaps, with no data, so an upgrade never erases what was written; the install identity creates the other two (D-17). The backend reads it at start and every 30 seconds; the kubelet refreshes a mounted ConfigMap in about a minute. A fact reaches the view within the collect interval plus about two minutes. The hub was not chosen: it would add a network path and a second trust path for data the site already holds.
- **D-23: Operator site evidence.** Signed with an operator key the trust document names, and published by `node deploy/bundle/site-evidence.mjs publish <signed file>`, as the publish identity `sterling-evidence-publish`, into `sterling-site-evidence-operator`: the signed site evidence export (48-02, purpose `site-evidence-export`, schema 1 or 2 after 48-11), the offline rescan summary (from 47-29's `rescan.json`, purpose `site-rescan`; its evidence time is the database build date from the signed database file), and the exchange agreements (per exchange id of `compliance/hosted/exchanges.json`: the agreement reference and its review date, purpose `site-agreements`). Signing has the same external-signer form as `site-export` (emit the signing input, attach the signature).
- **D-24: Layering.** Release observations first. A verified site observation with the same collector and subject replaces the release's for that rule (a site rescan replaces the release scan; your site's deployment facts replace the reference site's), and each result keeps its source. A rule that needs site evidence, at a site with none, shows the release's result with source "Supplier reference site" or no result, never as your site.
- **D-25: Push without reload.** The backend evidence service offers `getEvidence()` and a long poll `waitForEvidence(afterRevision)` (it resolves on a change, or after 55 seconds with the same revision) through 46-01's `bindBackendService`, so the view updates within about a second of the backend seeing a change and the helper is unchanged. The backend re-judges at start, every 60 seconds and on every source change. When the connection drops, the view says live updates are paused and shows freshness as unknown.
- **D-26: The published projection stays (owner question 3, default).** The README's read-only mount of the public dashboard projection keeps working and appears as its own source, "Published projection": Not verified (hash-checked on the host by `compliance:refresh`, not signed), never counted as passing. The release evidence stays the default.
