<objective>
Fix Phase 30 findings (c) and (d) and IN-03 in the fold driver (D-01, D-02): a re-delivered entry costs a hash, not a signature check and a decryption, and the memory the fold keeps for duplicates is bounded; a reducer-stage hold is retried when the same context can now answer it.

Purpose: Phase 31's store (31-13) and every later transport feed the fold repeatedly with the same entries and fill in blobs and keys behind one long-lived context object (Pitfall 1: a fresh context per call means a full refold). Both findings must be fixed before any store feeds the fold (ROADMAP prerequisites).
Output: `holdWaits.ts` (new, pure), changes to `fold.ts`, regression tests in `replicaReevaluation.test.ts`.

Branch: `feat/phase-31-02-fold-holds`, merged into `feat/phase-31-staff-roster` after wave 2.

File ownership in wave 2: `fold.ts`, `holdWaits.ts` and `replicaReevaluation.test.ts` only. `textFold.ts` and `versions.ts` are not touched here (they belong to 31-04 and 31-07); `holdWaits.ts` reads the hold reasons they already emit.
</objective>
