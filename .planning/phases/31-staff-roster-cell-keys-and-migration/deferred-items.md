# Phase 31 deferred items

## Found during 31-23 (focused test run)

- **A random grant wrap can be refused as "secret-like" (flaky, pre-existing since 31-15).** `buildGrant` (src/domain/replica/cellKeys.ts) signs its wraps with `signPayload`, which runs `assertNoSecrets` over the payload. A wrap is 92 random bytes in base64url, and base64url contains `-` and `_`, so a wrap can by chance hold text such as `-rt_xxxxxxxx`, `_oc_xxxxxxxx` or a leading `sk-xxxxxxxx` that `SECRET_PATTERNS` (src/domain/team/secrets.ts) treats as a key. Rough odds: about 5 in 100,000 per wrap. Seen once in staffReplicaMembership ("admission grants every epoch ...": `PayloadError: Nothing was signed: the payload has a secret-like value at $.wraps[0].wrap`); the same file passed 26 of 26 when run again. In use, a grant, an admission or a rekey would fail once with "NEAR AI could not finish that" and work when run again. Fix belongs to the owner of cellKeys.ts or signedPayload.ts: for example, let a signer exempt fields that are known random binary (wraps, sealed labels, keys), or make a fresh wrap when signing refuses. Not fixed in 31-23 because it changes the shared signer outside this plan's files.

**Resolved on the integration branch (after 31-23).** `signPayload` now names, per purpose, the exact fields that hold freshly generated random base64url (cell grant `labelSealed` and `wraps[i].wrap`; invite `secret` and `lead.x25519`; join request `x25519`, `x25519Sig` and `mac`). A value at one of those paths that is pure base64url skips the token patterns but is still refused if it holds private key material; every other field, and the same value under any other purpose, gets the full check. Test: teamSignedPayload "generated random fields of the Phase 31 purposes are not mistaken for tokens, and nothing else is let through". This also explains the one-off replicaCellKeys failure seen at the wave-6 merge.
