<objective>
Harden the text reducer (D-01 (a), D-02 WR-02 client part, WR-04, WR-05 text part, WR-08 text part) and bind every Yjs client id to its writer through the roster (D-03 as refined by D-41).

Purpose: owner decision 1 of 2026-11-19 (30-UAT test 1): no admitted writer can take another writer's attribution by registering a client id first. With slots from the roster, a race between two writers for one id becomes impossible rather than resolved. The other fixes keep one hostile entry from switching compaction off for a product and bound what a writer can make the fold build.
Output: changes to `textFold.ts`; regression tests in `replicaDoc.test.ts` and `replicaClientIds.test.ts`. The seat fixtures in the other agent-writing test worlds were added, still inert, by 31-01.

Branch: `feat/phase-31-04-text-reducer`, merged into `feat/phase-31-staff-roster` after wave 2.

File ownership in wave 2: `textFold.ts`, `replicaDoc.test.ts` and `replicaClientIds.test.ts`; the four seat-fixture files from 31-01 are listed only so a missed seat can be added (no other wave-2 plan touches them). `doc.ts` is owned by 31-03 in this wave, so this plan uses only the `doc.ts` functions that exist at HEAD; the blob size gate in `applyCompaction` (which needs 31-03's `sealedBlobWithin`) is plan 31-07.

Recorded planning choices (Claude's discretion, D-02 asks for caps without numbers) [ASSUMED values]: `COMPACTION_WINDOW = 50` accepted updates between one writer's compactions of one product; `MAX_REGISTRATIONS_PER_WRITER_PRODUCT = 4096` (a fresh client id per editor session needs room); `MAX_PRODUCTS_PER_STREAM = 1024`. None is reached by any honest scenario in the test suite.

<assumption_delta_decision>
- Signal: pluralization. Client ids were chosen by the registrant (one writer's claim, first claim wins); now many writers' ids are fixed by the roster.
- Primary noun: the writer's roster slot (a number 1 to 4095 assigned by the signed roster entry that admits or adds the device); a Yjs client id is derived from it as slot * 2^20 + counter (D-41).
- Decision: promote. The roster slot is the identity; the registrant-chosen id is demoted to a checked detail inside the writer's own range (doc.client still records which actor uses which id, and an id outside the range is refused foreign-client-id).
- Invariant test: a property test in `replicaClientIds.test.ts` asserts that in every fold whose roster names owners, every accepted doc.update's client ids derive from its writer's slot (Task 2). It goes red if a later phase lets a registrant choose an id outside its slot again.
</assumption_delta_decision>
</objective>
