<objective>
The shared contracts both work packages build on (D-49): the kind schema additions for the roster and migration, the new kind `invite.void`, and four signed-payload purposes. They land in one plan before any roster fold or store exists, so WP-R1 (31-12, 31-14 to 31-17) and WP-R2 (31-13, 31-19) never edit the same schema file.

Output: changes to `kinds.ts`, `kindSchemas/roster.ts`, `kindSchemas/project.ts`, `projectFold.ts`, `signedPayload.ts` and the pinned-count tests.

Branch: `feat/phase-31-09-shared-contracts`, merged into `feat/phase-31-staff-roster` after wave 4. This is the first phase-scope plan; waves 1 to 3 were the Phase 30 hardening.

File ownership in wave 4: these nine files only (31-10 and 31-11 are host files under `src/staff/replica/`).

Recorded planning choices: new fields are optional on the wire so every Phase 30 sample and vector stays valid; the roster fold (31-12, 31-14) requires them where D-41, D-44 and D-49 need them. The device slot is a field of the device descriptor, so `member.admit`, `device.add`, `device.rotate`, `hub.admit` and the genesis `lead.device` all carry it the same way (reading of D-41 "assigned in the roster entry that admits or adds it" and D-49 "the device slot"). `device.add` also gets an optional `invite` (not listed in D-49): it lets the fold apply D-17's single-use rule to the short invites of D-18 (Add My Other Machine); without it a second-machine invite could only be closed by a void.
</objective>
