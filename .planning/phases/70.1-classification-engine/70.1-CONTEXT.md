<domain>
## Phase Boundary

One pure engine decides what any classification proposal may do to a label, under your organization's signed policy, and records what it did. It needs no model and no network. Phase 74.3 feeds it a model's answer; Phase 93 later feeds it ingested items.

In this phase:
- `src/domain/classify/`: the proposal record v1 with its `basis`, the raise, keep and lower rules (asymmetric), threshold arithmetic and bands, the possible-spill outcome, marking and code-word scanning, the guide and compilation rule evaluator over typed facts, the session's running fact set, the hidden-instruction detector, and `assess()` which joins them.
- The signed policy section `classification@1` (`src/domain/gate/classificationSection.ts`), registered like Phase 41's sections and only tightened by newer or lower layers.
- Five label events named and recordable: `label.auto-raised`, `label.exception-queued`, `label.exception-resolved`, `label.could-be-lower`, `label.affirmed`.
- Property tests and the red-team fixtures that need no model.

Not in this phase:
- Running a model, endpoints, passports, evaluation, the panel, affirmation, lowering by credential, the spill report, agent outputs and cells. They are Phase 74.3.
- Retention classes, topics, document types, privacy facts, the `no-train` handling flag (label v2), rule simulation before signing (TAG-07) and the bulk exception queue. They are Phase 93's (report 02).
- Any change to the label v1 format, the label map v1 or the session mark. A raise uses the existing paths (Phase 70: Set Label, the session mark, the raise-only label map).
</domain>

## Implementation Decisions

### Scope and order

- **D-01 (placement, owner decision D14 default):** This phase is pure code with no model and no network. The research made it wait for Phase 70's PR 4b and 4c. Both are merged: PR #85 (4b, labels written to disk) and PR #87 (4c, the session mark), and all 32 Phase 70 plans have summaries (ROADMAP progress row: "Executed: all parts merged (last #95)"). Phase 41's v2 policy document is on `main`. So 70.1 can start now, beside Phase 71 (core) and Phase 33's waves. Each plan works on `feat/phase-70.1-NN-<slug>` from `feat/phase-70.1`, merged back after its wave; one integration PR at the end (70.1-05).
- **D-02 (folder and imports):** New pure folder `src/domain/classify/`. It imports only `src/domain/gate/` (`labels.ts`, `dominance.ts`, `shape.ts`, `record.ts`, `classificationSection.ts`) and never the other way, so there is no gate-to-classify import. The policy section parser lives with the other sections in `src/domain/gate/classificationSection.ts` (the pattern 71-06 uses for `credentialsSection.ts`), because `policyDocument.ts` must parse it. No I/O, no clock, no vscode, no package. Files stay under 800 lines; the architecture and copy-lint baselines only shrink.
- **D-03 (data attributes only, owner decision D1):** The proposal record and the model answer shape (74.3) are closed schemas of label fields, bases, typed facts about the content and confidence. Neither has any key for a person attribute (clearance, nationality, organization, serves, compartment holdings, export eligibility, agreements, role authority). A test lists the exact key set of the record and refuses a record that carries any other key. A fact that a document names a person (`named-person`) is a fact about the content, never an attribute of that person.

### The rules

- **D-04 (asymmetric application, owner decision D2 default):** `decide()` computes `applied = join(start, raise parts)` with `dominance.ts`'s `joinLabels` per scale (`raiseMark` across scales). Because the join never lowers, no field can go down by construction; a property test checks `markAtLeast(applied, start)` on every result. Each field gets a direction: level up, same or down; compartments added or removed; releasability narrowed or widened (a partly overlapping set is both: the join keeps the narrowing and the widening part is dropped); handling added or removed. Every lowering part (level down, compartment removed, handling removed, releasability widened, declassification) becomes a `could-be-lower` suggestion naming who may decide it (74.3 enforces the authority). Nothing is ever lowered automatically, whatever the confidence.
- **D-05 (never classify from the bottom, research 3.3):** The caller passes `start` as a mark: the join of the session's high-water mark, the labels of the sources the content was built from, the project, folder or cell label, and on ingest the source label and your organization's ingest default. The engine refuses an empty start (`no-start`) rather than assuming the lowest level, so injected text such as "this document is unclassified" can only ever fail to raise.
- **D-06 (bases, research 3.4):** Six basis kinds, exactly the list of 33.1 D-40 on `docs/phase-33.1-amendments` (PR #189): `source`, `marking`, `guide`, `detector`, `compilation`, `judgement`, exported once as `BASIS_KINDS`. Every basis has a `ref` of 1 to 128 characters with no line break, never the matched text: the source item id, the marking pattern id, the guide rule id, the detector id, the compilation rule id, or for `judgement` the SHA-256 of the labelled rationale. When a cell entry carries `basis` (74.3), its `ref` is the proposal record hash.
- **D-07 (thresholds, owner decision D5 default):** For each `scale/level` the signed section holds a cost ratio `r` (under-classifying cost over over-classifying cost) and a recall target. The raise threshold is `τ = 1 / (1 + r)`. The research's examples (r = 4, 9, 19, 49; τ = 0.20, 0.10, 0.05, 0.02; recall 0.90, 0.95, 0.98, 0.99 for Protected A; Protected B and Confidential; Protected C and Secret; Top Secret) appear only in tests and docs as examples; nothing ships them as values. A level with no entry has no automatic model raise: a judgement there is at most a suggestion.
- **D-08 (bands):** The input is a calibrated probability per level that the true level is at least that level (74.3 calibrates; the engine records the calibration id). The engine first makes the cumulative probabilities non-increasing up the scale by taking, for each level, the largest probability at or above it (this can only raise). It then raises to the highest level whose probability is at least its τ, suggests the highest level whose probability is at least τ/4, and otherwise does nothing. The model's own stated confidence is never an input.
- **D-09 (floors and judgements):** `source`, `marking`, `guide`, `detector` and `compilation` bases are floors: they raise with certainty and use no threshold. A `judgement` raises only the level, through the bands. Compartments, releasability narrowing and handling flags proposed by a judgement alone are suggestions, never applied, because research 5.1 takes them from sources, detectors and guide rules, and research 3.6 names a model-only narrowing of releasability as a way to cut off a coalition partner (Claude's discretion, from the research).
- **D-10 (shadow mode, owner decision D10 default):** `decide()` takes a mode per `scale/level`: `shadow` or `enforce`. In shadow mode a judgement never applies a raise; it becomes a suggestion with the reason "shadow". Floors apply in both modes, because they are your organization's signed rules, not the model. Phase 74.3 decides when a level leaves shadow (the 4-week period and the recall targets).
- **D-11 (review, owner decision D4 default):** An automatic raise applies at once and the outcome tells the caller to notify the originator or steward. A raise by more than the section's `review.jumpLevels` (default 1) levels, or to the scale's top level when `review.topLevel` is true (default true), also queues `label.exception-queued` with kind `large-raise`.
- **D-12 (recall drops tighten, research 3.2):** `effectiveThreshold(signed, history)` halves a level's τ for each audit window whose measured recall is below its target, down to τ/8, and returns to the signed τ after a window that meets the target. It is never above the signed value, so it only ever causes more raises (Claude's discretion on the step and the floor). 74.3 supplies the history from its blind audit.
- **D-13 (system-high and the possible spill, owner decisions D6 and D12 defaults):** The section's `systemHigh` is a mark: the highest labels this system (this deployment layer) may hold. A proposed label or floor that no label of `systemHigh` on the same scale is at least, and that no approved scale mapping covers, gives the outcome `possible-spill`: the applied label is the join of `start` with the system-high label of that scale (or every system-high label when the scale is absent) plus the handling flags `local-only` and `no-agent-tools`; the outcome carries `freeze: true` and queues `label.exception-queued` with kind `possible-spill`. The predicted label is kept in the record and never applied. A section with no `systemHigh` gives no spill outcome.
- **D-14 (stale results):** `decide()` requires the current `{ item, contentHash, revision }`. A model result for another content hash gives the outcome `stale`, applies nothing and writes no event.
- **D-15 (events, D-49):** The five ids are appended to `LABEL_EVENT_IDS` in `labels.ts`, so `record.ts` and the record id test accept them with no other change. They are named now so a record a later version writes is always nameable. `decide()` returns event descriptors; the caller records them with `buildDecisionRecord`, carrying only the log copy of the proposal (D-21). Outcomes `affirmed`, `reverted-by-request` and `lowered` are later events about a record (74.3), never edits of it.

### The signed section

- **D-16 (`classification@1`, owner decision D11 default):** A new v2 policy section `classification` with feature `classification@1`, appended to `FEATURE_IDS` and `POLICY_SECTIONS` (append-only). Keys: `v`; `systemHigh` (labels); `thresholds` (per `scale/level`: `costRatio`, `recallTarget`, `secondFamily`, the last read by 74.3's two-family rule); `shadow` (`defaultMode`, and `levels`: the `scale/level` entries your organization has moved to `enforce`); `roles` (`{ passport, role, levels, evaluation, since }`: which passport holds which classifier role (`primary`, `second-family`, `hidden-instruction`) at which levels, the hash of the signed evaluation report that justified it, and the date the role began; read by 74.3); `review` (`jumpLevels`, `topLevel`, `lowerRequestAgeDays`, default 7, read by 74.3); `markings` (banner and portion-marking patterns per label, English and French); `codeWords` (tokens with the label they imply, and the label of the list itself); `factTypes` (additions to the shipped base vocabulary); `guideRules` and `compilationRules`. A rule is `{ id, guideRef, label, description, when: { allOf, sameSubject? }, then }`: `label` is the label of the rule's own text, `description` is at most 280 characters of plain words (74.3 passes descriptions to a model only where the endpoint may hold their label), `allOf` names fact types, and `then` holds only label fields (level, compartments, releasability, handling). Guide text itself is not in the bundle; a guide whose rules are classified is distributed only in that security domain's own policy layer. Unknown keys, levels not on their scale and malformed tokens are refused with one plain reason, as every Phase 41 section does.
- **D-17 (layers only tighten):** In `layers.ts`'s rule table, only the organization layer sets `systemHigh`, `shadow.defaultMode`, `shadow.levels` and `roles`. A personal or project layer may only lower thresholds (more raises), add markings, code words, fact types and rules, and lower `review.jumpLevels`; it may never remove a rule, raise a threshold, change `systemHigh` or move a level from `shadow` to `enforce`. A newer organization layer is free, as for every section.
- **D-18 (facts and compilation, research 3.5):** A shipped base vocabulary of fact types (`unit`, `location`, `date`, `future-date`, `capability`, `operation`, `named-person`, `codeword`, `marking`, `controlled-item`, `hidden-instruction`), extended by the section's `factTypes`. A fact is `{ type, subject? }` where `subject` is an opaque key the caller derives per session, never the value. Compilation rules run over the item's facts and over the session's running fact set (types, subject keys and item ids only; no values), so three harmless answers in a row that together match a rule raise the session. The set holds at most 4,096 facts; reaching the cap queues `label.exception-queued` with kind `aggregate-cap` rather than dropping facts silently (Claude's discretion).
- **D-19 (hidden instructions, research 3.6):** The caller passes the content as visible text plus hidden parts (comments, zero-width text, alt text, metadata). A deterministic detector finds hidden text addressed to a classifier or an AI (English and French phrases, and instruction verbs aimed at a label) and adds the fact `hidden-instruction`, which adds `no-agent-tools` and queues `label.exception-queued` with kind `hidden-instruction`. It never lowers anything.
- **D-20 (labels v1 only):** No new label field. Caveats such as `CAN EYES ONLY` are expressed as releasability tokens and compartments through guide rules. `no-train` and retention classes wait for label v2 and Phase 93.

### The record

- **D-21 (proposal record v1, research 3.9):** Fields: `v`, `item`, `contentHash`, `revision`, `start`, `proposal` (the proposed label per scale and each field's direction), `bases`, `facts` (types and subject keys), `confidence` (per-level calibrated probabilities, the calibration id, sample agreement, second-family agreement), `model` (passport id and hash, artifact hash, endpoint class, use tier, or `none` for rules only), `prompt` (template hash, policy bundle hash, decoding settings), `rationale` (`{ label, text }`), `outcome` (`auto-raised`, `suggested`, `kept`, `none`, `stale`, `possible-spill`), `applied`, `suggestions`, `exceptions`, `actor` (the agent `did:key` or `rules`). `recordHash` is SHA-256 of the canonical JSON (`src/domain/team/canonical.ts` rules, computed by the caller's hash function so the domain stays pure). `recordForLog(record)` keeps ids, hashes, kinds, counts, labels and the outcome, and replaces the rationale and fact subjects with their hashes, the way `redactRecord` does for decision records. The rationale is derived content, labelled at the item's label, and stays with the item (74.3).
- **D-22 (permanent shapes checkpoint):** The record v1 keys, the five event ids, the six basis kinds and the `classification@1` keys become permanent once a release ships them (a change is a v2 beside v1, D-22 of Phase 70). 70.1-01 ends with a decision checkpoint that shows them with the fields 74.3's panel needs drafted beside them (research phase warning for 70.1). Reversibility: costly, not one-way (a v2 can sit beside v1).

## For the owner to confirm

Accept with one line ("accept Phase 70.1 defaults"), together with owner decisions D2 to D6 and D8 to D14 above. Each line gives the default, then the alternative.

1. **D-09: a model judgement alone may raise only the level;** compartments, releasability and handling from a judgement are suggestions. (Alternative: let a judgement add compartments and handling above the threshold too, which raises more and risks cutting off partners.)

3. **D-13: a possible spill raises the item to the system-high with `local-only` and `no-agent-tools`,** and keeps the predicted label in the record only. (Alternative: apply the predicted label as well, which locks everyone on that system out of the item.)
4. **D-18: when a session's fact set reaches 4,096 facts, it goes to review** instead of dropping the oldest. (Alternative: drop the oldest facts, which can miss a compilation.)
