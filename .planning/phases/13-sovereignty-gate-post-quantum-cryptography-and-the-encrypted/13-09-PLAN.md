## Decisions and assumptions

- **Vault (one-way for vault file format v1):** `.near-kb/keys/items.vault` = canonical `{ v: 1, nonce, ct }` where ct = AES-256-GCM(vaultKey, canonicalBytes({ keys: { [itemId]: base64 key } }), AAD = utf8("near-ai-kb/item-vault/v1|" + kbId)); `vaultKey = itemVaultKey(localSecretsRoot, kbId)` = HKDF-SHA-256(localSecretsRoot, salt = utf8(kbId), info = "near-ai-kb/item-vault/v1", 32), so a phrase restore can reopen it. Rewrites are atomic (tmp + rename; the vault is mutable by design, unlike segments). `.near-kb/.gitignore` (plan 13-06) keeps `keys/` out of git.
- **Erase order:** append the tombstone first, then destroy the key and rewrite the vault; on open, `sweep(tombstonedIds)` destroys any key still present (crash between the two steps, or a restored backup).
- **Honest residuals (A6 + RESEARCH Pattern 6), carried into the plan 13-12 UI copy:** copies already read are not recalled; a backup made before erasure may still hold the key; SSD/journaling filesystems can retain old blocks; the vault key is derivable from the phrase, so the guarantee is "key removed from this base's key store and tombstoned". Timestamps of erased items stay in the skeleton (OQ2).
- **Phase 14 input (recorded):** any index, snapshot, or embedding of an erasable item must be encrypted under that item's key or rebuilt on erasure.
