## Phase Boundary

Phase 33 is drop A's last phase (WP-LIVE and Integration A of DESIGN 18). It turns the pure replica core (Phase 30), the roster, keys, store and migration (Phase 31) and the hub with its client transport (Phase 32) into something people use from the editor, and releases drop A in 0.4.x:

- **The live replicator.** One per shared project per device: the hub transport kept open over server-sent events, pushing local appends and folding remote ones, running the 15.3 sync connection machine, with the hub's address supplied, `blobsCitedBy` passed to `HubTransport.push`, `fetchJoinRequests` called on a `join-request` event, and the hub witness findings turned into the `attention` state. (MUS-09)
- **Product editors bound to the shared text** (DESIGN 5.4): local edits become Yjs operations under the device's roster-bound client id, remote changes arrive as edits without echo, undo removes only your own edits, the header region stays read-only, an outside disk change is offered as Take This Change as My Edit or Restore, other people's cursors show with names, and Show Who Wrote This attributes every part to a person or to an agent on a named person's machine. (MUS-09)
- **Presence, sync status and the offline banner** in the Staff Room (DESIGN 10.5, 19): who is online and what they work on, one plain sentence with one action per sync state, the offline banner and "not yet confirmed by your organization's server" on decisions since the last checkpoint. (MUS-09)
- **Contested decisions on screen** (DESIGN 6.4, 15.5): the decision queue card, settling by a fresh decision, and the "changed while deciding" refusal in the decision dialog. (MUS-09)
- **Share with people** as the one way in: the Phase 31 preview commands become a setup step and Staff Room actions (turn on, invite, open an invitation file, admit, remove, grant your organization's server, re-admit it after a fork finding, make a single-machine copy), with their old ids as hidden aliases. (MUS-09)
- **POST-01, the generic `roster.require` feature check**: a client, or the hub, that lacks a feature a project requires refuses to fold it with the update sentence instead of ignoring entries it does not know. It must be in the field before Phase 33.1 ships positions. (POST-01)
- **Phase 32's carried follow-ups**: WR-07 on the hub side (blob-missing per entry, not per batch), IN-02 (Start Again rebuild crash safety), IN-06 (a bound on join requests per invitation), the `MigrationResult.withheld` notice, and the longer-term fix for the two restore limits in SECURITY.md and `relay/README.md`.
- **Scenarios over a real hub, the label leak test over the hub, README and SECURITY sections, and the drop A release** (success criteria 3 and 4).

Not in this phase: git per-writer refs, sealed bundle files and LAN peer links (Phase 34); shared run summaries, claims and leases, "agent writing here" from claims, observation sharing and hub watches, and the hub loading an organization policy (coherence C1, C2) (Phase 35); positions, postings, handover, delegation, genesis mode and `project.mode` (Phase 33.1); roster clearance as an input of `decideRoute` (`route.clearance`, Phase 41 D-53, stays 33.1); Get Started itself and the webview stepper (Phase 32.1); register field-level co-editing beyond what the Phase 30 register reducer already folds (shown here only as the "Pick one" card if the reducer exposes it); credentials and DIDs (Phase 71); hub federation (L5); Team Mode import (L2).

## Implementation Decisions

### Order, base and branches
- **D-01:** Phase 33 builds on `origin/main` with Phases 30, 31, 32 and 41 merged. The first task of every plan re-reads the names it relies on from main (the `HubTransport` push signature, `hubSync.ts` exports, `ReplicaProject`, `MigrationResult`, `TrustFacts`, `term()`, the copy lint and architecture baselines) and stops if they differ from the plan.
- **D-02 (branch name corrected 2026-11-23):** One integration branch `feat/phase-33-live-multi-user`, plan branches `feat/phase-33-NN-<slug>` from its HEAD, merged back after each wave, one integration PR for the phase (the Phase 31, 32 and 41 pattern). Plans in one wave never change the same file. The drop A release is a separate `release/0.4.N` PR after the phase PR merges (D-38).
- **D-03:** Phases 32.1, 32.2 and 44 are planned and may build in parallel worktrees. Phase 33 does not edit Get Started's files when they exist, the guide question registry, `src/domain/gate/**` beyond reading it, or compliance files. It registers its setup step through the existing `registerSetupStep` registry (D-19), which Phase 32.1 keeps as the guide's step registry (EXPERIENCE 1).

### POST-01: the generic feature check (one-way door)
- **D-04 (wire shape):** A new roster-family kind `roster.require` with data `{ features: string[] }`, written only by a lead device (lead or deputy), linear in the roster chain like every roster entry. Feature ids use the policy's `name@N` pattern (Phase 41 D-50). The project's required set is the union of every folded `roster.require`; a feature once required is never dropped (a later entry can only add). Its schema is settled in the first plan because roster kinds are permanent in shared logs.
- **D-05 (known features):** `KNOWN_REPLICA_FEATURES` in `src/domain/replica/` lists the features this client folds. Drop A ships it with the features it actually has (proposed: `replica@2`, `cells@1`, `hub@1`, `require@1`), so a project can already require them; `positions@1` is added by Phase 33.1. One registry; nothing else decides "do I know this feature".
- **D-06 (fail closed, whole project):** When the folded required set holds a feature this client lacks, the fold stops for that project: no state is projected, nothing is appended, the editor binding and replicator stay off, and the Staff Room shows "This project needs a newer version of the extension. Update to keep working on it." (portfolio DESIGN 3.9, exact words). The store keeps every entry, so updating resumes with no loss. The check runs on the roster fold, before any other family, so no entry from a later feature is ever half-applied.
- **D-07 (the hub obeys it too):** The hub folds `roster.require` in its roster cache. A hub that lacks a required feature refuses appends for that project with a plain reason (`needs-update`) and keeps serving reads, so an older hub can never accept a relieved holder's writes. A client also announces its `KNOWN_REPLICA_FEATURES` at session start; the hub refuses a session for a project whose required set the client does not cover, with the update sentence, so a client too old to know `roster.require` at all (the 0.4.35 preview) cannot write through the hub once a project requires anything.
- **D-08:** Making a project multi-user writes `roster.require { features: ["require@1"] }` right after genesis, so every drop A project starts with the check armed. Existing preview projects get it on their next lead open after updating (one entry, lead device only).

### The live replicator (sync connection machine, DESIGN 15.3)
- **D-09 (network-change trigger superseded 2026-11-23):** One `LiveReplicator` per shared project per device in `src/staff/replica/`, built on `HubTransport` and `hubSync.ts` (never a second transport). States exactly as DESIGN 15.3: `single-machine`, `connecting`, `authenticating`, `catching-up`, `live`, `offline`, `refused`, `attention`, as a pure transition table in `src/domain/replica/` with every transition tested, plus `needs-update` from D-06 as a ninth state that only an update leaves. No state waits silently: `connecting` gives up to `offline` after 10 s, `offline` retries with back-off to 5 minutes and on Sync Now or a network change.
- **D-10 (hub address):** The roster stores the hub's pin and id, not its address. The address comes from the enrolment hub file or the invitation (Phase 32 invitation hub field), is kept per project per device in the project's local store settings (not in `settings.json`), and can be changed by the person under Share with people ("Change your organization's server address"), with the pin re-checked on every connection. A changed address never changes the pin.
- **D-11:** Pushes pass `blobsCitedBy` to `HubTransport.push` (Phase 32 follow-up). Appends are local first: the store writes, then the replicator pushes; a failed push leaves the entry queued, never lost.
- **D-12:** A `join-request` server-sent event makes the lead's and deputy's replicator call `fetchJoinRequests` and raise the Staff Room's "{name} wants to join. Compare this code with them: ..." card with Admit and Decline (Phase 31 flow, unchanged).
- **D-13:** Hub witness findings (withhold, delay, replay, reorder, roll back, fork the view, inject, corrupt blob, other project's stream) map to `attention` with the plain sentence the witness already names; "delayed" findings stay `live` with a detail line. The way out of a fork or rollback finding is the lead's **Re-admit your organization's server** action (SECURITY.md promises it "with the editor's hub commands"), which signs a fresh `hub.admit` citing the new pin or the restored checkpoint after the lead compares the twelve fingerprint words (Phase 41 D-12 style).
- **D-14:** Refusal (`refused`) shows the reason and the person to ask (staff lead by `term()` word); `connecting` after the lead acts. Quarantine of this device (equivocation proof) shows "One of your computers signed two different histories. Your new work is held until the staff lead looks at it."

### Editor binding (DESIGN 5.4)
- **D-15 (refined 2026-11-23 by D-52, D-53):** The binding follows the y-codemirror and y-monaco pattern: local `onDidChangeTextDocument` changes become `Y.Text` operations with a local origin object; remote Yjs changes become a `WorkspaceEdit` applied with an echo guard keyed on that origin; local edits batch into one `doc.update` per product at most every 500 ms (DESIGN 5.2). On a detected mismatch between the editor text and `Y.Text` (fuzz-found or real), the binding resyncs the editor from `Y.Text` and logs one line. Clean-room: we read the y-codemirror and y-monaco sources (MIT) for the pattern and cite them; no code copied.
- **D-16 (superseded 2026-11-23 by D-54):** Undo and redo in a bound product run through a Yjs `UndoManager` scoped to local origins, through `undo` and `redo` keybindings with a `when` context `nearAi.staffBoundEditor`, so VS Code's own undo never replays a remote edit. Outside bound products, undo is VS Code's.
- **D-17:** The header region (projected from the fold) is read-only: an edit to it is reverted with one notice "The header is kept by the project. Change it from the Staff Room." Saving writes the projection. A disk change outside the binding is offered as **Take This Change as My Edit** (signed by the person) or **Restore**.
- **D-18 (cursors and attribution):** Remote cursors and selections are Yjs relative positions in presence messages sealed under the product's cell key, at most 10 per second, never stored, shown as editor decorations with the person's name and position word from `term()`. **Show Who Wrote This** toggles gutter colours per author with a hover naming the person, or "{agent job} agent, run {n}, on {person}'s computer". Colour is never the only carrier (a name on hover and in the accessible text).

### Share with people, presence, status, contested

The Phase 31 preview commands (`nearAi.staff.makeMultiUser`, `inviteToProject`, `joinProject`, `admitToProject` and the rest) keep their ids as hidden aliases that open the right step or Staff Room action. Opening a `.near-staff-invite` file opens the join step already filled in. When Get Started (32.1) lands, it lists the same step; nothing in Phase 33 changes.
- **D-20 (preview switch; superseded 2026-11-23 by D-64):** `nearAi.staff.multiUserPreview` is retired at the drop A release: shared projects are on for everyone, the setting is kept one minor release as deprecated and ignored, and its description says so. Projects that never turn on sharing behave exactly as before (MUS-06 parity test stays).
- **D-21 (presence):** Heartbeat every 5 s, time to live 30 s, as DESIGN 10.5; fanned out only to the cell's access list and never written to disk. The Staff Room header lists people with position and a dot (green "Live", grey "last seen 14:02") and a hover "Working on the intelligence estimate. Running 2 agents." The person setting "Show others what I am working on" (on by default) lives in the Share with people section, not as a new top-level setting page.
- **D-22 (status; superseded 2026-11-23 by D-57):** Sync state joins the one NEAR AI status item that exists today (`gateStatusBar.ts`), as one short word after the label and trust ("Protected B · Verified · Synced"), with detail in its popover or tooltip; no new status bar item (EXPERIENCE 5). The Staff Room bar shows the full sentence and one action per state (DESIGN 19 wording, "changes" never "entries", "your organization's server" never "hub").
- **D-23 (offline banner):** Shown in the Staff Room while `offline`: "You are offline. Your changes are kept here and will sync when your organization's server is back. Decisions you make now may become contested if someone else decides the same thing." Decisions folded after the newest checkpoint show "not yet confirmed by your organization's server".
- **D-24 (contested):** The decision queue card uses DESIGN 19's wording with both names and reasons and the two actions; settling writes a fresh decision whose `decisionsSeen` lists every contested decision. The decision dialog acts on the hash and state on screen and refuses with "Someone else decided this version while you were deciding. Look again." if another decision on that version folds while it is open. A focused browser check covers these two paths (authorization contract, DESIGN 17).
- **D-25 (N changes since):** The Staff Room shows "v5 awaiting decision, 37 changes since"; after 20 changes it prompts the product's owner once to propose a new version; never withdraws (owner decision 4).
- **D-26 (trust line):** Product rows and agent cards in the Staff Room use the one trust line from `TrustFacts` (Phase 41 D-38). No new badge state.
- **D-27 (words):** Every new string follows the glossary: "your organization's server", "Who can see this", "member" and lead words from `term()` in the project's mode (Corporate and software until 33.1 sets a mode), "agent team" and "work team" never a bare "team", "private" only when checked, organization Confidential shown as "Sensitive", no em-dashes, "your organization". The copy lint baseline can only shrink; new files pass the architecture test (no `getConfiguration` outside `services/settings.ts`, no `vscode` below the editor layer, size limits).

### Phase 32 follow-ups and hub hardening
- **D-28 (WR-07 hub side):** The hub answers `blob-missing` per entry (that entry refused and retryable, the rest of the batch appended), not per batch. The client keeps its Phase 32 `heldBack` behaviour.
- **D-29 (IN-02):** Before moving a temporary folder in as the store, Start Again recovery checks it against the counts the intent records (`carried`, `grants`, `blobs`); on a mismatch it rebuilds again from the source. A disaster test kills the rebuild part way.
- **D-30 (IN-06):** At most 8 pending join requests per invitation and 64 per project at the hub; beyond that the hub refuses with "This invitation has too many people waiting. Ask the staff lead for a new one." Both numbers live in the hub's limits file with the others.
- **D-31 (`MigrationResult.withheld`):** After Share with people converts a project, products withheld from conversion (labels the lead's declared clearance does not cover) are listed by name with what to do ("Ask someone cleared for {label} to make a single-machine copy and share it again"), never silently dropped.
- **D-32 (restore limits, one-way for the hub API):** A restored hub starts in **restore mode** when its state directory carries the restore marker the operator's restore procedure writes (`relay/README.md` restore drill gains one step). In restore mode the hub accepts only hand-backs (checkpoints and entries members' computers already hold, Phase 32 D-70) and refuses new appends with a retryable `restoring` answer, until every enrolled device that held a lost checkpoint has handed back or the operator ends restore mode. Clients show "Your organization's server is being restored. Your changes are kept here." (an `offline`-like detail line, not `attention`). This removes limit 1 for restores done by the procedure; limit 2 (a lost checkpoint no client received) stays documented as accepted, with the operator step that clears it unchanged.
- **D-33 (other Phase 32 leftovers):** Kept as documented limits and moved to Phase 35's hub work, not built here: WR-02 for cells the hub cannot open, checkpoints whose covered heads exceed 64 KiB, clients not recomputing checkpoint order, and the deleted-store-with-mark case of 32-01.

### Scenarios, leak test, docs and release

The editor binding is covered separately with fuzzed interleavings against a fake document. Each scenario runs inside the memory cap.
- **D-35 (leak test over the hub):** The Phase 32 two-compartment label leak test is repeated through the live replicator and a real hub: two people each cleared for one compartment, every byte each device and the hub receive captured, no plaintext and no stream of the other compartment reaches a device, the hub holds only ciphertext for ungranted cells, presence and cursor messages included.
- **D-36 (docs; Marketplace framing superseded 2026-11-23):** README (the Marketplace listing) gets a "Work on a staff project with other people" section that replaces the single-machine sentence from 0.4.35; SECURITY.md gets a multi-user staff projects section. - **D-38 (drop A release, success criterion 4; superseded 2026-11-23 by D-66):** After the phase PR merges, a `release/0.4.N` PR (N the next free patch after Drop A merges) is prepared with `scripts/prepare-release.mjs` and the release skill: version bump, CHANGELOG section named, README checked, `prepare-release check`, `verify:release`, secret scan. ### The late joiner's text and history (2026-11-25)

- **D-70 (G430; decided by the coordinator on the owner's behalf, 2026-11-25; refines Phase 30 CR-01, Phase 31 D-04 and D-43 here; built by plan 33-32):** option 4 together with option 3 of the G430 research.
  1. **Compaction rule.** In `textFold.ts` `applyCompaction`, on the provisional path (the fold does not hold every covered entry), a struct's client counts as registered when either (i) a `doc.client` registration for it exists, or (ii) all four of these hold:
     - (a) the roster the compaction cites assigns the client id's slot to a device (`clientIdOwner`; slots are never reused);
     - (b) every cover the fold does not hold is at or below its writer's base head, taken from a checkpoint the witness on this computer trusts (the join bases the fold is given through `foldCheckpoints.ts`);
     - (c) for each such cover, the fold holds no entry of that writer at that seq;
     - (d) a cover at the base head's own seq names the base head's hash (added 2026-11-25 after the independent check, W4).

     Outside (i) and (ii), `compact-unregistered-client` stays. CR-01 attribution is unchanged: text that only the compaction holds is unverified, is attributed at most to the compaction's writer (for client ids registered to it), and is otherwise shown as not yet checked (`NOT_VERIFIED_TEXT` in `whoWroteThis.ts`).
  2. **History backfill.** After going live, a computer that started from a base pulls each writer log from seq 0 up to the base head in the background (`hubSync.ts`), checking every entry's signature and its link to the entry before it. The entry at the base head must hash to the base head, or the pull is refused. While the pull runs, the status says the earlier history is still being checked. A server that does not serve it is retried with back-off and reported as such; the status never stays at "checking" without saying so. When every log is complete, the computer recomputes the trusted base checkpoint over the streams whose covered past it holds in full: `recomputeCheckpoint` for the counts, `checkpointHeads` for each head's lamport and roster. A refused pull or a mismatch is a witness finding against the server, a hub fault: `forked-view` with a new proof reason `history-mismatch` in `hubWitness.ts`. The server is then distrusted until the lead's Re-admit (D-42). A joiner does not judge the order hash: the server nests every earlier checkpoint in it (`hub/src/checkpoints.ts`), and a joiner holds only the newest one, so judging it would fault every honest server.

     **What is owed, and when it is done (refined 2026-11-25 after the independent checks, B2, I7 and the re-check).** The rule is fixed by its class, not its instances: nothing about the check is inferred from whether base heads are held, and two independent paths keep it from being skipped.
     - **Path 1, the obligation is recorded at the moment of reliance, and saved first.** When an exchange starts a writer log at a trusted base's head, the base's checkpointHash is added to an owed list in the witness memory (`historyOwed`). The witness is saved before any page of that log is stored. A new trusted base that this computer starts a log from adds a new entry. The list survives restarts and the lead's Re-admit. It holds at most `MAX_HISTORY_OWED` entries; at that bound an exchange reads a new log in full instead of starting it at a base.
     - **Path 2, the held chain is history to fetch whatever the list says.** Every log the store holds with a gap below its head is fetched across that gap, even when nothing is owed, including a log held only from above seq 0.
       - **What counts as held (re-check W1).** The scan walks down from each log's head through prev links. A stored line counts as held only if its hash is the prev of the held line above it. A line at that seq that does not link (a fork) is a gap, and the right line is fetched beside it. The pulled chain must end at the prev of the lowest linked line; for a log started at a base, that is the base head.
       - **Two kinds of gap no fetch can fill.** Neither is fetched again in that start, and neither counts towards "could not be fetched yet". Each is reported with its own finding, `history-refused`, in words that name the writer's history as the cause, never your organization's server.
         - `link-refused`: the linking line is one the decode check refused.
         - `not-accepted`: that writer's own flooding, `MAX_REFUSED_PER_WRITER` refused lines in that stream.
       - **A store-wide cap filled by others is a local cause** (the held list or the waiting list full), with no blame on the writer. It is reported as `waiting` (`store-full` or `store-busy`) and retried.
       - **The skip list is per start (accepted, re-check).** After a restart, a log the store kept none of is fetched once more. That refetch never counts towards "could not be fetched yet".
       - If a gap is found while nothing is owed (a lost save, or a fresh witness after a damaged one), the recheck of the next base the witness trusts becomes owed (an entry `next`, saved first).
       - **`next` resolves only to a trusted checkpoint whose heads include every log filled under it (re-check I5).** Once every gap is filled and chain-checked:
         - with such a checkpoint, it is rechecked;
         - with a trusted checkpoint that does not include them, `next` settles at once with a `base-unverifiable` finding (re-check W2);
         - with no trusted checkpoint at all yet, it waits (`no-base-yet`, with its own sentence) until the next exchange shows one, and then resolves or settles.
         So a damaged witness converges.
       - The gap scan is one pass over the store, made once per start of the live connection whether or not `startFromBase` is on (re-check I4), and again while work remains. A computer that holds every log from seq 0 owes nothing and pays for no recheck.
     - **The vouching invariant (final check, replaces the earlier "settles instead of staying owed" wording).**
       - A base vouches for provisional text, under rule (ii) and the D-71 rule, only in streams it has been judged on, or while it is still owed and awaiting judgement.
       - The witness memory keeps which streams each base was judged on (`judged`). `vouchingOf` derives the vouching map from that and the owed list. The fold's `baseOf` answers only from bases in that map, and only for their streams (`FoldOptions.vouching`). The chain stage's join bases are unchanged.
       - When a base leaves the owed list without being judged on a stream (`history-refused`, `base-unverifiable`), it stops vouching in that stream. The provisional compaction there falls back to refused, and a D-71 update to held.
       - A base is never "done" without a judged stream.
       - **It cannot be relied on again to vouch there (final check, second pass).** The witness memory keeps a bounded record, `unvouched: [{ base, coverage, streams | all }]`.
         - It holds every base that settled without judgement on some streams, with those streams.
         - It also holds every judged base dropped by `MAX_JUDGED`, with all of its streams.
         - `vouchingOf` subtracts those streams even while the base is owed again.
         - `witnessRelied` on such a base, for a stream in its record, reads that log in full instead of starting it at the base.
         - A stream leaves the record only when a later recheck of that base judges it.
         - At `MAX_UNVOUCHED`, the oldest record is dropped, and `unvouchedFloor` rises to its coverage. Every base at or below the floor vouches nowhere and is never relied on, so dropping a record only ever removes vouching. Text never flips back to shown between runs.
     - **Each owed base is handled on its own, and the run reports the worst state.** A base that is waiting, unchecked or missing never stops work on the others. Every entry ends in one of these:
       - **Done.** Its recheck judged at least one stream with no mismatch. It leaves the list, and those streams are recorded in `judged`. Streams it could not judge stop being vouched for.
       - **Settled without judgement.** It leaves the list and vouches nowhere, and it is never "done".
         - `history-refused`: every unjudged stream is blocked only by `link-refused` or `not-accepted` logs.
         - `base-unverifiable`: the base cannot be found or verified on this computer, or a `next` meets only a trusted checkpoint that does not include the filled logs.
         - While a log stays blocked, so some text loses its vouching and is not shown, the run reports `incomplete`. The sync sentence then says so in words that name the writer's history and say the text before it cannot be vouched for, never the plain synced sentence.
         - A `history-refused` that removed vouching is an attention finding.
         - A `base-unverifiable` whose logs are all complete hides no text, so it is a detail line. Its base is still never counted as done.
       - **Still owed.** If the recheck can judge no stream for any other reason, the base stays owed: `unchecked` (`nothing-judged`), or `waiting` (`cannot-open-yet`, when `openedUnder` gives nothing). Local causes have their own state and sentence, never the "could not be fetched from your organization's server" one.
