<objective>
The server side of POST-01 and the hub hardening carried from Phase 32: your organization's server obeys `roster.require` for appends and sessions (D-07), answers a missing blob per entry instead of per batch (D-28), and starts in restore mode after a restore done by the procedure, so an honest restore no longer looks like a fork (D-32, D-45). The client's side of the same wire is 33-08 in the same wave; both use the contract below word for word.

Wire contract shared with 33-08 (never change one side alone):
- Append refused for a lacking feature: HTTP 403, body `{ error: 'needs-update', message }`, nothing stored.
- Append in restore mode outside checkpoint coverage: HTTP 503, header `Retry-After: <LIMITS.restoreRetrySeconds>`, body `{ error: 'restoring', message, retryAfterSeconds }`.
- Session refused for features: HTTP 401, `{ error: 'session-refused', reason: 'needs-update', message }` with the update sentence.
- Per-entry blob-missing: HTTP 200 with the append answer's per-entry refusal list (the shape `checkBatch` already returns for per-entry refusals) holding `{ entry, reason: 'blob-missing' }` for each entry whose declared or base-read blob the hub lacks, and `seq-gap` for that writer's later entries in the batch; the batch-level 409 is no longer sent for this reason.

Restore-mode rule settled here (A6, F9; reported to the owner in the summary): marker file `restore-mode` in the state directory; accept an append only when `coveredBefore` (the WR-02 rule) holds for its place against checkpoints the hub kept or was handed back since the restart; otherwise `restoring`. Mode ends when every admitted person device (not hubs, not revoked) has made one checkpoint ask since the restart, or when the operator removes the marker; on ending, the hub removes the marker itself and logs `hub.restore-ended`.

Branch `feat/phase-33-07-hub-rules` from `feat/phase-33-live-staff` HEAD (D-02), merged back after wave 3.
