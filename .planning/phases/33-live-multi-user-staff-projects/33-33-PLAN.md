## The rule (D-71)
In `textFold.ts` applyUpdateEntry, a span whose client has no registration in the product counts as the entry's writer's own when both of these hold:
- **(a) own slot:** `view.ctx.roster.clientIdOwner(client, entry.body.roster)` equals `entry.session?.device ?? entry.header.writer`. This is the comparison applyClient already makes, so a session key's ids belong to the device that certified it (D-62).
- **(b) the log starts at a base:** `view.baseOf(entry.header.stream, entry.header.writer)` exists, and `view.holdsPlace(entry.header.stream, entry.header.writer, base.seq)` is false. The fold holds none of the writer's log up to the base head, so the registration may be in the part this computer has not received.

Everything else is unchanged: a registered owner that is another writer is still refused `foreign-client`, and any other unregistered client is still held `unregistered-client`. The clock rule, deletions and the `incomplete` flag work as today. A client accepted under this rule has its text flagged `unverified: true` with no writer, through the attribution proof, until a registration for it is folded.

## Why a missing registration can only sit below the base
The fold admits a writer's entry above the base only when every entry of that writer between the base head and it is admitted (the chain rule of 33-14 and Phase 31 D-04). A registration is an entry in the same writer's log and the same stream. So when the update is admitted and its registration is not, the registration is at or below the base head, or it was never written.

## Threat analysis (before any code; each row has a test in Task 1)
- **Forgery of attribution (another device's text):** an update inserting under a client whose slot belongs to another device. Rule (a) fails, so it is held as today. Slots are never reused, and `foreign-client-id` already stops anyone registering another device's slot (Phase 31 D-03). The rule can never make text look like another device's.
- **Planting text that was never registered:** a writer types under its own slot and never writes `doc.client`, so no actor (person or agent run) is claimed.
  - A full member holds the writer's whole log, so (b) fails and the update is held as today.
  - A joiner shows the text before the history arrives, marked not verified and naming nobody.
  - Once the history is in, (b) fails there too, and the update is held exactly as on the full member.
  - Residual: for that short time a joiner sees text a full member does not. It is unverified and names nobody, and the writer could have shown it legitimately by registering. Accepted, low.
- **Equivocation (a forked log):** a writer signs two histories below the base, for example two registrations of one client under different actors.
  - The joiner follows only the branch through the trusted base head (33-14). 33-32's history pull refuses a history that does not end at that head's hash.
  - Once the history is in, the chain stage's equivocation handling decides, exactly as on a full member.
  - The rule names no actor before then, so a fork cannot make it name the wrong one.
- **Session keys:** an update signed by a session key whose certificate's device is not the slot owner fails (a) and is held. A revoked or quarantined certifying device stops its session keys at the fold (D-62), before this rule is reached.
- **A lying server:** the base comes only from witness-trusted checkpoints. A base the served history contradicts is distrusted by 33-32, and then the fold drops the base, so (b) fails.

## Version safety (no feature gate, no roster.require)
- Rule (b) needs a join base, and only a hub checkpoint with `startFromBase` gives one. Both are unreleased, so no released client ever applies the rule.
- A full member holds every entry up to every base head, so (b) is false for every writer and its fold is byte for byte unchanged. Task 1 tests this.
- Once the history is served, the registration folds before the update, because it is earlier in the writer's own chain and inside the checkpoint's final prefix. The update is then accepted through the registration exactly as on a full member, so text, state vector, registrations and digests converge. Task 1 tests that the incremental fold equals the fold from scratch.
- No wire format, entry kind or digest input changes: the registrations in the canonical digest still come only from `doc.client` entries. Mixed builds in drop A differ only in how soon a joiner shows this text, never in the result once the history is in.
