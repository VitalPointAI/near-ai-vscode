## The rule (D-71)
In `textFold.ts` applyUpdateEntry, a span whose client has no registration in the product counts as the entry's writer's own when both of these hold:
- **(a) Own slot.** `view.ctx.roster.clientIdOwner(client, entry.body.roster)` equals `entry.session?.device ?? entry.header.writer`. This is the comparison applyClient already makes, so a session key's ids belong to the device that certified it (D-62).
- **(b) The log starts at a base.** `view.baseOf(entry.header.stream, entry.header.writer)` exists, and `view.lowestHeld(entry.header.stream, entry.header.writer)` is undefined or above the base's seq. In other words, the fold holds no entry of that writer at any seq at or below the base head, so the registration may be in the part this computer has not received.
  - `baseOf` already answers only from bases that vouch for that stream (33-32's `FoldOptions.vouching`, D-70's vouching invariant). So a base that settled without judging the stream makes the update held again, with no extra check here.

Everything else is unchanged:
- A registered owner that is another writer is still refused `foreign-client`.
- Any other unregistered client is still held `unregistered-client`.
- The clock rule, deletions and the `incomplete` flag work as today.

A client accepted under this rule has its text flagged `unverified: true` with no writer, through the attribution proof, until a registration for it is folded. This holds even next to a provisional compaction, whose claimant can never speak for a client it did not register (CR-01).

## Why a missing registration can only sit below the base
The fold admits a writer's entry above the base only when every entry of that writer between the base head and it is admitted (the chain rule of 33-14 and Phase 31 D-04). It admits an entry at or below the base only as part of a chain from seq 0. A registration is an entry in the same writer's log and the same stream. So when the update is admitted and its registration is not, the registration is at or below the base head, or it was never written. With rule (b), any held part of the writer's log at or below the base (a prefix from seq 0) turns the rule off, so a partly received history never lets the rule stand in for a registration the fold could already hold.

## Threat analysis (before any code; each item has a test in Task 1)
- **Forgery of attribution (another device's text).** An update inserting under a client whose slot belongs to another device fails rule (a), so it is held as today. Slots are never reused, and `foreign-client-id` already stops anyone registering another device's slot (Phase 31 D-03). The rule can never make text look like another device's.
- **Planting text that was never registered.** A writer types under its own slot and never writes `doc.client`, so no actor (person or agent run) is claimed.
  - A full member holds the writer's whole log, so (b) fails and the update is held as today.
  - A joiner shows the text before the history arrives, marked not verified and naming nobody. Once the history is in, (b) fails there too, and the update is held exactly as on the full member.
  - Residual: for that short time a joiner sees text a full member does not. It is unverified and names nobody, and the writer could have shown it legitimately by registering. Accepted, low.
- **Equivocation (a forked log).** A writer signs two histories below the base, for example two registrations of one client under different actors.
  - The joiner follows only the branch through the trusted base head (33-14), and 33-32's history pull refuses a history that does not end at that hash.
  - Once the history is in, the chain stage's equivocation handling decides, exactly as on a full member.
  - The rule names no actor before then, so a fork cannot make it name the wrong one.
- **A claimant speaking for others (I8).** With a provisional compaction by writer M in the same product, the attribution proof's claimant is M. A client accepted under D-71 has no registration, so M can never be named for it.
- **Session keys.** An update signed by a session key whose certificate's device is not the slot owner fails (a) and is held. A revoked or quarantined certifying device stops its session keys at the fold (D-62), before this rule is reached.
- **A lying server.** The base comes only from witness-trusted checkpoints. A base the history contradicts is distrusted by 33-32, and the fold then drops it, so (b) fails, the update is held again and its text is gone.

## Version safety (no feature gate, no roster.require)
- Rule (b) needs a join base, and only a hub checkpoint with `startFromBase` gives one. Both are unreleased, so no released client ever applies the rule.
- A full member holds every entry from seq 0, so `lowestHeld` is 0 for every writer and (b) is false. Its fold is byte for byte unchanged; Task 1 tests this.
- Once the history is served, the registration folds before the update, because it is earlier in the writer's own chain and inside the checkpoint's final prefix. The update is then accepted through the registration exactly as on a full member, so text, state vector, registrations and digests converge. Task 1 proves the incremental fold equals the fold from scratch for the whole history and for a part of it that comes first.
- No wire format, entry kind or digest input changes: the registrations in the canonical digest still come only from `doc.client` entries. Mixed builds in drop A differ only in how soon a joiner shows this text, never in the result once the history is in.
