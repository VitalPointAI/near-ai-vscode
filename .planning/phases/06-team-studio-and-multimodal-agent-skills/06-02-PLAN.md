<threat_model>
## Trust Boundaries

| Boundary | Description |
|---|---|
| Provider catalog ↔ capability snapshot | Remote metadata becomes local eligibility facts and may be malformed, stale, or contradictory. |
| Team member contract ↔ route selector | Imported skill/tool declarations meet provider/model capabilities and privacy constraints. |
| Capability route ↔ approval/dispatch | A selected operation, model, cost, and privacy boundary become authorization inputs. |
| Host capability result ↔ webview | Untrusted UI receives bounded explanation DTOs but cannot authoritatively select or fabricate eligibility. |

## Least-Privilege Constraints

- Catalog parsing is allowlisted and bounded; unsupported fields are ignored, while missing required capability facts produce unavailable rather than inferred support.
- CapabilityRouter has no credential access and does not call arbitrary URLs; provider adapters are selected by validated profile/provider configuration.
- Reputation ranking runs only over candidates already compatible with the requested role, skill, modality, privacy boundary, budget, and lifecycle requirements.
- Route snapshots are immutable for an approval/request; a refresh, profile switch, or model change requires a new route and policy decision.
- Analytics/audit store capability IDs, provider/model labels, and reason codes only; no raw model response, media bytes, prompt, or credential is retained.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-06-06 | Tampering | provider capability metadata | critical | mitigate | Strict schema normalization, freshness/readiness checks, contradiction rejection, and unsupported-state tests prevent forged capability. |
| T-06-07 | Elevation of privilege | member skill to provider operation | critical | mitigate | Require exact capability intersection, provider operation allowlists, privacy/budget/cancellation/publication requirements, and approval-bound route snapshots. |
| T-06-08 | Spoofing | model/provider identity | high | mitigate | Bind snapshots to validated profile/provider, model ID, source, and fetched-at time; never derive capability from display names. |
| T-06-09 | Information disclosure | catalog/route/webview/analytics | high | mitigate | Emit bounded metadata and reason codes only; redact provider payloads, raw media, prompts, credentials, and paths in negative tests. |
| T-06-10 | Denial of service | catalog refresh and compatibility matrix | medium | mitigate | Bound model rows, metadata fields, refresh frequency, candidate counts, and explanation sizes; retain a safe unavailable state on failure. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installation is planned; any proposed dependency must pass the package-legitimacy gate. |

</threat_model>
