**The script (D-61, D-63).** New `deploy/keycloak/guests.mjs` in the style of `enrol.mjs`: a header comment with usage, then exported functions that take injected clients, then the CLI. Subcommands in this task:
- `create`, with flags `--user`, `--email`, `--first`, `--last`, `--serves`, `--nationality`, `--organization`, `--until`, `--requested-by`, `--approved-by`, `--approval-ref` and `--no-link`.
  - It checks the request with the pure `checkGuestRequest(request, settings, now)`, then looks up the lead (an enabled account outside `guests`) and, for `allied-military` or `industry`, the approver.
  - It refuses an existing username or email.
  - It creates the account with: group `/guests`, the attributes, `guestUntil` normalised to UTC, and the required action `webauthn-register-passwordless`.
  - **The registration link.** Unless `--no-link` is given, `create` sends the link through Keycloak's execute-actions email (`PUT users/{id}/execute-actions-email`, action `webauthn-register-passwordless`, 24-hour lifespan).
    - Keycloak sends it with the realm's `smtpServer`, which `apply.mjs` fills from the realm site file's `smtp` (host, port, from; STARTTLS on).
    - Before sending, `create` reads the realm's `smtpServer`. If the host is empty or `not-set`, it does not try to send. It says the account was created without a link, names the realm site file's `smtp` settings, and points to `guests.mjs link`.
    - A site with no mail server at all can only enrol in person through a site mailbox. Staff enrolment has the same need (47-17).
  - **No mail sent, said plainly.**
    - With `--no-link`, `create` makes no email call and ends with "The account is ready. Send the registration link with guests.mjs link --user <name> when the guest is at the enrolment desk."
    - When Keycloak refuses or fails the send (for example 500 "Failed to send execute actions email"), the account stays. Nothing is deleted or rolled back. `create` exits 1 with what happened, Keycloak's answer, where the mail settings are, and the next step `guests.mjs link --user <name>`. It is never silent: a later `create` for the same person would only say the name exists.
- `link`, with `--user`, sends the registration link again through the same path, with the same mail check and messages. It refuses an ended guest, a guest past `guestUntil`, and a guest who already has two passwordless keys.
- `end`, with `--user` and `--reason`, calls `endGuest`. `endGuest`:
  - disables the Keycloak account (`enabled: false`);
  - ends its sessions (`POST users/{id}/logout`);
  - records `guestEndedAt` and `guestEndedReason`. A Keycloak `PUT users/{id}` with `attributes` replaces the whole attribute set, so it writes back the full representation it just read with only these fields changed. The test checks the other guest attributes survive;
  - sets `disabled: true` on OpenBao `identity/entity/name/guest-<id>`. It reads the entity first: a POST to a name that does not exist would create a new entity, which the operator's enrolment token allows. A guest who was never enrolled has no entity, so `endGuest` skips that step; this is not an error;
  - stops the guest's Theia sessions through an injected sessions client, `stop(email)`. The CLI's default adapter spawns `kubectl get sessions.theia.cloud -n <guests.sessionsNamespace> -o json`, keeps the records whose `spec.user` is the guest's email, and deletes each by name. `--no-sessions` skips it for hosts without kubectl.
  - It never deletes anything else: no account, no credential, no entity, no key, no Workspace, no volume.

Connection flags are as in `enrol.mjs`: `--keycloak`, `--keycloak-token-file`, `--bao`, `--ca-file`, `--bao-token-file`, `--site` and `--realm-site`. The realm site file gives `guests.maxDays`. When it is 0 or absent, `create` refuses with "Guests are off at this site. Set guests.maxDays in the realm site file."

|-----------|----------|-----------|----------|-------------|-----------------|
| T-47-63 | Elevation of privilege | guest gaining an administrator role, a deciding power or another person's keys | high | mitigate | `guests` has no role (checkRealm). The only OpenBao policies are the staff ones, templated on the entity. expireGuests ends a guest found with a role, group or policy. The fold and hub refuse an observer's deciding acts (33.1 D-27, transfer to 33.1 for that part). |
| T-47-64 | Spoofing | an outsider admitted without approval | high | mitigate | Lead required. For allied military and industry, an approver who is an enabled member of security-contacts and neither the lead nor the guest, plus an approval reference. All checked before any write. Keycloak admin events log the operator. |
| T-47-65 | Elevation of privilege | a guest account without an end, or enrolled after its end | high | mitigate | create and extend refuse a missing end, a past end or one beyond maxDays. enrol refuses a past or missing end and a disabled account. |
| T-47-66 | Information disclosure | a guest reading another person's secrets or keys | high | mitigate | Staff policies templated on the entity (D-40). The tracer shows 403 on staff's KV path. |
| T-47-67 | Tampering | the guest-expiry credential used to change an entity's policies or touch staff entities | high | mitigate | Path limited to guest-*; allowed_parameters only disabled true; no create. Checked against OpenBao dev. |
| T-47-68 | Repudiation | a guest's records deleted without a second person | medium | mitigate | No script deletes anything. guest-removal deletes are control-grouped (two key-custodians approvals). |
| T-47-76 | Tampering | guest-removal used to delete a staff member's KV data or Transit keys | high | mitigate | The delete paths `kv/metadata/users/*`, `transit/keys/person-*` and `transit/keys/kek-*` are named by entity id, so OpenBao cannot limit them to guests. Only the entity path is limited by name (`guest-*`). Every delete is control-grouped, so nothing happens without two key custodians. Transit deletes also need `deletion_allowed`, a second control-grouped request under key-move. The policy is attached only to the operators who run removals. The runbook (47-21) requires the two custodians, before approving each request, to confirm that the request's entity id belongs to an entity named `guest-<id>`. The residual risk is two custodians approving a wrong request; it is accepted with owner item 19. |
| T-47-SC | Tampering | npm/pip/cargo installs | high | accept | No package installed; Node built-ins only |
