<objective>
The off-site copy, required, 3-2-1 (CP-6, CP-9; D-81 in `47-COMPLIANCE-CONTEXT.md`, owner decision d, 2026-11-24). Every day the site copies two things to a write-once S3-compatible store at a second organization site:
- its encrypted backups: the Longhorn backup target, which holds every volume's backup, including the OpenBao snapshot, Postgres dump and OpenSearch snapshot volumes;
- the write-once audit archive (48.1).

The copy carries a manifest signed with a non-exportable Transit key and chained day to day. The keys that open the backups travel separately with the custodians. Disconnected sites write the same set to signed media. A quarterly drill verifies and restores from the copy. Per D-70 (the owner's direction of 2026-11-24), the obligation is delivered as code and tests wherever possible.

Purpose: one site's loss (fire, flood, seizure) must not take its only backups with it.

Output: `deploy/bundle/lib/offsite.mjs` (`push`, `pack`, `verify`; it uses 48.1-20's S3 client `deploy/audit/lib/s3.mjs`), the Transit key and policy, the `sterling-offsite` release, the required `offsite` site setting with the preflight refusal, and tests.

Lab simulation (48.1 hand-off H-06): the second site is 48.1-20's local second site `deploy/lab/worm-site`. `sh deploy/lab/worm-site/up.sh` starts the object-lock store 48.1-20 chose (not MinIO or Garage, AGPL), creates a versioned, object-locked bucket, writes the credentials to a file outside the repository, and prints the endpoint. This plan does not choose or configure the store.

What the set holds (D-81):
- **The Longhorn backup target tree.** It holds every volume's backup, encrypted with `longhorn-crypto`. It is mounted read-only from the site's NFS backup target, through a PersistentVolume and claim, because Pod Security restricted allows no inline NFS volume.
- **The audit archive.** The objects of 48.1's write-once audit archive bucket, read from the object store settings in 48.1-15's `deploy/values/site.example/sterling-audit-archive.yaml`: each day's files, manifest and signature, copied unchanged with their retain-until dates.
- **The manifest** `offsite-<day>.json`:
  - format `sterling-offsite/1`, `site`, `day`, `createdAt`;
  - `objects`: each with key, size, SHA-256, source (`backup` or `archive`) and retain-until date;
  - `previousManifestSha256`;
  - `keyBackups`: where the escrow and HSM key backups are held. These are the digest-only escrow records (47-25), never key material;
  - signed with Transit key `offsite-manifest`; the public key is exported at the key ceremony (47-17).

Not in the set:
- **etcd snapshots.** A site lost entirely is rebuilt by a fresh install from the bundle and data restores (recovery order stage 0, 47-27); etcd snapshots serve the on-site rollback only, and stay on the node.
- **Plain dumps.** Postgres dumps and OpenSearch snapshots reach the set only inside the encrypted Longhorn backups of their volumes.
- **Keys.** No key ever travels in it.

Object lock: each object is PUT with `x-amz-object-lock-mode: COMPLIANCE`, `x-amz-object-lock-retain-until-date` and `x-amz-checksum-sha256`. The retention is 1,825 days for archive objects (owner decision b, D-82) and `offsite.backupRetentionDays` for backup objects. The job never deletes; expired objects are removed by the store's own lifecycle, set by your organization. An object already present (HEAD with the same SHA-256) is not uploaded again, so daily runs are incremental.

The S3 client is 48.1-20's `deploy/audit/lib/s3.mjs` (SigV4 on `node:crypto`: put with object lock, head, get, list versions). It is reused, not duplicated. The shared job image gains `deploy/audit/lib/` in its copy list.

The shared image's register entry: the base `image:registry.access.redhat.com/ubi9/nodejs-22-minimal` (47-20: component `keycloak`, crypto `uses-platform`) still holds for crypto and air gap. The off-site job's TLS and SigV4 signing run through Node's crypto on the host's OpenSSL, and the second site is inside your organization's network. Its purpose must name all three jobs the image runs: guest expiry, revocation (47-31) and the off-site copy. That wording goes into 47-20's entry when this branch is rebased (ledger H-11), with `role` and `architectureArea`, so 47-33 makes no register edit of its own.

The OpenBao pieces follow the audit archive's pattern in 48.1-14: a non-exportable Transit key, and a Kubernetes auth role bound to one service account whose policy may only sign with that key.
