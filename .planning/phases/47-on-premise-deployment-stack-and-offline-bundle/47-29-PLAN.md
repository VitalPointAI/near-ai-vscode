<objective>
Vulnerability scanning and SBOMs for the bundle's images (RA-5, RA-5(2), SI-2, CM-4; D-72 in `47-COMPLIANCE-CONTEXT.md`): Per D-70 (the owner's direction of 2026-11-24), the obligation is delivered as code and tests wherever possible.
- the bundle build makes SBOMs with the pinned syft and scans them with the pinned grype, for the 38 upstream images in `deploy/bundle/images.lock.json` and, in the same loop, for our built and released images;
- the build ships the vulnerability database and grype for offline rescans;
- the build writes the change and impact record for the site change board;
- the build adds signed database refreshes between bundles.

Purpose: an air-gapped site cannot look anything up. It needs, inside the media it already trusts, what it runs (SBOMs), what is known to be wrong with it (scans and the database), and what an update changes, so its change board can decide and it can rescan as new vulnerabilities are published.

Output: build.mjs changes, `deploy/bundle/lib/scan.mjs`, `deploy/bundle/lib/change-record.mjs`, `deploy/bundle/scan.mjs`, `deploy/test/scan.test.mjs`, and the runbook sections in `bundle-update.md` and `maintenance.md`.
</objective>

Facts (D-72 discovery, Grype 0.122.1 source):
- `grype db list -o json` prints a one-item list whose entry has `built`, `schemaVersion`, `path` (the archive address, relative to the listing at `https://grype.anchore.io/databases`) and `checksum` (`sha256:<hex>`).
- `grype db import FILE` imports an archive.
- `grype db status -o json` reports the imported database's build date and schema.
- The settings `GRYPE_DB_CACHE_DIR`, `GRYPE_DB_AUTO_UPDATE`, `GRYPE_DB_VALIDATE_AGE` and `GRYPE_CHECK_FOR_APP_UPDATE` exist; the last is on by default and would try the network at start.
- Syft: `syft scan registry:<ref> --output cyclonedx-json=<file>`, with `SYFT_REGISTRY_INSECURE_USE_HTTP=true` for a plain-HTTP staging registry and `SYFT_CHECK_FOR_APP_UPDATE=false`.
- Use the pins in `compliance/ci/tool-pins.json` (syft 1.57.2, grype 0.122.1, owner-approved) through `install-tool.sh` on the build host. Grype reaches sites as a raw pinned download through `planTools`, like cosign.
- 47-26 has already updated the register entries for this use.

Per D-72.

`deploy/bundle/lib/scan.mjs` (Node built-ins; `SYFT` and `GRYPE` from the environment or PATH; an injectable `run` and `fetch`):
- `sbomImage(ref, out, { plainHttp })`.
- `downloadDatabase(dir)`:
  1. runs `grype db list -o json` with a private `GRYPE_DB_CACHE_DIR`;
  2. resolves the archive address against `https://grype.anchore.io/databases`;
  3. refuses any host other than `grype.anchore.io`, and any scheme but https;
  4. downloads it streaming while hashing, renaming it only when the hash equals the listing's checksum;
  5. returns `{ file, built, schema, checksum }`.
- `importDatabase(file, cacheDir)`.
- `scanSbom(sbom, out, { cacheDir })` runs grype with `GRYPE_DB_CACHE_DIR` set to that cache and `GRYPE_DB_AUTO_UPDATE=false`, `GRYPE_DB_VALIDATE_AGE=false` and `GRYPE_CHECK_FOR_APP_UPDATE=false`, report-only with no fail threshold.
- `summarize(grypeJson)`.
- `deployFiles(deployTreeTar, scratch)`: extract with `tar -xf` into a scratch folder and hash each file.

`build.mjs`:
- `SITE_TOOLS` gains `grype`.
- `buildBundle` takes `security: { previous }`. After the images are staged and signed, and before `store save`:
  - make an SBOM of every image from the staging registry by digest;
  - download and import the database once;
  - scan each SBOM;
  - write `security-reports.tar` (sorted names, `--mtime=@0`, owner 0, like `deployTree`);
  - add it and `vulnerability-db.tar.zst` as file items.
- `buildWholeBundle` always does this and takes `--previous <previous bundle folder>`. Without it, the change record says "first bundle".
- Selected mode (`--images`, `--files`) does it only with `--security`.

`deploy/bundle/scan.mjs rescan --from <import out folder> --out <report folder> [--db <signed database file> --public-key <file>]`:
1. extract grype from its pinned tarball in the out folder into a scratch folder;
2. import the bundle's database, or, with `--db`, first verify the database file with `verifySignedFile` and the given key, then import it;
3. scan every SBOM in `security-reports.tar`;
4. write `rescan.json` and print the counts by severity and the database's build date and age in days.

2. `check.mjs` verifies it.
3. Import it into the `--network none` target as in 47-06.
4. In a container that shares only that target's network namespace, run `scan.mjs rescan --from <import out>`. It completes with the database date shown. A `fetch("https://grype.anchore.io")` in the same container fails, showing there was no route, and the rescan still succeeded.

Record the outputs in the SUMMARY.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-47-101 | Tampering | substituted vulnerability database | high | mitigate | Host allow-list (grype.anchore.io, https only), checksum from the listing, then the bundle signature or the signed database file; rescan verifies before use |
| T-47-102 | Information disclosure | grype calling out from a site | medium | mitigate | Auto-update, age validation and application update checks off on every call; private cache; test-enforced with a spy |
| T-47-103 | Repudiation | an update installed without impact review | medium | mitigate | Change record in every bundle with a decision section for the change board (CM-4) |
| T-47-104 | Spoofing | a stale database presented as current | low | mitigate | Every report states the database build date and age; an older database than the bundle's is refused |
| T-47-SC | Tampering | npm/pip/cargo installs | high | accept | No package installed; syft and grype are the owner-approved pins |
</threat_model>
