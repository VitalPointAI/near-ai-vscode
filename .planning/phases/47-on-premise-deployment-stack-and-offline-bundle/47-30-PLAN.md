Outbound kinds, recognized by content and never by file name:
- user export: JSON with `format` `sterling-users/1`, signed beside as `<file>.sigstore.json`;
- CSR: a PEM file holding exactly one `CERTIFICATE REQUEST` block, signed beside;
- revocation list: a PEM file holding `X509 CRL` blocks only, signed beside;
- site evidence export (48-02): JSON whose top-level keys are exactly `payload`, `purpose`, `signedAt`, `signer` and `v`, with `purpose` `site-evidence-export`. It is signed in the compliance package's own envelope format. Do not write a second verifier for that format: `outbound.mjs` recognizes it, records its SHA-256, and notes that HQ's deployment collector verifies it.

The kinds match what 48.1's exchange register lists; a new kind needs both.

The transfer record format is `sterling-transfer/1`:
- `direction` (`in` or `out`), `site`, `checkedAt` (UTC), `result`;
- inbound: bundle `version`, `marking`, manifest SHA-256, archive SHA-256, item count;
- outbound: `files`, each with `name`, `kind`, `sha256`, `marking` (the export's marking, or `UNCLASSIFIED` for the other kinds) and `signature` (`verified` or `envelope-not-verified-here`).

People fill in the human custody fields (seal number, courier, hand-over signatures) on the runbook's form.

Guest records (47-21, wave 8): `users.mjs export --include-guests` adds `guest` objects to the same file. The marking covers the whole file, guests included, and this plan runs after 47-21 because both edit `users.mjs` and `deploy/runbooks/README.md`.

Version safety (read before coding: 47-CONTEXT.md D-68 and D-69; 32.1 D-62 and D-67):
- **The bundle manifest is not changed.** D-68 keeps `sterling-bundle/1` as the only format until a change ships its reader first. The bundle's marking is the owner's classification (UNCLASSIFIED, D-74), so `check.mjs --record` writes it into the inbound transfer record as a constant, and the manifest carries nothing new.
- **The user export carries the marking as a feature of `sterling-users/1` (D-69).**
  - Every export carries `marking` and lists `marking@1` in `requires`, sorted with `guests@1` when guests are in it.
  - `USERS_FEATURES` gains `marking@1`: the import reads and prints the marking, so the reader ships with the writer in one change.
  - The export uses 47-21's target-site check, the same function and flags (`--target-site`, `--sites`, `--site-exports`). It writes no file unless the target site's newest verified signed evidence export shows `marking@1` in `reads.users` (reported from `USERS_FEATURES` by 47-32's release record).
  - So a site whose import cannot read the marking is never sent a file it would refuse.

Per D-74. Writing rules as 47-17: plain words, "your organization", every command one that exists, no capacity figure. The runbook starts with what it is for, who does it (operators, couriers, key custodians for escrow media) and what they need. Sections:

1. **Markings.** The bundle is UNCLASSIFIED: label its media so. User exports hold personal information and carry the site's `personalDataMarking`; label their media with it. CSRs, revocation lists and site evidence exports hold no personal information. Escrow media and recovery material follow the key ceremony runbook's handling.
2. **Approved media (MP-7).** Write-once optical media, or your organization's approved hardware-encrypted removable drives (FIPS 140-3 validated); nothing else. User exports go only on encrypted drives.
3. **Chain of custody and transport (MP-5).**
   - A custody form with these fields: transfer record file and its SHA-256, media serial, tamper-evident seal number, marking, from, to, courier, and the time and signature of each hand-over (two people at the hand-off).
   - Sealed transport, kept in your organization's approved container.
   - The receiving operator checks the seal and the record before use.
   - Records are kept with the site's runbook records.
4. **Malicious-code scanning (SI-3) decision.** Signatures prove where content came from, not that it is free of malicious code, and they do not cover the non-image payloads. Scan every medium on your organization's approved scanning station: on the connected side before writing, and at the air-gapped entry point before import. Write the result on the custody form. This runbook ships no scanning engine (owner item D-74).
5. **Inbound: the HQ build host to an air-gapped site.**
   1. Build and check the bundle on the connected build host, and write it to new media.
   2. Scan the media.
   3. Carry it under custody to a verification host at the enclave boundary.
   4. Run `check.mjs --bundle --public-key --record` there (the public key from the install media).
   5. Import (`bundle-update.md`).

   The transfer is one-way: media that has been inside the enclave never goes back to the connected side unless it has been sanitized.
6. **Outbound: from an edge.**
   1. Put only the files to send in an empty folder: user exports, CSRs, revocation lists, site evidence exports.
   2. Run `outbound.mjs check --dir --public-key --site --record`.
   3. Write them to approved media, scan, seal and record.
7. **After import: sanitizing (MP-6 with MP-4).**
   - Write-once media: destroy it under your organization's destruction procedure, or keep it as the archive copy under custody.
   - Reusable drives: sanitize under your organization's procedure (CCCS ITSP.40.006) before reuse.
   - The import host keeps the last two verified bundles on the backup target for a registry rebuild (`recovery-plan.md`) and deletes other staging copies.
8. **The OS repository mirror, database refreshes and off-site sets.** Updates to the site's own OS repository mirror, and the signed vulnerability database files, cross by the same steps. A disconnected site's daily off-site set (`offsite.mjs pack`, 47-33) goes on its own medium; the receiving site checks it with `offsite.mjs verify --from-dir`, not with the outbound check, because it is a folder tree.
9. **Disposal (48.1 hand-off).**
   - A departed person's workspace volume is deleted with their Workspace, and its backups expire with the backup and off-site retention. Every workspace volume shares one LUKS class key, so one person's data cannot be crypto-erased alone; this is a known limit (48.1-08).
   - Media that held a volume backup is sanitized like any other.
   - An HSM leaving service is zeroized under the vendor's procedure with two custodians present, recorded as SR-12 disposal, and its key backups are destroyed under the key ceremony's destruction record.

`README.md`: add the media handling runbook to the index, in the order a site uses it.
