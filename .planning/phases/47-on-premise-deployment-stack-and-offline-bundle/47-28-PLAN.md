<objective>
Site maintenance (MA-2, MA-6, SI-2; D-75 in `47-COMPLIANCE-CONTEXT.md`): three checks as code that run before the risky maintenance steps, and the maintenance runbook that wraps them. The runbook covers node OS patching and drain, the RKE2 upgrade order, certificate renewal and intermediate expiry, HSM firmware, patch timelines and maintenance records. Per D-70 (the owner's direction of 2026-11-24), the obligation is delivered as code and tests wherever possible.

Purpose: the dangerous mistakes in maintaining a small cluster are a drain that breaks quorum or removes a volume's last copy, an upgrade that skips a version or runs without fresh backups, and a CA that expires unnoticed. Each becomes a refusal before the step, not a recovery after it.

Output: `deploy/bundle/maintenance.mjs` (`drain-check`, `upgrade-check`, `cert-check`), `deploy/test/maintenance.test.mjs`, and `deploy/runbooks/maintenance.md`. 47-17 (same wave) lists `maintenance.md` in the runbook index by this name.

Per D-75.

`deploy/bundle/maintenance.mjs`:
- holds the shared pieces: argument parsing, the injectable `run`, a `kubectlJson(args)` helper, and an output style of one plain line per problem (exit 1 on any problem) and per warning (exit 0);
- exports `certCheck({ run, tls, now, horizonDays })` and the CLI `cert-check [--horizon-days 90]`.

The problems `cert-check` reports:
- every cert-manager Certificate that is not Ready, whose `renewalTime` has passed (renewal overdue), or whose `notAfter` is within 7 days;
- every certificate in `sterling-site-ca`'s chain (parsed with `X509Certificate`) expiring within the horizon. The message names the subject and the action: the site intermediate is renewed by the key ceremony, `pki-files.mjs csr` (47-14); the HQ root by HQ's key ceremony;
- the API server serving certificate expiring within the horizon, with the action to restart `rke2-server` on each server one at a time, or `rke2 certificate rotate` (as the docs confirm).

End to end:
1. On the lab VM (`vm.sh up`, RKE2 as 47-05, under its lock), forward the API server.
2. Apply a stand-in `sterling-site-ca` ConfigMap holding a short-lived test CA made with openssl in the scratchpad, valid 30 days.
3. Run `cert-check`: it exits 1, naming that CA with the key ceremony action.
4. Run `cert-check --horizon-days 10`: the CA passes.
5. `vm.sh down`.

Start `maintenance.test.mjs` with the cert-check cases on fixtures: a Ready certificate, a not-Ready one, an overdue renewal, a chain certificate inside the horizon, and an API certificate inside the horizon. Record the lab run in the SUMMARY.

Refer to sibling runbooks by bare file name (`bundle-update.md`, `key-ceremony.md`, `media-handling.md`): 47-17 writes the first two in this wave, and 47-30 writes the third in wave 8. The runbook starts with what it is for, who does it (site operators; key custodians for the HSM), and what they need. Sections:

1. **Before any maintenance.** Record the change in your organization's change log, with what, when, who and which components (MA-2). Run `maintenance.mjs cert-check`. Tell people their sessions will stop. Take fresh backups.
2. **Node OS patching.** Updates come only from the site's own OS repository mirror; the mirror is refreshed by media under the media handling runbook. One node at a time:
   1. `maintenance.mjs drain-check --node`;
   2. `kubectl cordon`, then `kubectl drain --ignore-daemonsets --delete-emptydir-data`;
   3. update from the site repository and reboot;
   4. `sh check-time.sh <node folder>` (the clock must still follow the site source);
   5. wait for the node to be Ready, then `kubectl uncordon`;
   6. wait until every Longhorn volume is healthy again before the next node.
3. **RKE2 upgrade.** The new RKE2 comes only in a new signed bundle: check and import it (bundle-update.md), then `maintenance.mjs upgrade-check --bundle`. Upgrade servers one at a time, then agents. For each node:
   1. `rke2 etcd-snapshot save` (servers);
   2. drain-check, then drain;
   3. run the new bundle's `install-node.sh` (it re-checks every pin and the clock);
   4. wait for Ready, then uncordon.

   One minor version per bundle, never a downgrade.
4. **Certificates.** cert-manager renews leaf certificates by itself. The site intermediate is renewed through the key ceremony (`pki-files.mjs csr`, key-ceremony.md) well before cert-check's horizon. The HQ root is renewed by HQ's ceremony. RKE2's own certificates follow what the docs confirm. Run cert-check monthly and before every change.
5. **HSM firmware.** Follow the vendor's procedure with the key custodians present. Install only firmware versions listed on the module's CMVP certificate, or the FIPS 140-3 approved mode no longer holds. Take an OpenBao Raft snapshot first. Restart one OpenBao pod, see it unseal by itself, then the others.
6. **Patch timelines (SI-2).** Your organization's timelines by severity apply from a bundle's `created` date. The values are an owner item; this runbook does not set them.
7. **Maintenance records and spares (MA-2, MA-6).** What to record. Your organization's support agreements and spares for the HSM and the nodes.
