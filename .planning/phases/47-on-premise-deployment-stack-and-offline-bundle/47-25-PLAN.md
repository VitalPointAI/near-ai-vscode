<objective>
Escrow of the keys a restore depends on (CP-9, CP-10; D-73 in `47-COMPLIANCE-CONTEXT.md`): Per D-70 (the owner's direction of 2026-11-24), the obligation is delivered as code and tests wherever possible.
- the RKE2 server token, without which no etcd snapshot can be restored (docs.rke2.io);
- the secrets-encryption configuration;
- the `longhorn-crypto` key, without which no Longhorn backup of an encrypted volume can be read once the cluster is gone.

Purpose: backups are useless if the keys that open them die with the cluster. The escrow is a deliberate, checked act held by key custodians, not a hope.

Output: `deploy/rke2/escrow-node.sh` (save and check on a server node), `deploy/bundle/escrow.mjs` (export and check of `longhorn-crypto`), and `deploy/test/escrow.test.mjs`. The custody procedure is written by 47-17 in `key-ceremony.md` and `recovery-plan.md`.
</objective>

Escrow output goes to a folder the custodians choose on escrow media. The record holds digests only, so it can be kept with the runbook records while the values stay on the media.

Per D-73.

`deploy/rke2/escrow-node.sh` (POSIX sh, `set -eu`, run as root on a server node, exit 2 on bad arguments). The data folder is `${RKE2_DATA_DIR:-/var/lib/rancher/rke2}` (overridable for tests). The two files are `server/token` and `server/cred/encryption-config.json`.
- `save <out-dir>`:
  - refuses an out folder inside the data folder, and one that already holds an escrow record;
  - creates the folder with mode 0700 and copies each file with mode 0600, without reading it onto the terminal;
  - writes `escrow-record.json` with `format` `sterling-escrow/1`, `kind` `rke2`, the node's host name, `createdAt` in UTC, and `files` (each with `name` and `sha256`);
  - prints only the file names and a reminder that the out folder goes to custody media and the record to the runbook records.
- `check <record>`: recomputes each file's digest and exits 1, naming every file that changed ("rotated since the escrow on <date>; make a new escrow"), or 0 with "escrow current".

`deploy/bundle/escrow.mjs` (Node built-ins; `kubectl` from `KUBECTL` or PATH; an injectable `run` function that never receives a secret value as an argument):
- `export --out <dir>` reads Secret `longhorn-system/longhorn-crypto` with `kubectl get secret -o json`, parsed in memory. It writes `longhorn-crypto.json` (the Secret's data keys and base64 values, mode 0600, folder 0700) and `escrow-record.json` (`kind` `longhorn-crypto`, the Secret's `resourceVersion`, the SHA-256 of the data serialized with sorted keys, `createdAt`). It refuses a missing Secret or an out folder that already holds a record.
- `check --record <file>` compares the current data digest and exits 1 when it differs.
- `record-key-backup --out <dir> --token-label <label> --token-serial <serial> --backup-ref <the HSM backup's identifier> --custodians <a,b> --held-at <site>` writes an `escrow-record.json` of kind `hsm-key-backup` (owner decision a, D-80). It records the backup of the HSM token that holds the site signing key and the seal key: no key material, only who holds which backup where. The development token is the owner's SoftHSM2 token made by `deploy/keys/new-dev-site-key.sh` (48.1-22). These scripts never read or copy it; its loss means running that script with `--rotate`.
- Exports `exportEscrow`, `checkEscrow` and `recordKeyBackup` for the tests.
- Nothing prints a value.

Lab end to end, under the VM's lock:
1. `vm.sh up`; RKE2 installed with `install-node.sh` as 47-05 did (with 47-22's clock files if 47-22 has merged, otherwise as 47-05).
2. `escrow-node.sh save /root/escrow-test` then `check`: current.
3. `rke2 secrets-encrypt rotate-keys` as the RKE2 documentation says, then `check`: exit 1 naming `encryption-config.json`.
4. Create a stand-in `longhorn-crypto` Secret in a `longhorn-system` namespace (lab-core has no Longhorn), run `escrow.mjs export` then `check` through the API server forward (current), patch the Secret, and `check` again (exit 1).
5. `vm.sh down`.

Record the outputs in the SUMMARY, with the confirmed encryption configuration path.

`escrow.mjs export` changes:

Template `escrow-currency.yaml` (rendered with the storage class, so only when `storageProvider` is longhorn): CronJob `sterling-escrow-currency`.
- **Schedule:** daily at 05:00 UTC, `concurrencyPolicy: Forbid`.
- **Image:** our `sterling/openbao` image by digest. It is a UBI image with `sh` and `sha256sum`, set through the descriptor's images entry the way the openbao release does.
- **Mounts:** Secret `longhorn-crypto` and ConfigMap `sterling-escrow-record`, both read-only.
- **The check:** a `/bin/sh` script hashes each key file named in the record and exits 1 when any differs or is missing, printing only key names.
- **Security context:** restricted, with a read-only root filesystem.

It is the Job whose failure 48.1-16's escrow-currency alert reads.

The RKE2 token and encryption configuration are node files that no restricted pod may read, so their currency stays with `escrow-node.sh check`.
