<objective>
Revocation on disable (AC-2(3), AC-2(4), AC-12, IA-4; D-79 in `47-COMPLIANCE-CONTEXT.md`). Today, when a person is disabled or removed in Keycloak, their OpenBao token and Theia session live on until the idle stop or the 8-hour renewal limit (Phase 46 D-22, a contract note in `workbench/README.md`). A reconcile job closes that window to at most `revocation.checkMinutes`: it disables the person's OpenBao entity, which stops every token it holds at once, and stops their Theia sessions. Per D-70 (the owner's direction of 2026-11-24), the obligation is delivered as code and tests wherever possible.

Purpose: removing someone's access must remove it everywhere, promptly, without an operator remembering three systems. Keycloak authenticates only (owner direction 2026-11-24): access is by verified credentials, enforced at key release. A Keycloak disable therefore cannot end a person's credentials. The job asks the issuing officers to revoke them, and they do it in their own sessions (71-12).

Output: `deploy/keycloak/revoke.mjs`, a shared module with 47-20's guest expiry (`deploy/keycloak/lib/offboard.mjs`), the client `sterling-access-revocation`, the OpenBao policy and role `access-revocation`, the CronJob in the realm release, `enrol.mjs reenable`, the setting, tests, the runbook section and a lab check.
</objective>

What 47-19 and 47-20 fixed, reused here:
- Person entities are `keycloak-<Keycloak user id>` (`enrol.mjs`, 47-07); guest entities are `guest-<id>` (47-19, D-62).
- Disabling an entity makes every token it holds unusable at once; that is how "ending" works (D-62). It is the entity-scoped revoke used here too.
- 47-20's guest-expiry job:
  - a confidential Keycloak client with a service account;
  - an OpenBao jwt role bound to that client's audience and `azp`, with a 5-minute token that cannot be renewed;
  - a Kubernetes ServiceAccount that may only list and delete `sessions` (group `theia.cloud`) in the sessions namespace. Deleting a Session stops its pod and keeps the Workspace and volume;
  - the `sterling/guest-expiry` image, which carries `deploy/keycloak/`, `deploy/openbao/` and `deploy/bundle/lib/`;
  - `guests.mjs expire --in-cluster`, which reads its settings from the environment and revokes its own token at the end.

This plan shares that mechanism:
- the same image, with the CronJob overriding the command (renaming the image to a general name is an owner choice, not done here);
- the same functions, extracted into `lib/offboard.mjs` and used by both jobs;
- the same role and permission pattern;
- separate credentials, so each job keeps least privilege: the guest job can manage guests only, and this job can only read users and disable entities.

Why a reconcile poll, not admin events alone: a poll of the users list compared with OpenBao entities and Theia sessions catches every change, including those made while the job was not running, and needs no event retention. Keycloak admin events stay on for the audit trail (D-35), and every action the job takes is printed to its log for the site log store.

Shell rules: TMPDIR in the session scratchpad; tests under `systemd-run --user --scope -q -p MemoryMax=4G -p MemorySwapMax=0 choom -n 1000 -- timeout 300`; podman and the lab VM under the heavy-run lock (`flock -o`), one heavy run at a time. Node built-ins only.

**The client.** In `realm.json`, add `sterling-access-revocation`, shaped exactly like `sterling-guest-expiry`:
- confidential, with service accounts on and the standard, implicit and direct-grant flows off;
- secret `$(env:STERLING_ACCESS_REVOCATION_CLIENT_SECRET)`;
- an audience mapper for `sterling-access-revocation`.

Its service account gets the realm-management role `view-users` and nothing else. That role is read-only; the job never changes a Keycloak account.

**Why realm-wide read, on purpose, unlike `sterling-guest-expiry`.** The guest job's fine-grained permissions are limited to the group `guests`, and 47-20 forbids widening them (its probe rule "never add `view-users`"). That rule is about the guest job, which writes. This job must see every person: staff, guests, and people removed from every group. No group-scoped permission can express that. `view-users` is the narrowest realm-wide grant, and it only reads. The job's only write is `disabled = true` in OpenBao, never in Keycloak. Its client shares the guest job's shape (confidential, service account, no flows, audience mapper) and its shared functions, not its Keycloak grants.

**Read 47-20's probe table first** (47-20-SUMMARY.md, the table 47-31 relies on):
- **Row 1 (list):** if the guest job needed `query-users` or `query-groups` to list, add the same role here, alongside `view-users`, and record it.
- **Row 7 (end Keycloak sessions):** this job cannot log anyone out, because it only reads. It relies on the probe's evidence that a refresh-token grant for a disabled account is refused. If the probe instead showed that refresh still works after a disable, record it as a stop: return `## CHECKPOINT REACHED` with that answer. The entity disable and the session stop still cut the working session, so say what remains (a Keycloak session that can mint tokens for nothing behind OpenBao).

**`access-revocation.hcl`:**
- `list` on `identity/entity/name`;
- `create` only on `kv/data/site/revocation-requests/*`, with no read, update, delete or list. This is the create-only pattern of 71-12's inbox: the job can file a request and nothing else there;
- `read` and `update` on `identity/entity/name/keycloak-*` and on `identity/entity/name/guest-*`, with `allowed_parameters` limited to `disabled = [true]`;
- nothing else, with a comment saying why.

**`apply.mjs`:** add the policy, and the jwt role `access-revocation` bound like `guest-expiry`: `bound_audiences` and `bound_claims.azp` are `sterling-access-revocation`, `token_ttl` 5 minutes, not renewable, policy `access-revocation`.

**`revoke.mjs`**, exporting `reconcileAccess({ keycloak, bao, sessions, log })`. Run as `reconcile --in-cluster`, it reads its settings from the environment as `guests.mjs expire --in-cluster` does, with its own client id and secret file, then:
1. **Keycloak users.** Read `GET users/count`, then every user through paged `GET users?briefRepresentation=true`, giving a map from id to `enabled` and `email`. The list is complete only when the pages add up to the count.
2. **Entities.** List the OpenBao entity names and read each one. Skip names that are not `keycloak-<id>` or `guest-<id>`, and skip entities already disabled.
3. **Revoke.** For each remaining entity, revoke when:
   - the user is in the map and disabled (reason `keycloak-disabled`); or
   - the user is absent from a complete list and `GET users/<id>` answers 404 (reason `keycloak-removed`).

   Reasons are path-safe tokens, because they become part of the request path (71 D-22; 47-20 uses `guest-ended`).

   An absent user in an incomplete list is never revoked; that run exits non-zero. Revoking means setting `disabled: true` on the entity.
4. **Credentials to revoke (71 D-22).** For each person revoked in step 3, file one request at `kv/data/site/revocation-requests/<entity>-<reason>`, written with `cas: 0` so a second run finds it filed and moves on.
   - Format `sterling-revocation-request/1`, the one format 47-20 also writes: the entity name, the Keycloak id, the reason (`keycloak-disabled` or `keycloak-removed`), the time seen and the job name (`sterling-access-revocation`). No secret is in it.
   - 71-12's revocation card resolves the person through the OpenBao entity and the people directory. It shows each officer only the credentials they issued to that person (from the issued register), and the officer revokes or suspends in their own session after a step-up.
   - The issuer step-up role deletes the request once every credential issued to that person is revoked or suspended. This job never deletes it.
   - The job never signs or edits a status list.
5. **Sessions.** List the Theia Cloud Sessions and stop each one whose `spec.user` is not the email of an enabled user in the map. When the list is incomplete, stop only those owned by a user who is explicitly disabled.
6. **Output and exit.** Print one line per action: entity or session, reason, never a token. Revoke the job's own token at the end. Exit non-zero when any side failed, still trying the other side. `--no-sessions` skips Kubernetes, for runs outside a cluster.

- one revocation request filed per revoked person and reason, written with `cas: 0`; a second run files nothing new; the request holds no credential, key or token;
