  <behavior>
    - Same-record stale writers receive a conflict and permitted current version. Competing stock allocations cannot oversubscribe, and a failed transfer changes neither side.
    - At crash before commit there is no half-effect. At crash after commit before ack the same request returns the same receipt with one state change and one signed event/outbox.
    - Out-of-order application and durable review are allowed, but an unresolved position or retry pins the checkpoint.
    - Worker A starts work, its lease expires, worker B reclaims with a newer fence, and A resumes. A cannot apply state, insert a disposition, publish an outbox entry, or move the checkpoint.
  </behavior>
  <action>
    Add the shared interactive/bulk transaction, per D-04 and D-05. Use expected versions for ordinary edits. For assignment, return, reservations and transfers lock stock bucket and invariant rows in documented table-then-stable-key order, using identical order in every caller. Keep transfer atomic. Use row uniqueness and balance constraints, and require enough quantity under lock. Recheck expected version, signed policy revision, scoped grant, approval validity and covered before/after bytes under lock. Sign the canonical transition through the issuer boundary before locking, then recompute and re-sign if the checked inputs diverge. Avoid network, image transfer or human review under locks.
    Commit effective state, exact signed event, idem receipt and outbox plus any now-contiguous partition cursor together. Match dedup by tenant/source plus event id/version and hash; handle contradictory claims by field authority and evidence review, without a newer source timestamp overwriting verified custody. Retry deadlocks, serialization failures and transient lock timeouts with bounded delay and jitter; restart the full transaction and release persistent conflicts to retry/review. Keep takeover serialized against the same row. Recheck validity before commit or condition the final claim/disposition write on the expected active fence and abort the whole transaction if zero rows qualify. The fence covers success, conflict review and rejection, and cursor movement. Add a deterministic two-worker PostgreSQL fixture using barriers with A suspended before the application transaction, expired on the database clock, B claiming a new generation and committing, then A resuming. Compare signed facts, receipts, outbox, state, cursor and dispositions to B alone. Repeat with B stopped after reclaim but before applying, so an old worker cannot sneak through by finding no existing receipt.
