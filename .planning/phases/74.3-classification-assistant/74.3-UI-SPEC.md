This file satisfies the UI gate named in 74.3-CONTEXT D-13 and in the precondition of 74.3-05 Task 1.

Sources read: 74.3-CONTEXT.md (D-01 to D-30, owner positions), the 14 plans (in full: 05, 06, 08, 09, 10, 11, 12; must-haves of 01, 03, 07, 13, 14), 70.1-CONTEXT.md (owner decision table D1 to D14, D-04 to D-21), `.planning/research/ai-classification/RESEARCH.md` (3.4, 3.10, 3.11, 4.1, 4.4, 5.1, 6.1 to 6.5, 10), `.planning/research/coherence/GLOSSARY.md` and `EXPERIENCE.md`, `src/test/copyLint.test.ts`, 46-CONTEXT D-15, D-16, D-21, D-25, D-43, 46-07 (step-up refusal text), 71-12 (issue card pattern), 71-13 (credential cache sentences), 32.1-CONTEXT "Version safety" (no user text tells a person to update), 48-CONTEXT D-09 (no capacity figures), and the native workbench on `origin/feat/phase-46-wave-1` (PR #187): `sterling-welcome-module.ts` (the 10-icon rail), `sterling-portfolio.css`, `sterling-resource-inventory-module.ts` and `.css`, `sterling-work-areas.css`, `sterling-compliance-module.ts`, `session-identity-frontend-module.ts`, `common/session-identity.ts` (`stepUpUrl`), and the 62 UI-SPEC for format.

## Spacing Scale

Every margin, padding and gap in the new surfaces is one of 4, 8, 16, 24, 32, 48 or 64 px. There is no 12px step.

| Token | Value | Usage |
|---|---|---|
| xs | 4px | Icon to text gap; gap between a field label and its control; gap between rows in a list; badge vertical padding (0) and the gap inside a badge |
| sm | 8px | Gap between bases rows and between buttons; badge and chip horizontal padding; padding inside the label block and notices; panel horizontal padding and section gap under 320px panel width; list row padding (8px all round) |
| md | 16px | Panel horizontal padding and gap between panel sections from 320px up; dialog body padding; Reviews card padding and gap; Reviews page row gap |
| lg | 24px | Space above the panel footer; dialog section breaks; gap between the Reviews list and detail columns |
| xl | 32px | Bottom padding of the panel scroll area; empty-state top padding; Reviews page top padding |
| 2xl | 48px | Reviews page bottom padding (matches the 46 pages) |
| 3xl | 64px | Not used in this phase |

Fixed sizes (not spacing):

| Item | Value |
|---|---|
| Panel minimum width | 240px; nothing scrolls horizontally from 240px up |
| Buttons, inputs and selects (panel, dialogs and Reviews page) | 32px minimum height; icon-only buttons 32px by 32px. The Reviews page overrides the reused 34px (see "Reviews page overrides") |
| Minimum target | 24px by 24px everywhere (WCAG 2.5.8); links in the bases list get 4px vertical padding to reach it |
| Dialog width | `min(480px, 90vw)`; Request dialog `min(512px, 90vw)` |
| Reason field | 4 rows, resizes vertically only |
| Icon size | 16px (codicon default); the panel empty-state icon 32px |

Named exceptions (not spacing tokens): 1px borders and dividers; 2px focus outline with 2px offset (existing 46 rule); 3px inline-start accent bar on the label block (existing `.sterling-portfolio-source` precedent). Radii follow the existing Sterling CSS: 5px buttons, inputs and rows, 8px the label block and notices, 12px badges and cards. Shadow geometry is listed under "Elevation" and is not spacing.

## Typography

Exactly 3 sizes and 2 weights across the panel, the dialogs and the Reviews page (the page's reused sizes are overridden; see "Reviews page overrides"). The 46 pages use weights 650 and 730 in places; the new surfaces use 600, which reads the same at these sizes.

12px and 13px are merged into one 13px size. A 1px step does not carry meaning in a narrow panel, and Theia's own UI text is 13px. Secondary text (badges, chips, the item name line, the trust line, hints, the character counter, `dt` captions, times) differs from body text by colour (`--theia-descriptionForeground`), never by size.

| Role | Size | Weight | Line height | Used for |
|---|---|---|---|---|
| Body | 13px | 400 | 1.5 | All running text, secondary text in muted colour, bases, notices, suggestions, buttons, form fields, list rows, badges, chips, dialog text |
| Heading | 16px | 600 | 1.25 | Panel section headings ("Why", "Suggestions"), dialog titles, Reviews section headings, detail titles and field legends |
| Display | 20px | 600 | 1.25 | The label itself in the panel's label block and in the Affirm dialog; the Reviews page `h1` |

Weight 600 is also used for Body-size field labels and the request id in a row. No other weight.

Rules: no italics; ids, hashes and fingerprints in the editor font at 13px; numbers `font-variant-numeric: tabular-nums`; every text container `overflow-wrap: anywhere`; the item name clamps to 2 lines with the full name in `title`; nothing else truncates. Copy must tolerate 30% longer text (a later French pass) without layout change.

### Times

Every time on these surfaces is written plainly (owner-confirmed 2026-11-24, Q12): day, short month, year, 24-hour time and zone, in that fixed order, for example "24 Nov 2026 14:02 UTC". Build it from `Intl.DateTimeFormat('en-CA', { day: '2-digit', month: 'short', year: 'numeric', hour: '2-digit', minute: '2-digit', hourCycle: 'h23', timeZoneName: 'short' }).formatToParts(date)` and join the parts in this order, so it never changes with the browser's locale. The zone is the session's zone; the `time` element's `datetime` holds the ISO value. Ages in rows ("9 days ago") stay plain words, with the full time in `title`.

Accent reserved for (explicit list):
1. Focus ring on every focusable element: `outline: 2px solid var(--theia-focusBorder); outline-offset: 2px` (existing 46 rule).

3. The one primary button of the visible state: "Affirm label", "Affirm and submit", "Affirm and release", "Send request", "Lower label", "Approve lower label", "Run evaluation", "Sign report", "Sign and show next item" or "Sign and finish audit". At most one per surface state.

## Elevation (owner direction 2026-11-24: cards look lifted)

The owner chose the original 74.3 theme with the cards inside each panel or page looking lifted off the surface beneath. Elevation is decoration only: every state still comes from words, icons and badges, and every card keeps its 1px border, so no edge or meaning depends on a shadow.

### Tokens

Set once on the root of each new widget (`.sterling-classification-panel`, `.sterling-classification-dialog`, `.sterling-classification-reviews`), built only from Theia theme variables. Theia's dark, light and high contrast themes are told apart by the theme-type class Theia puts on `body`: `theia-dark`, `theia-light`, `theia-hc` and `theia-hcLight` (Theia 1.77, `color-application-contribution`).

| Token | Value | Used for |
|---|---|---|
| `--sterling-card-surface` | dark themes: `color-mix(in srgb, var(--theia-editorWidget-background) 94%, var(--theia-foreground) 6%)`; light themes: `var(--theia-editor-background)` | Card background, a little lighter than the panel or page beneath. On the Reviews page in a light theme, where the page is already `--theia-editor-background`, the shadow and the 1px border carry the lift |
| `--sterling-card-highlight` | dark themes: `inset 0 1px 0 color-mix(in srgb, var(--theia-foreground) 10%, transparent)`; light themes: `inset 0 0 0 transparent` | 1px top highlight edge so the lift reads on dark surfaces |
| `--sterling-elevation-1` | `0 1px 2px var(--theia-widget-shadow), 0 4px 12px color-mix(in srgb, var(--theia-widget-shadow) 50%, transparent)` | Resting cards: a tight contact shadow plus a softer, wider ambient one |
| `--sterling-elevation-2` | `0 2px 4px var(--theia-widget-shadow), 0 8px 24px color-mix(in srgb, var(--theia-widget-shadow) 60%, transparent)` | Hovered interactive cards, the selected request row, dialogs |
| `--sterling-lift-motion` | `box-shadow 120ms ease-out, transform 120ms ease-out` | Hover transition; `none` under `prefers-reduced-motion: reduce` |

```css
.sterling-classification-panel, .sterling-classification-dialog, .sterling-classification-reviews {
  --sterling-card-surface: var(--theia-editor-background);
  --sterling-card-highlight: inset 0 0 0 transparent;
  --sterling-elevation-1: 0 1px 2px var(--theia-widget-shadow), 0 4px 12px color-mix(in srgb, var(--theia-widget-shadow) 50%, transparent);
  --sterling-elevation-2: 0 2px 4px var(--theia-widget-shadow), 0 8px 24px color-mix(in srgb, var(--theia-widget-shadow) 60%, transparent);
  --sterling-lift-motion: box-shadow 120ms ease-out, transform 120ms ease-out;
}
body.theia-dark :is(.sterling-classification-panel, .sterling-classification-dialog, .sterling-classification-reviews) {
  --sterling-card-surface: color-mix(in srgb, var(--theia-editorWidget-background) 94%, var(--theia-foreground) 6%);
  --sterling-card-highlight: inset 0 1px 0 color-mix(in srgb, var(--theia-foreground) 10%, transparent);
}
.sterling-classification-card { background: var(--sterling-card-surface); border: 1px solid var(--theia-panel-border, var(--theia-widget-border)); box-shadow: var(--sterling-card-highlight), var(--sterling-elevation-1); }
.sterling-classification-card.is-interactive { transition: var(--sterling-lift-motion); }
.sterling-classification-card.is-interactive:hover, .sterling-classification-card.is-interactive[aria-pressed='true'] { box-shadow: var(--sterling-card-highlight), var(--sterling-elevation-2); transform: translateY(-1px); }
@media (prefers-reduced-motion: reduce) {
  .sterling-classification-card.is-interactive { transition: none; }
  .sterling-classification-card.is-interactive:hover, .sterling-classification-card.is-interactive[aria-pressed='true'] { transform: none; }
}
body:is(.theia-hc, .theia-hcLight) .sterling-classification-card { box-shadow: none; border-color: var(--theia-contrastBorder); }
@media (forced-colors: active) { .sterling-classification-card { box-shadow: none; border: 1px solid var(--theia-contrastBorder, currentColor); } }
```

### What is lifted

| Surface | Card | Level |
|---|---|---|
| Panel | The label block | elevation-1 |
| Panel | Each notice (raise, approval result, spill, out of date, cell access) | elevation-1; the spill notice keeps its error-coloured border |
| Panel | Each suggestion row (it holds a button) | elevation-1, not interactive itself |
| Panel | The Why section, actions, trust line, record and footer | not lifted: they sit on the panel surface, so the lifted cards stand out |
| Dialogs (Affirm, Raise, Request, review confirmations) | The dialog itself | elevation-2 (Theia's dialog frame keeps its own shadow; this token replaces it on these dialogs so they match); the record preview and "Who must approve" boxes inside are elevation-1 |
| Reviews page | The header card (`.sterling-portfolio-source`) and the section cards (`.sterling-portfolio-layout > section`) | elevation-1 |
| Reviews page | Request, spill and audit rows (`.sterling-portfolio-row`) | elevation-1 resting; elevation-2 and 1px lift on hover and when selected (`aria-pressed="true"`, which also keeps its `--theia-focusBorder` border) |
| Reviews page | The evaluation report table | inside its section card; not lifted again |

Rules:
- Cards never nest more than one level: a lifted card inside a lifted card (the record preview inside the Affirm dialog) uses elevation-1 inside elevation-2, never more.
- Hover lift is only on interactive cards (rows that select). Buttons keep Theia's own button styles.
- Shadow offsets and blurs (1, 2, 4, 8, 12 and 24px) are shadow geometry, not spacing, and are named here so the spacing check ignores them. The 1px hover lift is motion, not layout: it never moves neighbouring content.
- In Theia's high contrast themes and under `forced-colors: active` the shadows are removed and a `--theia-contrastBorder` border carries the edge.

   - a second line (Body) for markings and handling in words, joined by " · ": export markings by their glossary words ("ITAR", "Controlled goods (Canada)", "US export-controlled (EAR)"), other compartments by their policy name, and handling as "Keep on this system" (`local-only`) and "No agent tools" (`no-agent-tools`); omitted when empty;
   - the state line (Body): state icon plus the state sentence from the copy table;
   - the trial chip when the item's current or proposed level is in its trial period.
3. **Notice area**: at most one notice, by priority: possible spill, approval result, raise notice, out of date, cell access change. A notice is a lifted card (elevation-1, 8px radius) with an icon, a sentence, and at most one link or button.
4. **Why** (Heading): the bases list (`ul`), one row per basis, in the order floors first (source, marking, guide, detector, compilation), then the assistant's judgement. Each row: icon, words, and a link where one exists. More than 5 rows: first 5 plus "Show {n} more reasons" (button, `aria-expanded`; when open it reads "Show fewer reasons").
5. **Suggestions** (Heading, only when any): each row a lifted card (elevation-1) holding a sentence and one secondary button ("Accept label" for a suggested higher label, "Add marking" for a suggested compartment, "Add handling" for a suggested handling flag, "Request a lower label" for a could-be-lower line).
6. **Actions** (wrap; full width under 280px): primary "Affirm label", secondary "Raise label", secondary "Request a lower label". A disabled action uses `aria-disabled="true"` and shows its reason as text directly under the row, linked by `aria-describedby`.
7. **Trust line** (muted): "Proposed with {model} · Runs on {place}" or "Rules only: {cause}", then the "Show trust details" disclosure (`button[aria-expanded]`; open: "Hide trust details") holding: model approval id, endpoint, calibration id, second check result, prompt template fingerprint (editor font). These admin words are allowed only inside this disclosure (glossary rule 1 allowed context: details pane).
8. **Record** (muted, only when affirmed): "Classified by {person}, {position}. Assisted by {model}." and "Affirmed {date}".
9. **Footer**: "Open Classification Reviews" link, only for people who hold a reviewing role.

Reading order puts Why before the actions on purpose: a person meets the basis before the Affirm button (research 3.11, automation bias).

## Item states

The state machine is 74.3-05's `itemState.ts`: `draft`, `assessing`, `proposed`, `unassessed`, `affirmed`, `lower-requested`. The panel shows eight visible states; three are overlays on that machine (raised, frozen, out of date). Exact copy for every cell is in the Copywriting Contract.

| Visible state | Machine state or overlay | Badge | Icon | Primary | Other actions |
|---|---|---|---|---|---|
| Draft | `draft` | "Draft" | `edit` | none | Raise label |
| Checking | `assessing` | "Checking" | `sync` | none (Affirm `aria-disabled` with reason) | Raise label |
| Proposed | `proposed`, outcome `suggested`, `kept` or `none` | "Proposed" | `lightbulb` | Affirm label | Raise label, Request a lower label, Accept label or Add marking on each suggestion |
| Raised, with notice | `proposed`, outcome `auto-raised` | "Raised" | `arrow-up` | Affirm label | Raise label, Request a lower label (named in the notice) |
| Rules only | `unassessed` | "Rules only" | `checklist` | Affirm label (records "no assistant") | Raise label, Request a lower label |
| Under review | `lower-requested` | "Under review" | `clock` | none | Raise label; Affirm label at the current label (owner decision Q6) |
| Possible spill | any state with an unresolved `possible-spill` exception | "Possible spill" | `stop-circle` | none | none; Affirm, Raise and Request are hidden; editing stays open |
| Out of date | unsaved edits, or `draft` reached by editing an affirmed item | "Out of date" | `history` | none until saved; then the state that follows | Raise label |
| Affirmed | `affirmed` | "Affirmed" | `pass` | none | Raise label, Request a lower label |

Transitions the person sees:
- Save: Draft or Out of date becomes Checking. Checking always ends in Proposed, Raised or Rules only; it never waits forever (D-12, timeout gives Rules only).
- A result for older content is dropped silently and the panel keeps showing Checking for the newer save (70.1 D-14).
- Rules only becomes Checking again when a listed model server returns; the result can only raise (owner decision D9 default). The panel then shows Raised or Proposed; if the person had already affirmed, the label stays affirmed unless the result raises it, in which case the item shows Raised and asks for a new affirmation before the next submit or release.
- Affirm: Proposed, Raised or Rules only becomes Affirmed.
- Edit after Affirmed: Out of date, label kept; the next submit or release asks again.
- Request a lower label: becomes Under review, label unchanged. Approval verified: Affirmed at the lower label. Refused or unverifiable: Affirmed at the same label.
- Possible spill: frozen until the security officer resolves it. "Not a spill" unfreezes and keeps the label; "handled" keeps it frozen.

## Interaction contracts

### Panel follows the active editor

- The panel shows the item in the active editor. With no classifiable item active it shows the empty state.
- The panel never takes focus on its own. A raise notice or a possible spill reveals the panel without focusing it (`activate: false`).
- Nothing on the panel blocks typing. Every call is asynchronous (D-08).
- The status bar entry shows "$(tag) {level label} · {badge}" for the active item (scale name plus level only, never compartments, markings or handling), for example "$(tag) Canada, Classified: Secret · Proposed"; "$(stop-circle) Possible spill" when frozen; "$(sync~spin) Checking" while checking. Its tooltip is the state sentence. Clicking it runs "Show Classification". It never shows a file name.

### Raise, Accept label and Add marking

- "Raise label" opens the Raise dialog: a radio group "Choose a higher label" listing only levels above the current one on the item's scale, and checkboxes "Keep on this system" and "No agent tools" when not already set. Buttons "Keep current label" and primary "Raise label". Nothing lower is ever offered.
- "Accept label", "Add marking" and "Add handling" on a suggestion apply that one addition. None of them ever appears on a lowering.
- Both go through the backend, which re-checks with the engine (T-74.3-19). The frontend never computes a label.

### Affirm (74.3-06)

- Affirm is asked only at "Affirm label" in the panel, and at Submit, Release and Release to observers when no valid affirmation exists for the current content and label. Never on save (research 3.11, T-74.3-27).
- From Submit or Release the dialog's primary reads "Affirm and submit" or "Affirm and release", and the act runs right after the signature.
- Hosted session: signs with the session's certified key; no passkey per affirmation. If the session key is not yet certified, the dialog shows the one-time confirm state first (copy table), with "Confirm with your passkey or security key"; the page reloads through `stepUpUrl()` and returns to the same item; the person presses Affirm again. Single computer: signs with the device key, no prompt.
- Enter does not affirm unless focus is on the primary button (override `AbstractDialog`'s Enter-to-accept). Initial focus goes to the dialog title, so a stray Enter cannot sign.
- Refused while Checking (reason shown) and while frozen (reason shown). Refusals cross the RPC as data with their sentence (46 D-16).

### Request a lower label (74.3-09)

- The dialog always shows "Who must approve" before the person can send.
- If the person's own authority covers the change (`own-items` up to the current level), the primary reads "Lower label": one step-up, then the person's own signed lowering is applied directly (owner decision Q4). Otherwise the primary reads "Send request".
- The reason is stored with the item at its label; only its hash travels (D-18). The reason text is never shown in a toast, the status bar or a log.
- If the person edits the item after sending, the panel says the request covers the earlier version (copy table); the approval will not verify for the new content (planner note P3).
- With no organization server (single computer): the request is recorded; the item does not move to Under review (owner decision Q5); the panel shows the local sentence.

### Classification Reviews: step-up and reloads

- Every section opens in the locked state with one button "Confirm with your passkey or security key". The step-up is a full-page sign-in (`stepUpUrl()`), so the helper line says the page reloads.
- Before leaving, the page saves only `{ section, rowId }` in `sessionStorage` (ids, never content). After the return it reopens the section, selects the row, moves focus to the detail heading, and never runs a signed action by itself: the person presses Approve or Sign again.
- One confirmation unlocks the lists for the step-up window. Approve and Sign need a fresh step-up; if the window has passed, the press gives the step-up refusal sentence with the confirm button in the same place.
- Lists are never cached across sessions (74.3-09 Task 2).

### Notifications

- A raise of an item that is not in the active editor: info notification "A label was raised to {level label}." with action "Show label". It never names the file (a file name can carry a code word).
- A possible spill: warning notification "Possible spill. Sharing of one item is stopped." with action "Show label". Never a file name, a basis or a label above system-high.

### Shadow (trial) indicators (74.3-11)

- The panel shows the trial chip when the current or proposed level is in trial: "Trial at {level}: suggestions only".
- In trial a model judgement is a suggestion row with the trial sentence and "Accept label"; signed rules (markings, code words, guide and compilation rules) still apply and say so (70.1 D-10).
- The Model evaluation section shows each level's mode in a table: "Trial (suggests only)" or "In use (raises labels)", with role start date and audited recall against target.

### Observers and the blind audit

- Observer sessions never receive proposals, bases, rationales or the trust line (33.1 D-35, D-40). The panel is not registered for observer views.
- While a reviewer has an item open from the Blind audit section, the panel for that item shows only the hidden-during-audit sentence (planner note P5).

### Assistant off (D-28)

With no organization policy carrying `classification@1`, the panel shows the assistant-off empty state, the status bar entry is not shown, the editor title action opens the panel to that state, Affirm is not asked at Submit or Release, and Set Label and Lower This Chat's Label work as today.

## Copywriting Contract

Rules for every sentence here: plain short words; "your organization", never a provider name in front of "organization"; no em-dash; never "the AI classified" or "the AI decided"; the assistant "proposed", a named person "affirmed"; no sentence tells a person to update anything; no capacity figure, response time or count of people a server supports; no classified content (no item text, rationale, fact value, file name or label above system-high) in a notification, the status bar, a request, a spill report or a log; labels always as scale name plus level. `{label}` is the full label as `labelShown` gives it (scale name plus level, then export markings, compartments and handling in words) and appears only on the item's own surfaces (the panel and the dialogs about that item). `{level label}` is scale name plus level only (`labelKeyShown`, no compartment, marking or handling) and is the only form allowed in notifications, the status bar, the Reviews lists and any count or summary line, because a compartment name can itself be a code word. Every button is a verb plus a noun ("Close without affirming", never "Cancel"; "Reload label", never "Retry"). Every sentence is a `*_TEXT` constant in `workbench/extension/src/common/classification.ts` (or the named extension file), and the copy lint covers it. Placeholders in braces are filled by code. The example people and items are fictional.

## Security rules for the UI (checked in tests)

1. No classified content leaves the item's surfaces: notifications, the status bar, request and spill-report payloads, the Reviews lists and every log line carry only ids, level labels (scale name plus level, at or below system-high), basis kinds and refs, people and times; never a compartment or marking name. A test renders each notification and status text with a fixture whose file name and content hold a fictional code word and asserts it is absent.
2. The AI never appears to set person attributes: no surface shows, suggests or pre-fills clearance, nationality, organization, compartment holdings, export eligibility, agreements or role authority. The cell notice counts people who lose access because of the new label, computed by `mayRelease`, and never says the assistant decided anything about them. A test greps the `*_TEXT` constants for "assistant" next to any person-attribute word.
3. Lowering always shows who must approve: the Request dialog's "Who must approve" box, the Under review state sentence, the could-be-lower suggestion, the Set Label refusal and the spill "not a spill" review all name the approver. A test asserts each of these strings contains its approver words.
4. The frontend never offers a lower label except inside the Request dialog, and the backend re-checks every raise, affirmation and lowering.
5. No capacity figures in this phase's copy or docs (48 D-09). Measured metrics (recall, over-classification, changes by people, review load, time from save to proposal) appear only inside the signed evaluation report and the Model evaluation section that shows it, as your organization's own measurements, never as a claim about what a server or site can handle.

2. **Q2, no new rail icon:** the rail keeps its 10 icons; the panel is a right-side view reached from the editor title tag icon, the status bar label and the palette, and Classification Reviews from the panel footer. Alternative: an 11th rail shortcut "Classification" (icon `tag`).

## Planner notes (conflicts and gaps found; the PLAN files are not edited here)

These come from tracking the item state machine against the plans. The plan reviser decides; each names the plan.

- **P1 (74.3-05 Task 3, coherence):** the trust line text "passport <id>" puts a "never on main screens" glossary word on the panel; this spec uses `trust.model` and keeps the id under Show trust details (Q9).
- **P2 (74.3-13 Task 2, coherence):** the notice "2 holders will lose access at the next key" uses key-group words the glossary keeps off screens; this spec uses `raiseNoticeCell` ("2 people lose access under your organization's access rules").
- **P3 (74.3-05 Task 2 and 74.3-09, state machine):** `lower-requested` has no `edit` transition. An edit changes the content hash, so the approval can never verify; the item needs `edit` from `lower-requested` to `draft` (label kept), with `request.editedSince` shown. Q6's default also needs `finalize` from `lower-requested`.
- **P4 (74.3-10, stuck state):** the security officer's resolution is recorded in the officer's session, but no plan says how it reaches the reporter's item, so the reporter's item can stay frozen forever. Recommended: the resolve step writes a signed resolution to the reporter's `classification-inbox` (as 74.3-09 does for approvals), and the reporter's backend applies it after verifying, showing `spill.notASpill` or `spill.handled`.
- **P5 (74.3-12 Task 2, blindness):** a reviewer who opens an audit item in the editor would see the panel's proposal. The panel must show `hiddenForAudit` for that item while the audit card has it open.
- **P6 (74.3-09 Task 1, stuck state):** in local mode the plan records the request and moves the item to `lower-requested`, which nothing resolves. Q5's default avoids the stuck state.
- **P7 (74.3-09 Task 1):** a site with no `classificationOfficers` accepts requests nobody can read. The panel shows `lower.who.none` and disables Send; the backend needs to read whether any officer is listed.
- **P8 (74.3-06 Task 3):** Theia's `AbstractDialog` accepts on Enter by default; the Affirm dialog must override it (Q8).
- **P9 (74.3-05, 74.3-10):** notifications and the status bar must never carry a file name, a basis text or a label above system-high (security rule 1).
- **P10 (existing, outside this phase):** Set Label shows handling flags as raw tokens today (`labelParts` in `src/services/gateCommands.ts`). Not changed here; noted for the coherence review.
- **P11 (glossary):** add, in the plan that first shows them: "classification assistant", "trial" (Q1), "classification authority", "Classification Reviews", "Keep on this system", "No agent tools", "possible spill", "affirm", "proposed label", "request a lower label", "Rules only".
- **P12 (74.3-05 Task 2, state machine):** `itemState.ts` has no `raise` or `accept` event, yet the panel offers Raise label, Accept label, Add marking and Add handling in several states. Recommended: one `raise` event (person raise or accepted suggestion, label only goes up) allowed in every state except while frozen; in `draft`, `proposed` and `unassessed` it keeps the state with the higher label; in `affirmed` it returns the item to `proposed`, because the affirmation covered the old label (see P14); in `lower-requested` it moves to `proposed` and the pending request is void, because its `from` label no longer matches. The property test's "no transition lowers a label" still holds.
- **P13 (74.3-05 Task 2):** the machine allows request-lower only from `proposed` and `unassessed`, but research 6.5 and this spec offer Request a lower label on an Affirmed item (the common case: a person affirms, then finds the label too high). Add `affirmed` to `lower-requested`, label unchanged.
- **P14 (74.3-05 Task 2, owner decision D9):** an item affirmed while `unassessed` ("no assistant") must still be re-queued when a listed endpoint returns. Add `affirmed` plus `endpoint-back` to `assessing` for items whose affirmation records no assistant. A result that raises voids the affirmation (to `proposed` with the raise notice, and the next submit or release asks again); a result that does not raise returns the item to `affirmed` with its affirmation intact.
- **P15 (74.3-10 with 74.3-06):** the freeze is "the item's unresolved exception" but no plan says where it is stored or how it sits on top of the six states. Recommended: stored with the item (the workspace store `.near-ai/state/classify/` for files, the cell for staff products), keyed by item id, never in the label map; it is an overlay that every state shows as Possible spill and that blocks affirm, submit, release and share in every state while editing and saving continue (the machine keeps moving underneath, and a new revision still above system-high writes no second report); it is cleared only by a verified "not a spill" resolution delivered as P4 describes; "handled" keeps it until a classification authority's lowering or removal.
- **P16 (74.3-05 Task 1):** the Out of date state for unsaved changes (`outOfDateUnsaved`) needs the editor's dirty state. Recommended: the frontend derives it from Theia's `Saveable` dirty flag for the active editor, with no RPC field and no content sent; 74.3-05 should name this input to the panel. If the plan prefers not to, drop `outOfDateUnsaved` and keep only `outOfDateEdited`.
- **P17 (74.3-09 must-haves):** the second must-have says the authority's card lists requests "with item id, labels and the reason", but Task 2's action (and this spec) shows the reason only when the requester's item store is readable to the authority, otherwise "Reason kept with the item". Align the must-have to the action.
