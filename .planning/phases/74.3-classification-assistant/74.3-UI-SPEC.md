## Spacing Scale

Every margin, padding and gap in the new surfaces is one of 4, 8, 16, 24, 32, 48 or 64 px. There is no 12px step.

| Token | Value | Usage |
|---|---|---|
| xs | 4px | Icon to text gap; caption to value gap in form blocks; gap between a field label and its control; stamp horizontal padding and the gap inside a stamp; the hatched margin of a stopped stamp; strip vertical padding |
| sm | 8px | Gap between bases lines and between buttons; strip horizontal padding; padding inside notices; panel padding; section gap under 320px panel width; register line padding (8px all round); caption to its rule |
| md | 16px | Panel horizontal padding and gap between panel sections from 320px up; dialog body padding; Reviews card padding and gap; Reviews page row gap |
| lg | 24px | Space above the panel footer; dialog section breaks; gap between the Reviews list and detail columns |
| xl | 32px | Bottom padding of the panel scroll area; empty-state top padding; Reviews page top padding |
| 2xl | 48px | Reviews page bottom padding (matches the 46 pages) |
| 3xl | 64px | Not used in this phase |

Fixed sizes (not spacing):

| Item | Value |
|---|---|
| Panel minimum width | 240px; nothing scrolls horizontally from 240px up |
| Buttons, inputs and selects (panel, dialogs and Reviews page) | 32px minimum height; icon-only buttons 32px by 32px. The Reviews page overrides the reused 34px (see "Reviews page overrides") |
| Minimum target | 24px by 24px everywhere (WCAG 2.5.8); links in the bases list get 4px vertical padding to reach it |
| Dialog width | `min(480px, 90vw)`; Request dialog `min(512px, 90vw)` |
| Reason field | 4 rows, resizes vertically only |
| Icon size | 16px (codicon default); the panel empty-state icon 32px |

Named exceptions (line widths, not spacing tokens): 1px hairline frames and rules; 2px focus outline with 2px offset (existing 46 rule); 2px solid frame of a stopped stamp; 3px `double` rule for final stamps and the final strip (a double border needs 3px to draw two lines). The hatched margin inside a stopped stamp or strip is 4px (the xs token). Radii (SDL 2): 0 for frames, strips, stamps, notices, registers and form blocks; 2px for buttons, inputs and selects only. No shadows.

## Typography

Exactly 4 sizes and 2 weights across the panel, the dialogs and the Reviews page (the page's reused sizes are overridden; see "Reviews page overrides"). Applies SDL 6. The 46 pages use weights 650 and 730 in places; the new surfaces use 600.

The previous revision merged 12px into 13px because a 1px step carried no meaning. The caption role below is different in kind, not by a pixel: it is uppercase, tracked and semibold, and it names a field rather than saying something, as a printed form's field captions do (SDL 4). Muted running text (the trust line, hints, the counter, times) stays at 13px and differs by colour only.

| Role | Size | Weight | Line height | Case and tracking | Used for |
|---|---|---|---|---|---|
| Caption | 11px | 600 | 1.4 | uppercase by CSS, `letter-spacing: .08em` | Field captions above values, section captions (followed by a hairline rule: "BASED ON", "SUGGESTIONS", "WHO MUST APPROVE"), stamps, the trial stamp, the control block captions, table headers in the evaluation report |
| Body | 13px | 400 | 1.5 | normal | All running text, values in form blocks, bases, notices, suggestions, buttons, form fields, register lines, dialog text; the marking strip is Body size at weight 600, uppercase by CSS, `letter-spacing: .12em` |
| Heading | 16px | 600 | 1.25 | normal | Dialog titles, Reviews section titles and detail titles, the panel's empty-state title |
| Display | 20px | 600 | 1.25 | normal | The Reviews page `h1` only |

Weight 600 is also used for Body-size field labels of inputs and the request id in a register line. No other weight. The panel has no Display text: its focal point is the marking strip, which carries weight, case and rules instead of size (SDL 1).

Uppercase is always `text-transform`, never typed copy, so screen readers and the copy lint see the plain words.

Rules: no italics; ids, hashes and fingerprints in the editor font at 13px; numbers `font-variant-numeric: tabular-nums`; every text container `overflow-wrap: anywhere`; the item name clamps to 2 lines with the full name in `title`; nothing else truncates. Copy must tolerate 30% longer text (a later French pass) without layout change.

### Times

Every time on these surfaces is day, short month, year, 24-hour time and zone, in that fixed order: "24 Nov 2026 14:02 UTC". Build it from `Intl.DateTimeFormat('en-CA', { day: '2-digit', month: 'short', year: 'numeric', hour: '2-digit', minute: '2-digit', hourCycle: 'h23', timeZoneName: 'short' }).formatToParts(date)` and join the parts in this order, so the order never changes with the browser's locale. The zone is the session's zone. The `time` element's `datetime` holds the ISO value. Ages in register lines ("9 days ago") stay plain words, with the full time in `title`. Staff date-time groups are owner question Q12.

## Layout

### Classification panel (top to bottom)

The panel is one sheet: no cards, no boxes inside it, sections divided by a caption and a hairline rule (SDL 5). Panel padding 8px; 16px between sections from 320px wide.

1. **Marking strip** (`-strip`, SDL 1), full width, sticky at the top of the panel's scroll area: the item's full label in words, uppercase by CSS, centred: "Canada, Classified: Secret · ITAR · Keep on this system". Export markings by their glossary words ("ITAR", "Controlled goods (Canada)", "US export-controlled (EAR)"), other compartments by their policy name, handling as "Keep on this system" (`local-only`) and "No agent tools" (`no-agent-tools`). Line: `provisional` (dashed foot rule) until affirmed, `final` (double foot rule) once affirmed, `stopped` (hatched ends) while frozen. It is a `p` with `aria-label="Label: {label}"`; it is not a heading.
2. **Item line**: file or product codicon and the item name (2-line clamp, muted), and on its own line the state stamp (`-stamp`, SDL 3) and, when the item's current or proposed level is in trial, the trial stamp. The state sentence follows as Body text.
3. **Notice area**: at most one notice, by priority: possible spill, approval result, raise notice, out of date, cell access change. A notice is a 1px frame, radius 0, with a codicon, a sentence, and at most one link or button. The possible spill notice uses the stopped treatment (2px error frame, hatched margin, text on plain paper).
4. **BASED ON** (caption and rule): the bases register (`ul`), one line per basis, in the order floors first (source, marking, guide, detector, compilation), then the assistant's judgement. Each line: codicon, words, and a link where one exists. More than 5 lines: first 5 plus "Show {n} more reasons" (button, `aria-expanded`; when open it reads "Show fewer reasons").
5. **SUGGESTIONS** (caption and rule, only when any): each line a sentence and one secondary button ("Accept label" for a suggested higher label, "Add marking" for a suggested compartment, "Add handling" for a suggested handling flag, "Request a lower label" for a could-be-lower line).
6. **Actions** (wrap; full width under 280px): primary "Affirm label", secondary "Raise label", secondary "Request a lower label". A disabled action uses `aria-disabled="true"` and shows its reason as text directly under the row, linked by `aria-describedby`.
7. **ASSISTED BY** (caption and rule): the trust line "Proposed with {model} · Runs on {place}" or "Rules only: {cause}", then the "Show trust details" disclosure (`button[aria-expanded]`; open: "Hide trust details") holding, as a form block: model approval id, endpoint, calibration id, second check result, prompt template fingerprint (editor font). These admin words are allowed only inside this disclosure (glossary rule 1 allowed context: details pane).
8. **Control block** (`-control`, SDL 4, only when affirmed), a `dl` with captions above values: CLASSIFIED BY "{person}, {position}"; BASED ON "{basis kind words, joined}"; ASSISTED BY "{model}" or "No assistant"; AFFIRMED "{time}". When not yet affirmed it is absent (the Affirm dialog previews it).
9. **Footer**: "Open Classification Reviews" link, only for people who hold a reviewing role.
10. **Foot strip**: the marking strip repeated at the end of the content whenever the content is taller than the panel (SDL 1), `aria-hidden="true"` because the top strip already names the label.

Reading order puts BASED ON before the actions on purpose: a person meets the basis before the Affirm button (research 3.11, automation bias).

## Item states

The state machine is 74.3-05's `itemState.ts`: `draft`, `assessing`, `proposed`, `unassessed`, `affirmed`, `lower-requested`. The panel shows eight visible states; three are overlays on that machine (raised, frozen, out of date). Exact copy for every cell is in the Copywriting Contract.

| Visible state | Machine state or overlay | Stamp text | Stamp line (SDL 3) | Strip line (SDL 1) | Icon | Primary | Other actions |
|---|---|---|---|---|---|---|---|
| Draft | `draft` | "Draft" | neutral (1px solid) | provisional | `edit` | none | Raise label |
| Checking | `assessing` | "Checking" | provisional (dashed) | provisional | `sync` | none (Affirm `aria-disabled` with reason) | Raise label |
| Proposed | `proposed`, outcome `suggested`, `kept` or `none` | "Proposed" | provisional (dashed) | provisional | `lightbulb` | Affirm label | Raise label, Request a lower label, Accept label or Add marking on each suggestion |
| Raised, with notice | `proposed`, outcome `auto-raised` | "Raised" | provisional (dashed) | provisional | `arrow-up` | Affirm label | Raise label, Request a lower label (named in the notice) |
| Rules only | `unassessed` | "Rules only" | provisional (dashed) | provisional | `checklist` | Affirm label (records "no assistant") | Raise label, Request a lower label |
| Under review | `lower-requested` | "Under review" | waiting (dotted) | final if affirmed, else provisional | `clock` | none | Raise label; Affirm label at the current label (owner question Q6) |
| Possible spill | any state with an unresolved `possible-spill` exception | "Possible spill" | stopped (2px frame, hatched margin) | stopped | `stop-circle` | none | none; Affirm, Raise and Request are hidden; editing stays open |

Transitions the person sees:
- Save: Draft or Out of date becomes Checking. Checking always ends in Proposed, Raised or Rules only; it never waits forever (D-12, timeout gives Rules only).
- A result for older content is dropped silently and the panel keeps showing Checking for the newer save (70.1 D-14).
- Rules only becomes Checking again when a listed model server returns; the result can only raise (owner decision D9 default). The panel then shows Raised or Proposed; if the person had already affirmed, the label stays affirmed unless the result raises it, in which case the item shows Raised and asks for a new affirmation before the next submit or release.
- Affirm: Proposed, Raised or Rules only becomes Affirmed.
- Edit after Affirmed: Out of date, label kept; the next submit or release asks again.
- Request a lower label: becomes Under review, label unchanged. Approval verified: Affirmed at the lower label. Refused or unverifiable: Affirmed at the same label.
- Possible spill: frozen until the security officer resolves it. "Not a spill" unfreezes and keeps the label; "handled" keeps it frozen.

## Interaction contracts

### Panel follows the active editor

- The panel shows the item in the active editor. With no classifiable item active it shows the empty state.
- The panel never takes focus on its own. A raise notice or a possible spill reveals the panel without focusing it (`activate: false`).
- Nothing on the panel blocks typing. Every call is asynchronous (D-08).
- The status bar entry shows "$(tag) {level label} · {stamp text}" for the active item (scale name plus level only, never compartments, markings or handling), for example "$(tag) Canada, Classified: Secret · Proposed"; "$(stop-circle) Possible spill" when frozen; "$(sync~spin) Checking" while checking. Its tooltip is the state sentence. Clicking it runs "Show Classification". It never shows a file name.

### Raise, Accept label and Add marking

- "Raise label" opens the Raise dialog: a radio group "Choose a higher label" listing only levels above the current one on the item's scale, and checkboxes "Keep on this system" and "No agent tools" when not already set. Buttons "Keep current label" and primary "Raise label". Nothing lower is ever offered.
- "Accept label", "Add marking" and "Add handling" on a suggestion apply that one addition. None of them ever appears on a lowering.
- Both go through the backend, which re-checks with the engine (T-74.3-19). The frontend never computes a label.

### Affirm (74.3-06)

- Affirm is asked only at "Affirm label" in the panel, and at Submit, Release and Release to observers when no valid affirmation exists for the current content and label. Never on save (research 3.11, T-74.3-27).
- From Submit or Release the dialog's primary reads "Affirm and submit" or "Affirm and release", and the act runs right after the signature.
- Hosted session: signs with the session's certified key; no passkey per affirmation. If the session key is not yet certified, the dialog shows the one-time confirm state first (copy table), with "Confirm with your passkey or security key"; the page reloads through `stepUpUrl()` and returns to the same item; the person presses Affirm again. Single computer: signs with the device key, no prompt.
- Enter does not affirm unless focus is on the primary button (override `AbstractDialog`'s Enter-to-accept). Initial focus goes to the dialog title, so a stray Enter cannot sign.
- Refused while Checking (reason shown) and while frozen (reason shown). Refusals cross the RPC as data with their sentence (46 D-16).

### Request a lower label (74.3-09)

- The dialog always shows "Who must approve" before the person can send.
- If the person's own authority covers the change (`own-items` up to the current level), the primary reads "Lower label": one step-up, then the person's own signed lowering is applied directly (owner question Q4). Otherwise the primary reads "Send request".
- The reason is stored with the item at its label; only its hash travels (D-18). The reason text is never shown in a toast, the status bar or a log.
- If the person edits the item after sending, the panel says the request covers the earlier version (copy table); the approval will not verify for the new content (planner note P3).
- With no organization server (single computer): the request is recorded; the item does not move to Under review (owner question Q5); the panel shows the local sentence.

### Classification Reviews: step-up and reloads

- Every section opens in the locked state with one button "Confirm with your passkey or security key". The step-up is a full-page sign-in (`stepUpUrl()`), so the helper line says the page reloads.
- Before leaving, the page saves only `{ section, rowId }` in `sessionStorage` (ids, never content). After the return it reopens the section, selects the row, moves focus to the detail heading, and never runs a signed action by itself: the person presses Approve or Sign again.
- One confirmation unlocks the lists for the step-up window. Approve and Sign need a fresh step-up; if the window has passed, the press gives the step-up refusal sentence with the confirm button in the same place.
- Lists are never cached across sessions (74.3-09 Task 2).

### Notifications

- A raise of an item that is not in the active editor: info notification "A label was raised to {level label}." with action "Show label". It never names the file (a file name can carry a code word).
- A possible spill: warning notification "Possible spill. Sharing of one item is stopped." with action "Show label". Never a file name, a basis or a label above system-high.

### Shadow (trial) indicators (74.3-11)

- The panel shows the trial stamp (dashed, `beaker`) next to the state stamp when the current or proposed level is in trial, with this sentence: "Trial at {level}: suggestions only".
- In trial a model judgement is a suggestion row with the trial sentence and "Accept label"; signed rules (markings, code words, guide and compilation rules) still apply and say so (70.1 D-10).
- The Model evaluation section shows each level's mode in a table: "Trial (suggests only)" or "In use (raises labels)", with role start date and audited recall against target.

### Observers and the blind audit

- Observer sessions never receive proposals, bases, rationales or the trust line (33.1 D-35, D-40). The panel is not registered for observer views.
- While a reviewer has an item open from the Blind audit section, the panel for that item shows only the hidden-during-audit sentence (planner note P5).

### Assistant off (D-28)

With no organization policy carrying `classification@1`, the panel shows the assistant-off empty state, the status bar entry is not shown, the editor title action opens the panel to that state, Affirm is not asked at Submit or Release, and Set Label and Lower This Chat's Label work as today.

## Copywriting Contract

Rules for every sentence here: plain short words; "your organization", never a provider name in front of "organization"; no em-dash; never "the AI classified" or "the AI decided"; the assistant "proposed", a named person "affirmed"; no sentence tells a person to update anything; no capacity figure, response time or count of people a server supports; no classified content (no item text, rationale, fact value, file name or label above system-high) in a notification, the status bar, a request, a spill report or a log; labels always as scale name plus level. `{label}` is the full label as `labelShown` gives it (scale name plus level, then export markings, compartments and handling in words) and appears only on the item's own surfaces (the panel and the dialogs about that item). `{level label}` is scale name plus level only (`labelKeyShown`, no compartment, marking or handling) and is the only form allowed in notifications, the status bar, the Reviews lists and any count or summary line, because a compartment name can itself be a code word. Every button is a verb plus a noun ("Close without affirming", never "Cancel"; "Reload label", never "Retry"). Every sentence is a `*_TEXT` constant in `workbench/extension/src/common/classification.ts` (or the named extension file), and the copy lint covers it. Placeholders in braces are filled by code. The example people and items are fictional.

## Security rules for the UI (checked in tests)

1. No classified content leaves the item's surfaces: notifications, the status bar, request and spill-report payloads, the Reviews lists and every log line carry only ids, level labels (scale name plus level, at or below system-high), basis kinds and refs, people and times; never a compartment or marking name. A test renders each notification and status text with a fixture whose file name and content hold a fictional code word and asserts it is absent.
2. The AI never appears to set person attributes: no surface shows, suggests or pre-fills clearance, nationality, organization, compartment holdings, export eligibility, agreements or role authority. The cell notice counts people who lose access because of the new label, computed by `mayRelease`, and never says the assistant decided anything about them. A test greps the `*_TEXT` constants for "assistant" next to any person-attribute word.
3. Lowering always shows who must approve: the Request dialog's "Who must approve" box, the Under review state sentence, the could-be-lower suggestion, the Set Label refusal and the spill "not a spill" review all name the approver. A test asserts each of these strings contains its approver words.
4. The frontend never offers a lower label except inside the Request dialog, and the backend re-checks every raise, affirmation and lowering.
5. No capacity figures in this phase's copy or docs (48 D-09). Measured metrics (recall, over-classification, changes by people, review load, time from save to proposal) appear only inside the signed evaluation report and the Model evaluation section that shows it, as your organization's own measurements, never as a claim about what a server or site can handle.

## Planner notes (conflicts and gaps found; the PLAN files are not edited here)

These come from tracking the item state machine against the plans. The plan reviser decides; each names the plan.

- **P1 (74.3-05 Task 3, coherence):** the trust line text "passport <id>" puts a "never on main screens" glossary word on the panel; this spec uses `trust.model` and keeps the id under Show trust details (Q9).
- **P2 (74.3-13 Task 2, coherence):** the notice "2 holders will lose access at the next key" uses key-group words the glossary keeps off screens; this spec uses `raiseNoticeCell` ("2 people lose access under your organization's access rules").
- **P3 (74.3-05 Task 2 and 74.3-09, state machine):** `lower-requested` has no `edit` transition. An edit changes the content hash, so the approval can never verify; the item needs `edit` from `lower-requested` to `draft` (label kept), with `request.editedSince` shown. Q6's default also needs `finalize` from `lower-requested`.
- **P4 (74.3-10, stuck state):** the security officer's resolution is recorded in the officer's session, but no plan says how it reaches the reporter's item, so the reporter's item can stay frozen forever. Recommended: the resolve step writes a signed resolution to the reporter's `classification-inbox` (as 74.3-09 does for approvals), and the reporter's backend applies it after verifying, showing `spill.notASpill` or `spill.handled`.
- **P5 (74.3-12 Task 2, blindness):** a reviewer who opens an audit item in the editor would see the panel's proposal. The panel must show `hiddenForAudit` for that item while the audit card has it open.
- **P6 (74.3-09 Task 1, stuck state):** in local mode the plan records the request and moves the item to `lower-requested`, which nothing resolves. Q5's default avoids the stuck state.
- **P7 (74.3-09 Task 1):** a site with no `classificationOfficers` accepts requests nobody can read. The panel shows `lower.who.none` and disables Send; the backend needs to read whether any officer is listed.
- **P8 (74.3-06 Task 3):** Theia's `AbstractDialog` accepts on Enter by default; the Affirm dialog must override it (Q8).
- **P9 (74.3-05, 74.3-10):** notifications and the status bar must never carry a file name, a basis text or a label above system-high (security rule 1).
- **P10 (existing, outside this phase):** Set Label shows handling flags as raw tokens today (`labelParts` in `src/services/gateCommands.ts`). Not changed here; noted for the coherence review.
- **P11 (glossary):** add, in the plan that first shows them: "classification assistant", "trial" (Q1), "classification authority", "Classification Reviews", "Keep on this system", "No agent tools", "possible spill", "affirm", "proposed label", "request a lower label", "Rules only".
