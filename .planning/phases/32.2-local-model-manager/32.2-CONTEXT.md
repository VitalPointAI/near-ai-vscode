<domain>
## Phase Boundary

Phase 32.2 delivers one page, **Local models** (palette "NEAR AI: Manage Local Models"; tab title "Local models"), on the webview kit, reached from Get Started's "Set up local AI", from Settings > AI services and models, and from the model picker. It answers four questions:

- **What can this machine run?** Hardware detection with unified memory as a first-class device class (Strix Halo GTT plus VRAM, GB10 through meminfo, Apple working set), fixed tools only, no shell. (LMOD-01) Fit bands and speed estimates per model and quantization from GGUF header ranged reads and the bandwidth formula, always labelled "estimate", replaced by a measured benchmark per machine, server and artifact. (LMOD-03)
- **Which servers are here?** One adapter per local server (Ollama, llama.cpp server, Lemonade, LM Studio, vLLM, NVIDIA NIM, LocalAI, Jan, and any OpenAI-compatible URL), each a `ModelEndpoint` and, where the server can install, a `LocalServerAdmin`; identified by signature endpoints on loopback, policy-named hosts and approved found servers (the 32.1 discovery rules). (LMOD-02)
- **Which models should I use?** Recommendations by job and kind of work from passports and the signed local catalogue (shipped, replaceable by the policy's `models.localCatalogue`); PRC-origin and passport-less models only into the research workspace's list. (LMOD-04)
- **Install, update, remove safely, and assign to jobs.** Licence acceptance, disk check, HTTPS from pinned sources or your organization's mirror, sha256 verified before the file is visible to any server, GGUF or safetensors only; update only within the passport; remove after a confirmation naming the jobs affected. (LMOD-05) Models by job for fast, standard, deep, embeddings and safety within the policy's defaults, a person's own setting kept, the tool-calling and embedding tests before a job's model counts as viable. (LMOD-06) Local audit records for every action; SECURITY.md and README sections. (LMOD-07)

When a job has a tested local model, the 32.1 guide shows "This computer" as viable with no change to the guide.

Not in this phase: the guide itself, its questions, recommendation, record writer and discovery (32.1; this phase uses them); the appliance's default server and measured numbers on the appliance (Phase 85); passport enforcement and the research workspace's own surfaces (74.1); installing a model server for the person (never); Cohere (36, 37).
</domain>

<decisions>
## Implementation Decisions

### Accepted design defaults (owner, PR #137)
- D5 (owner): the appliance's default local server is set by Phase 85's measurements; until then llama.cpp server with Vulkan on Strix Halo, and Ollama recommended on personal machines.
- D8 (owner): the local model manager is its own phase, after the shared contract of 32.1, run in parallel with the rest of 32.1.
- D10 (owner, refined by the coherence review): the catalogue is `models.localCatalogue` inside the policy v2 `models` section (`models@1`), so one signature covers models and their artifacts. Phase 41 shipped its entry shape (passport, 1 to 8 artifacts with format, quantization, source, sha256, integer sizeBytes, licence id and url; minFitBand; at most 64 entries).
- D11 (owner): allowed download sources are Hugging Face (pinned to a commit) and the Ollama registry; your organization's mirror replaces both when named.
- D12 (owner): servers on other machines are reached only as the 32.1 discovery rules allow (named, announced on listed networks, confirmed scans of listed ranges; candidates until approved with a pinned certificate).
- Western model direction (owner): the shipped recommendations follow passports for Nemotron 3 (Nano, Super), gpt-oss (20b, 120b) and Command A+ where licensed; PRC-origin models only into the research workspace's list, labelled "research only", never in a Models by job selector.

### Contract and structure
- **D-01:** 32.2 starts when 32.1's contract plan has merged and uses its `DeviceClass`, server adapter registry shape and `ViabilityResult` unchanged; it adds no second registry. If 32.2 needs a contract change, it is made in 32.1's contract files by the 32.2 plan that needs it, as an additive change, and noted for the integration merge.
- **D-02:** Pure code in `src/domain/localModels/` (fit, speed, GGUF header parsing, catalogue selection, the local model state machine, job assignment rules); host code in `src/services/localModels/` (detection, adapters, downloads, the page host); the page in `media/localModels/`. Architecture test and copy lint baselines do not grow.
- **D-03:** Model listing joins `ModelEndpoint` as an optional `listModels()` (deferred from Phase 41 to 32.2), implemented by every adapter here and by `NearAiClient` through its existing listing, without changing the NEAR AI behaviour.

### Hardware detection (LMOD-01)
- **D-04:** Detection per GUIDE 6.3: files first (`/proc/meminfo`, `/proc/cpuinfo`, `/sys/class/drm/card*/device/*`, `/sys/class/kfd/kfd/topology/nodes/*/properties`), fixed binaries with fixed arguments only (`nvidia-smi` with the fixed query, `sysctl -n` with fixed names, PowerShell `Get-CimInstance Win32_VideoController` with fixed arguments), resolved from known install paths before PATH, `execFile` without a shell, 3-second timeout, 64 KB output cap, working directory outside the workspace.
- **D-05:** Strix Halo GPU-usable memory is GTT plus VRAM; when GTT is far below RAM the page shows the fix to raise the GPU memory limit (`ttm.pages_limit`) with a link to AMD's documented steps, never running it. GB10 (`nvidia-smi` name contains "GB10", memory "Not Supported") uses `/proc/meminfo` as unified memory. Apple uses about 75 percent of RAM, marked as an estimate. Windows AMD and Intel memory is "could not be measured", and the benchmark decides.
- **D-06:** Every platform has a fixture-based test (captured file contents and tool output for Strix Halo, GB10, Apple, discrete NVIDIA, Windows, CPU only); no test runs a real tool.

### Server adapters (LMOD-02)
- **D-07:** One adapter per row of GUIDE 6.4's table, data-driven from the contract's probe table: ports, signature request, list models, loaded models, install capability. Install through Ollama (`/api/pull`, `/api/delete`), llama.cpp router mode (a verified GGUF placed in its models folder) and Lemonade (its own pull, if research confirms the API; otherwise list only in this phase). LM Studio, vLLM, NIM, LocalAI, Jan and any OpenAI-compatible server are list only.
- **D-08:** Exact ports and signature endpoints are checked against current releases during research (research flag 2 of the roadmap) and pinned in the probe table with one test per row against a fake server; a server whose signature does not match is "unknown server", never trusted as the kind it claims.
- **D-09:** Ollama digest: if research shows the model layer digest equals the GGUF file's sha256, the catalogue's `sha256` covers both. If not, the plan adds one optional field `ollamaDigest` to the `localCatalogue` artifact shape in Phase 41's parser (no catalogue ships before this phase, so no stored bundle is affected) and verifies both.

### Fit, speed and benchmark (LMOD-03)
- **D-10:** Memory needed = weights + KV cache + overhead (GUIDE 7.2), KV cache from a GGUF header read by HTTP range requests of the header only (a small in-house parser modelled on gguf-parser-go's approach, no new dependency), per-layer values for sliding-window or hybrid layers; safetensors weights from the header's tensor sizes. Default context 32k for standard, 8k for fast, adjustable on the page.
- **D-11:** Fit bands at 60, 85 and 98 percent of available memory (Comfortable, Fits, Tight, Will not fit); available memory per device class as GUIDE 7.2. Speed = bandwidth / bytes per token x 0.55, from a small table of known devices (Strix Halo about 256 GB/s, GB10 about 273 GB/s, Apple and common discrete GPUs), else "unknown". The worked example of GUIDE 7.2 is a test.
- **D-12:** The benchmark is optional and asked for: a fixed 512-token prompt and 128 generated tokens through the selected server, recording prompt speed, generation speed and time to first token, stored in extension storage per (machine, server, artifact); measured numbers replace estimates on the page and are labelled "measured on {date}".

### Catalogue and recommendations (LMOD-04)
- **D-13:** A shipped catalogue sits in the starting rules' `models` section (`models.localCatalogue`) with passports from `shippedPassports.ts`, so it carries the same signature as the starting rules; an organization policy's `models.localCatalogue` replaces it entirely. Each shipped artifact's sha256, size, commit and licence are taken from the public model pages during execution and checked by a test that the catalogue parses; nothing is invented in the plan.
- **D-14:** Recommendations come from passports, never model names (model provenance 8.2): the GUIDE 7.3 table filtered by fit, ordered for the kind of work only where passports allow both choices. A model whose highest approved use is research only, or that has no passport, appears only in a separate "Research only" list; it can be installed there and is never offered to any Models by job selector. Until 74.1 the research workspace that uses that list does not exist; the list says so.

### Install, update, remove (LMOD-05)
- **D-15:** Install follows GUIDE 7.5 exactly: licence shown (id, link, obligations from the passport) and accepted, recorded; disk space checked; HTTPS from the catalogue source pinned to a commit or the policy's mirror; sha256 computed while writing a partial file in the manager's own folder (extension global storage); on mismatch the partial file is discarded and the attempt recorded; only then is the file moved where the server reads it, or pulled through the server and the server's reported digest checked. GGUF and safetensors only; nothing with remote code.
- **D-16:** Downloads go through the outbound check like any request (Emergency stop applies) and name their destination host in SECURITY.md's "Where your data goes"; the download host sees the IP address and the model name, which the page says once before the first download.
- **D-17:** Update is offered only when the catalogue lists a newer artifact for the same passport and, for a model used above "chat you review", only when the passport covers the new hash.
- **D-18:** Remove asks first, naming the model, its size and the jobs that lose it, and shows which next viable model each job falls to; it never removes a file the manager did not install, and for a server-managed model it calls the server's delete.
- **D-19:** OpenSSF Model Signing is verified when an artifact carries a signature and the catalogue names the signer; the hash check is always required. If research finds no artifact in the shipped catalogue carries one, the verifier is planned but marked optional for the shipped set.
- **D-20:** The local model state machine is GUIDE 8.6 exactly (`listed`, `downloading`, `verifying`, `installed`, `tested`, `assigned`, `rejected`, `update-available`, `removing`), as a pure reducer tested transition by transition; a download can be cancelled at any point and leaves no partial file visible to a server.

### Models by job (LMOD-06)
- **D-21:** One "Models by job" service writes the job assignments (fast, standard, deep, embed, safety) for the local endpoint into the existing settings keys behind the glossary's "Models by job" (`nearAi.agent.fastModel`, `standardModel`, `deepModel` and their successors), only within the policy's `models.defaults` and passports; a value a person set by hand is kept and shown "set by you". If the one Settings page does not exist yet, the manager is the place to set local jobs and the settings section reuses the same service later; no second store.
- **D-22:** A job's model counts as viable only after the 32.1 test request passes, plus, for standard and deep, the tool-calling test, and for embeddings, the vector-length test; this feeds the 32.1 viability check, so the guide shows local AI as viable with no guide change. Changing the embedding model says first that it rebuilds the knowledge base index.

### Records, docs and the page (LMOD-07)
- **D-23:** Install, update, remove, assignment, rejected download and benchmark each write one record through 32.1's record writer (events `local-models.installed`, `local-models.updated`, `local-models.removed`, `local-models.assigned`, `local-models.rejected`, `local-models.benchmarked`), with model ids, artifact hashes, server kind and version; no prompt text.
- **D-24:** The page is built on the webview kit with the house accessibility standard (estimates say "estimate" in text; progress in one polite live region; confirmation dialogs as native buttons; reduced motion honoured). SECURITY.md gains "Local model downloads" and the local models part of the new "Get Started and local models" section; README gains the model manager in the feature list.

### Claude's Discretion
- File split inside the two folders, the known-device bandwidth table's exact rows, the probe timeouts, and the page's layout within the kit.
</decisions>
