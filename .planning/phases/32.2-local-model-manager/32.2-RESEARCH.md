## Summary

Phase 41 left almost everything this phase needs as interfaces and parsers: `ModelEndpoint` and `LocalServerAdmin` (interfaces only), the `localCatalogue` entry shape with a strict parser and a narrowing rule per key, shipped passports for the Western models, and `resolvePassport` and `passportCovers`. Nothing implements them yet. The hard work is therefore in four places the context does not spell out. First, the shipped passports list only `nearai-tee` hosting, and a passport that lists `local` at T2 or above must carry the exact artifact hash, so a shipped catalogue needs new local passport rows (new ids) or local models will report a hosting mismatch for every request. Second, passports match served model ids exactly, so the manager must control the id a server serves each install under. Third, the catalogue must hold third-party GGUF conversions (no official NVIDIA GGUF exists for Super, and Command A+ GGUFs are third-party, 3 to 5 split files). Fourth, the speed formula only reproduces the worked example when active parameters come from tensor dimensions in the full GGUF header (about 13 MB), not from the first few kilobytes.

Every research flag is answered with evidence from this session. The Ollama model layer digest is the sha256 of the layer bytes, `/api/tags` returns the manifest digest instead (observed against a running Ollama 0.40.13), a library model's layer is not byte-identical to the Hugging Face GGUF (observed: 4,683,074,048 bytes against 4,683,073,536), but a GGUF pushed with `POST /api/blobs/:digest` and created with `files` keeps its sha256 as the model layer (observed on a scratch instance). So no `ollamaDigest` field is needed: one sha256 per artifact source, and the shipped install path is "the extension downloads and verifies, then pushes the blob". Lemonade's pull has no commit pin and no hash check, so Lemonade is list only in this phase. No shipped target repository carries an OpenSSF signature file, so the signature verifier is planned and marked optional.

**Primary recommendation:** Build the pure core first (GGUF reader, fit, speed, catalogue and local passport rows, state machine) in parallel, then the download engine, the adapters and the benchmark and tests, then the install orchestration and Models by job service, then records and the page, then entry points and docs. Install through the extension's own verified download for every server (Ollama by blob push, llama.cpp by a folder), never through a server's own pull for the shipped catalogue.

## Research Flags Resolved

### Flag (a): Does Ollama's model layer digest equal the GGUF file's sha256?

Answer: **the layer digest is the sha256 of the layer bytes, so it equals the file's sha256 exactly when the layer is that file as-is. That holds for a GGUF pushed as a blob and created with `files`. It does not hold for Ollama library models. `/api/tags` `digest` is neither.** Evidence, all gathered this session:

- `[VERIFIED: registry.ollama.ai manifest and a running Ollama 0.40.13]` For `qwen2.5-coder:7b`, `GET /api/tags` returned digest `dae161e27b0e90dd...`; the sha256 of the registry manifest JSON (`GET https://registry.ollama.ai/v2/library/qwen2.5-coder/manifests/7b`, `Accept: application/vnd.docker.distribution.manifest.v2+json`) starts with the same 16 characters. So `digest` in `/api/tags` is the manifest digest. The Ollama source agrees: `Manifest.digest` is `sha256` of the manifest file bytes (`manifest/manifest.go`, `verifiedData()`), and `/api/ps` reports `ManifestDigest` `[CITED: github.com/ollama/ollama manifest/manifest.go and server/routes.go]`.
- `[VERIFIED: same sources]` The manifest's layers include `application/vnd.ollama.image.model` with digest `sha256:60e05f21...` (4,683,074,048 bytes), and `POST /api/show` returns a `modelfile` whose `FROM` line ends in `/blobs/sha256-60e05f21...` (dash, not colon). That is how the model layer digest is read back from a server, on any host (take the trailing `sha256-<64 hex>`).
- `[VERIFIED: Hugging Face API, observed]` The Hugging Face Q4_K_M GGUF of the same model is 4,683,073,536 bytes with a different sha256. So a library model's layer is not the Hugging Face file (a re-written GGUF, 512 bytes longer). A catalogue sha256 for an Ollama registry artifact is therefore the registry's model layer digest, a separate artifact row from a Hugging Face row.
- `[VERIFIED: scratch Ollama instance on its own port and models folder, observed]` A 1.2 MB public GGUF was pushed with `POST /api/blobs/sha256:<its sha256>` and a model was created with `POST /api/create {"model":..., "files": {"x.gguf": "sha256:<same>"}, "stream": false}`; `/api/show` then reported `FROM .../blobs/sha256-<the file's sha256>`. A push with a wrong digest returned 400, as documented `[CITED: docs.ollama.com/api (Push a Blob: 400 if the digest does not match; Create: files maps file names to SHA-256 digests)]`. Tested only on one small llama-architecture file, so other architectures are `[ASSUMED]`; the install verifies the `FROM` digest every time, so a rewrite would be caught and rejected, not trusted.

**Decision for the plan (resolves D-09):** no `ollamaDigest` field and no change to `models.ts` or `layers.ts`. One sha256 per artifact, always the sha256 of exactly the bytes at that artifact's `source`. The shipped install path for Ollama is: the extension downloads from Hugging Face at the pinned commit, verifies, pushes the blob (Ollama verifies the digest again on receipt), creates the model, then `verifyHash` reads `FROM` from `/api/show` and compares. An Ollama-registry artifact (optional, your organization's catalogue) uses `/api/pull` and the same `FROM` check, and is weaker (the bytes reach the server before the check): record it as `verifiedBeforeVisible: false` and say so on the page. Contingency if execution finds `create` rewriting a layer: the additive `ollamaDigest` change touches `models.ts` (`parseLocalArtifact` keys, `LocalArtifact`), `layers.ts` (one `ONLY` line), `policyFixtures.ts`, `gatePassports.test.ts`.

### Flag (b): Strix Halo GTT limits, GB10 memory

- `[CITED: rocm.docs.amd.com/en/latest/how-to/system-optimization/strixhalo.html]` The firmware VRAM carve-out should stay small (the page suggests 0.5 GB), and "By default, the GTT limit is set to approximately 50 percent of total system RAM." The limit is raised with the TTM `pages_limit` (`/sys/module/ttm/parameters/pages_limit`, in pages) through AMD's `amd-ttm --set <GB>` helper, which writes a modprobe file and needs a reboot (example: 100 GB is 26214400 pages, which checks out as 4 KiB pages). `amd-ttm` with no argument shows the current limit. Minimum kernels for gfx1151 support are named on the page (Ubuntu 24.04 HWE 6.17.0-19.19~24.04.2, OEM 6.14.0-1018, or Linux 6.18.4 elsewhere). The page does not mention `rocm-smi`, `amdgpu.gttsize` or the sysfs files.
- `[CITED: docs.kernel.org/gpu/amdgpu/driver-misc.html]` `mem_info_vram_total` and `mem_info_gtt_total` are in bytes. The sysfs directory (`/sys/class/drm/card<N>/device/`) is not stated on that page, so it stays `[ASSUMED]` from the design's GUIDE 6.3 and the standard amdgpu layout. That `mem_info_gtt_total` reflects the effective TTM limit is `[ASSUMED]` and is the first thing to confirm on a real Strix Halo (Phase 85 hardware).
- `[CITED: docs.nvidia.com/dgx/dgx-spark/known-issues.html]` On the integrated GPU, `nvidia-smi` shows "Memory-Usage: Not Supported", expected because iGPUs have no dedicated framebuffer. The page reads `/proc/meminfo` (`MemAvailable`, `SwapFree`, `HugePages_*`), and warns `cudaMemGetInfo` can under-report because of reclaimable DRAM. It does not name GB10 itself; the "name contains GB10" test stays from the design.
- Recommendation `[ASSUMED]`: for GB10 use `MemTotal` as the unified capacity for fit bands (stable) and show `MemAvailable` as "free now"; `MemAvailable` moves with the page cache and would flicker the bands.
- Apple: about 75 percent of RAM `[ASSUMED]` (Metal's recommended working set is a lower fraction on smaller machines); label as an estimate as D-05 says.

Fixtures needed (D-06): Strix Halo with default GTT (about 50 percent of RAM, so gpt-oss-120b shows "Will not fit" and the page shows the `ttm.pages_limit` fix and AMD link) and tuned GTT (about 110 GB usable, the worked example); GB10 (`nvidia-smi` text with `Not Supported`, meminfo); Apple (`sysctl` output); discrete NVIDIA (the fixed CSV query); Windows (PowerShell JSON with `AdapterRAM` capped at 4 GB, so AMD and Intel read "could not be measured"); CPU only (RAM minus 8 GiB).

### Flag (d): GGUF header layout, ranged reads, Hugging Face range support

- `[CITED: github.com/ggml-org/ggml docs/gguf.md]` and `[VERIFIED: parsed real headers this session]`: magic `GGUF` (4 bytes), `version` uint32 (3), `tensor_count` uint64, `metadata_kv_count` uint64, then key-value pairs (`key` as uint64 length plus bytes, `value_type` uint32, value), then tensor infos (`name` string, `n_dims` uint32, `dims` uint64 x n, `type` uint32, `offset` uint64), then alignment padding (`general.alignment` default 32) and tensor data. Value types: 0 uint8, 1 int8, 2 uint16, 3 int16, 4 uint32, 5 int32, 6 float32, 7 bool, 8 string, 9 array (element type uint32, count uint64, arrays may nest), 10 uint64, 11 int64, 12 float64. The standard spec lists `[arch].context_length`, `.block_count`, `.embedding_length`, `.attention.head_count`, `.attention.head_count_kv` (absent or equal means no GQA), `.attention.key_length`, `.attention.value_length` (default `embedding / head_count`), `.expert_count`; it does not define a sliding-window key. Real files add `[arch].attention.sliding_window` and `[arch].expert_used_count`.
- Real header facts (observed): gpt-oss-20b (`general.architecture = gpt-oss`): `block_count` 24, `context_length` 131072, `embedding_length` 2880, `head_count` 64, `head_count_kv` 8, `key_length` 64, `value_length` 64, `sliding_window` 128, `expert_count` 32, `expert_used_count` 4; all architecture keys lie within the first 1 KB. gpt-oss-120b: `block_count` 36, same heads, `expert_count` 128, `expert_used_count` 4. Nemotron 3 Nano 30B-A3B (`general.architecture = nemotron_h_moe`, a hybrid Mamba and transformer): `block_count` 52, `context_length` 1,048,576, `attention.head_count_kv` is a **per-layer int32 array** (52 entries, non-zero in 6 attention layers, value 2), `feed_forward_length` is also a per-layer array, `key_length` 128, `value_length` 128, `ssm.*` keys, 116 key-values, architecture keys start after about 75 `general.*` entries (dataset names), still within the first 128 KB. So the KV reader must accept scalar or array `head_count_kv`, and a first range of 256 KiB covers the architecture keys in all three; extend in 1 MiB steps up to a cap (for example 32 MiB) otherwise.
- Header size is dominated by the tokenizer: the full header (key-values plus tensor infos) is 13.0 MB for gpt-oss-20b (12.98 MB of key-values, 28 KB of tensor infos, 459 tensors) and about 13.0 MB for gpt-oss-120b (observed), against 12 to 63 GB files. "Header only" is still correct (0.1 percent of the file) but is not "a few kilobytes". Cache the parsed result per artifact sha256 in extension storage.
- Sliding window layers: gpt-oss uses sliding-window attention on alternating layers, but the pattern is not a header key (the spec has none), so the estimator uses the conservative all-layers-full-attention KV, labelled estimate, unless a small architecture table says otherwise `[ASSUMED]`. That overestimates gpt-oss KV by about half (about 1.2 GB at 32k for the 120b).
- Hugging Face range requests `[VERIFIED: curl against huggingface.co, observed 2026-11-21]`: `GET https://huggingface.co/<repo>/resolve/<40-hex commit>/<file>` answers `302` to a CDN host (`us.aws.cdn.hf.co`) with `accept-ranges: bytes`, `x-linked-size` and `x-linked-etag` (the file's sha256 for LFS files, equal to the API's `lfs.sha256`); the second hop answers `206` for `Range: bytes=0-15` with `content-range: bytes 0-15/12109566624`, first bytes `47 47 55 46 03 00 00 00` (GGUF, version 3). Pin to the commit (`resolve/<commit>/`), never `main`. File contents are served from hosts under `hf.co` and `huggingface.co` (Hub docs list `cas-server.xethub.hf.co`, `transfer.xethub.hf.co`, `us.aws.cdn.hf.co`, `cdn-lfs-us-1.hf.co` and EU equivalents, and warn that the hostnames change) `[CITED: huggingface.co/docs/hub/en/models-downloading]`.
- The public model API gives what execution needs to fill the catalogue without inventing anything: `GET https://huggingface.co/api/models/<repo>?blobs=true` returns the repo `sha` (the commit to pin), and per file `size` and `lfs.sha256`. Execution takes these values from that response (and cross-checks `x-linked-etag`), never from this document.
- Safetensors (for D-10's safetensors sizing): the file starts with an 8-byte little-endian length followed by a JSON header with dtype, shape and byte offsets per tensor `[ASSUMED]` (the docs page did not render the format block); one ranged read of 8 bytes, then one of the header length (cap it, for example 16 MiB). Nothing in the shipped set is safetensors only, and none of the adapters in this phase installs safetensors (an Ollama create from safetensors needs the config and tokenizer files the catalogue artifact shape cannot hold, vLLM is list only), so safetensors artifacts get fit estimates and "not installable here".
- `@huggingface/gguf` exists (MIT, 0.4.6, depends on `@huggingface/tasks`) and the legitimacy check returns OK, but D-10 chose an in-house parser, and the real need (a few key-values, tensor dims, skipping arrays) is about 200 lines. Keep D-10.

- Observed: none of the six candidate repositories checked (ggml-org gpt-oss-20b and 120b, ggml-org Nemotron 3 Nano, unsloth Nemotron 3 Super, nvidia Nemotron 3 Nano and Super BF16, bartowski Command A+) lists a signature file (`.sig`, `sigstore`, `cosign`, `attest`). ### Pattern 1: Download with a streaming hash into a partial file (item 5)
**What:** one `node:https` GET per hop, manual redirects, hash while writing, verify, then rename.
**When to use:** every artifact the extension downloads (Hugging Face, an organization mirror).
**Example (shape, not final code; write it with injected `request`, `fs` and clock for tests):**
```typescript
// Source: Node 22 docs (https, crypto, fs/promises); behaviour of resolve URLs verified with curl on 2026-11-21.
import { createHash } from 'node:crypto';
import { open, rename, rm, statfs } from 'node:fs/promises';
import https from 'node:https';

async function getOnce(url: URL, headers: Record<string, string>, signal: AbortSignal): Promise<https.IncomingMessage> {
  return await new Promise((resolve, reject) => {
    const req = https.get(url, { headers, signal }, resolve); // https only; no agent that skips certificate checks
    req.on('error', reject);
  });
}

/** Follows at most 5 redirects; every hop must be https and its host must pass `hostAllowed`; no Authorization header is ever added. */
async function open200or206(start: URL, headers: Record<string, string>, hostAllowed: (h: string) => boolean, signal: AbortSignal) {
  let url = start;
  for (let hop = 0; hop < 6; hop += 1) {
    if (url.protocol !== 'https:' || !hostAllowed(url.hostname)) throw new Error('host-refused');
    const res = await getOnce(url, headers, signal);
    if (res.statusCode === 200 || res.statusCode === 206) return res;
    if ([301, 302, 303, 307, 308].includes(res.statusCode ?? 0) && typeof res.headers.location === 'string') { res.resume(); url = new URL(res.headers.location, url); continue; }
    res.resume(); throw new Error(`http-${res.statusCode}`);
  }
  throw new Error('too-many-redirects');
}

async function downloadVerified(res: https.IncomingMessage, partial: string, expectedSha256: string, signal: AbortSignal): Promise<boolean> {
  const hash = createHash('sha256');
  const file = await open(partial, 'wx', 0o600); // fails if a partial already exists; folder is 0o700 and never a server folder
  try {
    for await (const chunk of res) { // backpressure comes from awaiting the write
      if (signal.aborted) throw new Error('cancelled');
      hash.update(chunk);
      await file.write(chunk);
    }
    await file.sync();
  } finally { await file.close(); }
  return hash.digest('hex') === expectedSha256;
}
// Caller: free = (await statfs(dir)).bavail * (await statfs(dir)).bsize before starting (bavail, not bfree);
// on false: rm(partial); on true: rename(partial, finalPathOnTheSameFilesystem) (atomic, so a server never sees a half file).
```
Rules that come with it (all testable): resume only by re-hashing the existing partial first (read it through the hash, then `Range: bytes=<size>-`, expect `206` with a matching `content-range`; a `200` restarts from zero); cap redirects at 5; the size must equal the catalogue `sizeBytes` (stop early when `content-length` or the bytes received disagree); never follow a redirect to a non-`https` URL or outside the allowlist (Hugging Face resolve URLs redirect from `huggingface.co` to CDN hosts under `hf.co`); never forward credentials to another host; the destination folder is created `0o700`; temporary and partial names never end in `.gguf` (the llama.cpp router scans for it), and the rename happens inside one filesystem (`EXDEV` means the models folder is elsewhere: copy to a `.part` name inside that folder, then rename in place).

### Pattern 2: Ollama install by blob push (the shipped path)
`HEAD /api/blobs/sha256:<d>` (exists?), else `POST /api/blobs/sha256:<d>` with the file streamed as the body (201 created, 400 digest mismatch), then `POST /api/create { model: <served id>, files: { "<file name>.gguf": "sha256:<d>" }, stream: false }` (split GGUFs: every shard under its original split file name `[CITED: docs.ollama.com/api/create]`), then `POST /api/show { model }` and parse the trailing `sha256-<64 hex>` of the `FROM` line to compare with the catalogue hash. `remove` is `DELETE /api/delete { model }`. Disk: the extension's verified copy and Ollama's blob can both exist, so require 2x the size free when both live on the same disk, and delete the extension's copy after the server reports the model verified (keep it only if the person asks). Streaming the body of a multi-GB `POST` needs a streamed request (Node `http.request` piping a read stream, or `fetch` with `duplex: 'half'`); a plain curl probe against a freshly started server timed out on the first call this session, so first-connection delays and the response status must be handled and tested (a 201 or 200 is success, anything else is a failure and the blob is left to Ollama's own cleanup).

### Pattern 3: One adapter per server, composed
`LocalAdapter { endpoint: ModelEndpoint, admin: LocalServerAdmin }`. `endpoint` is `new NearAiClient({ baseUrl: '<origin>/v1', apiKey, route: 'local', fetchFn })` plus a `listModels` that wraps `listLocalModels` (marks `privacyBoundary: 'local'`) and `facts.endpointId` filled when a policy endpoint matches; `admin.kind` is the table row's kind, `identify` runs the signature request, `listInstalled` the list call, `install`/`remove` exist only for Ollama and llama.cpp. All rows are data from `probes.ts`; no adapter reads another's code.

### Pattern 4: "Set by you" for Models by job
A job value counts as set by the person when any of: a workspace folder or workspace value is defined, a project choice exists (`projectChoiceFor`), or the global value is defined and is not the value this manager last wrote (the manager keeps `{ key -> lastWritten }` in extension storage; without it a value the manager wrote itself would be indistinguishable from the person's). The service never overwrites a set-by-you value, shows "set by you", and writes only the global setting for values it owns. A setting the manager wrote and the person later changed stays theirs.

### Anti-Patterns to Avoid
- **Using `/api/tags` `digest` to verify a file:** it is the manifest digest, never the file's sha256.
- **Letting a server pull from the network by itself for the shipped catalogue:** the bytes would reach the server before the check; only the Ollama registry artifact path does this, and it says so.
- **Writing `getConfiguration(` outside `services/settings.ts`:** a new architecture-baseline violation.
- **Reading the whole file for fit:** read the header only; cache per sha256.
- **Matching a passport by a wildcard prefix of a name:** a person could name any model to match it; use exact served ids the manager controls, plus a ledger of what the manager installed.

## Local Hosting, Passports and Served Ids (a finding the context does not state)

1. The shipped rows list `hosting: ['nearai-tee']` only (`shippedPassports.ts:60`, `:96`, `:153`). For a `local` endpoint, `passportCovers` ends at `hosting-mismatch` (`models.ts:713`) for every shipped model, even at T0. In Phase 41 this is only recorded as `wouldRefuse`, but Phase 74.1 turns it into a refusal, so shipping a local catalogue without local-hosting passports ships local AI that 74.1 would then block.
2. A passport that lists `local` at T2 or above must carry an `artifact` (`models.ts:369-373`), which is one `{ format, sha256, quantization, remoteCode: false }`. So the shipped local passports are **new rows with new ids** (`shippedPassports.ts` header: "an id here never changes in place: a changed row gets a new id"), one per (model, quantization), `hosting: ['local']`, `maxTier: 'T2'`, an `artifact` whose `sha256` equals the catalogue artifact's, `lineage.method` including `quantization`, `licence` as the model page states. Whether to assert T2 on a third-party conversion is a judgment for the owner (Open Question 1); the safe floor is `maxTier: 'T1'`, which needs no artifact but then cannot do agent work.
3. A split GGUF (Nemotron 3 Super, Command A+) is several files but `PassportArtifact` holds one hash. Recommended: the catalogue lists each shard as its own artifact (same `quantization` token, distinct `source` file names with the `-0000N-of-0000M` suffix) and the manager treats all artifacts of one quantization as one install unit (all or none, fit uses the sum of `sizeBytes`); the local passport row names the first shard's hash plus the group is checked by the catalogue. If the owner wants the passport to cover every shard, that is a schema change (Open Question 2).
4. Served ids. `resolvePassport` matches the id the server serves (`ModelInfo.id`), anchored and case-sensitive. Ollama serves `name:tag` (the `:latest` suffix appears when no tag is given), llama.cpp router serves the file stem. Adapters normalise what they list (strip `:latest`) so the id seen by the gate is the id in the table. Assignment additionally requires the manager's ledger to show the install and `verifyHash` to pass at assign time, so naming another model the same way does not make it assignable.
5. PRC-origin and passport-less models install only into a research namespace (Ollama names under `research/`, llama.cpp under a `research/` subfolder not read by the router unless the person points it there) and never reach `jobs.ts`' assignable set; the page labels the list "research only" and says the research workspace does not exist until Phase 74.1 (D-14). The existing chat model picker lists whatever the server serves, so the namespace is a convenience, not a control; enforcement is Phase 74.1 (record this limit on the page and in SECURITY.md).
6. Where the shipped catalogue sits. The starting rules today are the v1 bundle (`defaultBundlePayload`, `bundle.ts:163-196`), converted to a v2 document without a `models` section (`policyDocument.ts:279-312`), and `isDefaultBundle` compares hashes of the default payload (`bundle.ts:732-741`), so adding a `models` section to the starting rules would change every stored default bundle's "unedited" status. This keeps D-13's behaviour with no change to the bundle hash logic. An organization mirror needs no schema key: the organization writes its own catalogue whose `source` values are its own `https://` URLs (the parser accepts any text up to 256 characters, and the fixture already uses an `https://models.example.org/...` source), so the mirror is named by the signed catalogue itself; the downloader accepts exactly three source forms: the Hugging Face form, the Ollama registry form, or an exact `https://` URL, and for the last it trusts only the organization-signed catalogue entry.

## Fit and Speed (item 3)

**Memory needed** = `sizeBytes` (weights, the file or the sum of the group) + KV cache + overhead. KV cache = `context x sum over layers( kv_heads_l x (key_length + value_length) ) x bytes per element` (f16 = 2, q8_0 about 1.06); with a scalar `head_count_kv` this is the design's `2 x layers x context x kv_heads x head_size x bytes`. `key_length` and `value_length` default to `embedding_length / head_count`. Hybrid models (Nemotron 3) count only layers whose per-layer `head_count_kv` is non-zero; recurrent state (`ssm.*`) is small (tens of MB) and is covered by the 1 GiB overhead. Overhead = 1 GiB (+ the server's reported compute buffer when known).

**Memory available** (`unified`: GPU-usable memory minus 8 GiB; `discrete`: VRAM (RAM offload shown separately as "slow"); `cpu-only`: RAM minus 8 GiB). **Bands** by ratio: up to 0.60 Comfortable, up to 0.85 Fits, up to 0.98 Tight, else Will not fit; define the boundary values as inclusive upper bounds and test both sides of each.

**Speed** (estimate, `x 0.55`): `bandwidth / bytesPerToken x 0.55`. Method validated against real headers this session: from the full header, element count `n = product(dims)` per tensor; expert tensors (name contains `_exps`) count `expert_used_count / expert_count` of their elements; the token embedding (`token_embd.weight`, a row lookup) is excluded; `activeParams = nonExpert + experts x used / count`; `bitsPerWeight = fileBytes x 8 / totalParams`; `bytesPerToken = activeParams x bitsPerWeight / 8`. Results `[VERIFIED: computed from the real headers]`: gpt-oss-120b total 116.83 B, active 5.13 B (published 5.1 B), 4.34 bits per weight, 2.78 GB per token, **50.6 tokens per second at 256 GB/s**; gpt-oss-20b total 20.91 B, active 3.61 B (published 3.6 B), 4.63 bits per weight, 2.09 GB per token, 67.4 tokens per second. Summing actual tensor bytes instead (non-expert tensors are stored at higher precision) gives 33 to 39 tokens per second for the 120b, below the context's "roughly 45 to 55", so the plan must use the active-parameter method, not byte sums. Per-tensor byte sizes are available if wanted: `size_i = offset_(i+1) - offset_i` over sorted offsets, and the sum plus the aligned data start equals the file size exactly (checked, difference 0). Dense models (no `_exps` tensors) use all non-embedding parameters. Unknown bandwidth gives "unknown". Known rows (Claude's discretion): Strix Halo 256 GB/s, GB10 273 GB/s (the design's values), plus Apple and common discrete GPUs.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| sha256 of a download | a manual rolling hash | `createHash('sha256')` on the stream | correct and fast |
| Redirect following | `fetch` defaults or an HTTP client library | manual loop above | only a manual loop can refuse a host, protocol, or credential leak on each hop |
| Tier and passport logic | a second evaluator | `resolvePassport`, `effectiveMaxTier`, `JOB_MINIMUM_TIER` | one label and tier algebra (ADR-004) |
| Strict parsing of server JSON and page messages | ad hoc casts | `shape.ts` helpers (`checkKeys`, `ownValue`, `refused`) | own-property, no prototype keys |
| The catalogue shape | a second schema | `parseModelsSection` | one signature, one narrowing table |
| Settings writes | `getConfiguration` in new files | functions added to `services/settings.ts` | architecture rule |
| Chat to a local server | a new streaming client | `NearAiClient` with `route: 'local'` | tested transport, stall handling |
| Memory sizing | file-size heuristics | header-derived numbers above | reproduces the published figures |

**Key insight:** the dangerous parts here (a hash that does not mean what it seems, a model name that borrows a passport, a download that follows a redirect anywhere) are all deceptively small pieces of code. Each gets one owner, one test file and a fixture.

## Common Pitfalls

### Pitfall 1: Comparing the wrong digest
**What goes wrong:** `/api/tags` digest compared with the file's sha256 never matches (manifest digest), so every install "fails", or someone relaxes the check.
**How to avoid:** read the `FROM` blob digest from `/api/show`; test with a fake server whose `tags` digest differs from its `FROM` digest.
**Warning signs:** a verifier that reads `digest` from a list call.

### Pitfall 2: Shipped passports do not cover local hosting
**What goes wrong:** local models report `hosting-mismatch` now (recorded) and are refused when 74.1 enforces.
**How to avoid:** the new local passport rows with exact artifacts (above); a test that `passportCovers` returns `covers: true` for each shipped local entry at T2 on a `local` endpoint.

### Pitfall 3: Name borrowing
**What goes wrong:** a model named like a passport match inherits its tier.
**How to avoid:** exact served ids, the install ledger, `verifyHash` at assign time; no wildcard in local rows.

### Pitfall 4: Redirects to hosts nobody named
**What goes wrong:** Hugging Face redirects to CDN hosts; a naive allowlist of `huggingface.co` breaks every download, and a naive "follow redirects" lets a compromised redirect send the request anywhere or carry credentials.
**How to avoid:** allow the suffixes `huggingface.co` and `hf.co` over `https` only, matched as the exact host or at a dot boundary (`host === suffix || host.endsWith('.' + suffix)`), never a bare `endsWith`, so `evil-hf.co` and `xhf.co` are refused (the Hub documentation says the hostnames change, so list the suffixes, not hostnames, and name them in SECURITY.md), re-check every hop, no credentials, test with a fake CDN on a second host.

### Pitfall 5: The partial file becomes visible
**What goes wrong:** a server (llama.cpp router scanning `.gguf`) loads half a file, or a verified file is swapped before the rename.
**How to avoid:** partial in the manager's own `0o700` folder under a non-`.gguf` name, same-filesystem rename only after the digest matches, and a test that lists the server folder during the download and after a cancel at each state.

### Pitfall 6: Disk checks that ignore the second copy
**What goes wrong:** blob push needs the extension's copy and Ollama's copy; a 63 GB model fails at 70 percent on a 100 GB disk.
**How to avoid:** `statfs` `bavail * bsize`, 2x for the blob path on one disk, plus a margin; message names the shortfall in GB.

### Pitfall 7: Treating a model's id as stable across servers
**What goes wrong:** the same artifact is `gpt-oss-120b-mxfp4` on llama.cpp and `...:latest` on Ollama, so the passport misses and the job assignment survives a server change wrongly.
**How to avoid:** the id table in `localId.ts`, adapter normalisation, a test per server kind.

### Pitfall 8: The setting the manager wrote looks like the person's
**How to avoid:** the last-written ledger (Pattern 4); a test that a person's later edit is kept and a manager value is replaced on reassign.

### Pitfall 9: `getConfiguration` and the frozen file
**What goes wrong:** the architecture test fails on a new `get-configuration` violation, or a change to `nearAiClient.ts` (frozen size) fails the size rule.
**How to avoid:** all settings access in `services/settings.ts`; no edit to `nearAiClient.ts`; keep new files under 800 lines.

### Pitfall 10: Probe port collisions
**What goes wrong:** a server on 8000 or 8080 is taken for the wrong product, then its model list is trusted as that product's.
**How to avoid:** ordered signature requests per port, two matches or none is "unknown server", one test per row and per collision.

### Pitfall 11: Servers that lie or flood
**How to avoid:** 3 to 5 second probe timeouts (60 seconds only for the one-word test, because a cold load can take that long), 1 MiB response caps, strict JSON, count limits on lists, never record raw server strings (secret scan, no `model_path`).

### Known Threat Patterns

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Tampered or swapped model file | Tampering | sha256 from the catalogue checked before visibility; HTTPS pinned commit; one-changed-byte test |
| Redirect to an attacker host or credential leak | Information disclosure / Tampering | manual redirects, host allowlist matched exactly or at a dot boundary (lookalike hosts refused, 32.2-05), no Authorization ever sent |
| Path traversal through a file name in a source or a shard name | Tampering | derive file names from a validated basename pattern (`[A-Za-z0-9._-]`), reject `/`, `\`, `..`, absolute paths |
| Server impersonation (a fake server on a known port) | Spoofing | signature request per row, "unknown server" when ambiguous, record kind and version only; a local process already has this machine's trust |
| Hostile server response (huge JSON, lies about size) | Denial of service | response caps, timeouts, list limits, header read cap |
| Name borrowing for a passport | Elevation of privilege | exact served ids, install ledger, `verifyHash` at assignment |
| Partial or unverified file loaded by a server | Tampering | partial outside server folders, rename after verify |
| Disk exhaustion | Denial of service | `statfs` before, size check while streaming, cleanup on cancel |
| Test request leaks data | Information disclosure | fixed texts only, through the outbound guard, counted in spend where applicable |
| Download host learns the person's IP and model | Information disclosure | said once on the page before the first download; SECURITY.md row; an organization mirror replaces the public hosts |
| Tool execution during detection | Elevation of privilege | fixed binaries and arguments, known paths first, `execFile` with no shell, timeout and output cap, cwd outside the workspace |
| Research-only model reaching a normal picker | Elevation of privilege | namespace and never in `jobs.ts`' assignable set; honest limit stated until 74.1 |
