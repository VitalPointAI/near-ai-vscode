<domain>
## Phase Boundary

Every cell epoch key that Phase 31 and 33 wrap to a device today with X25519 is wrapped instead with a hybrid of P-256 ECDH and ML-KEM-768, both listed in CCCS ITSP.40.111 v5 for Unclassified, Protected A and Protected B. The switch happens per project through Phase 33's `roster.require`, each cell moves at its next epoch, and nothing breaks for people on the way. It lands before any site holds Protected B data.

In this phase:
- `near-ai/cell-wrap/v2` with test vectors (33.2-01).
- A second device key binding: each device, hosted person and hub publishes a P-256 key and an ML-KEM-768 key bound to its Ed25519 key (33.2-02).
- Grant pages, because a v2 wrap is about 1.2 KB against 92 bytes (33.2-03).
- The `wrap@2` feature, the cutover rule in the fold and the hub, the Protected B rule and a CI check that no new wrap uses X25519 after cutover (33.2-04).
- Where the new private keys live: keyring, Transit envelope, hub (33.2-05).
- The lead's switch and the Give keys card, and the scheduled rekey per cell (33.2-06), then the close-out (33.2-07).

Not in this phase:
- Signatures: Ed25519 stays (`eddsa-jcs-2022`, `did:webvh`, Phase 69 signing). ML-DSA is a later decision (research 10.4).
- The second suite ML-KEM-1024 + P-384 for Protected C and classified: reserved, not built (D-08).
- HPKE's `MLKEM768-P256` (draft-ietf-hpke-pq): a later version once it is an RFC (D-08).
- Credentials and `mayRelease` (Phase 71). The preparer calls `mayRelease` through 33.1-23's call sites; this phase changes only the wrap format underneath them.

## Implementation Decisions

- **D-01 (why its own phase):** The research put the wrap in Phase 71 (core). It is planned here instead, as 33.2, because every file it changes is Phase 31 and 33 staff replica code, it needs Phase 33's `roster.require` (33-03), feature registry (33-18) and hosted envelope (33-23) and nothing from credentials, and its deadline is a deployment gate ("before any site holds Protected B data"), not Stage 1. See 71-CONTEXT.md D-02.
- **D-02 (wire format, research 10.4):** Recipient keys: a P-256 public key (65 bytes, uncompressed) and an ML-KEM-768 encapsulation key (1,184 bytes). Wrap: a fresh ephemeral P-256 key; `Z_ec` = ECDH with the recipient's P-256 key; `(Z_pq, ct_pq)` = ML-KEM-768 encapsulation; HKDF-SHA256 (the SP 800-56C two-step KDF) with IKM `Z_ec || Z_pq` (the classical, listed secret first), salt SHA-256(`eph_pub || ct_pq`), info `near-ai/cell-wrap/v2` NUL cell NUL epoch NUL device writer NUL SHA-256(recipient P-256 key || recipient ML-KEM key), giving 32 bytes; AES-256-GCM over the 32-byte epoch key with the info as associated data. Wire: version byte 2 | eph_pub (65) | ct_pq (1,088) | iv (12) | tag (16) | ciphertext (32) = 1,214 bytes, base64url. Version 1 stays readable forever. Only `node:crypto` (Node 24.22 and 26.13.1 both have OpenSSL 3.5.9 and `crypto.encapsulate`).
- **D-03 (second device key binding):** Binding domain `near-ai-vscode/device-kem/v2\n`; the device's Ed25519 key signs the domain line, the P-256 key, the ML-KEM key and the device's writer id. Carried by: (a) a new kind `device.kem { device, p256, mlkem768, sig }`, in its own `device` family off the linear roster line, signed by the device itself or by a lead device (for the hub), valid only when `sig` verifies under the named device's Ed25519 key and the device is admitted and not revoked at the cited roster; (b) an optional `kem { p256, mlkem768, sig }` in the device descriptor and the join request, written only in projects that require `wrap@2`. Kinds are kept and relayed by older clients without changing state (`kinds.ts`), so `device.kem` is safe to publish before the switch. The safety words cover the kem keys when present. Private keys: the P-256 scalar and the 64-byte ML-KEM seed, in the keyring on a single computer, in the Transit-KEK envelope in a hosted session (33 D-61, beside the X25519 key), and in the hub's own key file.
- **D-04 (grant pages):** A v2 grant may be several signed pages per epoch. The founding page carries the label and the hashes of the other pages; each page is a signed object (purpose `staff-cell-grant`) no larger than `GRANT_MAX_BYTES`; the founding entry's `grant` hash commits to the founding page and therefore to every page. A missing page is the per-entry blob-missing state of 33-07, with its existing recovery. One page holds at most 600 v2 wraps; a 400-person HQ needs one page, 2,000 devices need four.
- **D-05 (rollout, `wrap@2`):**
  - `wrap@2` joins `KNOWN_REPLICA_FEATURES` only on a client where a start-up probe of ML-KEM-768 and P-256 succeeds; otherwise the client lacks the feature and a project that requires it shows the update sentence (33 D-06, D-67). No silent downgrade.
  - New shared projects require `wrap@2` at creation, beside `require@1` (33 D-08).
  - In an existing project, every device of the new version publishes its `device.kem` at its next open. The lead's Staff Room shows "Switch to post-quantum keys" once the lead's own device has published; the card lists any device that has not, by person name. Switching writes `roster.require { features: ["wrap@2"] }` (person key, step-up).
  - After the switch, each cell moves to v2 at its next epoch. The lead's client offers one scheduled rekey (`cell.rekey` reason `scheduled`, no new reason value) for every cell whose current epoch has v1 wraps, once every active device of that cell's holders has v2 keys, or at once with the stragglers left for later.
  - A device that has no v2 keys at a v2 epoch gets no wrap. When it publishes `device.kem`, a holder's client shows "Two computers are ready for keys. Give keys." and one action writes a later grant of the existing epoch (a mechanism Phase 31 already has). No device is removed for being late, and no state waits silently.
- **D-06 (cutover rule, one pure check):** `wrapFormatProblem(grant, requiredAt)`: in a project whose folded `roster.require` includes `wrap@2`, a grant page for an epoch founded after that entry that holds any v1 wrap is invalid. The fold and the hub call the same function, so they agree.
- **D-07 (the Protected B rule):** Independently of the switch, the wrap preparer never writes a v1 wrap for a cell whose label's routing tier is `local-only` or `deny` (by default Protected B, Protected C and every classified level, Platform direction decision 11). Such a cell in a project that has not switched cannot be shared until the lead switches; the card says so. This makes "every Protected B cell is on v2" an invariant rather than a schedule.
- **D-08 (reserved versions):** Version byte 3 is reserved for ML-KEM-1024 + P-384 (Protected C and classified, pending the Cyber Centre's advice) with feature id `wrap@3` reserved; readers refuse it as "not supported yet". A standard HPKE form (`MLKEM768-P256`, once an RFC) would take the next free version number.
- **D-09 (the CI check):** `architecture.test.ts` asserts that X25519 key agreement for wrapping appears only in the v1 wrap module and that its write function is reachable only from `wrapForDevice`'s pre-switch branch; a behaviour test drives every wrap path (first grant, member-removal rekey, handover stage and restage, delegate's grant, marking narrowing, earlier-epoch grants, the observer key change of 33.1) with `wrap@2` required and asserts no v1 wrap is produced. Both run in the required `test` job.
- **D-10 (order and branches):** Depends on Phase 33 merged (33-03, 33-18, 33-21 to 33-23). It edits roster and wrap files that 33.1's waves 1 to 7 and its observer waves also edit, so it merges between 33.1's wave 7 and wave 8 on the 33.1 integration branch order, or after 33.1 if that window has passed; the merge order is serial. It must be on `main` before any site holds Protected B data; until then 48.1-09 lists the X25519 wrap as an open crypto condition (other planner). Each plan works on `feat/phase-33.2-NN-<slug>` from `feat/phase-33.2-pq-keys`.
- **D-11 (no new dependency, words):** `node:crypto` only. Plain short sentences; "post-quantum" is explained once on the card ("protects shared work against future quantum computers"). Never log a key, a seed, a wrap or a shared secret.

- **D-12 (permanent shapes accepted, owner 2026-11-24, 33.2-01 Task 3):** every shape in 33.2-01's checkpoint is accepted as proposed (33.2-01-SUMMARY.md lists them): the v2 wire, KDF and info of D-02; four details D-02 left open (the recipient-key hash written as 64 lowercase hex in the info; the version byte not separately in the associated data; v1 recognised by its 92-byte length and no later version ever 92 bytes long; every version byte 3 and above read as "not supported yet"); the D-03 binding (signed bytes: domain line, P-256 key, ML-KEM key, writer id as 64 hex, 1,342 bytes) and `device.kem`; the D-04 grant pages, where the founding page is `{ cell, epoch, roster, labelSealed, wraps, pages }` with `pages` the sorted grant hashes of the other pages, and each other page has the same fields with an empty `labelSealed` and an empty `pages`; `wrap@2`, with version 3 and `wrap@3` reserved. Private parts are kept only as seeds (the 64-byte ML-KEM seed d then z, the 32-byte P-256 scalar), because BoringSSL in VS Code's Electron imports no other ML-KEM form (33.2-RESEARCH.md).
- **Compliance note (2026-11-24, checked against CCCS ITSP.40.111 v5):** P-256 ECDH (5.3), ML-KEM-768 (5.4, up to Protected B), HKDF-SHA256 as the SP 800-56C two-step KDF (10.2), AES-256-GCM and SHA-256 are listed; Ed25519 signatures are unchanged. The shapes add no compliance issue. Existing caveats stay: the validated-module condition (48.1-09 POA&M) and anything above Protected B (`wrap@3` reserved).

- **D-13 (execution, 2026-11-24, 33.2-02 and 33.2-04):** the signed invitation gains an optional `requires` (the project's required features, sorted, as `roster.require` writes them); a join request carries `kem` only when it lists `wrap@2`, and a lead's check refuses unexpected `kem` as malformed. Invitations are one-time files, not log entries. The lead's invitation flow must pass the folded required set (wired with 33.2-05); 33.1-18's observer invitation should use the same two fields. Publishing `device.kem` at open is behind `ReplicaProjectDeps.publishKem`, off by default, so a command's short open still writes nothing; the host turns it on where a project opens for live work.

- **D-14 (execution, 2026-11-24, 33.2-05 and 33.2-06):** requiring `wrap@2` at creation is `ReplicaProjectDeps.wrapV2AtCreation`, on unless set false (33.2-06, after every wrap path moved to `wrapForDevice`). The genesis names the lead device's post-quantum keys and the base cell starts v2. Format rule (`wrapPlan.formatFor`): new epochs in a switched project v2; earlier epochs there 'best' (v2 to a device with keys, else v1); unswitched projects v1, except a Protected B cell, refused with the D-07 sentence. A device without keys of the needed format waits; it never gets the older format instead.
