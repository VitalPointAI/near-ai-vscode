# Phase 33.2 Plan 01: cell-wrap/v2 tracer Summary

**A cell epoch key is wrapped to one device with P-256 ECDH plus ML-KEM-768, HKDF-SHA256 and AES-256-GCM in a 1,214-byte format, proven on every runtime we ship on and against the NIST and RFC vectors, with the permanent shapes accepted by the owner.**

## Accomplishments

- Runtime confirmations on Node 24.22.3, Node 26.13.1, VS Code 1.147's Electron (BoringSSL), code-server 4.144's bundled Node and the Theia preview image (`33.2-RESEARCH.md`). FIPS 203 ACVP keyGen 25/25, decapsulation 10/10, encapsulation (reverse) 25/25, key checks 10/10 on Node 24 and 26.
- `src/domain/replica/cellWrapV2.ts` (274 lines): the D-02 construction, `wrapForDevice` (refusals `no-v2-keys`, `no-v1-key`, `v2-unavailable`, never a fallback), `wrapFormatOf` (v1 by length, version 3 and above "not supported yet"), `probeWrapV2`.
- Frozen vectors in `test/fixtures/replica/cell-wrap-v2/vectors.json`; the vector made on OpenSSL opens under BoringSSL.

**probe rule:** `probeWrapV2()` is true only when `crypto.encapsulate` and `crypto.decapsulate` exist, the ML-KEM-768 key from the FIPS 203 ACVP keyGen tcId 26 seed has the published key's SHA-256, and one v2 wrap to that key plus the RFC 5903 P-256 scalar opens to the same 32 bytes; anything else is false and the client lacks `wrap@2`. Not cached; the feature registry calls it once at start-up.

## The owner's answer on the permanent shapes (Task 3)

Accepted on 2026-11-24 ("if I accept 33.2 shapes, do any of them introduce any compliance issues? If not, go ahead and accept them"), after the coordinator checked them against CCCS ITSP.40.111 v5: every primitive is listed (P-256 ECDH 5.3, ML-KEM-768 5.4 up to Protected B, HKDF-SHA256 as the SP 800-56C two-step 10.2, AES-256-GCM, SHA-256; Ed25519 signatures unchanged). No new compliance issue. Existing caveats: the validated-module condition (48.1-09 POA&M) and anything above Protected B (`wrap@3` reserved).

Accepted as proposed:
1. Wire: `02` | eph_pub 65 | ct_pq 1,088 | iv 12 | tag 16 | ciphertext 32 = 1,214 bytes, base64url. IKM `Z_ec || Z_pq`, salt SHA-256(eph_pub || ct_pq), info `near-ai/cell-wrap/v2` NUL cell NUL epoch NUL writer NUL hex SHA-256(P-256 key || ML-KEM key), also the AES-GCM associated data.
2. The four details: the key hash as 64 lowercase hex in the info; the version byte not separately in the associated data; v1 recognised by its 92-byte length and no later version ever 92 bytes; every version byte 3 and above reads "not supported yet".
3. Binding: domain `near-ai-vscode/device-kem/v2\n`, signed bytes domain || P-256 (65) || ML-KEM (1,184) || writer id (64 hex) = 1,342 bytes, signed by the device's Ed25519 key.
4. `device.kem { device, p256, mlkem768, sig }` in its own `device` family; optional `kem { p256, mlkem768, sig }` in descriptors and join requests, only in projects that require `wrap@2`.
5. Grant pages: founding page `{ cell, epoch, roster, labelSealed, wraps, pages }` with `pages` the sorted grant hashes of the other pages; other pages the same fields with an empty `labelSealed`; each a signed `staff-cell-grant` within 1 MiB, about 600 v2 wraps.
6. `wrap@2`; version 3 and `wrap@3` reserved.

- A self-consistent but wrong ML-KEM would pass a round trip alone and break interop between devices. The probe rule in the research file says so.
