# Phase 33.2 Plan 04: Where the new private keys live Summary

**Each computer, each hosted person and the hub keep their P-256 scalar and ML-KEM-768 seed beside their X25519 key, in the same protected place (secret storage, the Transit-KEK envelope, the hub's key file), and can publish the bound public keys.**

## Accomplishments

- Single computer: keys made once under the identity lock, read back, never replaced; `ensureDeviceKem` checks the probe, publishes once and never throws.
- Hosted person: the envelope's sealed content gains v2; a v1 envelope opens and gains the keys at the next session start under the same wrapped data key; `drop()` releases them with the X25519 key. `publishPersonKem` signs the binding and the entry with the person key; a refused confirmation returns "Confirm with your passkey or security key to work on shared projects." with the "Confirm with your passkey or security key" fix and leaves the keys made.
- Hub: `--generate-key kem`, optional `HUB_KEM_KEY`, hub file `kem` with its binding, `hubDeviceKemData` for the lead, and `openHubWrap` opening v1 and v2 wraps in the ring and at enrolment.

## Deviations from Plan

- **Publishing is opt-in at open [Rule 1]:** publishing on every open broke 17 command tests whose flows promise to write nothing. `publishKem` is off by default; the host turns it on where a project opens for live work (with the native engine, 33-24).
- **Hosted publishing is a function, not yet called at session start:** the workbench has no replica project until 33-24; `publishPersonKem` is ready for that call site.
- **Tests first:** written with the code and committed together for Tasks 2 and 3.
- **Known open issue, not changed here:** in hosted sessions the person's public key cannot yet be read from Transit under Phase 47 policy (owner deciding); tests pass the key in directly. No OpenBao policy was changed.
