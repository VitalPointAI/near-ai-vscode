## 4. HKDF-SHA256 and hashes

- `hkdfSync('sha256', …)` gives the RFC 5869 appendix A.1 output on all five runtimes [primary] https://www.rfc-editor.org/rfc/rfc5869 ; [verified by running].
- `sha3-256` is missing in VS Code's Electron (BoringSSL) and present on the OpenSSL runtimes [verified by running]. The v2 construction uses only SHA-256, so it is unaffected. A SHA-3 combiner such as X-Wing's would not run in the extension host, one more reason beside research 10.3 not to use it.

## 5. The combiner against RFC 10024

- RFC 10024 section 4.3 (Proposed Standard, August 2026): "For SecP256r1MLKEM768, the shared secret is the concatenation of the ECDHE and ML-KEM shared secrets", the ECDHE part being the x-coordinate. X25519MLKEM768 puts ML-KEM first "for historical reasons" [primary] https://www.rfc-editor.org/rfc/rfc10024.
- Section 5: SP 800-56C rev 2 approves HKDF over two shared secrets "with the condition that the first one is computed by a FIPS-approved key-establishment scheme", which is why the ECDHE secret comes first in SecP256r1MLKEM768 [primary].
- So D-02's IKM `Z_ec || Z_pq` follows the same order and the same reason: the listed classical secret first [inference from the two quotes].
- Section 6 warns that the TLS hybrid's security "relies crucially on the TLS 1.3 message transcript, and one cannot assume a similar hybridization is secure in other protocols" [primary]. D-02 supplies its own transcript: the salt is SHA-256(`eph_pub || ct_pq`), binding both ciphertexts, and the info carries SHA-256(recipient P-256 key || recipient ML-KEM key) with the cell, the epoch and the device writer. That binds every public input of both halves into the key, which is what the transcript does in TLS [inference].

## 6. Keys at rest: the Transit envelope

- 33-23 seals the X25519 private key as `{ v: 1, wrappedKey, iv, ciphertext, tag }`: AES-256-GCM under a data key that the person's Transit KEK wraps, kept in the key store (33-23 Task 2, 33 D-61) [repo]. The envelope seals bytes; it does not care which algorithm they belong to.
- The v2 private parts are a 32-byte P-256 scalar and a 64-byte ML-KEM seed (96 bytes). Sealing them with AES-256-GCM under a fresh data key, opening them, and re-importing gives the same P-256 and ML-KEM public keys on all five runtimes [verified by running]. So the envelope carries them as it carries the X25519 seed, beside it; Transit never needs ML-KEM or ECDH (research 10.2).
- 33-23's `openEncryptionKey` is not yet on `origin/main` or `origin/feat/phase-33-engine-wave-1` [repo, checked 2026-11-24]. 33.2-05 adds the v2 parts once it lands.

## 7. Who lacks wrap@2

- Every runtime probed today passes, including VS Code's Electron build with BoringSSL [verified by running].
- The extension's floor is `engines.vscode >= 1.101.0` [repo]. Older VS Code builds ship an older Electron and Node; whether a given one has `crypto.encapsulate` and `ml-kem-768` is [unverified]. The probe decides per process, so such a client lacks `wrap@2` and shows the update sentence in a project that requires it (33 D-06, D-67). It never falls back to v1.
- A runtime whose crypto library lacks ML-KEM may still define `crypto.encapsulate` (for RSA or EC KEMs). So the probe does a full round trip, not a function check alone.

probe rule: probeWrapV2() returns true only when crypto.encapsulate and crypto.decapsulate are functions and one cell-wrap/v2 wrap of a fixed epoch key to a recipient made from fixed seeds (ML-KEM-768 from its 64-byte seed in the PKCS#8 seed form, P-256 from a 32-byte scalar) unwraps to the same 32 bytes; any other result or any throw is false, and the client then lacks wrap@2.
