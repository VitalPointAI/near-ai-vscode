# Phase 33.2 Plan 07: The switch, Move and Give keys Summary

**The lead switches shared work to post-quantum keys, moves it to new keys and gives keys to late computers from the native Staff Room. Each step is one card with one action, and each card goes away when it is done.**

## What a person sees

| Card | Who sees it | Words | Actions (button label) |
|---|---|---|---|
| Switch | a lead or deputy computer that has published its post-quantum keys, before the switch | "This protects shared work against future quantum computers." and, when someone has no keys yet, "These people have a computer that has not published its post-quantum keys yet. It gets its keys once it does: Pat Analyst." | Switch to post-quantum keys |
| Move | a lead or deputy computer after the switch, while any part still has older keys | "Some shared work still has older keys. Moving gives it new post-quantum keys." and, while a part waits, "Part of it waits for a computer that has not published its post-quantum keys. It moves when that computer does, or now if you choose, and that computer gets its keys later." | Move all shared work to the new keys (ready parts); Move it now without waiting (while any part waits) |
| Give keys | a computer that holds a part's current key, while a late computer waits for it | "Two computers are ready for keys. Give keys." | Give keys |

Refusals, word for word (`STAFF_ROOM_TEXT`):
- "This shared work already uses post-quantum keys."
- "Only the lead or the deputy can do this."
- "Your computer has not published its post-quantum keys yet. It does when you next open this shared work."
- "This shared work has not switched to post-quantum keys yet."
- "Nothing is ready for new keys right now. Look again."
- A person key that wants a fresh confirmation gets "Signing needs a fresh confirmation with your passkey or security key." with the link that confirms it, the same as a decision.

## Accomplishments

- **Task 1, the card model** (`5c5c63f0`): Switch, Move and Give keys. Switch names the people whose computers have not published keys. Move lists ready and waiting parts. Each card disappears with its condition, and a table test walks every transition.
- **Task 2, the actions** (`5c5c63f0`):
  - `switchToV2` writes one `roster.require` through the checked append. Two leads switching at once give one switch, and a refused step-up writes nothing.
  - `moveCellsToV2` writes scheduled rekeys whose wraps are all v2.
  - `giveKeys` writes a later grant of the current key, to late computers only.
- **Task 3, the cards in the native Staff Room** (`6f5869e1`):
  - The Staff Room model now accepts `wrapCards` and turns them into its own cards. This is the part of Task 1 that waited for `staffRoomLive.ts`.
  - The live engine gives the room this computer's cards and runs the three actions.
  - The room's channel carries the three actions, and the widget sends them.
  - The cards draw with the existing card renderer. The only view change is three codicons.

## Deviations from Plan

1. **[Rule 3] Files outside Task 3's list.** Tests run in the backend, but a button needs a channel method and a widget case to reach them. So the work also touches:
   - `common/staff-room.ts`: the card kinds, the three methods and the refusal sentences.
   - `staff-room-service.ts`: the three methods and the cards in the room.
   - `staff-engine.ts` and `staff-engine-entry.ts`: the bundle's names.
   - `staff-room-view.ts`: three icons.
   - `staff-room-widget.ts`: four action cases.
   - `staffRoomLive.ts` and `wrapSwitchModel.ts`: the card sentences and the card conversion, both Task 1 files.
2. **"No new widget code" holds for drawing.** Cards with actions already draw through the shared renderer; the view only gained three entries in its icon map. Sending an action needed four cases in the widget's `act`. The decision dialog's done, refused or step-up handling became one `signed()` helper, and decisions and key actions both use it (behaviour unchanged; the 33-26 tests pass).
3. **[Rule 2] Move never waits without an action.** Before any computer is ready, the plan's single Move action would have had nothing to move, so the card gets "Move it now without waiting" while any part waits (D-05: "or at once if the lead chooses"). This closes T-33.2-22.
4. **Refusal sentences are in `common/`** (`STAFF_ROOM_TEXT`), per the 33-26 rule. The card sentences are `*_TEXT` constants of the model, as Task 1 set them. The copy lint reads both.
5. **[Coordinator, glossary] The Move button says "Move all shared work to the new keys".** The plan said "Move every cell to the new keys", but the glossary says people never see "cell" in its key meaning, and the glossary wins. The constant `MOVE_CARD_TEXT`, the workbench test that asserts the button, the 33.2-07 plan's must-have and objective, and the 33.2-08 plan's spec step now use the new words. The model test asserts through the constant. The copy lint passes.
6. **Tests first.** Both test files were written before the code. The first run after the code passed, so no failing run was recorded.
