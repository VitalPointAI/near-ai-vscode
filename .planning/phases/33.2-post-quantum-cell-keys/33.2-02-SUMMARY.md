# Phase 33.2 Plan 02: device.kem Summary

**Each device, hosted person and hub can publish a P-256 key and an ML-KEM-768 key bound by its own Ed25519 signature; the fold and your organization's server check it with one function, and the six safety words cover the keys when a join request carries them.**

## Accomplishments

- `device.kem` in its own `device` family (55 kinds), with exact shape checks; the optional descriptor `kem` is checked when a device is added (`bad-binding` otherwise) and kept on the device record.
- The roster fold places `device.kem` after the line, like session certificates: refusals `kem-binding-invalid`, `kem-device-not-admitted`, `kem-wrong-writer`; every fold order gives the same `kemKeysAt`.
- Invitations may list the project's required features (`requires`); a join request carries `kem` only when that list has `wrap@2`, and an older-style check refuses unexpected keys as malformed.
- The safety code appends the joiner's P-256 and ML-KEM keys after the nonce when present; without them the words are unchanged (the frozen v2 words still pass).
- The hub judges each `device.kem` append with `deviceKemProblem` at the cited roster; a roster it does not hold yet is stored, as for roster entries.
