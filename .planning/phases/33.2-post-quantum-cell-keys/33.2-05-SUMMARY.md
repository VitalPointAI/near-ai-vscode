# Phase 33.2 Plan 05: wrap@2 and the cutover rule Summary

**Once a project requires wrap@2, no epoch founded afterwards may carry an X25519 wrap: the fold and your organization's server apply the same function; computers and hubs know wrap@2 only where the cell-wrap/v2 probe passes.**

## Accomplishments

- `wrapFormatProblem`: refuses `old-wrap-after-switch` for any v1 wrap on any grant or page of an epoch founded after the switch; earlier epochs may still be granted either way; every fold order agrees.
- The hub refuses such a grant at append with the same reason (judged against the roster it holds, and again by the fold for epochs founded in the same batch).
- `knownReplicaFeatures(probe)`; the client (`clientReplicaFeatures`) and the hub (`hubReplicaFeatures`) probe once; a computer without wrap@2 stops a project requiring it with the update sentence.
- `ensureRequireArmed({ withWrapV2 })` writes require@1 and wrap@2 in one entry at creation; an existing project never gains wrap@2 by being opened.

- **wrap@2 at creation is off by default [Rule 4-like sequencing, decided as the least risky reading]:** turning it on made 153 existing tests fail, because every host wrap path still writes X25519 grants, which a switched project now refuses. `wrapV2AtCreation` is off until 33.2-06 moves the paths to `wrapForDevice`; then the host turns it on. Tests cover it with the option on.
- **Test changes:** `staffHubTransport` now expects the session answer to announce wrap@2 (D-05); `replicaBoundaries` lists `wrapFormat` as hub-side; `.dockerignore` lets it into the hub image.
- **Base cell at creation stays v1:** its epoch is founded before the switch, so the rule allows it; moving it to v2 belongs with the wrap paths (33.2-06).
