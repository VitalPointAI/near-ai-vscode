# Phase 33.2 Plan 06: Every wrap path through the entry point Summary

**Every way a cell key reaches a device now goes through `wrapForDevice` with the format `formatFor` gives; new shared projects start switched; a Protected B cell is never wrapped the older way; a CI check keeps it so; SECURITY.md says which wrap protects shared work.**

## Accomplishments

- `wrapPlan.ts` decides the format in one place; `labelCells`, `membership` (admission, rekeys, clearance, legacy at handover), `hubMembership` and the genesis use it. `wrapEpochKey` is called only in `cellKeys.ts` and `cellWrapV2.ts`.
- New projects require `wrap@2` at creation: the genesis carries the lead device's post-quantum keys and its base cell starts v2. Joining devices send their keys (the invitation names the required features) and the admission writes them into the roster; hubs carry theirs in the hub file.
- Devices open v2 wraps: the key ring and the hub use `unwrapForDevice`.
- The 153 tests that failed with `wrapV2AtCreation` on were fixed by moving the paths, not by changing assertions (see Deviations for the test-side changes).

## Deviations from Plan

- **Extra paths found [Rule 3]:** `hubMembership.ts` (the hub's grants) and the genesis in `replicaProject.ts` also hand out keys; both moved. `giveLegacy` (the legacy cell at handover) is the handover path that exists today; the 33.1 handover stage, restage, delegate's grant and marking narrowing are not on this branch, and their future code is held to the same rule by the architecture check.
- **membership.ts is frozen at 1,537 lines:** the per-device grant and new-epoch page code lives in `wrapPlan.ts` (`grantsTo`, `newEpochPages`); `rekeyPlans`, `writeRekeys` and `RekeyOutcome` are exported for 33.2-07.
- **Key ring and welcome [Rule 1]:** a device could not open v2 wraps (key ring) and a welcome did not carry `device.kem`; both fixed.
- **Secret scanner [Rule 1]:** the `kem` fields of join requests and hub files are generated public values; added to the scanner's exempt paths (random base64 matched a token pattern by chance).
- **Test-side changes, no assertion loosened:**
  - Hand-built test grants (`staffReplicaMembership` cell helpers, `staffReplicaProject` MJ-07 founding grant) now go through the entry point, and the hand-built join in `joinScenario` carries the keys as the product does.
  - Tests that open a wrap themselves use the device's real keys through `unwrapForDevice` (MJ-04, the hub test's `hubOpens`); the test hub has a kem key like a hub made with `--generate-key kem`.
  - `staffRequireGate`: a newer version knows everything this one does (now including `wrap@2`), and a new project requires `require@1` and `wrap@2`.
  - `staffKemKeys`: the publishing tests run on a project made before the switch (where publishing at open matters), and a new test shows a switched project needs no `device.kem` because the genesis names the keys.
  - `staffReplicaMigration`'s fixed randomness also fixes P-256 key pairs and stands in for ML-KEM encapsulation (OpenSSL takes no outside randomness for it; nothing in a conversion opens its own wraps), so the interruption tests still compare byte for byte.
