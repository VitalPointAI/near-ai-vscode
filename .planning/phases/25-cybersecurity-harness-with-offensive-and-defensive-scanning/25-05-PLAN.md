<objective>
Build the run engine: the append-only hash-chained ledger store with evidence blobs and pruning (CYBER-11, D-27, D-28), the critic that verifies findings with bounded re-probes (CYBER-05, D-22), the host-tool runner that executes a detected tool through the approval-gated shell path and stores its verbatim output as evidence (D-12's missing-tools discipline, D-27 kind 2), and the four-role run orchestrator that drives the protocol driver through planner/operator/critic/reporter, records every step, compacts context, replays runs, and hands a complete result to the future panel (CYBER-04, D-02, D-20).

Purpose: This is the heart of the harness — everything the panel (25-07) and the report/export (25-07) consume is produced here, and the honest-failure behavior (D-19's visible incompatibility, D-24's verdicts, D-12's missing-tools discipline) is defined by this plan. D-27 evidence kind 2 is delivered here because the evidence store lives here: no other plan has both the blob store and the ledger entry to hang the verbatim bytes on.
Output: four service/agent modules, four test files.

Recorded planning choices:
- **The one execution path (B1 reconciliation, D-02 vs D-19).** Step execution is `startCyberRun` + `CyberProtocolDriver` (this plan). There is exactly one path, and it is JSON-in-text: the driver asks a model for plain text, `parseStep` extracts a Step, the run executes it. The assistant message's `tool_calls` array is never read — 25-08 attaches cyber tools to the chat turn for *permission and display reasons only*, never as a dispatch mechanism. What D-02 reuses from the chat path is the surrounding machinery, not the loop: the approval card (`AgentConversation.askApproval`), the streaming event surface, the transcript/history, and the stop control. Concretely: (a) steps that need approval call the same `requestApproval` seam the chat loop calls, so the user sees one approval UI; (b) run events are posted through the conversation's `post` so they land in the existing chat transcript and (for the panel) its own listener; (c) the signal comes from the conversation's abort controller plus the global emergency stop. The chat `AgentRun` loop is *not* the executor: `AgentRun` is native-tool-calling-shaped (src/agent/loop.ts:218-233 dispatches `assistant.tool_calls`), which a raw-completion model never produces, so making it the executor would break D-19. 25-08 Task 2 states and tests this. Both decisions hold; neither is weakened.
- Ledger replay is offline by construction: replayRun reads the stored ledger + evidence and re-renders findings; it has no network path at all.
- Pruning (discretion): evidence blobs keep the newest 3 runs per engagement by default (const PRUNE_KEEP_RUNS = 3); ledger entries are never pruned (append-only forever, they are small); the prune record names what was removed.
- The four roles share one model (D-20) with four prompts; the run passes `compactSteps` output when the step history exceeds the keep window.
- Cosmetic scope call: findings are rendered as text into the chat transcript and the panel timeline; the run never builds markup.
- **D-27 kind 2 ownership.** Raw host-tool output (nuclei JSONL, nmap XML, semgrep SARIF, trivy JSON) is captured by `cyberHostTools.ts` in this plan, not by 25-03. 25-03 owns *detection* (TOOL_CATALOGUE + detectTool + missingToolsNote) and its prohibition that detection never installs anything stands unchanged. This plan owns *execution plus verbatim capture*, because the evidence store and the ledger entry's evidenceHash exist here — a tool run in 25-03 could not have been hashed into the chain. Execution rides `ShellSession` from src/agent/shell.ts (the bashTool path at src/agent/tools.ts:332) so the tool run is a capability-'shell' action that passes decidePermission and the engagement grant exactly like every other intrusive action (D-04).
- **Verbatim means bytes.** `ShellSession.run` returns `truncate`d text (src/agent/shell.ts:175, a 30 000-char budget). The host-tool runner therefore captures raw stdout separately from the truncate step — its injectable runner returns the untruncated stdout buffer — and hands those bytes to `CyberEvidenceStore.put` untouched. Only the finding text and the model context see the truncated form. The stored blob is the evidence of record, so its SHA-256 covers exactly what the tool printed.
</objective>
