# Phase 45.1 Plan 01: The label table for allies and the signed label binding Summary

A Protected B label releasable to CAN and GBR now goes out through your organization's signed table as an abstract NATO-readable label (policy identifier, classification value, one Releasable To category) and comes back as the same label; 1,000 random labels round-trip exactly. A label is tied to its content by a signed binding that names only a staff session key or your organization's release key, and any change to the content, label, mapping version, time or proof is refused. Nothing ships with NATO values, so every export is refused until your organization's security officer sets the table.

## What was built

- **Task 1 (tracer):** the `labelInterop` section (feature `label-interop@1`), `mapOut` and `mapIn`.
  - `label-interop@1` is appended after `agreements@1` in `FEATURE_IDS`, `labelInterop` after `agreements` in `POLICY_SECTIONS` and `SECTION_FEATURES`. The section is read in `parseSections` after `agreements`. Its policy editor title is "How labels are written for allies".
  - `mapOut` refuses when no table is in force (`not-set`, the shipped default), for a label releasable to no one, for a label with handling flags, and for any scale, level, compartment or releasability token without an entry (`no-mapping`).
  - `mapIn` reads the partner form strictly (`malformed` for unknown keys, unsorted values, control characters or an unknown category type), refuses another mapping version, and refuses any policy identifier, classification, category or value the table does not list.
  - The tracer gate re-ran the task's check end to end after Task 2 and passed.
- **Task 2:** `bindLabel(signer, facts)` and `verifyLabelBinding(value, content, { publicKey, signer?, mapping?, label? })`.

### The section shape as built (feature `label-interop@1`)

```
labelInterop: { v: 1,
  version: whole number 1 to 2^31-1 (the mapping version),
  scales: { <scale id of labels.scales>: {            (1 to 16 scales; no two share a policy)
    policy: text (1..256),                           the abstract policy identifier
    levels: { <level on that scale>: text },          classification value; at least one; no value twice
    compartments: { <TOKEN>: { category, value } },   restrictive category values; no pair twice; up to 256
    releasableTo: { category: text, values: { <TOKEN>: text } }   the one permissive category; no value twice
  } } }
```

A compartment's category may not be the `releasableTo` category. `RELEASABLE-TO-NONE` has no entry anywhere.

### The partner form (`ExternalLabel`)

```
{ mapping: number, policy: string, classification: string,
  categories: [{ tag: string, type: 'permissive' | 'restrictive', values: sorted string[] }] }   sorted by type, then tag
```

### `LabelBinding` as built (33.1-21 cites these fields)

```
{ format: 'label-binding/1',
  label: { scale, level, compartments, releasability, handling },   your organization's label
  mapping: whole number 0 to 2^31-1,      0 = a release copy in your organization's form; >= 1 = the labelInterop version of an export
  contentHash: 64 lowercase hex,          SHA-256 of the content (contentHashOf)
  signer: 'session:<writer>' | 'org-release:<site>',
  time: 'YYYY-MM-DDTHH:MM:SS.sssZ',
  proof: DataIntegrityProof (eddsa-jcs-2022, proofPurpose assertionMethod, verificationMethod = signer) }
```

### Refusal ids

- **`LABEL_INTEROP_REFUSALS`:** not-set, no-mapping, releasable-to-none, handling, mapping-version, malformed.
- **`LABEL_BINDING_REFUSALS`:** malformed, signer-form, wrong-signer, content-changed, label-changed, mapping-version, signature.
- **Section:** the gate's shape reasons (`not-allowed-here`, `duplicate`, `empty-list`, `wrong-type`, `unknown-field`, `unknown-version`).
