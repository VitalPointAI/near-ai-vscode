# Phase 45.1 Plan 02: Base TDF objects and the exchange keys in OpenBao Summary

Your organization can now write a TDF object a partner's OpenTDF tools should read (AES-256-GCM payload, the key wrapped to the partner's EC or RSA key, the policy binding, GMAC segment hashes and the root signature, and the signed label binding as an assertion), and open one addressed to it through a decrypt callback with every binding checked. OpenBao as code creates the receiving key `exchange-receive-<site>` and the release key `release-<site>`, both non-exportable, each usable only by a named officer after a step-up. Reading the reference implementation found that partners' stock tools wrap RSA keys with OAEP SHA-1, which OpenBao cannot open, so that is gap G455.

## What was built

- **Task 1 (research):**
  - `45.1-RESEARCH.md` records the manifest, the key access objects, the wrapping, the policy binding, integrity, assertions, the OAEP hash chosen and what waits for 45.2.
  - Sources: the specification at commit 0a30366b (VERSION 4.3.0); the reference implementation `opentdf/platform` at f353c9b6 where the text is silent; OpenBao at 826bf075 for Transit's RSA decrypt. Each was read as text and nothing was run.
  - `manifest.schema.json` is copied unchanged. `examples.json` holds the specification's JSON examples with their comments removed and without the example NATO label. Both carry their BSD-3-Clause-Clear licence and source commit.
- **Task 2 (`tdf.ts`, 460 lines):**
  - `buildTdf({ content, external, binding, recipient, mimeType?, segmentBytes? })` refuses a binding over other content or another mapping version, an EC key not on P-256, an RSA key under 2048 bits and an RSA recipient with no OAEP hash.
  - `readTdf(object, { decryptKey, table, bindingKey })` never throws. It checks, in order: the structure, the one key access, the policy binding, each GMAC segment hash, the root signature, the payload, every assertion's JWS, the label assertion, the binding's signer, `mapIn` through the table, then `verifyLabelBinding` against the content and the label read back.
  - `readTdfManifest` reads the structure the specification marks required, including the specification's own example manifest.
  - `unwrapWithPrivateKey` opens EC or RSA key access with an in-process key, for tests and envelope-held keys.
- **Task 3 (OpenBao as code):**
  - Two keys, two single-path policies, two duty step-up roles bound to the step-up acr and the named subjects, and deny blocks in `key-move.hcl`.
  - A second run changes nothing. A key that already exists in another form (for example exportable) stops the apply with a plain message.
  - The site file gains `exchangeOfficers` and `releaseAuthorities` (empty by default), completing hand-off H-10's 45.1 part.

### The OAEP hash chosen, and why

- **Exports to an RSA key:** the hash the partner's server unwraps with, named per recipient. The OpenTDF reference server uses SHA-1 (`lib/ocrypto/asym_decryption.go`). An EC key is preferred when the partner offers one.
- **Our receiving key:** SHA-256, because OpenBao Transit decrypts RSA only with OAEP SHA-256 (`sdk/helper/keysutil/policy.go`) and the key must stay non-exportable (D-07). A partner's stock tool cannot address an object to it. The partner wraps with SHA-256, or addresses the object to its own key access server, which 45.2-06 reaches by rewrap. This is G455, and the ITSP.40.111 standing of SHA-1 in OAEP is unverified there.

### Refusal ids

`TDF_REFUSALS`: malformed, unsupported, key-access, policy-binding, integrity, payload, assertion, no-label, signer-unknown, label-binding (with the binding's own reason in `bindingReason`), label-mapping.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Security] Key moves could have made the exchange keys exportable**
- **Found during:** Task 3.
- **Issue:** `key-move.hcl` lets two custodians reconfigure (`transit/keys/+/config`), export, back up, restore and import any Transit key. That would let the receiving key become exportable, or the release key be replaced.
- **Fix:** exact-path deny blocks for both keys (config, import, import_version, export, backup, restore). An exact deny wins over the `+` paths. Test: "nothing can export, back up, reconfigure, replace or sign with the exchange keys, not even a key move".
- **Commit:** 117be94c.

**2. [Rule 3 - Blocking] Policies needed the site's key name**
- Policy files are static, so `apply.mjs` now fills an `@SITE@` placeholder.
- `siteName` must be lowercase letters, digits and dashes, because it names the keys. The site file's description says so, and any other value stops the plan.
- **Commit:** 117be94c.

**3. Existing openbao tests adjusted, nothing weakened**
- "every per-person path is templated on the entity" skips exactly the two named site-key paths. Those paths have their own tests, which hold them to named officers after a step-up.
- "every key-move path needs two approvals" reads the control-group blocks; the new deny blocks are checked in their own test.
- **Commit:** 117be94c.

**4. Plan text against the copied data**
- The plan asked for "two or three example manifests". The specification has one full manifest example, plus key access, segment and payload examples, so all of them were copied.
- The example NATO label in that manifest was left out, by the phase rule that no NATO label value is kept in the repository.
- The key access example's `wrappedKey` is shortened with "..." in the text, so the test reads it with a whole key.

**5. Order of work**
- In Tasks 2 and 3 the tests and the code were written together. Their failing-first run was not recorded separately: the first capped run had one failing test (the shortened example key), which was fixed in the test.

**6. Helm for the render tests**
- `HELM` pointed at the pinned `compliance/out/tools/linux-amd64/helm`. It was copied, and is git-ignored, from a sibling worktree's CI tool download.
- Without it, 12 render tests fail with "helm was not found", which is infrastructure and not code.
