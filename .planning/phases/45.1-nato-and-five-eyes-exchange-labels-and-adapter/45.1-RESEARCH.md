## 1. Findings in one page

1. **The tag `4.3.0` is not the current text.** The git tag `4.3.0` (2023-01-04) has no JSON schema; the main branch still says 4.3.0 in `VERSION` and carries `schema/OpenTDF/json-schema/schema.json` (added 2025-04-08). We follow the main branch at the commit above and cite it by commit [spec].
2. **The version field has three names.** `manifest.md` requires a top-level `tdf_spec_version`; `schema.json` requires `payload.tdf_spec_version`; the reference writes a top-level `schemaVersion` (value `4.3.0`) and reads `tdf_spec_version` at either place only when `schemaVersion` is absent. A manifest with no version is read as "legacy" (before 4.3.0), which changes how hashes are encoded [spec, ref: `sdk/manifest.go`, `sdk/tdf.go` `isLegacyTDF`]. **We write all three, each `4.3.0`.**
3. **RSA key access is RSA-OAEP with SHA-1 in the reference** (`rsa.EncryptOAEP(sha1.New(), ...)` and `rsa.OAEPOptions{Hash: crypto.SHA1}`, MGF1 with SHA-1, empty label) [ref: `lib/ocrypto/asym_encryption.go`, `asym_decryption.go`]. The specification says only "e.g., using RSAES-OAEP" [spec: `protocol/protocol.md`].
4. **OpenBao Transit decrypts RSA with OAEP SHA-256 only** (`rsa.DecryptOAEP(sha256.New(), ...)`, no hash option) [bao: `sdk/helper/keysutil/policy.go`]. So **an object a stock OpenTDF tool wraps to our RSA receiving key cannot be opened by `exchange-receive-<site>`**. See section 5 for the choice.
5. **EC key access is ECDH on P-256, then HKDF-SHA256 with salt SHA-256("TDF") and no info, giving a 32-byte AES-256-GCM key that seals the payload key with a random 12-byte nonce** (stored nonce, then ciphertext, then the 16-byte tag). The key access object's `type` becomes `ec-wrapped` and it carries `ephemeralPublicKey` (the sender's one-time public key, PEM) [ref: `sdk/tdf.go` `generateWrapKeyWithEC`, `tdfSalt`; `lib/ocrypto/ec_key_pair.go` `CalculateHKDF`, `aes_gcm.go`]. Neither `ec-wrapped` nor `ephemeralPublicKey` is in the specification text [spec absence].
6. **The policy binding is Base64 of the lowercase hex of HMAC-SHA256(payload key, the Base64 policy string)** in the reference [ref: `createPolicyBinding`]. The specification says "A Base64 encoding of HMAC(KEY, POLICY)" [spec: `key_access_object.md`]; its own example decodes to a hex string, which matches the reference. We write the hex form and accept both forms on read.
7. **Integrity (4.3.0, not legacy):** each segment is sealed on its own with AES-256-GCM and a random 12-byte nonce, stored as nonce, ciphertext, tag (28 bytes more than the plaintext). The segment hash for `GMAC` is the segment's GCM tag; the root signature is HMAC-SHA256(payload key, every segment hash in order); both are written as Base64 of the raw bytes (legacy files Base64 a hex string) [ref: `hmacIntegrity`, `readAEADTag`, `rootIntegrity`; spec: `integrity_information.md`].
8. **Assertions are checked by default in the reference reader, with HS256 over the payload key.** An assertion's binding is a JWS whose claims are `assertionHash` (lowercase hex SHA-256 of the RFC 8785 form of the assertion without `binding`) and `assertionSig` (Base64 of the aggregate segment hash followed by the raw assertion hash) [ref: `sdk/assertion.go` `signAssertions`, `GetHash`; `sdk/tdf.go` reader]. A partner's tool refuses an object whose assertion binding does not check, so our label binding assertion carries one.
9. **The reference reads a statement's object `value` back as a string** (it re-encodes the object with Go's encoder before hashing) [ref: `Statement.UnmarshalJSON`]. An object value would hash differently on their side. **Our assertion's statement value is a string** (the JSON text), which hashes the same on both sides.
10. **The schema has two quirks:** the key access `required` list sits on the array, not on its items, and names `sid` and `kid` (which `key_access_object.md` calls optional); and `encryptionInformation` itself has no `required` list [spec: `schema.json`]. We write `kid` and `sid` so both readings are satisfied.

## 2. The manifest

|---|---|---|

| `encryptionInformation.type` | `split` | [spec] |

| `encryptionInformation.method` | `algorithm` `AES-256-GCM`; `isStreamable` (true in the reference); `iv` (Base64, required by the text; the reference writes it empty, because each segment carries its own nonce) | [spec: `method.md`; ref: `chunked_writer.go`] |
| `encryptionInformation.integrityInformation` | `rootSignature { alg: HS256, sig }`, `segmentHashAlg` `GMAC`, `segments [{ hash, segmentSize, encryptedSegmentSize }]`, `segmentSizeDefault` (reference 2 MiB), `encryptedSegmentSizeDefault` (size + 28) | [spec; ref: `tdf_config.go`] |
| `encryptionInformation.policy` | Base64 of the policy JSON `{ uuid, body: { dataAttributes: [{ attribute }], dissem: [] } }`; an attribute is a URI `{namespace}/attr/{name}/value/{value}` | [spec: `policy.md`, `attributes.md`] |
| `assertions` | Optional; section 4 | [spec: `assertion.md`] |

The container is a ZIP archive with `manifest.json` at its root and the payload in `0.payload` [spec: `manifest.md`; 45.2-RESEARCH section 6].

The post-quantum types are not in the specification text and wait for ACP-240's later editions (G356, 45.1 deferred ideas).

## 4. Assertions and their binding

- An assertion is `{ id, type (handling | metadata), scope (tdo | payload), appliesToState (encrypted | unencrypted), statement { format, value, schema? }, binding { method: jws, signature } }` [spec: `assertion.md`, `assertion_statement.md`, `assertion_binding.md`].
- The text asks only that the binding cover "the assertion content and sufficient TDF context ... to prevent replay" [spec]. The reference's binding is in finding 8; it ties the assertion to this object's payload through the aggregate segment hash [ref].
- Our label binding travels as one assertion: `id` `label-binding`, `type` `handling`, `scope` `payload`, `appliesToState` `unencrypted`, `statement { format: string, value: <JSON text of { external, binding }> }`. `external` is the label in the partner form (45.1-01's `ExternalLabel`) and `binding` the signed `LabelBinding` (45.1-01). Its JWS binding follows the reference (HS256 over the payload key), so a partner's tool accepts the object. The label binding's own signature (your organization's release key) is what proves who bound the label; the JWS only ties the assertion to this object.

## 5. The OAEP hash chosen, and why

- **Wrapping to a partner's RSA key:** the hash is the partner's, so the recipient record names it (`oaepHash`). A partner running the OpenTDF reference key access server needs **SHA-1** (finding 3); a partner whose server uses SHA-256 says so. Nothing is defaulted. SHA-1 here is the OAEP padding hash, not a signature, but whether CCCS ITSP.40.111 accepts it for this use is **[unverified]** (gap G455).
- **Our own receiving key `exchange-receive-<site>`:** **SHA-256**, because OpenBao Transit decrypts RSA only that way (finding 4) and the key must stay non-exportable (D-07). An object a partner's stock OpenTDF tool wraps to it with SHA-1 cannot be opened; the partner must wrap with SHA-256, or address the object to their own key access server, which Phase 45.2-06 reaches through rewrap. This is gap G455 too.
- **Partner EC keys** (`ec:secp256r1`) avoid the question for exports and are preferred when the partner offers one [inference].

## 6. What we build now (45.1-02 Task 2)

- `buildTdf` writes the manifest and the payload as objects (the ZIP container is packed where the file is handed over, 45.1-04): version fields of finding 2, one key access object to the partner's key (RSA-OAEP with the named hash, or the EC scheme), the policy and its binding, AES-256-GCM segments with GMAC hashes and the HS256 root signature, and the label binding assertion with its JWS.
- The policy's `dataAttributes` are empty in part 1. Attribute URIs need the partner's attribute namespaces, which come with the partner records of Phase 45.2-06 (hand-off H-2); until then the label travels in the assertion, checked by the label binding's signature, the assertion's JWS and the root signature.
- `readTdf` opens an object addressed to us through a decrypt callback (OpenBao Transit at a site, a test key in tests) and checks, in order: the manifest's shape, the key access, the policy binding, every segment hash and the root signature, the payload, the assertion binding, and the label binding against the content and the label read back through your organization's table.

- Conformance against partners' sample objects and a round trip with the OpenTDF quickstart's server (45.2-10, 45.2-12). Until then, interoperability of what 45.1 writes is **unverified**: it follows the reference implementation's code, not a test against it.
