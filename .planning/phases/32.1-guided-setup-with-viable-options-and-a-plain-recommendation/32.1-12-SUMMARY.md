# Phase 32.1 Plan 12: Apply engine summary

Apply runs the reviewed changes as ordered, idempotent steps (signed label, connection, project layer, proposals, answers) after a fresh preflight, records one chained `setup.guide.applied` record, and never widens your organization's rules or lowers a label.

Codex built the three tasks on `feat/phase-32.1-get-started` (commits `8bc96934`, `546bf956`, `1fe91398`, `ede4d723`, `0999dd63`; see the plan's execution checkpoint). This closeout settled the three items that were left open.

## Open items closed

1. **Deadline at the write boundary.** Decided: no Apply-level timer (the plan's `APPLY_STEP_TIMEOUT_MS` is not added). `runApply` already waits for each step's terminal result. The label map, project.json and audit writers each take a file lock whose wait is bounded (`stateMirrorLock`, 120 s) and throws before writing. The proposal and connection steps wait on the person, whose editor or flow owns the lifetime. A timer that reported `failed` while a write could still land would leave the record and the project disagreeing. The one gap was the message: a busy label lock reported "Sign the label file again with Set Label first", which sent the person to Set Label for a valid file. It now reports `LABEL_BUSY_TEXT`, and a re-run finishes only the label (`db1d615b`).
2. **Contact-only guidance under your organization.** The controller used to drop the clearance proposal under an organization layer and left only "Waits for your rules change". `changeList` now takes `clearanceContact`. With it, the gap is one waiting item, "Your organization's rules: ask {contact} to add your clearance for {label}.", where `{contact}` is the verified policy's security contact. Apply records the item as waiting until the organization's rules cover the label (`adf6d744`).
3. **Discovery approvals, live revalidation and host wiring.** These are already integrated. Discovery approvals open through the shared `proposalStep` (`guideDiscovery.ts`). The controller's preflight re-reads the signed snapshot, re-checks the chosen option and re-decides the route before any write (plan 13). The run factory (`getStartedRun.ts`) wires the real host. The full acceptance set below was re-run.
