# Phase 32.1 Plan 21: Engine facts summary

The engine now has what the native front door needs, all in host-neutral code. It has one list of the commands between the extension and the Sterling workbench, with strict parsers for what crosses them. It has a hosted rule that only ever removes network actions. It accepts the four Defence work areas as kinds of work and lands each one on its own workbench page. In the Defence edition it can name the folder by its work area instead of "this project".

## What changed

- **Bridge (D-46, D-48).** `bridge.ts` holds `GUIDE_COMMANDS` (the seven ids, frozen), `parseGuideEnvironment` (exact keys, `hosted` or `local`, optional `ca-defence`, every value at most 40 characters) and `parseChecklistRows` (at most 20 rows of `{ id, title, shown, done }`). Anything else parses as `'invalid'`.
- **Hosted rule (owner D7, D-49).** `hostKindForEnvironment` maps `'invalid'` and `hosted` to `'hosted'`. A missing workbench (the VS Code build) keeps the caller's host kind. `HOST_KINDS` gains `'hosted'`, appended. With a hosted host kind, the local servers source sends no loopback probes and checks only the endpoints your organization's policy lists. The checking screen shows "Checked in your Sterling session" and no machine name. The controller passes its host kind to the screens. Plan 23 sets it from the environment.
- **Kinds of work (D-50, owner N2).** `KINDS_OF_WORK` gains `capability-development`, `planning`, `resource-management` and `exercises-training`. Each has an answer label and a policy-editor word. Unknown and repeated kinds are still refused. The maximum count follows the longer list.
- **Folder words (owner D10, D-59).** `folderNoun('ca-defence', kind)` gives "plan", "inventory", "exercise or training" or "program, product or project", and "folder" for any other kind. Outside the Defence edition it gives `undefined`. `applyFolderWords` rewrites whole phrases from one frozen table in a single pass, so a replacement is never matched again. The copy-lint invariant loads every setup `*_TEXT` constant in `src/domain/setup` and `src/services/setup` (55 modules; `getStarted.ts` is read as text and must hold none). It checks the text under each of the five nouns. The only category left out is the kind-of-work answer labels, and the test asserts that this exclusion matches exactly that key. On its first green run the invariant caught "Set up your project team", which is now in the table. No existing text constant was edited, so the VS Code build reads exactly as before.
- **Landings (D-22, D-50).** Planning lands on `planning` with `share-with-people` and `my-computers`. Capability development, resource management and exercises and training land on `capability-development`, `resources` and `training` with `share-with-people`. `get-started` and `work-area` join `LANDING_TARGETS`. `isLanding` refuses a work-area landing without a valid page, and a page on any other target. Planning follows the staff exercise rule.

## Deviations from Plan

- **[Rule 2] Default kinds kept at five.** The plan appends to `KINDS_OF_WORK` but does not say what a policy without `kindsOfWork` offers. The parser, the guide policy and the screens all defaulted to the accepted list, so the VS Code build would have offered nine kinds. `DEFAULT_KINDS_OF_WORK` keeps the five.
- **[Rule 3] `steps.ts`** had its own copy of the kind union and stopped compiling. It now imports the one type.
- **[Rule 2] Policy-editor words** for the four kinds, so the editor shows a word rather than the id.
- **One commit for the three tasks.** The kinds force the landing entries at compile time, and `screens.ts` and `bridge.ts` serve more than one task, so no split compiled on its own.
- **Controller host kind** (one line in `guideController.ts`, not in the plan's file list) so the hosted line shows whenever a run is hosted.
