## Phase Boundary

Phase 32.1 makes **Get Started** the one front door:

- A person answers four plain questions (kind of work, what the work touches, must it stay in Canada, and a pre-answered agent-work question) plus at most one follow-up. (GUIDE-01)
- The answers become a proposed project label on your organization's scales, applied through Set Label and only ever raised; Protected C, classified and contract work without Contract Security Program approval stop with a plain sentence and no option. (GUIDE-02)
- Only viable options are offered: detected, configured, allowed, and a test request just answered. Local servers on loopback, policy-named hosts, and servers found on your network and approved; NEAR AI; the device class. The rest are listed apart under "Not available here" with reason and fix. (GUIDE-03)
- A pure `recommend()` asks Phase 41's `decideRoute` about every option and ranks with rules R1 to R9, giving one recommendation with a one-sentence reason; ruled-out options are greyed with the gate's own sentence. (GUIDE-04)
- Option cards in plain words ending in the one trust line from `TrustFacts`; choosing otherwise records a reason. (GUIDE-05)
- Your organization's policy wins: rule changes are only ever proposals in the one policy editor; the `onboarding` v2 section supplies contacts, locked answers, kinds of work, default scale and discovery rules. (GUIDE-06)
- Check answers with a grouped list of what will change before Apply; re-runs show only differences, never lower a label and finish a partly applied run; one hash-chained local audit record per run. (GUIDE-07)
- Landing by kind of work with the first-run guarantee and a filtered checklist; every other setup path folds into Get Started with old command ids as hidden aliases; staff setup's "where" question and discovery `locality` removed; keyboard, screen reader and reduced motion as the house standard on the webview kit. (GUIDE-08)
- The guide suggests an organization mode from the kind of work, shows "Set by your organization" when fixed, and records the choice. ORG-01 to ORG-03 (mode table, `people.organization`, `term()` with the copy lint) were built in Phase 41 as FND-07; 32.1 is their first reader on screen. (ORG-04, and the 32.1 success criterion 7 for ORG-01 to ORG-04)

It also delivers the **shared contract** Phase 32.2 builds on (device class, server adapter registry, viability), as its first plan, so 32.2 can run beside the rest of 32.1.

Not in this phase: the local model manager page, hardware detection beyond the device class contract, server adapters with install, catalogue, fit and benchmark (32.2); the data-connection step (GUIDE-09, Phase 89); Cohere adapters and vault forms (36, 37: 32.1 only leaves the option slot); passport enforcement and the research workspace (74.1); `org-tee` verification (74.2); positions, postings and `project.mode` changes by the lead (33.1); the replica source of the project layer (33.1, Phase 41 D-22); the hub loading the organization layer (35); Phase 71 identities.

## Implementation Decisions

### Accepted design defaults (owner, PR #137 and the coherence review)
- D1 (owner): options that fail viability are listed apart under "Not available here", collapsed, never selectable.
- D2 (owner): "Not sure" about the data counts as Protected B (on the `org`-only scale: `org/Restricted`), with the sentence and the reminder.
- D3 (owner): Protected C and classified always stop in 32.1; an `authorizations[kind=accredited-device]` record is only noted ("recorded as accredited by {name}"), never turned into a recommendation.
- D4 (owner): the NEAR AI test request is the one-word completion, counted in spend.
- D6 (owner, refined by K23): single-machine answers in `.planning/.near-ai/project.json` under `setupGuide`; shared projects use project-stream entries; full records beside the gate's records; the kind of work in extension storage.
- D7 (owner): the `onboarding` section of policy v2, named in `requires` as `onboarding@1`, with `discovery.personalApprovals` default false.
- D9 (owner): numbered 32.1 and 32.2, after Phases 32 and 41, before 36 and 37.
- D12 (owner): network discovery. Named endpoints (`endpoints[]`) and announced servers (DNS-SD/mDNS, DNS SRV in a policy-named domain) are on by default, but only on networks the policy lists; active scans only of policy-listed ranges, only on the known model-server ports, confirmed by the person each time, rate-limited (at most 50 hosts a second, one connection per port) and recorded; a found server is a candidate (signature request only) until an administrator approves it through a proposal that pins its TLS certificate (SPKI hash).
- D13 (owner): an old discovery `locality` answer is shown once on the check page as "Your earlier answer", with no effect on routing; `local` only pre-orders viable local options.
- D14 (owner): "must stay in Canada" on a personal policy becomes a project-layer narrowing proposal, not a personal-layer one.
- D15 (owner): "Change setup answers" sits on every Home and as a hidden alias command; not in the chat title bar.
- D16 (owner): a joiner whose position implies the kind of work is not asked Q1; it is pre-answered and changeable on the check page.
- Viability (owner): an option is viable only when detected, configured, allowed and a test request succeeded in the last 10 minutes.
- Get Started is the only front door (owner, coherence Q9): keeps `nearAi.setup`; every other setup path is a step or checklist item; later phases register steps, never new setup commands.
- Mode words (owner, PR #150, 2026-11-21): Military position is "Position"; member is "Staff officer", also "Staff member" or "Defence team member"; Public service member is "Employee", also "Defence team member". Screens never spell them: every mode-varying word comes from `term()` (`src/domain/org/terms.ts`), so the guide works whether or not PR #150 has merged when a plan runs.
- Western model direction (owner): Nemotron 3, Command A+ and gpt-oss-120b are the Western bases; PRC-origin models are research-only (T0) and T1 at most by explicit acceptance. The guide never recommends a model by name: it reads passports (`src/domain/gate/shippedPassports.ts`, the `models` section).

### Order and the shared contract
- **D-01:** The first plan (wave 1) is the shared contract and nothing else: the step and option registry (`{ id, title, state(), viability(), run() }`, GUIDE 12.1), `ViabilityResult` and the option viability state machine (GUIDE 8.6), the `DeviceClass` type (`unified`, `discrete`, `cpu-only`, with GPU-usable memory and its source), the server adapter registry shape (probe table rows: kind, ports, signature request, list models, can install), the answer, label proposal and record types, and the `onboarding@1` section parser. 32.2 plans depend only on this plan, so 32.2 may run beside every later 32.1 wave.
- **D-02:** The contract lives in a new pure folder `src/domain/setup/` (domain layer: imports only `src/domain/**`), with host code in `src/services/setup/` (DEVELOPER-STRUCTURE section 2 and GUIDE 12.1 name these folders). The architecture test's baseline gains no lines.
- **D-03:** The `onboarding` section: Phase 41 registered the `onboarding@1` feature id and a section slot. 32.1 gives it its full strict parser (`contacts` up to 8 with topics `security`, `privacy`, `contract-security`, `it`; `locked`; `kindsOfWork`; `defaultScale`; `discovery { networks, announce, scanRanges, personalApprovals }`) with declared narrowing directions per key, through the one policy reader. If Phase 41 left the section as a strict stub, the plan replaces the stub; it never adds a second parser.

### Questions and labels (GUIDE-01, GUIDE-02)
- **D-04:** The question set is GUIDE 4.2 exactly, one question per screen in one webview stepper. Q3 (Canada) ships now, because Phase 41 built `route.residency` (REVIEW K10 satisfied). Q1's choices come from `onboarding.kindsOfWork` when set, else the six shipped kinds.
- **D-05:** The answer-to-label mapping is one pure table (GUIDE 4.3) tested row by row, including the `org`-only column. Personal information maps through `onboarding.defaultScale` when set.
- **D-06:** The label is applied through the existing Set Label machinery and only raises; a higher existing label is kept and shown. On a single-machine project the label is written to the project layer's single-machine source (D-10).
- **D-07:** The display rename of `org/Confidential` to "Organization: Sensitive" (owner Q8, tracked for 32.1 by Phase 41) lands in the one label display function, so the guide, Set Label and the trust line all show it; the id stays `org/Confidential`.

### Viability (GUIDE-03)
- **D-08:** Detection, probes and test requests run where the extension host runs, and the guide names that machine ("Checked on: {hostname}, a container"). Probes run in parallel with short timeouts; the checking screen has a 90-second ceiling after which slow probes show "still checking" with Continue without them.
- **D-09:** Network discovery follows D12 with no new runtime dependency: DNS SRV through `node:dns`; DNS-SD/mDNS browse through a small, reviewed listener on `node:dgram` that only listens and sends standard queries for the policy's service types, on policy-listed networks; scans through `node:net` with a token-bucket limiter. If research finds a maintained, permissively licensed mDNS library worth taking, it is a recorded dependency decision, not a silent addition. A candidate never receives anything but the signature request; approval writes a proposal (exact host, `scheme: https`, `tlsPin`, `region`, `maxLabel`) into the policy editor; with `personalApprovals` true the person may apply it to their personal layer, capped at `maxLabel org/Public`.
- **D-10:** Test requests use the fixed texts of GUIDE 6.5, go through the outbound check (Emergency stop, spend limit, the private-hardware floor apply) and are counted in spend.

### Recommendation and cards (GUIDE-04, GUIDE-05)
- **D-11:** `recommend()` is pure (`src/domain/setup/recommend.ts`, no I/O, no clock), calls the real `decideRoute` for every option with synthetic facts, and adds no rule about where a label may go; R2, R3, R4 and R9 are read from `decideRoute`'s answer and refusal sentence; R1 and R5 to R8 only rank and explain. Before Phase 74.1, R4 runs in report mode as the gate does (passport step records `wouldRefuse`), and the card says so in plain words when it matters.
- **D-12:** Each option's card is built from `TrustFacts`, so its last line is the same trust line people later see on every answer. "Private" appears only as "NEAR AI private hardware (checked each time it is used)".
- **D-13 (Cohere slot):** The option registry knows the endpoint classes `vendor-region` and `vendor-tee` but ships no adapter for them. A vault card appears only when the policy lists such an endpoint; with no adapter in this version it is under "Not available here" with "This version cannot connect to it yet. Update the extension." Phases 36 and 37 register their adapters and readiness checks into the same registry and change nothing else in the guide.
- **D-14:** A choice other than the recommendation asks for a short reason (up to 200 characters, secrets scanned out) that the record keeps.

### Policy wins (GUIDE-06)
- **D-15:** The guide reads only a verified bundle through the one policy reader; a failed-closed policy shows only its fix. No Edit Policy button, no label lowering, no "use another provider anyway". Contacts come only from the signed `onboarding.contacts`, shown as text, never as links to unknown schemes; with none, "your organization's security officer".
- **D-16:** Every rule change the guide needs (residency on a personal policy as a project-layer narrowing, approving a found server, adopting the Western defaults, and later a vault) is one proposal written through Phase 41's proposal API into the one policy editor; under an organization layer it is exported to `onboarding.contacts` and nothing changes locally. "Self-signed on this computer" copy until an organization issuer exists.

### Apply, re-run and the record (GUIDE-07)
- **D-17:** The guide session state machine is GUIDE 8.6 exactly (`not-started`, `answering`, `checking`, `choosing`, `reviewing`, `applying`, `applied`, `partly-applied`, `paused`, `abandoned`), as a pure reducer tested transition by transition; no state can wait forever.
- **D-18:** The check page lists changes grouped as Added, Changed and Removed; the button reads "Apply these settings"; nothing changes before it is pressed; a partly applied run lists what was and was not done, and a re-run finishes only the rest.
- **D-19:** The record writer and the hash-chained local audit (ADR-011, deferred from Phase 41 to 32.1) are built here as one shared writer in `src/domain/gate/record.ts`'s family: events `setup.guide.applied`, `setup.guide.abandoned`, plus `setup.discovery.scan` and `setup.discovery.approved-proposal`; a chain check; secrets scanned out; no free text but the kind of work's 60 characters and the choose-otherwise reason. Signed heads are not built here (ADR-011 later); nothing calls a record signed.
- **D-20:** Single-machine source of the project layer: `.planning/.near-ai/project.json` gains `setupGuide` (answers, latest record id) and the project-layer attributes Phase 41 defined (label, mode, exercise flag with reason, locked answers), read by Phase 41's project-layer parser. This is the single-machine source Phase 41 D-22 assigned to 32.1.
- **D-21 (shared projects):** In a shared project the answers, label and mode are project-stream entries, whose replica source belongs to Phase 33.1 (Phase 41 D-22). 32.1 writes through one narrow `ProjectLayerSink` interface: the single-machine sink ships here; the replica sink ships with 33.1. Until it lands, in a shared project the guide applies personal changes, shows project-level answers already set by the project as "Set by this project", and lists project-level changes it cannot yet make as "Waits for the next update: shared project settings", never writing them to `project.json` in git.

### What the code does today

- Policy features exist (`requires`, `src/domain/gate/features.ts`), but only one per section. Plan 21 (on the engine branch, not released) added the four work areas to `onboarding@1`. A release older than plan 21 reads a policy that lists one as a wrong value and fails closed with the Reset sentence. Plan 22 (not executed) does the same to `people@1`: it adds the `defence-team` mode, which `people.organization.mode` and `allowedModes` may name.
- A release that meets a feature it does not read fails closed (reading and planning only). The sentence tells the person to update the extension (`UPDATE_FIX` in `bundle.ts`). Opening a newer rules file is refused and changes nothing, but its sentence says the same. A stored layer this release cannot read (after the site moved back to an older release) fails the whole policy closed.
- The tool that writes and signs your organization's rules is `scripts/org-issuer.mjs` (`sign-layer`, `sign-enrolment`, `rotate`). It computes `requires` from the sections and checks nothing about the sites that will read the file.
- The signed site evidence export (48-02) carries component versions (Keycloak, OpenBao) but not the Sterling release or what it reads.
- A Theia Cloud session keeps its image until it stops. The lazy AppDefinition handler does not handle a changed AppDefinition (upstream main, read 2026-11-24; 47-32 checks it again at the pinned commit), so an update never restarts a running session. Nothing tells the person that a new release is waiting.
- Fourteen user sentences tell a person to update the extension: six on the policy path (`bundle.ts`, `enrolment.ts`, `gateCommands.ts`), and eight in team files, signed records, key histories, the replica reader, the policy draft hint and the guide's Cohere slot.

### Decisions

- **D-60 (one rule for the class):** Every shared, signed format follows one rule: an authoring check first, an edge refusal as the backstop. Both use `name@N` feature ids with Phase 33's pattern (`^[a-z][a-z0-9-]{0,31}@[1-9][0-9]{0,2}$`, 33 D-04; the policy's own wider pattern accepts every such id). No user text tells a person to update the extension or Sterling. The fix is always the administrator's. The class check (D-69) lists every format and where each half is planned.
- **D-61 (policy features by what a document uses):** Every policy feature has a `name@N` id in the one registry, `src/domain/gate/features.ts`. A feature is needed by what a document uses, not only by which sections it has. Each registry entry says what needs it: a section, a value, or an envelope field. One function computes the needed ids from a document, and both the builder (`buildOrganizationLayer`) and the parser use it, so they cannot disagree. A document that uses something without naming its feature is malformed, as a section without its feature is today.
  - The four work areas (D-50, N2) are the first value feature: `work-areas@1`, needed only when `onboarding.kindsOfWork` lists one of them. A policy that lists none of them stays readable by every release that reads `onboarding@1`. This replaces plan 21's summary decision that they ride on `onboarding@1`. No released policy uses them yet, because plan 21 is on the unmerged engine branch.
  - The Defence Team mode (D-51, plan 22) is the second: `defence-team@1`, needed only when `people.organization.mode` or `allowedModes` names `defence-team`. A policy that names only the four Phase 41 modes stays readable by every release that reads `people@1`. The project layer in `project.json` is not affected: it is unsigned and takes any mode id by pattern.
  - A document's format versions count as needs too: `policy-bundle@<bundleVersion>` and `vocabulary@<vocabulary>`. A release reads its `FEATURE_IDS` plus those two (`policyFeaturesRead()`).
  - The registry stays append-only: an id, once released, keeps its meaning.
- **D-62 (the authoring check, the primary guard):** `scripts/org-issuer.mjs` refuses to write a rules file, an enrolment file or a key handover when a target site cannot read every need of the document. It writes nothing on refusal (exit 1, as today).
  - Inputs: `--sites <file>`, your organization's sites, each with its id and the public key that signs its evidence (the Signer shape of 48-02's trust list plus `id`); `--site-exports <folder>`, the signed site evidence exports; and optional `--exclusions <file>` (D-63). `--sites` is required. An organization with no hosted sites passes an empty list, and the tool says "No sites were checked: your sites file lists none."
  - For each site the tool takes the newest export that verifies: purpose `site-evidence-export`, signed by that site's key, payload site equal to the id, `generatedAt` equal to the signing time, not in the future. It reads the site's release and `reads.policy` from schema 2 (D-67).
  - A site is **unknown** when it has no such export, when its newest one is older than 7 days (the deployment collector's window), or when it is schema 1. The default is to refuse an unknown site unless the author excludes it.
  - The refusal names each site, the release it runs (or "no recent evidence"), the features it lacks, and the release it needs: the oldest release among the verified exports, or the tool's own release, that reads them all.
  - On success the tool writes `minClient` (Phase 41 D-07) as the oldest release that reads every need, so an older site can name that release to its administrator.
  - Pure core: `src/domain/gate/siteSupport.ts`. Planned in 32.1-30.
- **D-63 (exclusions recorded in the signed rules):** An exclusion names a listed site and a reason of 1 to 200 characters, scanned for secrets. The tool writes the exclusions into the signed document as `excludedSites: [{ site, reason }]` (at most 64). That field is its own feature, `excluded-sites@1`, so the rule applies to itself: a site older than this release refuses the file instead of ignoring the record. The gate decides nothing from it; the policy view shows it to administrators. Planned in 32.1-30.
- **D-64 (the edge backstop and the exact fallback):** A computer or session that receives your organization's rules needing a feature its release does not read refuses the whole file. Nothing in it is applied. The signature is always checked first, so the fallback below never applies to a file that fails for any other reason (signature, key, expiry, older, replaced); those fail exactly as today.
  1. **On receipt** (opening a rules or enrolment file, or any later delivery through `OrganizationStore.accept`): the rules in force stay in force, unchanged. A refused update from the pinned key is kept as `organization-layer.waiting.json`. It applies itself at the next start of a release that reads it, if it is still newer than the rules in force and not expired. When a newer layer is accepted, or it expires, it is moved aside as `.replaced-<ms>`. A refused first enrolment or key handover is not kept, because it needs the person's twelve-word confirmation; the person opens it again after the update.
