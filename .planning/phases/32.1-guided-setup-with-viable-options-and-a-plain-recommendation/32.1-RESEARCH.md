## Summary

Phase 32.1 is mostly composition, not invention: Phase 41 already built the judge (`decideRoute`), the one fact record (`TrustFacts`), the policy sections (including the full `onboarding@1` parser), the proposal path into the policy editor, the mode table and `term()`, and the project layer type. What 32.1 adds is (1) a pure `src/domain/setup/` core (contract, answer-to-label table, `recommend()`, session machine, change list), (2) host code that gathers facts honestly (probes, a test request, discovery, hardware seam), (3) a hash-chained local audit that does not exist anywhere yet, (4) a single-machine source for the project layer, (5) one webview stepper on the first real use of the webview kit, and (6) folding about fifteen existing setup commands behind `nearAi.setup`.

Reading the code against `32.1-CONTEXT.md` found twelve places where the CONTEXT assumes something the code does not match (section "Findings that change the plan"). The ones that change plan content most: `decideRoute` lives in `routing.ts` with a six-argument signature, not in `decide.ts`; the `onboarding` parser and the `org/Confidential` to "Sensitive" display rename are already done, so D-03 and D-07 shrink to wiring and regression tests; the project's label already has a signed single-machine home (`labels.json`), so D-20 must not copy it into `project.json`; a person on the starting rules holds only an `org/Restricted` clearance, so applying `ca-protected/Protected B` is refused by Set Label's clearance rule unless the guide also proposes a clearance; the project layer type has no residency field, so D-14 cannot be expressed as a project-layer proposal without a gate change; and there is no existing hash chain (the "chain" in `decisionLog.ts` is a promise chain).

**Primary recommendation:** Build wave 1 as the contract alone (pure types, registry, viability reducer, device class, probe table data, answer and record types, a policy accessor over the existing parser), then run recommend, viability, discovery, audit and project store, the webview kit additions and the staff `locality` removal as six disjoint plans in wave 2. Keep `src/services/gateCommands.ts`, `src/domain/gate/**` existing files, `chat.ts` and the replica code untouched; every new behaviour goes in new files or in the files listed under plan ownership.

### Pattern 1: `recommend()` asks the real judge with facts from viability

**What:** For each option, build `RouteFacts` from its `ViabilityResult` (never synthesised optimistically), call `decideRoute`, then `trustFactsFor` and `trustLine`. A NEAR AI option is allowed at an attested-cloud label only when the viability result carries a fresh bound connection fact for that host; otherwise the gate's own refusal sentence is what the card shows.

```typescript
// Source: src/domain/gate/routing.ts:660 and :381 (signature and facts), trust.ts:81 and :205 (cards)
const decision = decideRoute(mark, routing, facts, defaultLabel, floor, policy);
const trust = trustFactsFor(decision, facts, { mark, routing, defaultLabel }, { verification });
const line = trustLine(trust, policy.scales).text; // "Runs on ... · ... · Allowed for ..."
```

`facts.binding` must be `{ state: 'bound', host, checkedAt }` and `facts.now` within `BINDING_MAX_AGE_MS = 600_000` of it (`routing.ts:353-361`), `facts.model.privacyBoundary` from the model catalogue entry that answered the test (`'tee'` for private hardware, `'local'` for a local runtime), `facts.use` from Q4 (`useTierFor`, T1 or T2). The passport step is report only (`routing.ts:802-813`), so `wouldRefuse` goes to the "why" disclosure, not to ranking.

### Pattern 2: Viability is a reducer over injected probes

States from design 8.6: `unknown -> checking -> viable | not-detected | not-configured | not-allowed | test-failed`, `viable -> stale -> checking`. `stale` after `600_000` ms, on a network change, a server stop answering, or a policy hash change. The runner takes `{ now, fetch, connect, resolver, socket, hardware }` so tests use a virtual clock and fakes.

### Pattern 3: Apply is an ordered list of idempotent steps with a recorded outcome each

Each step: `{ id, describe(before), run(), alreadyDone() }`. `alreadyDone()` makes a re-run finish only the rest (design 8.6 `partly-applied`). Proposals are a step that opens the editor and records `proposal opened`, never "applied".

### Pattern 4: Hash chain, minimal and checkable

```typescript
// Shape (new, src/domain/gate/auditChain.ts). Canonical JSON with sorted keys; hash = sha256(prev + canonical(body)).
interface ChainLine { seq: number; prev: string; hash: string; body: GuideEvent } // prev of line 1 = 64 zeros
// verifyChain(lines) -> { ok: true } | { ok: false; at: number; why: 'prev' | 'hash' | 'seq' }
```

A truncation of the tail is detectable only against a head kept elsewhere: write the latest `{ seq, hash }` to a small head file beside the log after each append, and have `verifyChain` compare. "Signed heads" stay deferred (ADR-011); say "tamper-evident local record", never "signed" (D-19, copy lint rule 7).

### Pattern 5: Typed webview protocol on the kit

`openPanel` today provides CSP (`default-src 'none'; style-src ${cspSource}; script-src 'nonce-...'`), nonce, `base.css`, layout probe, and a branded-title guard (`openPanel.ts:36-55`). Add `src/services/webview/protocol.ts`: `definePage<In, Out>({ parseInbound(value): In | undefined })`, an `exactKeys` helper (the repo's existing one is private in `teamStudioPage.ts:562`), and `post(out)`. Every inbound message is parsed strictly and an unknown or malformed one is ignored, never thrown (the pattern in `teamStudioPage.ts:486-698` and `policyEditor.ts`).

### Pattern 6: Legacy step adapter, so Phase 33 keeps working

`registerSetupStep(step: SetupStep, after?)` (`setupSteps.ts:110`) stays exported with its shape `{ id, label, detail, icon, command, isDone(ctx), isAvailable?(ctx) }`. Phase 41 already uses it (`gateCommands.ts:407`, `policySetupStep`) and Phase 33 will (33-CONTEXT D-19, D-03). The new registry accepts the legacy shape through a pure `fromLegacyStep()` and renders `{ state() = isDone, viability() = isAvailable, run() = executeCommand(command) }`.

### Anti-patterns

- A second security table in the guide. `recommend()` adds no rule about where a label may go (D-11).
- Writing the bundle, offering "Edit Policy", lowering a label or a "use another provider anyway" button (D-15).
- Sending anything but the signature request to a candidate; sending a key to a candidate or an unapproved host.
- `innerHTML` anywhere; the kit's page scripts use `textContent` (`openPanel.ts` comment, `media/policy/policy.js:2`).
- Reading `getConfiguration` outside `services/settings.ts` (architecture rule) or importing `SCALE_PRESETS` into `src/domain/setup/` (rule `scale-presets`).
- Persisting the viability snapshot with a hostname: store a `hostKind` (desktop, remote, container) and the result codes; name the machine only on screen.

## Network discovery without a new dependency

**Feasibility: yes for all three ways.**

1. **Named:** `endpoints[]` entries of the effective policy. Already in `RoutePolicy.endpoints` (`routing.ts:504-506`). Probe each with the signature request and, if approved, a test request. No new code beyond the runner.
2. **DNS SRV:** `new dns.promises.Resolver()` then `resolveSrv('_near-ai-models._tcp.' + suffix)` only for `suffix` values taken from `onboarding.discovery.networks[].dnsSuffix` and only while the current network matches that network entry. The resolver is injected (`{ resolveSrv }`) so tests use a table. Results are `{ name, port, priority, weight }`; each becomes a candidate that still needs the signature request.
3. **mDNS one-shot browse:** send a PTR question for each service type the policy names (the design names `_near-ai-models._tcp`; there is no standard Ollama or llama.cpp type `[ASSUMED]`, so "known types behind a published record" means types your organization publishes) to `224.0.0.251:5353` from an ephemeral source port with the QU bit set, read replies for a bounded window (default 2 s), parse PTR, SRV, TXT, A and AAAA, follow the SRV target to an address from the same packet. `[CITED: RFC 6762 5.1: queries from a source port other than 5353 are one-shot queries; 5.4: the top bit of the question class asks for a unicast response]`. This avoids binding 5353 (which collides with the system mDNS responder on macOS, Windows and Avahi) and needs no `addMembership`. A listening mode (join the group and wait) is not needed and is not planned. In a Docker bridge or a code-server container multicast usually does not reach the host network; the guide says so by naming the machine ("Checked on: a container") `[ASSUMED]` for the Docker behaviour.
4. **Scan:** only CIDRs in `onboarding.discovery.scanRanges` (IPv4 /16 to /32 by the parser, `sections.ts:299`), only when `NetworkFacts` says the current network is one of the policy's `networks`, only after a per-scan confirmation naming ranges, ports, the estimated time and "your network team may see this as a scan". Token bucket at 50 hosts per second; one connection in flight per (host, port); connect timeout about 800 ms; ports are the distinct ports of the probe table (11434, 9931, 8080, 13305, 8000, 1234, 1337). A /16 is 65,536 hosts, about 22 minutes at 50 hosts per second before any signature request, so show the estimate, run scans in the background after Continue (the 90-second ceiling applies to the checking screen, not to a scan), offer Stop, and write the scan record at the start and end.

**Which network am I on?** The policy identifies networks by `dnsSuffix` or `gateway`, and `os.networkInterfaces()` gives neither. Plan a `NetworkFacts` seam (`{ dnsSearch: string[], gateway?: string }`) with a Linux reader (`/proc/net/route`, `/etc/resolv.conf`; fixed files, no shell), and fixed-argument tool readers for macOS and Windows (`[ASSUMED]` commands: `route -n get default`, `scutil --dns`, PowerShell `Get-NetIPConfiguration`; verify in plan 04). Unknown network means scanning off and the sentence "This computer is on a network your organization's rules do not list, so scanning is off." This is also why a container reports "not on a listed network".

**Candidate rules (D-09, D-12):** a candidate gets GET signature requests only; the TLS handshake used to read its SPKI hash is a connection that sends nothing but the handshake (`tls.connect` with `rejectUnauthorized: false`, read `getPeerCertificate`, then `peerFingerprint(cert, 'public-key-sha256')`, close). Approval builds a `PolicyChange` whose `next()` adds one `PolicyEndpoint` `{ id, class: 'org-plain', host, scheme: 'https', tlsPins: [spki], region, maxLabel, provider? }` (`endpoints.ts:34`); the parser refuses classes and ceilings the rules forbid (`PATTERN_HOST_CEILING`, `classMayHold`). With `personalApprovals` false the proposal targets the organization layer and is exported. `endpoints[]` is `subset` under an organization layer (`layers.ts:78`), so a personal approval is possible only without an organization layer or with `personalApprovals` true and `maxLabel ['org/Public']` (`layers.ts:636`).

**Testing with fakes (no real network):**

- DNS wire codec: golden vectors from RFC 6762 and 1035 examples, plus a deterministic xorshift fuzz (10k packets, mutations of valid ones) asserting no throw, no unbounded loop and bounded output; explicit tests for compression pointer loops, pointer past the end, label over 63, name over 255, record count over a cap, packet over 9,000 bytes, an answer for a name the query did not ask for.
- mDNS: `DatagramLike { send, on('message'), close }` fake that replays packets; assert the question bytes, ephemeral source port, QU bit, window length.
- SRV: injected resolver.
- Scan: virtual clock plus fake `connect`; assert at most 50 hosts per virtual second, one connection per port, refuses a CIDR not in the policy, a network not listed, no confirmation.
- Candidate: fake HTTP server on 127.0.0.1 ephemeral port that records every request path and header; assert only signature paths, no `Authorization`, no body.
- Pin: `src/test/helpers/fakeHubServer.ts` already runs a TLS server; reuse it for SPKI reading and for `pinnedFetch` mismatch.

## Common Pitfalls

1. **Applying a label the person is not cleared for (F5).** Symptom: Apply fails for every `ca-protected` answer on the starting rules. Avoid: compute the clearance gap before building the change list; show it as a proposed own-clearance change; never route around `dominates`. Test: the starting rules (clearance `org/Restricted` only) with a Protected B answer lists a clearance proposal and leaves the label step "waiting".
2. **Duplicating the project label into `project.json` (F4).** Two sources diverge and `project.json` is git-shared and unsigned. Read the label from the label map every time; store only narrowing or descriptive fields.
3. **Granting an option because the test succeeded once.** Facts expire: bind `now` to the check and re-run the route decision with fresh facts at Apply (a NEAR option chosen at minute 11 must recheck, `BINDING_MAX_AGE_MS`).
4. **Greying an option because `wouldRefuse` has `route.passport`.** With shipped passports that is true for every local model (F8). Report, do not rank.
5. **Identifying a server by its port.** Ports are shared (8000, 8080). Ordered signatures; "unknown server" is a state, never the kind it claims (32.2 D-08).
6. **Sending a key to a candidate or to the wrong server.** Keys go only through the profile's client to the profile's host. Candidate and probe requests are keyless; a test asserts the recorded headers.
7. **A scan that never ends.** A /16 is about 22 minutes at the limit. Estimate first, background it, Stop button, hard cap on total hosts per confirmation, record start and end.
8. **Permissive DNS parsing.** Compression pointer loops and oversize counts are the classic defects in multicast listeners. Bounded codec plus fuzz test before any socket code exists.
9. **Copy lint failures from design copy (F14).** `accredited`, `attested`, `passport`, `residency`, `tier` appear in the design text; reword before writing constants. Em-dashes never. "Team" for people never (`bare-team`): staff and groups use `term()`.
10. **Mode words spelled out.** Anything that varies by mode (join word, lead, member) comes from `term(concept, mode)`; the lint's mode-word rule fires on literals (`copyLintScan.ts` `modeWordsFromTable`). The check-page row is `term('join', mode)`.
11. **Webview message injection.** Parse every inbound message with exact keys and bounds; set text with `textContent`; contacts shown as text only.
12. **Racing project.json writers.** The guide, staff setup, research profile and team updates all read-modify-write the same file. Use the one atomic helper in the guide and keep the others' behaviour; add a concurrency test with two writers.

### Known threat patterns

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| Rogue server on the network collecting prompts | Information disclosure | Candidate gets only signature GETs; approval pins SPKI; HTTP off-machine only for labels the policy allows (default Public) |
| Spoofed mDNS answer pointing at an attacker host or a huge record | Spoofing, DoS | Browse only types the policy names; bounded parser; a result is a candidate, never trusted |
| Scan used as network reconnaissance | Elevation, policy violation | Listed ranges and networks only, confirmed each time, 50 hosts per second, recorded, Stop |
| Port-collision misidentification | Spoofing | Ordered signatures; "unknown server" state |
| Fake local server on loopback | Spoofing | Same trust as any local process (design 14.1); record names kind and version; passport and route rules still apply |
| Attacker edits `project.json` in git | Tampering | Only narrowing or descriptive fields; label from the signed map; shared projects wait for 33.1 |
| Truncated or edited audit file | Tampering, repudiation | Chain plus head file; verify on read; never called signed |
| Webview message forgery or XSS | Tampering | Strict parse, `textContent`, CSP with nonce, no remote resources |
| Phishing through policy contacts | Spoofing | Contacts shown as text only, from the verified bundle |
| Test request leaks data | Information disclosure | Fixed text through the outbound check, spend counted |
