## Implementation Decisions

### The texts and how they are used
- **D-01 (what each text is):** AC322 DCRA v2 sets principles (data-centric security, zero trust, ABAC, data products with core metadata); ADatP-4774, 4778 and 5636 define the label, the binding and the core metadata; ACP-240(A) defines ZTDF and is not held. Nothing in this phase cites AC322 for ZTDF. Part 2b is built on the public OpenTDF specification 4.3.0 as the closest public approximation, and every statement about it says "ZTDF-compatible profile", never "ZTDF conformant", until the interop trial (45.2-10) passes against ACP-240(A) or partner samples.
- **D-02 (no copying, no NATO values):** The ADatPs are cited by section only. No prose, schema or example from them enters the repository. Test vectors are our own XML written to reproduce the structure of each example the texts give (each vector names the section it follows), with fictional values: the policies `ACME` and `MOCK` that the texts themselves use for fictitious examples, and OIDs under the documentation enterprise number `1.3.6.1.4.1.32473` (RFC 5612). No NATO label value (the NATO policy identifier, NATO OIDs, NATO classification names, context values) appears in shipped code or defaults (owner decision, 45.1 D-02); the security officer's signed table supplies them. Errata in the texts (research section 8) become negative vectors.

### Labels (4774)
- **D-03 (two labels, ours first):** Every export carries an `originatorConfidentialityLabel` in your organization's own national policy (identifier and `urn:oid:` from `labelXml`) and an `alternativeConfidentialityLabel` in the common target policy that `labelInterop` names, spelled through `labelXml`. The NATO policy is never written as the originator policy (4774 App 2 Annex C footnote). On import, every label the reader can map (the originator label and each alternative label whose policy the table knows) is mapped in, and the result is their join through `joinLabels`; a label in a known policy with a value the table lacks refuses the object, labels in unknown policies are skipped with a note, and none mappable means refused with a plain reason. Values are matched case-insensitively (4774 §5.1); XML syntax and attribute names are matched exactly against the schema.
- **D-04 (`label-xml@1`, the 4774 spellings):** A new signed policy section `labelXml` (feature `label-xml@1`, lowercase as `features.ts` requires, appended to the lists) holds only what 45.1's `labelInterop` table does not: per scale preset, the **originator** block (your organization's own `policyIdentifier`, its `urn:oid:` `uri`, the classification value for each level, and the tag name and optional URI of each compartment category and of the releasability category) and the **alternative** block for the common target policy that `labelInterop` already names (the tag names and optional URIs of its restrictive and permissive categories, an optional context category `{ tagName, uri?, values, releasableMarker }` and whether administrative categories are allowed only at the lowest classification), plus `reviewAfterDays` (the review date 4774 §4.3 requires) and `mapping`, which must equal the `labelInterop` mapping version or both are refused as "The label tables disagree; ask your security officer to sign them again together." The level-to-value and token-to-value facts of the alternative label stay in `labelInterop` only (one source), and one common target policy per scale follows 4774 §2.2 (a common policy instead of one mapping per partner). No `labelXml` section: every 4774 or ZTDF-profile export is refused with "Your organization has not set how its labels are written for NATO partners." The shipped default holds no values. Hand-off H-1.
- **D-05 (own narrow XML, no library):** `src/domain/exchange/xml/`: a reader that refuses DOCTYPE, entity declarations, external references, entity references other than the five predefined and numeric ones, processing instructions other than the XML declaration, CDATA, undeclared prefixes, duplicate attributes after namespace resolution, documents over 8 MiB, depth over 64 and more than 256 attributes on an element; comments are dropped. A writer that emits one deterministic form (UTF-8, no declaration-dependent output, attributes in a fixed order, minimal escaping). Exclusive XML canonicalization 1.0 without comments over the reader's tree (45.2-04). No XML package (45.1 D-10).

### Binding and core metadata (4778, 5636)
- **D-06 (binding objects):** We write a BDO per export: the binding information root in the 4778 namespace, one container, one metadata binding holding one `Metadata` entry per NCMS element (5636.1 §3.1) and one `DataReference` to the payload (`URI="0.payload"` inside our TDF-profile objects). The metadata label is a nested BDO inside a `BindingInformationContainer` per the 5636 BDO binding profile (Annex C App 2), binding an originator label to `URI=""`. We read encapsulating, embedded and detached BDOs, same-document references (`""` and `#id`) and external URIs; a `ds:Transforms` with XPath is refused with "Partial bindings are not supported yet." Granularity rules 1 to 4 (4778 §3.5) are applied when one BDO binds several labels. Schema order is followed: `ds:Signature` before the containers (4778 §4.8, erratum E6).
- **D-07 (the seven mandatory NCMS elements):** originator label; metadata label; `s5636:Creator` and `s5636:Publisher` with `s5636:type="organization"` and your organization's name from the site file, never a person (45.1 D-03, observers see no roster); `s5636:DateCreated` (the release time); `s5636:Identifier` (the export's receipt id, opaque); `s5636:Title` (the released version's title, which the releasing person confirms in the export dialog because a title can itself be sensitive). The metadata label equals the content label; it is never set lower automatically. An imported BDO without an originator label is refused; any other missing mandatory element is shown as a note, not a refusal, because it changes no access decision.
- **D-08 (signed binding, provisional profile):** `CryptoArtefactProfile` interface. The shipped profile `urn:near-ai:stanag4778:crypto-artefacts:provisional:1` (our own URN, never a NATO one): one `ds:Signature` as the first child of the binding information; exclusive canonicalization without comments; SHA-256 digests; `ecdsa-sha256`; one reference to the container by its `Id` and one to each data reference's octets; `KeyName` holding the SHA-256 fingerprint of the signer's public key, which partners pin. Verification accepts only that shape (what is signed is what is used), refuses every other algorithm, extra references and duplicate ids, and verifies only keys pinned in `exchangePartners`. Every reader and every document says the profile is provisional until ADatP-4778.2 chapter 2 is read; then it is swapped in a gap-closure plan. Unsigned standalone BDOs received from partners are refused (owner item 6); inside a TDF-profile object the assertion binding provides the integrity.
- **D-09 (signing keys):** A second release key `release-p256-<site>` (ECDSA P-256, non-exportable, OpenBao Transit) under the same `exchange-release` policy and step-up custody as `release-<site>` (45.1 D-03): it signs the 4778 XML Signature and the ZTDF-profile assertion bindings (JWS `ES256`), because partners' XML Signature and JWS tools verify ECDSA P-256 widely and Ed25519 rarely. Transit signs with `marshaling_algorithm=jws`, which gives the raw `r||s` form both formats need. 45.1's own JSON `LabelBinding` stays `eddsa-jcs-2022` with `release-<site>`. Owner item 2.

### The ZTDF-compatible profile (Part 2b)
- **D-10 (`ZtdfProfile`):** One interface in `src/domain/exchange/ztdfProfile.ts` holding every point where ZTDF may differ from OpenTDF 4.3.0: `labelAssertion` (type `handling`, scope `payload`, `appliesToState` `encrypted`, statement `schema` the 4774 namespace, `format` json-structured mirroring the 4774 element names with `Xmlns` and `CreationTime` as in the public example, research section 6; the reader also accepts the 4774 XML as a `string` statement); `bindingAssertion` (type `metadata`, statement `schema` the 4778 namespace, `format` string holding the BDO XML); `assertionBinding` (JWS `ES256` by `release-p256-<site>` over the assertion's canonical JSON and the manifest's policy and key access hashes, so an assertion cannot be moved to another object); `keyAccess` (the variants and fields 45.1-02's research records); `policyBinding` (HS256 per the specification); `rewrap` (the protocol of D-11); `manifestVersion`. The shipped profile is `ztdf-compatible/opentdf-4.3.0/1`. `tdf.ts` (45.1-02) gains assertions and profile hooks and names no 4774 or 4778 constant (architecture test). When ACP-240(A) or partner samples arrive, a new profile implements the interface; nothing else changes.
- **D-11 (key access to a partner):** Push for exports: the payload key is wrapped to the partner KAS public key pinned in `exchangePartners` (SPKI SHA-256 fingerprint, `kid`, `url`), plus a second key access to our own receiving key so your organization can reopen its own exports. Pull for imports: when a partner object's key access names only the partner's KAS, the exchange officer's backend sends that KAS a rewrap request in the shape of the public specification (`{KAS_URL}/v1/rewrap`, research section 6), with a fresh ephemeral P-256 key pair per request held in backend memory; only KAS URLs listed in `exchangePartners` are called; the KAS's TLS identity and key are pinned; the client authenticates with a client certificate from your organization's site PKI (owner item 8); an air-gapped site never calls out and says so. We do not run a KAS for partners: an export, once wrapped to a partner's key, cannot be withdrawn (45.1 D-07 kept; owner item 5).
- **D-12 (`exchangePartners`, feature `exchange-partners@1`):** A new signed policy section keyed by the `agreements@1` id (71-06 unchanged): `{ kas: [{ url, kid, alg ('rsa:2048' | 'ec:secp256r1'), spkiSha256, publicKey }], kasTlsSpkiSha256, bindingSigners: [{ spkiSha256, publicKey }], classicalUpTo? (highest level that may leave with classical key access) }`. The security officer sets it; the shipped default is empty, so nothing is exported or rewrapped until it is set. Hand-off H-2.

### Decisions, credentials and post-quantum
- **D-13 (one decision, honest PQC):** `mayRelease` (71-07) stays the only release rule, called by 45.1's `canExport`; AC322's PDP, PEP, PIP and PAP map to it as research section 9 shows. Exchange key access is classical because partners have no post-quantum key type: each export's sealed receipt records the key access algorithm; the export dialog says "This copy is protected with keys that a future quantum computer could break, because <partner> does not support post-quantum keys yet."; an export above the partner's `classicalUpTo` is refused with that reason; with no `classicalUpTo` set, the agreement's ceiling applies (owner item 4). A post-quantum key access type is a reserved profile field (`keyAccess.pqc`), refused as "not supported yet".
