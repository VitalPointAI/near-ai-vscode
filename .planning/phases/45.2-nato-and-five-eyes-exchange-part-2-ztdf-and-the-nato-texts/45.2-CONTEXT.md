## Implementation Decisions

### The texts and how they are used
- **D-01 (what each text is):** AC322 DCRA v2 sets principles (data-centric security, zero trust, ABAC, data products with core metadata); ADatP-4774, 4778 and 5636 define the label, the binding and the core metadata; ADatP-4778.2 profiles the binding for formats and the cryptographic artefact; ACP-240(A) defines ZTDF and is not held. Nothing in this phase cites AC322 for ZTDF. Part 2b is built on the public OpenTDF specification 4.3.0 as the closest public approximation, and every statement about it says "ZTDF-compatible profile", never "ZTDF conformant", until the acceptance trial (45.2-12) passes against ACP-240(A) or an ally's or vendor's paired KAS and samples (G354).
- **D-02 (no copying):** The ADatPs are cited by section only. No prose, schema or example from them enters the repository. Test vectors are our own XML written to reproduce the structure of each example the texts give (each vector names the section it follows), with fictional values that differ from every example in the texts: the policies `EXAMPLE-ORG` and `EXAMPLE-ALLIANCE`, never the texts' own example values (`ACME`, `MOCK`, `TEST Amoco`, their categories or dates), with category, value and attribute orders that differ from each example wherever the schema allows, and OIDs under the documentation enterprise number `1.3.6.1.4.1.32473` (RFC 5612). The public NATO policy identifier, its OID and the NATO classification names appear only in the NATO profile data file and its tests (D-21); a guard refuses them in the exchange code and the vectors. 45.2-09 runs a scratch-only check that no run of 80 or more characters of any committed exchange file matches the extracted texts. Errata in the texts (research section 8) become negative vectors.

### Label policy profiles (owner principle, 2026-11-24)
- **D-21 (profiles with provenance):** A label policy profile is a data file in the format `label-profile/1`, modelled on the concepts of an XML SPIF (4774 App 2 Annex B; 4778.2 §12.11) so a verified SPIF can later replace it: the policy identifier and its optional `urn:oid:` URI, the classifications in rank order with their marking words, the category tags (type, tag name, optional URI) and their values. Every value carries `provenance` (`verified`, `public-unverified` or `assumed`), `source` (a document or authority, cited by section), `date`, and, unless verified, `gap` (the gap id that tracks its replacement). A value may instead be a marked `placeholder` that is configurable per target system and always refused for an operational export. Drafts ship in `resources/label-profiles/`; your organization adopts a profile by embedding it in the signed policy's `labelXml` section, so the policy signature covers it, and exports read only adopted profiles. Shipped drafts (45.2-11):
  - **NATO profile, `public-unverified`:** policy identifier `NATO`, URI `urn:oid:1.3.26.1.3.1`, classifications UNCLASSIFIED, RESTRICTED, CONFIDENTIAL, SECRET and TOP SECRET (rendered COSMIC TOP SECRET), the category tags of 4774 App 2 with their URIs, and the country value `CAN`. Source: the owner's public ADatP-4774.2 guidance, cross-checked against our local ADatP-4774 and 4778.2 (research section 9a records what matches). Context values are not drafted (they need the mission context). Replacement: the current NATO SPIF from the NATO Metadata Registry and Repository, with mission context and release rules, obtained through PSPC's Contract Security Program (owner action b).
  - **Canadian DND/CAF profile, `assumed`:** policy identifier `CAN` (the security policy indicator of DND security orders, as in CAN SECRET and CAN PROTECTED B), classifications PROTECTED A, PROTECTED B, PROTECTED C, CONFIDENTIAL, SECRET and TOP SECRET. Its OID, caveats, releasability rules and versioned SPIF are not known: the URI is a marked placeholder set per target system, never an invented OID. Replacement: the target system's label-policy owner, through the DND project technical authority (owner action a).
- **D-22 (whose policy, and the operational rule):** The originator label is written in the policy of the information's owner, chosen per scale preset in `labelXml`: Government of Canada scales (`ca-protected`, `ca-classified`) use the Canadian profile, the `nato` scale uses the NATO profile, and your organization's own scale uses a profile your security officer adds (none ships). The alternative label is written in the common partner policy (D-03). An export whose partner entry in `exchangePartners` has `purpose: operational` is refused when any value it writes is `assumed`, unless your security officer has recorded an exception in `labelXml.assumedExceptions` (`{ profile, values, reason, until }`); a `placeholder` value is refused for every operational export, with no exception. `public-unverified` values are allowed and shown. Exports with `purpose: trial` (the development stage and allied test cells) may use assumed values and say so. Every export shows the provenance of the profiles it used, and its sealed receipt records the profile ids, their hashes and the lowest provenance used.

### Labels (4774)
- **D-03 (two labels, owner's first):** Every export carries an `originatorConfidentialityLabel` in the information owner's policy (D-22) and an `alternativeConfidentialityLabel` in the common target policy that `labelInterop` names, both spelled from adopted profiles. The NATO policy is the originator only for NATO-originated information (4774 App 2 Annex C footnote). On import, every label the reader can map (the originator label and each alternative label whose policy an adopted profile and the tables know) is mapped in, and the result is their join through `joinLabels`; a label in a known policy with a value the table lacks refuses the object, labels in unknown policies are skipped with a note, and none mappable means refused with a plain reason. Values are matched case-insensitively (4774 §5.1); XML syntax and attribute names are matched exactly against the schema.
- **D-04 (`label-xml@1`):** A new signed policy section `labelXml` (feature `label-xml@1`, lowercase as `FEATURE_ID_PATTERN` requires, appended to the lists) holds: the adopted profiles by value (D-21); per scale preset, the originator profile (D-22) and the level-to-classification map into it; the target profile of the alternative label; an optional context category for the target (`{ tagName, uri?, values, releasableMarker }`); `assumedExceptions` (D-22); `reviewAfterDays` (the review date 4774 §4.3 requires); and `mapping`, which must equal the `labelInterop` mapping version or both are refused as "The label tables disagree; ask your security officer to sign them again together." The level-to-value and token-to-value facts of the alternative label stay in `labelInterop` only (one source), and one common target policy per scale follows 4774 §2.2. No `labelXml` section: every 4774 or ZTDF-profile export is refused with "Your organization has not set how its labels are written for NATO partners." The shipped default policy adopts no profile.
- **D-05 (own narrow XML, no library):** `src/domain/exchange/xml/`: a reader that refuses DOCTYPE, entity declarations, external references, entity references other than the five predefined and numeric ones, processing instructions other than the XML declaration, CDATA, undeclared prefixes, duplicate attributes after namespace resolution, documents over 8 MiB, depth over 64 and more than 256 attributes on an element; comments are kept in the tree only for canonicalization with comments and never reach a decision. A writer that emits the XML normalization form 4778.2 Annex A recommends (no namespace prefixes except `xml`; attributes in another namespace prefixed `n0`, `n1` and so on; namespace declarations before attributes; attributes sorted by namespace URI then local name; whitespace preserved). Canonicalization 1.0, inclusive and exclusive, with and without comments, over the reader's tree (45.2-04). No XML package (45.1 D-10).

### Binding and core metadata (4778, 4778.2, 5636)
- **D-06 (binding objects):** We write a BDO per export: the binding information root in the 4778 namespace, one container, one metadata binding with an `Id`, holding one `Metadata` entry per NCMS element (5636.1 §3.1) and one `DataReference` to the payload (`URI="0.payload"` inside our TDF-profile objects). The metadata label is a nested BDO inside a `BindingInformationContainer` per the 5636 BDO binding profile (Annex C App 2), binding an originator label to `URI=""`. We read encapsulating, embedded and detached BDOs, and sidecar files named `<file>.bdo` beside their file with relative data references (4778.2 chapter 9, `urn:nato:stanag:4778:profile:sidecar:1:2`); same-document references (`""` and `#id`) and relative URIs inside the object or folder held; a `ds:Transforms` with an XPath other than the Enveloped Binding Data Object transform of 4778.2 Annex A is refused with "Partial bindings are not supported yet." Granularity rules 1 to 4 (4778 §3.5) are applied when one BDO binds several labels. Schema order is followed: `ds:Signature` before the containers (4778 §4.8, erratum E6).
- **D-07 (the seven mandatory NCMS elements):** originator label; metadata label; `s5636:Creator` and `s5636:Publisher` with `s5636:type="organization"` and your organization's name from the site file, never a person (45.1 D-03, observers see no roster); `s5636:DateCreated` (the release time); `s5636:Identifier` (the export's receipt id, opaque); `s5636:Title` (the released version's title, which the releasing person confirms in the export dialog because a title can itself be sensitive). The metadata label equals the content label; it is never set lower automatically. An imported BDO without an originator label is refused; any other missing mandatory element is shown as a note, not a refusal, because it changes no access decision.
- **D-08 (signed bindings to ADatP-4778.2):** `CryptoArtefactProfile` interface with one implementation, `urn:nato:stanag:4778:profile:cryptoartefact:1:2`, digital-signature variant (4778.2 chapter 2, Annexes A and B). Writing: a `Signature` with no prefix as the first child of the binding information; exclusive canonicalization; `ecdsa-sha256` (a mandatory algorithm, Table 2-4); SHA-384 digests (the mandatory digest, Table 2-3); a `Reference` with a shortname XPointer to each `MetadataBinding`; for each data reference whose URI is not a same-document XML reference (such as `0.payload` or a sidecar's relative file), a `Manifest` inside an `Object` with a `Reference` carrying the same URI and the digest of the referenced octets, and a `Reference` to that `Manifest`; an `Object` with `SignatureProperties` holding a WS-Security `TimeStamp` with `Created`, referenced; `KeyInfo` with `X509Data` carrying the signing certificate and its chain up to, not including, your organization's root CA, and never `KeyName`. Reading partners' bindings: every mandatory and optional algorithm of Tables 2-3 and 2-4 is accepted, prohibited ones are refused; canonicalization 1.0 and exclusive canonicalization, with and without comments, are accepted, and canonicalization 1.1 and 2.0 are refused as "not supported yet" (recorded as a condition at the trial if a partner uses them); the certificate chain must reach a trust anchor pinned for that partner in `exchangePartners` and be valid at the time stamp; certificate revocation lists are not fetched (a gap row, D-20); what is signed is what is used (the container processed is the one the reference resolved; duplicate ids refused; no other `Object` content trusted). The CMS artefact (Annex E) and the HMAC variant (Annex C) are not written; HMAC bindings from partners are refused, because no shared key exists. Unsigned standalone BDOs and sidecar files received from partners are refused (owner item 6); inside a TDF-profile object the assertion binding provides the integrity. (Amended 2026-11-25: under the owner's direction of that day, D-25 holds an unsigned or uncheckable binding in quarantine as a claimed label instead of refusing it, never trusted as a binding; owner question 1 confirms it. A binding that can be checked and fails is still refused.) Interop is unverified until the acceptance trial (G384, updated by hand-off H-11).
- **D-09 (signing keys):** A second release key `release-p256-<site>` (ECDSA P-256, non-exportable, OpenBao Transit) under the same `exchange-release` policy and step-up custody as `release-<site>` (45.1 D-03): it signs the 4778 XML Signature and the ZTDF-profile assertion bindings (JWS `ES256`). It needs an X.509 certificate from your organization's site PKI (47 wave 5) for `X509Data`: 45.2-04 confirms whether OpenBao Transit can produce a certificate signing request for a Transit key (Vault has one; OpenBao's support is not verified) and, if not, stops for an owner decision (H-12). Transit signs with `marshaling_algorithm=jws`, which gives the raw `r||s` form both formats need. 45.1's own JSON `LabelBinding` stays `eddsa-jcs-2022` with `release-<site>`. Owner item 2.

### The ZTDF-compatible profile (Part 2b)
- **D-10 (`ZtdfProfile`):** One interface in `src/domain/exchange/ztdfProfile.ts` holding every point where ZTDF may differ from OpenTDF 4.3.0: `labelAssertion` (type `handling`, scope `payload`, `appliesToState` `encrypted`, statement `schema` the 4774 namespace, `format` json-structured mirroring the 4774 element names with `Xmlns` and `CreationTime` as in the public example, research section 6; the reader also accepts the 4774 XML as a `string` statement); `bindingAssertion` (type `metadata`, statement `schema` the 4778 namespace, `format` string holding the BDO XML); `assertionBinding` (JWS `ES256` by `release-p256-<site>` over the assertion's canonical JSON and the manifest's policy and key access hashes, so an assertion cannot be moved to another object); `keyAccess` (the variants and fields 45.1-02's research records); `policyBinding` (HS256 per the specification); `rewrap` (the protocol of D-11); `manifestVersion`. The shipped profile is `ztdf-compatible/opentdf-4.3.0/1`. `tdf.ts` (45.1-02) gains assertions and profile hooks and names no 4774 or 4778 constant (architecture test). When ACP-240(A) or partner samples arrive, a new profile implements the interface; nothing else changes.
- **D-11 (key access to a partner):** Push for exports: the payload key is wrapped to the partner KAS public key pinned in `exchangePartners` (SPKI SHA-256 fingerprint, `kid`, `url`), plus a second key access to our own receiving key so your organization can reopen its own exports. Pull for imports: when a partner object's key access names only the partner's KAS, the exchange officer's backend sends that KAS a rewrap request in the shape of the public specification (`{KAS_URL}/v1/rewrap`, research section 6), with a fresh ephemeral P-256 key pair per request held in backend memory; only KAS URLs listed in `exchangePartners` are called; the KAS's TLS identity and key are pinned; the client authenticates with a client certificate from your organization's site PKI (owner item 8); an air-gapped site never calls out and says so. We do not run a KAS for partners: an export, once wrapped to a partner's key, cannot be withdrawn (45.1 D-07 kept; owner item 5; G387).
- **D-12 (`exchangePartners`, feature `exchange-partners@1`):** A new signed policy section keyed by the `agreements@1` id (71-06 unchanged): `{ purpose ('trial' | 'operational'), kas: [{ url, kid, alg ('rsa:2048' | 'ec:secp256r1'), spkiSha256, publicKey, oaepHash? ('sha256' | 'sha1', required for rsa:2048 and absent for EC, added 2026-11-25 by D-32) }], kasTlsSpkiSha256, bindingTrustAnchors: [X.509 certificates in PEM, each with its SHA-256 fingerprint], profileOverrides? (per profile, values set for this target system with their provenance, for example the Canadian policy OID once the target system's policy owner gives it), classicalUpTo? (highest level that may leave with classical key access) }`. A `classicalUpTo` above the ITSP.40.111 ceiling of D-13 is refused when the policy is parsed. The security officer sets it; the shipped default is empty, so nothing is exported or rewrapped until it is set. Hand-off H-2.

### Decisions, credentials and post-quantum
- **D-13 (one decision, honest PQC):** `mayRelease` (71-07) stays the only release rule, called by 45.1's `canExport`; AC322's PDP, PEP, PIP and PAP map to it as research section 9 shows. Exchange key access is classical because partners have no post-quantum key type: each export's sealed receipt records the key access algorithm; the export dialog says "This copy is protected with keys that a future quantum computer could break, because <partner> does not support post-quantum keys yet."; the effective cap for classical key access is the lowest of the partner's `classicalUpTo`, the agreement's ceiling, and the highest level ITSP.40.111 v5 approves classical key establishment for (Protected B, or the level the signed policy's scale mapping makes equivalent to Protected B; a scale with no such mapping, and every classified level, has no classical cap, so classical export is refused); an export above the cap is refused with that reason even when the agreement's ceiling is higher (owner item 4); and from 2036-01-01 (ITSP.40.111 v5 phases out classical key establishment used without a post-quantum scheme by the end of 2035) every classical key access is refused. Existing gap G356 carries this condition; 45.2-08 adds the date and the cap to its remediation. A post-quantum key access type is a reserved profile field (`keyAccess.pqc`), refused as "not supported yet".

- **D-25 (what an arrival proves; refused or held):** Each read gives its label an evidence class, derived only from what the adapter checked: `verified` (a binding the adapter checked, by a signer pinned for that partner in `exchangePartners`, over this content, and the label maps through the tables), `claimed` (a machine-readable label is present but its binding is absent, by a signer not pinned, or in a form this version cannot check yet, such as canonicalization 1.1 or an HMAC binding with no shared key), `inferred` (read from a human-readable marking, D-30) and `none`. Integrity failure of a check that can be made (a changed label, payload, metadata entry or policy; a replayed assertion; a pinned signer's signature that does not verify) refuses the arrival with its reason, as today (D-08, 45.1 D-06): tamper evidence is never held as unlabelled. Content that cannot be opened (no key access your organization can reach) is refused. One table, `REFUSAL_CLASS` in `inbound/adapter.ts`, sorts every refusal id of the readers the adapters use (45.1 `TDF_REFUSALS`, the profile's, 45.2-03's and 45.2-04's) into `refuse` or `hold`; a test fails when a refusal id has no class, so a new reader refusal cannot fall through by accident. `conversion.assumed` names each assumption with an id (D-34). **Fail-safe evidence (revised 2026-11-25 after the plan re-check; the class, not the instance):** the evidence shown is derived by one function, `evidenceOf(record, receipt)` in `inbound/adapter.ts`, whose default is the most cautious class, `unchecked` ("Not checked: an exchange officer must confirm or raise its label"). It never infers `verified` from the absence of assumptions. `verified` is shown only when the record's sealed import receipt carries a positive verification result, `verification { signerPartner, anchorSha256, by: { adapter, version } }` (the binding was checked, by a signer pinned for that partner, and the label mapped). The adapter that made those checks writes it, and the registry refuses a verification result from an adapter whose declaration lacks `binding-signature` and `label`. **The receipt is sealed for confidentiality, not authorship (revised 2026-11-25 after the second re-check)**, so `evidenceOf` and Accept as is trust a verification result only when both hold, re-checked every time the record is read:

The ZTDF-compatible stored form's conversion assertion records the evidence at import time for the file's own history only; no decision or display reads it. `claimed`, `inferred` and `none` are shown only from the known assumed ids the adapter wrote in `conversion.assumed`. Accept as is is offered only for `verified`; every class except a positively derived `none` keeps the record's provisional label as the floor of the never-lower rule (D-29). Normalisation can only copy evidence, never raise it. - **D-32 (OAEP SHA-1 senders and RSA key sizes, per ITSP.40.111 v5; G455):** Finding (research section 12.2): ITSP.40.111 v5 (effective 2026-05-29) no longer recommends SHA-1 (section 7.1: not for signatures or anything needing collision resistance, and to be phased out for HMAC, key derivation and random bit generation), lists no SHA-1 among its recommended hash functions (sections 7.2 and 7.3), says a primitive used inside a recommended scheme should itself be a recommended algorithm (section 1.1), and recommends RSA key transport as NIST SP 800-56B Rev. 2 specifies, with at least 2048 bits and at least 3072 bits by the end of 2030 (section 5.1).
