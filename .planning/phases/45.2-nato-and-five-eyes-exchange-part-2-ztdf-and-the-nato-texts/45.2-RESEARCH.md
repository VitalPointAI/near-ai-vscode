## 0. Summary

1. **AC322 is not ACP-240(A) and does not define ZTDF.** The DCRA v2 is NATO's architecture blueprint (data products, mesh, governance, data-centric security and zero-trust principles, ABAC). It never mentions ACP-240, ZTDF or TDF. For metadata it requires the NATO Core Metadata Specification ADatP-5636 together with ADatP-4774 and ADatP-4778 (AC322 Annex 2 para 15.3 and para 80; Appendix 4 para 12) [text]. ACP-240(A) (CCEB) is the implementation specification that defines ZTDF, the encrypted object and its key access; we do not hold it.
2. **Part 2a is fully buildable now:** 4774 labels, 4778 binding objects and 5636 core metadata, both directions, plus conformance to AC322's data-centric security, ABAC and data-product metadata principles. One piece is still provisional: the **signed** binding. ADatP-4778 allows a W3C XML Signature in the binding object but leaves its profile (what is signed, canonicalization, algorithms) to ADatP-4778.2 chapter 2, "Cryptographic Artefacts binding profile", which ADatP-5636 makes mandatory for cryptographic bindings and which we do not hold [text 4778 §3.6, §4.5.1; 5636 Annex C App 2 §C-2.2.6].
3. **Part 2b is a ZTDF-compatible profile on OpenTDF 4.3.0.** The public OpenTDF text says ZTDF "builds directly upon the OpenTDF specification", "extends OpenTDF by mandating the inclusion of specific cryptographic assertions required for Five Eyes contexts", and that "the detailed specifications for IC-TDF and ZTDF are maintained separately" [primary]. Its assertion-statement page shows a 4774 label carried as an assertion statement whose `schema` is the 4774 namespace and whose `format` is `json-structured` [primary]. Every point where ZTDF may differ goes behind one profile interface. **ZTDF conformance is unverified until ACP-240(A) or partner samples are available.**
4. **45.1 lines up well,** with five gaps that 45.2 closes: the label table lacks the 4774 spellings (our own policy identifier for the originator label, tag names, category URIs, the context category, a review date); the binding is our own JSON object, not a 4778 binding object; no 5636 metadata; no assertions in the TDF object; no pull key access from a partner's KAS.
5. **Post-quantum is an honest gap at the boundary.** Our cells use the hybrid P-256 + ML-KEM-768 wrap (33.2). The public OpenTDF key access object has no post-quantum key type and partners' KASs use RSA or EC [primary]. Exchange key access stays classical, is recorded per export and is shown plainly.
6. **Texts still needed:** ADatP-4778.2 (signed-binding profile, file and XML profiles), ACP-240(A) with the ZTDF specification, your organization's national policy identifier and value domains, the NATO marking guidance AC/322-N(2011)0130-REV1 (only if we label in the NATO policy), and allied or vendor samples with a test KAS (section 10).

## 2. AC322 DCRA v2: what it requires

AC322 is principle-level. It puts the actual exchange between systems out of its scope and defines "how to make data available for that exchange" (Annex 2 para 55). The requirements that apply to an exchange at our release boundary:

| Area | What AC322 says (Annex 2 unless noted) | What it means for us |
|---|---|---|
| Standards in force | Para 15.3: the DCRA follows "the principles approved by Allies in the Data Centric Security Implementation Plan", "supporting standards such as STANAGs 5636, 4774 and 4778" | 4774, 4778 and 5636 are the conformance targets for labels, binding and metadata |
| Architectural principles (Table 1) | Security by Design (DCS and zero trust); Interoperability by Design (open or NATO standards, documented APIs); Data Sovereignty; Technology Independence; User Proximity ("disconnected, denied, intermittent, limited" environments) | Our cells protect data at source; exchange formats are NATO standards; push key access works offline |
| Data products | Para 26: a data product carries "confidentiality and administrative markings", provenance and amplifying information. Appendix 4 para 12: metadata "must be based on the NATO Core Metadata Specification (ADatP-5636 ic.w. ADatP-4774 and ADatP-4778)". Appendix 4 para 14: confidentiality and common metadata are covered by existing NATO standards; provenance and amplifying metadata still need refining | Every export carries the 5636 mandatory metadata, its 4774 labels and a 4778 binding. Provenance and amplifying metadata are not required yet |
| Data-centric security (Appendix 9) | Para 1: zero trust, "never trust, always verify"; para 2: ABAC over user, role, device, data sensitivity and context; para 3: the PEP intercepts, the PDP decides, the PIP supplies attributes, the PAP manages policies; para 4: encryption and digital signatures complement access control; paras 6 to 11: ICAM (authorization, authentication, digital certificates, digital identity lifecycle) | Mapped in section 9: the PDP is `mayRelease`, the PIP is verified credentials, the PAP is the signed policy |
| Federation and data spaces | Para 47: federated identity, decentralized authentication, cross-domain policy enforcement; paras 40 to 45 and Appendix 3: trust "negotiated case-by-case", usage policies set by data owners, "decentralized identity management" | Exchange happens only under a recorded agreement (`agreements@1`); identities are DIDs with credentials |
| Interfaces | Para 56: interfaces "capable of enforcing policy for sharing, labelling, terms of use" | The release boundary is that interface |
| Key management | Not specified. Appendix 9 names encryption, signatures and "Digital Certificate Services" only | Our own key custody (OpenBao Transit, step-up) is not constrained by AC322 |
| DCAT catalogues, data mesh, data quality | Appendix 4 and 10 | Out of scope for this phase (no catalogue, no mesh); recorded as "not in this phase" rows in the conformance matrix |

Two cautions:
- **AC322 Appendix 5 "Data Labelling" is about annotating AI/ML training data,** not confidentiality labels. It belongs to the AI-classification research, not here.
- **AC322 never names ACP-240, ZTDF or TDF,** and no section of it is a container or key-access specification. Nothing in this phase cites AC322 for ZTDF.

The DCS maturity levels come from 5636.1 §2.2 (citing IMSM-1049-2019): level I, labelling and binding by 4774 and 4778 with a guard; level II, rich 5636 metadata and alliance-wide ABAC; level III, cryptographic protection with control after release [text]. Our cells are level III internally. At the boundary, 45.1 plus 45.2 deliver levels I and II and the cryptographic container of level III. Control after release would need a KAS run by us, which we do not run (CONTEXT D-11).

## 3. ADatP-4774: what the implementation needs

| Topic | Section | Content (summary) |
|---|---|---|
| Purpose and requirements | §1.2, §2.3 | XML labels understood by all partners; at least two policies in parallel (an originator label plus an alternative label in another policy); ownership; categories; succession |
| Primary elements | §4.2 | Governing policy, one classification, privacy mark (legacy), categories of three types: restrictive, permissive, informative. Defined subcategory tags: Context, Releasable To, Only, Additional Sensitivity, Administrative (Table 1) |
| Succession | §4.3, §5.1 | A future label at a date. Without a succession element, a review date SHALL be given; a review date in the past does not invalidate the label |
| Values | §5.1 | Values inside the confidentiality information are case-insensitive and in English. Under the NATO policy: the creation date SHALL be present; a policy URI, if present, SHALL be a `urn:oid:` URN |
| Label elements | App 1 | Three top-level elements of one type: `originatorConfidentialityLabel`, `alternativeConfidentialityLabel`, `metadataConfidentialityLabel`; plus `ConfidentialityLabel` kept for backward compatibility only (Annex A) |
| Label type | App 1, Tables 4 to 8 | Optional `Id` and `ReviewDateTime` attributes. Sequence: `ConfidentialityInformation`, optional `OriginatorID` (attribute `IDType`, eight forms, Table 9), `CreationDateTime`, optional `SuccessionHandling` (`SuccessionDateTime`, `SuccessorConfidentialityLabel`), then extensions in other namespaces |
| Confidentiality information | App 1 | Sequence: `PolicyIdentifier` (text, optional `URI`), `Classification` (text; its `URI` is prohibited), optional `PrivacyMark`, any number of `Category` (attributes `Type` in RESTRICTIVE, PERMISSIVE, INFORMATIVE; `TagName` required; optional `URI`), each holding `GenericValue` elements. `IntegerValue` and `BitStringValue` SHALL NOT be used |
| Schema | App 1 Annex A | Namespace `urn:nato:stanag:4774:confidentialitymetadatalabel:1:0`, schema version 1.3, elements qualified, attributes unqualified; extension points allow foreign-namespace elements and attributes, which "MAY be ignored" |
| Examples | App 1 Annex B | Four fictitious labels: permissive categories; restrictive and informative categories; `Id`, `ReviewDateTime` and `OriginatorID`; succession |
| NATO policy conventions | App 2 | How the NATO policy fills the elements: policy identifier and its OID, the classification value domain (held in AC/322-N(2011)0130-REV1, not in this text), the "Context" category being mandatory with a "Releasable" marker value when "Releasable To" is present, the "Only" category, "Additional Sensitivity", "Administrative" (informative, lowest classification only), and the marking rule for the top level. These are **values and rules of the NATO policy**; under the owner's decision none ships, and the security officer's table supplies them |
| Clearances | App 2 Annex A | A clearance schema (`urn:nato:stanag:4774:confidentialityclearance:1:0`) with a list of classifications and the permissive and restrictive categories a nation holds. Our credentials (71) carry the same facts per person; we do not exchange clearances |
| Policy information files | App 2 Annex B | An XML SPIF (xmlspif.org) describes a policy's values and their relations; Schematron is suggested for value validation |
| PUBLIC policy | App 2 Annex C and D | For information ingested from public sources. Footnote: the NATO policy must not be used in the originator label of information NATO does not own; it may be used in an alternative label |

**Consequence for us (inference):** our exports carry an **originator label in your organization's own national policy** (its identifier and OID from the security officer), and an **alternative label in the partner's or the common policy** from the label table. Never the NATO policy as originator.

## 4. ADatP-4778: what the implementation needs

| Topic | Section | Content (summary) |
|---|---|---|
| Requirements | §2.2 | Add metadata without breaking existing bindings (for example an alternative label); detect changes to object and metadata; bind at any time; bind to parts of composite objects; work with any format |
| Approaches | §3.2 | Encapsulating (object and metadata inside the binding), embedded (binding inside an XML object, referring to it), detached (binding outside, by reference to the object, the metadata or the cryptographic artefact) |
| Binding data object | §3.3, §3.4 | The binding information as XML is the BDO; a dedicated BDO per frequently used object is recommended |
| Granularity | §3.5 | Four rules: children inherit a parent's metadata unless they have their own of the same type; parents never inherit from children; different types accumulate; the same type supersedes |
| Profiles | §3.6 | Per-format profiles are not in this text; they live in the NISP (ADatP-34), and in ADatP-4778.2 |
| Namespaces | §4.3.1 | `mb` = `urn:nato:stanag:4778:bindinginformation:1:0`; `ds` = XML Signature; `xmime` = XML media types |
| Elements | §4.3.2 to §4.3.7 | `MetadataBindingContainer` (one or more `MetadataBinding`, optional `Id`); `MetadataBinding` (one or more `Metadata` or `MetadataReference`, then one or more `Data` or `DataReference`; all metadata binds to all data); `Metadata` (inline, optional `xmime:contentType`, `encoding`); `MetadataReference` and `DataReference` (`URI` required, optional content type, encoding and one `ds:Transforms` with exactly one XPath 1.0 transform); `Data` (inline, `encoding` SHALL be present when encoded) |
| Binding information | §4.5.1, Table 9 | Root `BindingInformation` in the `mb` namespace: one or more containers and zero or more `ds:Signature` (W3C XML Signature, second edition, reference [10]) |
| Management | §4.6 | Encapsulating BDO: `BindingInformation` is the document root; embedded: inside the XML object, data references preferably within that object; detached: references external. Embedding metadata (not referencing it) is recommended |
| References | §4.7 | `URI=""` means the root of the object; fragments follow the content type's fragment rules (XPointer for XML, JSON Pointer for JSON) |
| Schema | §4.8 | Version 1.4; extension points everywhere for foreign namespaces; **the sequence puts `ds:Signature` before the containers** |
| Examples | §4.9 | Encapsulating (XML and base64 data), embedded (with `URI=""`, and with an XPath idiom), detached (HTTP URI; a sibling fragment), one-to-many, many-to-one, many-to-many, a JSON object with a JSON Pointer fragment |

**What 4778 does not say:** which parts a `ds:Signature` must reference, which canonicalization and algorithms, how the signer's key is identified or trusted. Its reference [8] (NCIA TN-1455-REV1, "NATO Profile for the Binding of Metadata to Data Objects" v1.1) and ADatP-4778.2 chapter 2 hold that.

**Post-quantum, honestly:**
- Inside your organization, cell keys use the hybrid wrap (33.2): post-quantum now.
- At the boundary, key access is RSA-OAEP or P-256 ECDH, because the public OpenTDF key access object has no post-quantum type and partners' KASs offer RSA and EC [primary, section 6]. Anything exported is protected only by classical keys from then on. An adversary who records it today could open it with a future quantum computer.
- ITSP.40.111 v5 still lists P-256 ECDH and RSA key transport for Unclassified, Protected A and Protected B, with a phase-out for schemes used "without a post-quantum key establishment scheme" by the end of 2035 (research section 10.1).
- So each export records which key access algorithm it used (in its sealed receipt), the export dialog says so in one sentence, and the security officer can set a highest level for classical key access per partner (CONTEXT D-13). A post-quantum key access type is a reserved profile point for when ACP-240's later editions or a partner define one.
- Our receiving key (`exchange-receive-<site>`, RSA-3072, 45.1 D-07) is classical too, for the same reason.

## 11. Security notes for the plans

- **XML parsing is an attack surface.** No DTD, no entity declarations, no external references (XXE), only the five predefined entities and numeric references, no processing instructions except the declaration, size, depth and attribute limits, duplicate attributes refused, every prefix declared. Our own narrow reader; no XML library (CONTEXT D-05).
- **Signature wrapping.** A verifier must use exactly what was signed: one `ds:Signature` in the profile's position, references only to the container by `Id` and to the payload, exclusive canonicalization only, and the container it processes must be the one the reference resolved to; duplicate `Id`s refused.
- **Replay of assertions.** The assertion binding covers the assertion and the object's policy and key access context, so an assertion cannot be moved to another object (OpenTDF assertion binding page).
- **KAS calls (SSRF, leakage).** Only KAS URLs listed in the signed `exchangePartners` are called, over TLS, with the partner's KAS key pinned; never from the browser; no call at an air-gapped site.
- **Labels from outside are untrusted.** A partner's label is mapped only through our table; an unmappable label is refused; the result is the join of every mappable label, never lower.
- **Not a cross-domain guard** (45.1 D-08): exchange between accredited systems at the same classification.
