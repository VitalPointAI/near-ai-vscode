## Phase Boundary

Every dependency and image that Sterling Sovereign AI (SovAI) builds with or runs is reviewed once by an intake that records why it was approved, signs that approval with your organization's site key, and keeps the SBOM, scan and VEX beside it; builds use only approved inputs; approved content is rescanned every day; air-gapped sites receive it, its database and its withdrawals in the signed bundle and refresh files.

In this phase:
1. The intake: the policy gates, the state machine, the promotion record, approvals by named people, and the two stages (gather on a connected host with no key; decide and sign on a host with no internet and the HSM).
2. Your organization's software registry at HQ: Harbor for OCI content (images, charts, tools, dependency snapshots, the vulnerability database, every SBOM, scan, VEX and record as OCI referrers) and Verdaccio for npm (build side only).
3. Approved build inputs: the signed approved lists that CI checks before anything runs; npm, Go, Maven, PyPI, RPM and base images; image builds with the network off.
4. The bundle built only from HQ's approved content, with the records carried to sites; our own releases re-verified at HQ before any site gets them.
5. Continuous monitoring: the daily database sync (Anchore's Grype database and OSV), daily rescans, alerts, OpenVEX, withdrawals, and the signed refresh to sites.
6. The compliance obligations the controls require: fit entries, the new component, statements, evidence rules, documents, OSCAL, gap rows G517 to G525.
7. The move of CI and publication to self-hosted runners in Canada, behind an owner checkpoint (D-05, D-30).

Not in this phase:
- Language-package registries at sites (D-06): sites receive OCI content only.
- Building our own vulnerability database with grype-db and vunnel (the owner chose the mirror, D-07; G519 records the option).
- Moving the source code and the CI control plane off GitHub (G525 records it; see Deferred Ideas).
- A retention policy that deletes anything (D-11): it comes back to the owner (G522).
- Any change to another phase's planning files. Cross-phase items are in `48.3-HANDOFFS.md`.

## Implementation Decisions

### The owner's answers (locked, 2026-11-25: "accept supply registry defaults")
- **D-01 (owner, Q1):** One design, deployed twice. Sterling's build HQ in Canada (on-premise) holds the npm, Maven, Go, PyPI and RPM dependencies and the base images our builds use; each organization's HQ holds the OCI content for its own sites. In the lab they are one instance on the owner's machine. The site file chooses the role (`supply.roles`: `build`, `deploy` or both).
- **D-02 (owner, Q2):** Minimum age 7 days before any version of anything is used, in every ecosystem. A security fast lane lets a younger version in only with a named approver and a reason (the advisory id the new version fixes).
- **D-03 (owner, Q3):** Automatic approval when every gate passes. One named person approves an item with any flag (new name, install script, licence off the list, provenance regression, maintainer change, high finding). Two different named people approve a flagged install script or a fast-lane item.
- **D-04 (owner, Q4):** Licence allow-list: MIT, Apache-2.0, BSD-2-Clause, BSD-3-Clause, ISC, 0BSD, BlueOak-1.0.0, CC0-1.0, Unlicense, Python-2.0, Zlib; MPL-2.0, LGPL-2.1 and LGPL-3.0 (with or without "-only"/"-or-later") for unmodified, separately loaded components; GPL and AGPL go to review; a missing or unknown licence goes to review. An SPDX expression passes when every branch of an AND passes and at least one branch of an OR passes.
- **D-05 (owner, Q5, and "let's look to become fully sovereign compliant"):** Keep GitHub-hosted CI and GHCR for now, with HQ re-verifying every release (D-23). Plan the move to self-hosted runners in Canada, with GHCR made optional, as explicit later plans (48.3-23, 48.3-24, 48.3-25) that start with an owner checkpoint; they are not dropped. Until they land, G517 records that builds run outside your organization.
- **D-06 (owner, Q6):** No language-package registries at sites in the first cut. Sites receive OCI content only.
- **D-07 (owner, Q7):** Mirror Anchore's daily Grype database (checksum checked, signed by us) plus OSV (for malware, `MAL-` ids, and language advisories). Self-building with grype-db and vunnel stays an option (G519).
- **D-08 (owner, Q8):** A withdrawal at a site raises an alert and goes to the site change board. There is no automatic admission block.
- **D-09 (owner, Q9):** Approvals are signed with your organization's site key in the HSM (SoftHSM2 in development, 48.1-22), never with the supplier release key (G396, 48.1-17).
- **D-10 (owner, Q10):** VEX is OpenVEX, signed and attached. CSAF only if a customer asks.
- **D-11 (owner, Q11):** Nothing is deleted automatically. Approved versions referenced by any supported release are kept. A retention policy for refused and old quarantined items comes back to the owner for approval (G522).

### Owner rules that apply (locked)
- **D-12 (owner rules):** Every added resource has a passing compliance fit entry before use, and that register is a gate path (Verdaccio, osv-scanner, the Harbor HQ role, the self-hosted runner, ORAS only if spike S-B needs it). Gap ids only from G517 to G526, reserved for 48.3; never another number. Every caveat found goes into `compliance/gaps.json` with `appliesAt` and `blocksProduction`. Downloaded code is untrusted: it is read before it runs, it runs only after review, and only in a throwaway container with no network where possible. ### The intake
- **D-13: Components.** Harbor v2.15.5 (chart 1.19.4, already vendored) at HQ is the approved OCI store; Verdaccio (version chosen by spike S-C: the newest at or above 6.10.1 that is older than the 7-day gate and runs on Node 22) serves npm at the build HQ only; the intake is our own Node code in `deploy/supply/`, tested in `deploy/test/supply-*.test.mjs` (the required deploy job runs `deploy/test/*.test.mjs`); syft 1.57.2, grype 0.122.1, cosign 3.1.4 and hauler 2.1.2 are reused from `compliance/ci/tool-pins.json`; osv-scanner is a new pin. Grype is the one scanner of record; Harbor's and Zot's Trivy stay off. Nexus, Artifactory, Pulp, devpi, Athens, ChartMuseum and Gitea/Forgejo packages are not used (research comparison). Harbor has **no proxy-cache projects and no egress**: nothing at HQ but the gather host reaches the internet.
- **D-14: Two stages, so the connected host never holds the key.** (Planning choice, threat-driven: an internet-connected host that could sign with the site key unattended would put every site's trust one compromise away.)
  - **Gather** runs on the connected gather host at HQ, which holds no signing key. It fetches into quarantine, resolves npm with `--min-release-age=7`, downloads the Grype and OSV databases, and records facts only upstream can give: publish time, publisher, provenance verification, upstream signatures, the database listing. It pushes each gather set as an OCI artifact to Harbor project `quarantine` with a robot account that may only push there.
  - **Decide and sign** runs on the signing host: no internet, the HSM through PKCS#11 (48.1-17's `signImagePkcs11` and `signFilePkcs11`), reach to HQ Harbor, Verdaccio and the HQ cluster API. It re-derives every fact it can from the bytes alone (digest and integrity, npm registry signature against npm's pinned public keys, install scripts, licence, SBOM with syft, Grype with the signed database, OSV `MAL-` with the offline database), evaluates the policy with the gather host's claims, moves the state, signs approved records and publishes. A lying gather host can misstate only publish time, provenance and publisher (G524).
  - In the lab both stages run on the owner's machine. Real signing with the development site key needs the owner's PIN, so the owner runs the signing commands; agents run gather and `decide --dry-run`.
- **D-15: The states** (the research's machine, made explicit in `deploy/supply/lib/states.mjs`): `requested`, `quarantined`, `waiting`, `in-review`, `approved`, `refused`, `under-review-again`, `withdrawn`. Transitions: requested to quarantined (gathered); quarantined to refused (a hard gate fails), waiting (too young), in-review (flags) or approved (no flags, automatic); waiting is evaluated again by the scheduled run once its `releaseAt` passes and moves to refused, in-review or approved, so nothing waits forever; in-review to approved (the approvals D-03 names) or refused; approved to under-review-again (a new KEV, `MAL-` or above-threshold finding, or an upstream yank); under-review-again to approved (a VEX `not_affected` or an accepted risk, with approvals) or withdrawn (confirmed bad). Every `waiting` record has `releaseAt`; every `in-review` and `under-review-again` record has an owner role and a due date (policy: 5 working days, 1 for KEV and `MAL-`); past due raises an alert and never approves. `refused` and `withdrawn` are final for that record; a new request makes a new record. Withdrawal never deletes anything. `approved` is the only state Harbor's `approved` projects and Verdaccio serve and the only state the site key signs: the signature is the approval, with no second flag that could disagree with it.
- **D-16: The gates** (`deploy/supply/policy.json`, evaluated by `deploy/supply/lib/policy.mjs`; the research's gate table, with the owner's answers):

  | Gate | Check | Outcome |
  |---|---|---|
  | Age | published at least 7 days ago (D-02) | `waiting` with `releaseAt`; fast lane: in review, two approvers |
  | Name | never approved before; edit distance 1 or 2 from an approved or listed popular name; scope mismatch | in review |
  | Install scripts | `preinstall`, `install`, `postinstall`, `prepare` in the tarball's `package.json`, or `hasInstallScript` | in review, two approvers, per exact version; CI keeps `--ignore-scripts` |
  | Licence | SPDX expression against D-04 | outside: in review |
  | Integrity and signature | tarball sha512 equals the packument `integrity`; npm registry signature verifies against npm's pinned keys (`/-/npm/v1/keys`, pinned in `deploy/supply/keys/npm-registry-keys.json`) | mismatch: refused |
  | Provenance | verified when present (gather host, `npm audit signatures`); present on an earlier approved version and absent now, or the source repository changed | regression: in review |
  | Publisher | differs from the previous approved version's publisher | in review |
  | Malware | OSV `MAL-` match (offline database on the signing host) | refused; re-evaluated when the `MAL-` record is withdrawn |
  | Vulnerabilities | Grype on the SBOM: KEV match, or critical with a fix | refused |
  |  | high | in review |
  | Source form | git, http or file dependency; tarball off the registry | refused |

  The same shape applies to images (age from the upstream manifest or index creation date where present, else the gather date with the image's digest pinned; licence from the image's SBOM, recorded not gated, because base images carry many licences), Go, Maven, PyPI and RPM (age from the upstream publish time; licence from the package metadata). An organization's HQ may only tighten the policy in its site file (`supply.policy`): a longer age, more approvers, a shorter licence list; a looser value is refused with a plain message.
- **D-17: The promotion record.** Format `sterling-supply-record/1`, an in-toto statement whose predicate type is `urn:near-ai-vscode:supply-record:1` (our own namespace, as `urn:near-ai-vscode:compliance` is). It binds: the subject (OCI digest, or package URL plus integrity for npm, Go, Maven, PyPI and RPM entries), the origin (upstream host and the country of its operator where known, else `unknown`), each gate's result and evidence, the state, the approvals (D-18), the requester, the policy's SHA-256, the Grype database `built`, `schemaVersion` and checksum, the OSV database date, and `recordedAt`. It is signed with the site key as a cosign attestation (the attach path spike S-A proves on cosign 3.1.4, D-36) and stored as an OCI referrer beside the artefact, with the CycloneDX SBOM (`--type cyclonedx`), the Grype result (`--type vuln`, dated by the database `built`, never by the scan time, 48.2 D-15) and VEX (`--type openvex`). Non-image artefacts (npm sets, dependency snapshots, tools, the database) are OCI artifacts in Harbor so they get the same referrers (hauler `file` items, or ORAS if spike S-B shows hauler cannot carry referrers). npm tarballs in Verdaccio carry no referrers: each approved npm set is one OCI artifact in Harbor listing name, version and integrity, with its record, SBOM and scan; the lockfile's sha512 ties a tarball to it.
- **D-18: Approvers are named people, proven at sign-in.** The site file lists `supply.approvers`: Keycloak user ids (`sub`, lowercase UUIDs), never a group or claim (the 47-34 pattern). An approver signs in with the OAuth device authorization grant on a new realm client `sterling-supply-review` and a passkey step-up; the review command exchanges that token at OpenBao's jwt mount for role `supply-approver` (bound to the step-up acr and to the listed subjects, policy `supply-approver`: token lookup only); OpenBao's login proves the person and its audit log records it. The record stores each approver's subject, OpenBao entity id and sign-in time. Two approvals must come from two different subjects; a fast-lane approver may not be its requester. A VEX `not_affected` that returns an artefact to approved needs one approver, and two when the finding is a KEV match or a critical with a fix (D-28). Whether the pinned Keycloak 26.8 honours the step-up acr on the device grant is checked in 48.3-05 from its documentation and source (A3) and proven in the lab run (48.3-22); if it does not, the same client's authorization-code flow with PKCE and a loopback redirect is used on the approver's own computer instead (decided now), and the approver hands the resulting short OpenBao token (5 minutes, token lookup only) to the review command, which looks it up.
- **D-19: The signed approved lists are the lock CI checks.** `deploy/supply/approved/` holds one list per ecosystem (`npm.json`, `go.json`, `maven.json`, `pypi.json`, `rpm.json`, `images.json`), each with its `.sigstore.json`, signed in cosign key mode with Sterling's build HQ site key; its public key is `deploy/supply/keys/build-hq.pub`. `deploy/supply/keys/` becomes a gate path (added to `GATE_PATHS` in 48.3-15), so changing the trusted key needs the owner's approval; the lists themselves are protected by the signature. Every build input is checked against its list before anything from it runs; CI fails closed. Before the runner move, CI and image builds fetch the approved bytes from the public origins (identical bytes, by hash); after it, from HQ (G517). A dependency change works like this: the change fails CI with "not approved: name@version", the intake runs on the new lockfile, and the updated signed list is committed to the same pull request.
- **D-20: npm.** Resolution on the gather host with `npm install --package-lock-only --ignore-scripts --min-release-age=7` against registry.npmjs.org (npm 11.10.0 or later). Verdaccio receives the exact upstream tarball bytes through its publish API, sent by our own request (never `npm publish`, which honours a package's own `publishConfig.registry`); spike S-C proves the served `dist.integrity` equals upstream's. The `latest` dist-tag is set to the newest approved version. Lockfiles keep `resolved` on registry.npmjs.org (npm's `replace-registry-host` default redirects them to the configured registry). CI and image builds set `ignore-scripts=true` and `allow-git=none`. The `npm audit` steps stay in CI while it runs on GitHub-hosted runners (they still reach npmjs); the runner move replaces them with Grype and osv-scanner over the lockfile SBOMs at HQ (Pitfall 1). Developers and agents at HQ point their user `.npmrc` at HQ Verdaccio with a read token.
- **D-21: Go, Maven, PyPI and RPM.** At HQ the gather host runs each build's native resolver once in a throwaway container with network only to that ecosystem's origin (`go mod download -json`, `mvn -Dmaven.repo.local=... dependency:go-offline`, `pip download --require-hashes --no-deps --only-binary=:all:`, `dnf download --resolve`), and records every file's URL and SHA-256. The signing host checks the bytes (Go sums against `go.sum`; RPM GPG signatures against the Red Hat and PGDG keys; PyPI hashes against the requirements file; Maven by recorded SHA-256 only, G520), runs the gates and stores each approved snapshot as an OCI artifact in Harbor `approved/snapshots/<image>`. A build fetches only by URL and SHA-256 from the signed list (`deploy/supply/fetch-approved.mjs`, which runs no downloaded code) into a build context, then builds with the network off (`GOPROXY=file://`, `mvn -o`, `pip --no-index --find-links`, `dnf` from a local repository with `gpgcheck=1`). This generalises the repository's existing PGDG pattern (RPMs pinned by URL and SHA-256 in `tool-pins.json`).

### Registries, bundle and releases
- **D-22: The bundle takes only HQ's approved content.** `deploy/bundle/build.mjs` gets `--source-registry <hq>/approved` for third-party images; each image's identity stays its upstream ref and digest in `images.lock.json`; before an image or file goes in, its promotion record is verified with the site public key and checked against the digest; the records and their referrers travel into the bundle; the site import verifies them as it verifies signatures today (47-06, 48.1-17).
- **D-23: Our releases from GHCR are re-verified at HQ.** The gather host pulls each built and released image by digest from GHCR and verifies the GitHub attestations (keyless, so only on the connected host, as G476 says); the signing host verifies the supplier release key signature and the SBOM attestation in key mode, rescans with HQ's database, records and copies the image with all referrers into `sterling/` on HQ Harbor. Sites and organizations take releases only from HQ. The bundle build's re-signing with the site key (48.1-17) remains the organization's acceptance.
- **D-24: HQ Harbor.** OIDC sign-in to Keycloak for people, with no admin group: authority never comes from a Keycloak group or claim (47-34), so Harbor's only administrator is its built-in account, whose password stays in OpenBao and is used only by `harbor-projects.mjs`; readers your organization lists (`supply.harbor.readers`) become Limited Guest members of the approved projects; the audit log forwarded to the site log store through Harbor's syslog endpoint, with "skip audit log database" off; Trivy off; immutable tags on every project; projects as code (`deploy/supply/harbor-projects.mjs`): `quarantine` (push: gather robot; pull: signer robot only), `approved` and `sterling` and `supply` (push: signer robot only; pull: the bundle build, CI after the runner move, HQ builds); after the runner move, `ci-output` (push: the CI robot; pull: the signer only), from which the intake promotes our releases into `sterling` (48.3-25). G357 stands: HQ Harbor does not run admission in Deny until G357 closes. Sites: Zot gets `log.audit` (research: a cheap AU and G341 addition).
- **D-25: Verdaccio.** No uplinks; the web UI off; `max_users: -1` (no self-registration); `promotion` is the only account that may publish; per-reader accounts (CI, each developer or agent) whose passwords OpenBao generates and the install identity writes into the htpasswd Secret; nothing secret is stored in it (public packages only). It runs from our own image built from the reviewed npm package on `ubi9/nodejs-22`, on a Longhorn volume, with a NetworkPolicy that allows no egress, behind the HQ ingress. Tests prove that unauthenticated publishes, publishes by any account but `promotion`, and the trailing-slash form of GHSA-vjgw-2g79-p7w7 are refused. Its storage can always be rebuilt from Harbor's approved npm sets.

### Continuous monitoring
- **D-26: The databases.** The gather host downloads `databases/v6/latest.json` from grype.anchore.io and the archive it names, and the OSV offline database; the signing host checks the archive against the listing's checksum, signs it and stores it as `supply/grype-db:<built>` and `supply/osv-db:<date>` with annotations `{ built, schemaVersion, checksum, source }`. Every scanner, at HQ and at sites, imports a signed database file (`grype db import`, `GRYPE_DB_AUTO_UPDATE=false`, `GRYPE_CHECK_FOR_APP_UPDATE=false`); there is no HTTP database mirror (one path for HQ and sites). `MAL-` records are re-checked on every run, never cached as final (OSV withdrew 157 false reports).
- **D-27: Daily rescan, alerts and reconciliation.** After each sync the signing host rescans every stored SBOM of every approved artefact and every supported release, diffs against the previous run, and moves an artefact with a new KEV, `MAL-` or above-threshold finding to `under-review-again`. It writes one ConfigMap, `sterling-supply-status` in namespace `sterling-supply` (created empty by chart `sterling-supply-status`, 48.3-10), through ServiceAccount `sterling-supply-status` (get, update and patch of that ConfigMap only, by `resourceNames`; a 90-day token the operator mints for the signing host and the site import host), with the counts as labels (role, new findings, KEV, `MAL-`, overdue reviews, withdrawn still running, unmatched signatures, and the database freshness word current, ageing or out of date from 48.2 D-13's vulnerability thresholds). kube-state-metrics (on in `prometheus.yaml`) exposes them through its label allow-list; Prometheus rules raise `SupplyFindingNew`, `SupplyKevOrMalware`, `SupplyReviewOverdue`, `SupplyWithdrawnRunning`, `SupplySignatureUnmatched`, `SupplyDatabaseOld`, and the guards `SupplyStatusMissing` (absent) and `SupplySyncStale` (no change of the ConfigMap's resource version in 36 hours); Alertmanager mails them as 48.1-02 set up. Reconciliation: every signature or attestation by the site key on `approved/`, `sterling/` and `supply/` must match a record; one that does not raises `SupplySignatureUnmatched`.
- **D-28: OpenVEX.** `deploy/supply/vex.mjs` writes OpenVEX documents (our own JSON writer, signed through cosign; vexctl is not added) with statuses `not_affected` (with a justification from the OpenVEX list), `affected` (with an action statement), `fixed` and `under_investigation`; products are named by image digest or package URL, never by name alone, so a statement cannot apply to another build. A `not_affected` or `affected` statement carries the approvals D-18 sets. Each statement is attached as an `openvex` attestation and collected into the VEX set `supply/vex:latest`; Grype reads the set (`GRYPE_VEX_DOCUMENTS`) at HQ and at sites.
- **D-29: Sites.** The signed refresh file of 47-29 (`db-pack`) is extended to carry the newest signed database, the VEX set and the withdrawal list. The site import verifies it, compares the withdrawals with the release the site runs, writes the site's `sterling-supply-status` (withdrawn still running, database age) so the same alert rules fire at the site, and adds the withdrawals to the change and impact record for the change board (47-29). No admission rule blocks a withdrawn digest (D-08, Pitfall 8).
