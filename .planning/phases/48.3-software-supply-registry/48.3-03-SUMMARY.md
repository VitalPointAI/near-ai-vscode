## Decision

48.3-08, 48.3-12, 48.3-13 and 48.3-16 use hauler, already pinned and registered; they do not re-spike.

- **ORAS needed: no.** hauler 2.1.2 carries signatures and OCI 1.1 referrers for images and for file artifacts; 48.3-07 adds no ORAS pin and no fit entry.
- Images: `hauler store add image <hq>/approved/<repo>@<digest>` (never `--key`: hauler cannot read cosign v3 bundles, 47-01; never `--platform` with a digest), `hauler store save`, at the site `hauler store load` and `hauler store copy registry://<site registry>`; then `cosign verify --key` and `cosign verify-attestation --key <key> --type <each type>` at the destination for every artefact (Pitfall 2), with the site key for records.
- Files (npm sets, dependency snapshots, tools, the vulnerability database): pushed once at HQ as a hauler file artifact (`hauler store add file <file>`, `hauler store copy registry://<hq>/...`), attested on that digest exactly as images are (spike S-A's commands and the site-key attach path), and from then on **always taken from the registry by digest** with `hauler store add image <hq>/<repo>/<file>@<digest>`. `hauler store add file` of a local copy carries no evidence and is never used for an approved artefact after intake.
- hauler pushes by digest only (no tags) and maps `<host>/<repo>` to `<repo>`, so a site finds an artefact by digest; tag-based lookups are not relied on.
- Research open question 3 is **settled**: hauler keeps referrers through `store add` (from a registry), `store save`, `store load` and `store copy`, for images and file artifacts, on Zot 2.1.23. Harbor as the source or destination is checked in the lab run (48.3-22).
