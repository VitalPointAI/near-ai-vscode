# Phase 48.3 Plan 05: Promotion records, named approvers and the review client Summary

**An approval is now a person proven at sign-in (Keycloak device grant at the step-up level, exchanged at OpenBao's supply-approver role bound to the listed subjects), bound into a checkable `sterling-supply-record/1` in-toto statement; repeated, unlisted and fast-lane-requester approvals do not count; any site-key signature without a record is found.**

## What was built

- `record.mjs` builds the record and checks its content after cosign has verified the signature; it reads cosign 3.1.4's real download output (spike S-A's fixture), both the referrer bundle and the legacy envelope form.
- `approvals.mjs` turns an OpenBao login into `{ subject, entity, at }`, applies D-03, D-18 and D-28's counting rules, and reconciles signatures with records for `SupplySignatureUnmatched` (48.3-19).
- OpenBao role `supply-approver` (policy: `auth/token/lookup-self` read only), the site keys `supply.roles`, `supply.approvers` and `supply.policy`, and the realm client `sterling-supply-review`, refused by `checkRealm` if it loses its loopback-only redirects, PKCE, public form or step-up.

## Sources read (A3 and the OpenBao field names)

- OpenBao jwt API, `claim_mappings`: https://raw.githubusercontent.com/openbao/openbao/main/website/content/docs/api/auth/jwt.mdx lines 148-152 ("a map of claims (keys) to be copied to specified metadata fields (values)"); source `internal/builtin/credential/jwt/claims.go` `extractMetadata` lines 91-104: a non-string claim returns "error converting claim '<name>' to string" and the login fails. Read 2026-11-25. The same page documents `max_age` only for the OIDC flow, so it is not used.
- Keycloak 26.8.2 (the pinned image's version), `services/src/main/java/org/keycloak/protocol/oidc/grants/device/endpoints/DeviceEndpoint.java` lines 468-470 at tag 26.8.2: `AcrUtils.getAcrValues(null, null, client)` then `REQUESTED_LEVEL_OF_AUTHENTICATION` from the lowest LoA of those values. The server administration guide's device grant section (oidc.adoc) says nothing on acr. Read 2026-11-25. Whether the issued token carries the step-up acr is proven in the lab run (48.3-22).
- The existing `sterling-sessions` client already emits `AUTH_TIME` through `oidc-usersessionmodel-note-mapper` (jsonType long), so the session note exists; the review client emits it as a String.

## Deviations from Plan

**1. [Rule 1 - Bug] auth_time cannot be mapped as planned**
- **Found during:** Task 2, reading OpenBao's jwt source for the field names the plan asked to confirm.
- **Issue:** the plan maps `sub` and `auth_time`; OpenBao fails the login when a mapped claim is not a string, and `auth_time` is a number, so every approver login would have been refused.
- **Fix:** the review client's session-note mapper emits `sterling_auth_time` as a String; the role maps it to metadata `auth_time`; a test asserts the numeric claim is never mapped.
- **Commits:** 7a164589, 8c50f31c

**2. [Rule 2 - Security] No approver listed binds not-set instead of writing no role**
- The plan's case says no role is written when the list is empty. A role written from an earlier list would then stay admitted. The role is written bound to `not-set` (47-34's pattern for officers), which admits nobody, and nothing is deleted.

**3. [Rule 2 - Security] azp bound and checkRealm rules for the review client**
- The role also binds `azp` to the review client (only tokens issued to it), and `checkRealm` refuses the client if its redirects leave loopback, the implicit flow is on, or it stops asking for the step-up, so a hand-edited realm cannot weaken it.

**4. [Rule 1 - Correctness] The step-up on the device grant is the client's default ACR**
- From A3's source reading: a request's `acr_values` is ignored on the device endpoint, so the step-up is set as the client's `default.acr.values` and `minimum.acr.value`, not by the review command.
