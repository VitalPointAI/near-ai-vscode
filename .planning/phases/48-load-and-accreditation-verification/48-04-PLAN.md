<objective>
The two load populations that make per-person and per-hub figures representative: hub load through the hub's own test client, and an active sample of sessions driven by a real browser running a versioned activity profile and signing in with a WebAuthn virtual authenticator (D-19, D-21, D-23).

Purpose: VER-02 asks for "steady-state CPU and memory per person under the activity profile" and "load per hub"; a session with no frontend is not a person (research "Representative load"), and the hub's 150-person target needs a real client.
Output: a bounded local hub smoke and per-hub run-file proof under Task 1. The browser sample, profile, hooks and documentation depend on Tasks 2 and 3. The rig's multi-hub and resource measurements need a separate reviewed tranche.

Planning choices (reported):
1. The local hub tracer uses existing locked dependencies. The Playwright package and browser-source checkpoint remains a separate owner decision before browser work.
2. The hub's test client already dials literal IPv4 loopback and checks a certificate pin before writing a request. The bounded integration bundles the driver, shared hub helpers and actual in-process hub composition with the hub's locked esbuild and alias map. It writes only to a unique scratch output. No hub build that replaces `hub/dist` is needed, and the ordinary load CLI keeps its existing behavior.
3. Browser: Phase 46 pins `@playwright/test` in `workbench/` (46 D-28, D-41); `browser.ts` loads it with `createRequire` from `workbench/package.json` (owner item 6 default: no `loadtest` dependency, no change to `scripts/resource-check.mjs`). Chromium only, through a CDP session (`WebAuthn.enable`, `WebAuthn.addVirtualAuthenticator` with resident key and user verification) before navigating. The virtual authenticator stands for either `signInKeys` level (Phase 47 D-57): attestation is checked only at registration, so a sign-in ceremony costs the same with a phone passkey or a hardware key, and the test realm (attestation not required) measures both. Browser-dependent checks are `*.integration.ts` files run by this plan and on the rig, not by the CI glob `loadtest/test/*.test.ts` (48-06), because CI has no browser or hub build in that job.
4. This review covers Task 1 planning only. Local proof grants no authority to publish a PR, use the rig or run a browser.
</objective>
