Run the load test on the rig and publish the reference site's real state: a shakedown at the first stage, then stages to 1,000 sessions and beyond while the rig allows, the capacity page and sizing defaults regenerated from the run, and the first signed reference export with the operator's key in the trust list (D-01 to D-03, D-06, D-07, D-10, D-15, D-16, D-20 to D-23).

Output: committed run files, the regenerated capacity page, the reference export, the site key entry, any reader fixes the real outputs need, and gate PR 3 with the owner's approval.

Planning choices (reported):
1. A stage the rig cannot hold is a normal result (D-10): the run file says how far it got and why; the plan is complete when the run file is honest, not only when 1,000 is reached. If the rig cannot reach 1,000, the summary says so and the capacity gap from 48-05 stays open with its owner and date.
2. Readers in `compliance/src/siteExport.ts` were written against upstream formats (48-02); where a real output differs, fix the reader and its fixture here, in the same gate PR as the key.
3. On the load generator host, the harness runs under `systemd-run --user --scope` with a memory cap that leaves the host headroom; the cap and the host are recorded in the run file's hardware notes.
4. Branch `feat/phase-48-rig-run` from `main` after gate PR 1 merged. Register rows 1 and 2 and the capacity gaps are closed in 48-09 (the register file belongs to that wave).
