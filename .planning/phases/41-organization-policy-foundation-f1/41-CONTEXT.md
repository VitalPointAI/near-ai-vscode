## Phase Boundary

Phase 41 gives the product one foundation that every later feature reads the same way:

- **Your organization's rules reach every computer.** An organization layer signed by an issuer this computer pinned from a signed enrolment file (fingerprint read aloud as words), with personal and project layers that can only narrow it, and Reset touching only the personal layer. (FND-01)
- **Policy bundle v2.** Sections, `requires` feature ids, `needs-update` instead of Reset, every v1 bundle read as v2 with the same effect. (FND-02)
- **One list of where AI may run.** `endpoints[]` (class, exact host, scheme, TLS pins, region, label ceiling, attestation, provider) replacing `routing.localHosts`, with a migration and a one-time notice. (FND-03)
- **One exception record.** `authorizations[]` with kinds (`protected-b`, `t1-risk`, `accredited-device`, `residency-exception`, `declassify`) and an inner signature by a named person; "self-signed on this computer" until an organization issuer exists. (FND-04)
- **Residency in the gate.** A `residency` section and the `route.residency` rule; the accredited-device rule in report mode. (FND-05)
- **One label module and one decision function.** Dependency-free label algebra over the active scale table; `decideRoute` decides over label, use tier, hosting class, region, authorizations, passport and clearance; `nearAi.privacyMode`, member and team `privacy: private` and Team Mode's `teeOnly` and `allowedModels` are inputs to it; `TrustFacts` feeds the trust line. (FND-06)
- **The mode table and `term()`,** moved here from Phase 32.1, and the copy lint with a recorded baseline. (FND-07)
- **The model passport schema** (WP-0 of Phase 74.1) as the `models` section, parsed and checked in report mode. (FND-08)
- **`ModelEndpoint` and `LocalServerAdmin`** with `NearAiClient` as the first adapter; the architecture test with a recorded baseline; the policy editor shell that receives proposals. (FND-09)

Not in this phase: passport enforcement, the T0 lane, the Western defaults and the risk acceptance command (74.1); the org-tee verifier (74.2); Cohere adapters (36, 37); Get Started, the guide's mode suggestion (ORG-04) and removing the staff `where` question and discovery `locality` (32.1); `LocalServerAdmin` implementations and the local catalogue UI (32.2); positions, the delegation rule `mayDelegate`, genesis mode and `project.mode` changes, the replica source of the project layer (33.1); the hub loading the organization layer (35); the mechanical move PR (after this phase); the webview kit for existing pages, the record writer and the hash-chained local audit (32.1, the first phase after this that adds pages and records); Team Mode migration (L2); credentials and DIDs (71).

### Bundle v2 (FND-02)
- **D-04:** One normalised in-memory `PolicyDocument` (v2 shape) read from two wire forms: `bundleVersion: 1` (today plus S6's `requires`) and `bundleVersion: 2` (sections). v1 maps as POLICY-SCHEMA section 3 says: `ceiling` to `agents`; `scales`, `mappings`, `defaultLabel`, `routing` to `labels`; `routing.localHosts` to `endpoints` (D-12); `clearances` to `people.clearances`. Signed bytes and `bundleHash` of a stored v1 bundle never change; only an Edit or Apply writes v2. `parseBundle` stays as a wrapper that returns today's `PolicyBundle` view, and `BundleState.valid.bundle` stays the effective policy projected onto today's names, with `layers` beside it, so no consumer changes in the contract plan.
- **D-05:** The v2 envelope: `bundleVersion: 2`, `vocabulary`, `issuer`, `issuedAt`, `expiresAt`, `layer` (`organization`, `personal`, `project`), `parent?: { hash, issuer }` (personal and project layers name the organization layer they narrow), `requires`, `minClient?` (only to word the update message), and the sections of POLICY-SCHEMA section 2 that Phase 41 gives meaning: `labels`, `endpoints`, `authorizations`, `models`, `agents`, `residency`, `people`, `onboarding`, `limits`, `reserved`. Each section carries its own `v: 1`. A missing section means today's behaviour, stated in that section's parser. `data` and `directives` are not accepted yet: they arrive with their phases (85 onwards, 42) under their own feature ids, and until then a bundle naming them in `requires` gets `needs-update`.
- **D-06:** Feature ids in `KNOWN_BUNDLE_FEATURES` after this phase: `labels@1`, `endpoints@1`, `authorizations@1`, `residency@1`, `models@1`, `agents@1`, `people@1`, `onboarding@1`, `limits@1`, `layers@1`. A v2 bundle that uses a section without naming its id in `requires` is refused as malformed; an id the client lacks gives `needs-update` (S6). All ids are registered in the contract plan (41-01), so no later plan edits the registry.
- **D-07:** Strictness stays: unknown keys inside a known section are refused; when `bundleVersion` or `minClient` is newer than this client, the failure uses the update sentence, never Reset. Reset is never offered for a bundle this device did not sign (S6 already; kept).
- **D-08:** No fractions anywhere in a signed policy (today's `checkNumbers`): money in integer nano-USD (`dailyNanoUsd`), durations in integer seconds or days with the unit in the key name.
- **D-09:** Size: an organization layer may be up to 1 MiB (passports and endpoints need room); the personal layer keeps today's 256 KiB. The cap is checked on the file's bytes before any parsing.
- **D-10 (D-49 rule):** Every id the phase writes is named in the contract plan: route rules `route.endpoint-unknown`, `route.endpoint-ceiling`, `route.endpoint-pin`, `route.authorization-missing`, `route.residency`, `route.passport` (report only, recorded as `wouldRefuse`); policy events `policy.enrolled`, `policy.organization-updated`, `policy.organization-refused`, `policy.migrated`, `policy.proposal-applied`, `policy.proposal-exported`, `policy.reset-personal`; signing purposes `org-enrolment`, `org-policy-layer`, `policy-authorization`, `policy-proposal`. `policy.version` in records becomes `'bundle-2'` for a v2 effective policy and stays `'bundle-1'` for v1.

### Organization layer, enrolment and the pin (FND-01)
- **D-11 (owner Q2):** A computer learns its organization's root key from a signed enrolment file (`.near-org-enrolment`) that your organization's security contact hands out. It is read as hostile input, capped at 64 KiB before parsing, a `SignedPayload` with purpose `org-enrolment` signed by the issuer key itself. Payload: `v: 1`, `organization: { name, contacts }`, `issuer: { publicKey, did? }`, `issuedAt`, `expiresAt`, `serial`, optional `rotation: { previous: { publicKey }, sig }`, and the first organization layer, so "enrolled with no rules" cannot exist. The DID field is optional and unused until Phase 71.
- **D-12 (fingerprint words):** The fingerprint is read aloud as **twelve** words from the safety code word list over SHA-256 of a separate domain (`near-ai/org-issuer/v1`) and the raw public key (132 bits). The six-word safety code is safe only because it is interactive with a fresh nonce; a fixed issuer key can be attacked offline without limit, so six words are not enough. Modal copy: "Ask your organization's security contact to read their twelve words. Compare them with these: ..." with one button "The twelve words match"; the hex fingerprint sits under details. Declining writes nothing.
- **D-13 (pin):** The pin (issuer public key) and the last accepted organization layer `issuedAt` live in SecretStorage (`nearAi.gate.organizationIssuer`), like `clockMarker.ts`, so a disk writer cannot reset them; the layer files live under `<globalStorage>/gate/organization/`. Order on enrolment: write the layer file with the pin marked pending, then the pin; a pending pin with no layer reads as not enrolled, and a layer with no pin is ignored. `earlierInstallEvidence` counts the folder.
- **D-14 (updates and rollback):** A later organization layer is accepted only when signed by the pinned key and newer (`issuedAt`) than the last accepted; an older one is refused (`policy.organization-refused`, rollback); an expired one fails the whole policy closed with "Your organization's rules ended on {date}. Ask {contact} for the current rules." and the 30-day renewal notice applies to it as to today's bundle. Rotation: a new enrolment file signed by the new key with `rotation.sig` by the pinned key over the new key; the words are shown again before the new pin is kept.
- **D-15 (three key sources, never mixed):** The organization layer verifies only against the pin; the personal layer only against this device's own key history (`localKeyStatus`, as today); authorizations only against the named signers listed in the organization layer (`people.signers`), or this device alone when there is no organization layer. `combineKeyStatus` is never used across them. A layer signed by this device's key and presented as organization is refused `unknown-key`.
- **D-16:** No "leave your organization" command in Phase 41. The schema reserves an issuer-signed release (purpose name reserved, no code path); the only way out is the existing full reset of the extension's storage.
- **D-17 (issuer tooling):** `scripts/org-issuer.mjs` (plain Node, no dependencies, reuses the compiled signer): create an issuer key file kept offline, sign an enrolment file, sign an organization layer, rotate. Documented in SECURITY.md, with tests in `scripts/test/orgIssuer.test.mjs`. No UI for issuers in this phase.

### Layers and narrowing (FND-01)
- **D-18:** `composeLayers({ organization?, personal, project? }) -> { effective, ignored }` in `src/domain/gate/layers.ts`, pure. Without an organization layer the personal layer is the whole policy, exactly as today.
- **D-19 (declared directions):** One `NARROWING` table names a direction for every accepted key path: `tier-stricter`, `subset`, `number-lower`, `ceiling-dominated`, `boolean-safe`, `organization-only` (keys only the organization layer may set: `people.signers`, `onboarding.contacts`, `people.organization.allowedModes`, `endpoints` additions above `org/Public`). A test enumerates every key the parsers accept and fails when one lacks a direction.
- **D-20 (no lock-out):** At load, a personal value wider than the organization's is replaced by the organization value and listed in `ignored`, shown once as "These personal settings are wider than your organization allows and have no effect: ..."; the policy never fails closed for it. A new personal edit or proposal that widens is refused before signing with the key named ("Your organization's rules do not allow {key} to be wider than {value}.").
- **D-21 (failures):** An organization layer that fails to verify, is expired or is refused fails the whole policy closed (never fall back to the personal layer alone). A personal layer that fails fails closed with Reset offered for the personal layer only. Reset under an organization layer re-signs only the personal layer (`policy.reset-personal`) and never touches the organization files.
- **D-22 (project layer):** The project layer type, parser and composition exist (project label, mode within `allowedModes`, exercise flag, locked answers), tested with in-memory input. Its single-machine source comes with 32.1 and its shared source with 33.1. The exercise flag (owner Q10) is a project-layer attribute set with a reason and recorded.
- **D-23 (interim rule):** Until an organization layer exists, every acceptance, authorization and trust line that cites one says "self-signed on this computer"; "set by your organization" is shown only when the issuer is not this device.

### One endpoint list (FND-03)
- **D-24:** `endpoints[]`: `id` (stable token), `class` (`local`, `org-plain`, `org-tee`, `nearai-tee`, `vendor-tee`, `vendor-region`, `forwarded`, `closed-api`), `host` (exact; a `*.` pattern only for `org-plain` and then with a ceiling no higher than `org/Restricted` and Protected A), `scheme` (`https`, or `http-loopback` only for a loopback host), `tlsPins` (one to four lowercase 64-hex SPKI SHA-256 hashes, the shape `connectionBinding.ts` uses), `region` (`CA`, `US`, `EU`, `unstated`), `maxLabel`, `attestation?` (verifier spec id for `org-tee`, `vendor-tee`; implicit for `nearai-tee`), `provider?` (which `ModelEndpoint` adapter). Sorted by `id`, unique ids and hosts.
- **D-25 (maxLabel shape, from PR #140, Cohere D7):** `maxLabel` is a list of label keys holding **at most one level per scale** (for example `["org/Confidential", "ca-protected/Protected A"]`); a scale not listed means nothing from that scale reaches the endpoint. Checked with the label module's dominance per scale. The parser refuses for any `vendor-*`, `forwarded` and `closed-api` class: `org/Restricted`, Protected C, every classified level and NATO Restricted and above.
- **D-26 (Protected B, from PR #140):** A signed `maxLabel` alone suffices up to Protected A. Protected B (and anything the routing table sends `local-only` on a non-loopback endpoint) additionally needs a `protected-b` authorization naming that endpoint id, for every non-loopback endpoint class; an `org-plain` endpoint also needs a TLS pin, and `nearai-tee`, `org-tee` and `vendor-tee` need their verified connection binding. Protected C and classified never leave this computer (S1 stays).
- **D-27 (migration at today's effect):** Each `routing.localHosts` entry reads as an `org-plain` endpoint with the effect it has after the safety patch, except Protected B: an exact https entry gets a ceiling up to the levels that need no pin (Protected A, `org/Restricted`, NATO Unclassified); a pattern entry, or an exact entry without https, gets the levels the patched routing already allows it. Protected B on a migrated entry needs a TLS pin and a `protected-b` authorization (D-26). A one-time notice (`policy.migrated`, a `globalState` flag; a lost flag only repeats the notice) names each entry and what changed. `localHosts` is empty by default, so only people who edited their policy see it.
- **D-28:** Discovery and setup flows never write `endpoints[]`; they propose entries through the editor (D-44). `onboarding.discovery.personalApprovals` defaults to false; when true, a personally approved endpoint gets `maxLabel ["org/Public"]` only.

### One authorization record (FND-04)
- **D-29:** Each `authorizations[]` entry is a `SignedPayload` with purpose `policy-authorization` (so its signature and public key travel in the secret-scanner-exempt `sig` and `publicKey` fields). Body: `id`, `kind`, `subject` (`endpoint`, `model`, `device` or `item` id), `scope` (`projects`, `labels`, `uses`), `conditions`, `evidence` (assessment reference), `namedPerson: { name, role }`, `issuedAt`, `expiresAt`, `revokedBy?`. The envelope signer is the named person's key.
- **D-30 (maximum lengths):** `t1-risk` 90 days (owner O3, provenance), `protected-b` 365 days (Cohere 6.3), `accredited-device` 365 days, `residency-exception` 90 days, `declassify` as today's `label-declassify` rule.
- **D-31:** An authorization verifies only against `people.signers` of the organization layer; without one, only against this device's key, and every screen shows "(self-signed on this computer)". A person may self-sign a `t1-risk` record marked self-signed until the organization layer exists (PR #140 default). Once an organization layer exists, a self-signed authorization no longer counts unless this device's key is listed in `people.signers`.
- **D-32:** Today's `label-declassify` records keep working unchanged; the `declassify` kind is their v2 home for new records only (no rewrite of signed history).

### Residency and accredited devices (FND-05)
- **D-33 (owner Q7):** `residency: { v, required?, byLevel? }` (region codes per label key). `route.residency` refuses before sending when the endpoint's `region` does not satisfy the residency for the request's label or project, unless a `residency-exception` authorization covers that endpoint and scope. `unstated` never satisfies a residency rule.
- **D-34 (owner Q6):** Classified and Protected C on a device with no `accredited-device` authorization: warn and record `route.not-accredited` (S2's report mode), never refuse in this phase. The rule turns to refusal only when an organization layer is present and says so (`agents` section flag `requireAccreditedDevice`, default false); the switch exists in the schema now and is tested both ways.

### Added during planning (2026-11-20)
- **D-49 (v1 reader stays):** `parseBundle` and `verifyBundleEnvelope` stay the unchanged v1 readers, because the store re-signs their value on Apply and Renew and a v2 layer turned into today's view would lose its sections. The v2 reader is `verifyPolicyLayer` in `policyDocument.ts` (both layer purposes, the 1 MiB organization and 256 KiB personal caps, the repeat check, clock-behind and expiry).
