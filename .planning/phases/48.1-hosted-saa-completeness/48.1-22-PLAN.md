Planning choices (reported):
1. Signing tool (decided for 48.1-17): the pinned cosign 3.1.4 release stays unchanged for generating the signature payload, attaching the signature and verifying; only the private-key operation runs through OpenSC's `pkcs11-tool` on the PKCS#11 URI. The release binary has no PKCS#11 support, and building cosign from source with the `pkcs11key` tag would make us the builder of a large CGO tool and owe a rebuild on every cosign advisory; `pkcs11-tool` is an OS-vendor-signed package (LGPL-2.1, in the RHEL and Ubuntu archives, installable air-gapped from the site's OS repository mirror) that calls the token's own `C_Sign`, so the key operation happens inside SoftHSM2 in development and inside the HSM's validated module in production. Supply-chain cost: one OS package on the owner's machine and the HQ signing host, and one small reviewed signing module in this repository (48.1-17). OpenSSL 3's pkcs11 provider was the alternative; it adds a provider configuration for the same `C_Sign`, so it was not chosen.
2. The fit review of softhsm2 and opensc: this plan records the desk review in its summary (licence, source, version, use); 48.1-06 adds the `host` resource kind that discovers deploy/host-packages.json, so both become register entries before 48.1-17 uses OpenSC for signing.
3. The executor never runs the script against the owner's configuration; it tests the script with fake tools in temporary folders. The real SoftHSM2 path is proven in 48.1-17 once the packages are installed.
</objective>
