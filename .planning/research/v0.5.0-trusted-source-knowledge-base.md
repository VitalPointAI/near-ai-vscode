# v0.5.0: Trusted-source knowledge base (requirements brief)

Captured 2026-10-27 from the product owner for milestone v0.5.0. Plan it with
`/gsd-new-milestone` and the normal discuss → plan → execute → verify cycle.
Not part of v0.4.0.

## Purpose

Research teams (including defence and law-enforcement topics) need a curated,
self-improving base of trusted sources and the intelligence collated from them:
a context graph that augments the model with real-time strategic, operational,
and tactical context for the task at hand.

## Decisions already made

- **Source grading: NATO Admiralty codes.** Source reliability A–F and
  information credibility 1–6 on every source and every claim (e.g. "B2").
  **Agents propose and assign grades and keep revisiting them** as new
  information confirms or contradicts a source or claim; every change keeps its
  evidence and reason (an analyst can still override, recorded the same way).
- **User thresholds.** Per project, the minimum reliability and credibility a
  claim must meet to appear in a research report; below-threshold material is
  excluded or marked unconfirmed, and every reported claim shows its grade and
  sources.
- **RAFT analysis.** Relationships (edges), Actors (nodes), Functions (what each
  actor does), Tensions (each relationship's relative strength: positive,
  negative, or neutral). Visualized as a professional network diagram.
- **Scope slicing.** One broad graph with every factor relevant to a strategic
  situation, sliced into smaller graphs focused on an area of interest or
  operations (by geography, time window, topic, or set of actors); agents work
  within a slice.
- **Geospatial.** Geocoded information on a 3D globe, each OSINT source (or
  source type) on its own layer that can be turned on and off, each event
  adding detail. **Use an open-source, feature-rich globe and imagery stack**
  (candidates: CesiumJS with open imagery such as OpenStreetMap / NASA GIBS /
  Natural Earth, or MapLibre GL globe; no proprietary tokens required).
  Geocode with an offline gazetteer (e.g. GeoNames) so place names never leave
  the machine.
- **Temporal.** Everything is time-stamped (when it happened, when it was
  reported, when it was graded) so the user can roll time back and replay how
  events unfolded, and the history can train prediction models that show how
  events could unfold, with probabilities.
- **Sensitivity.** Treat collated intelligence as sensitive: these projects run
  on TEE-attested models only (no forwarded or cloud-only models, including for
  sub-agents, attachments, and embeddings), store the graph locally only, and
  encrypt it at rest (key in VS Code SecretStorage / OS keychain).

## Builds on (v0.4.0)

Web search with untrusted-content fencing, hidden-content stripping, injection
detection, and citation checks; the research project type and team; project
memory (context graph store); Agent Activity; MCP connections for external
data feeds.

## Open questions for the discuss phase

- Graph store at scale (encrypted SQLite via WASM vs. append-only event log
  with snapshots) and expected volume.
- Prediction models: which methods (e.g. Bayesian / temporal graph models,
  forecasting from event sequences), where they train (locally vs. TEE), and how
  probabilities are calibrated and explained.
- Export and sharing formats for graded reports and graph slices.

## Decided when the milestone started (2026-10-28)

- **Scope:** the whole brief ships in v0.5.0, including the globe, temporal
  replay, and prediction models. Evidence-based model defaults move to v0.6.0.
- **Intake:** agents during research runs; analysts adding or importing
  directly (CSV, STIX, GeoJSON); standing feeds (RSS, MCP, watched folders).
- **Small teams share a base.** This replaces "store the graph locally only":
  each analyst's changes are signed, end-to-end encrypted, append-only events
  in a git repository or shared folder the team controls, so the host sees only
  ciphertext and the log is the temporal record. Members are invited by public
  key; removing one rotates the base key (they keep what they already had).
- **Prediction:** scenario forecasts and RAFT tension trends, both with
  probabilities and evidence. The user chooses whether models train and run
  locally or on NEAR TEE models.
- **Organisation scale ships in v0.5.0** (decided the same day, after asking
  whether the signed event log scales). The signed, encrypted event log stays
  the source of truth, with periodic snapshots so loading does not replay the
  whole history. Sync is pluggable: a git repository or shared folder for small
  teams, and an end-to-end encrypted relay the organisation hosts (it sees only
  ciphertext and enforces who may append) for larger ones. Access is by
  compartment (need-to-know: each compartment has its own key) and role
  (e.g. reader, analyst, approver), with a UI to manage both. Group key
  management must stay practical into the hundreds of members.

## Decided while defining requirements (2026-10-28)

- **Volume: several million entries and more.** The read side is a disk-backed,
  encrypted, partitioned index from the start (not only in memory); the store
  benchmark targets millions of entries.
- **Erasure by crypto-shredding.** Erasable items get their own keys;
  destroying the key makes the item unreadable everywhere while the log stays
  intact and verifiable. Members keep what they already read.
- **Post-quantum ready throughout.** Hybrid key encapsulation (ML-KEM-768 with
  X25519) for every key wrap; hybrid signatures (Ed25519 with ML-DSA) for log
  segments, membership, and capability tokens; AES-256 and SHA-256/384 for
  symmetric parts; hybrid post-quantum TLS to the relay. Because ML-DSA
  signatures are large (about 3.3 KB), the log signs sealed segments (or a hash
  tree over them) rather than each entry. Node 22 in the extension host has no
  ML-KEM or ML-DSA, so a vetted pure-JS implementation is needed (audit status
  to confirm in phase research).
- **Local LLM runtimes are allowed** in knowledge-base projects alongside NEAR
  TEE models (local inference never leaves the machine), labelled as local.
  Forwarded (non-TEE cloud) models stay blocked.
- **Web search and fetch: a per-project switch, on by default**, with a note
  saying the search provider sees the topics researched.
