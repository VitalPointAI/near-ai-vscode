# v0.6.0: Evidence-based model defaults (requirements brief)

Captured 2026-10-28 from the product owner for milestone v0.6.0 (moved from v0.5.0 on 2026-10-28, after the knowledge base). Plan it with
`/gsd-new-milestone` after the trusted-source knowledge base
(`v0.5.0-trusted-source-knowledge-base.md`). Not part of v0.4.0 or v0.5.0.

## Purpose

The model and role defaults should come from measured evidence, not judgment.
What we did by hand for 0.4.0 (run the live eval across models and
builder/reviewer pairs, check the misses, and pick the setup that balances
cost, speed, privacy, and accuracy) becomes a standing central process. Its
result is pushed to every installed extension as the recommended setup.

## Decisions already made

- **Recommended default setup from evidence.** For each agent role (and
  builder/reviewer pairings where they help), the extension recommends models
  chosen from eval results that balance four measures: accuracy, cost, speed,
  and privacy. Accuracy outweighs cost and speed: a setup that is cheaper or
  faster but produces wrong output more often is not recommended. Privacy is a
  hard floor before the trade-off: the product is a privacy product.
- **Run centrally, push to the app.** Evals run on our side, never on users'
  machines or keys. The extension receives the results; users do not install
  anything or spend anything to get recommendations.
- **Re-evaluate when NEAR AI changes.** Whenever a model is added to NEAR AI's
  catalog, the eval runs against it to see whether it beats the current
  recommended setup in any role. (Price changes and model removals should
  trigger the same check.)
- **Per project type.** Results and recommendations are kept per kind of
  project, so the best model for, say, a research project can differ from a
  software project. Start with the existing project types (software, research,
  presales, writing, data, general) and add eval tasks for each.
- **The user stays in control.** Every recommendation can be overridden at any
  time, per role, in the extension settings. When the user changes a model,
  the extension shows the trade-offs of the new setup against the one they are
  leaving: accuracy, cost per task, speed, and privacy (TEE-attested vs.
  forwarded), from the same evidence.
- **Never switch automatically.** The extension ships with a set of defaults.
  When a better combination is found, the user gets a notification that it is
  available, with its metrics against their current setup, and decides whether
  to switch. This applies the same way to users on the defaults and users who
  have overridden roles.
- **We pay for the central evals.** The cost cap per round is to be decided.
- **Notify whenever a combination beats the user's current setup.** The
  comparison is against what the user actually runs (defaults or their own
  choices), not only against the shipped defaults. The notification appears
  once per new recommendation, can be dismissed, and never comes back for a
  combination the user declined.
- **The central eval runs on the development machine,** with the same live eval
  used for 0.4.0, not on separate infrastructure.
- **Misses are checked before a recommendation ships.** Every miss is checked
  against the run's output, as for 0.4.0, so grader false positives never
  drive a recommendation.
- **Each project type defines its own success KPIs.** When a project type's
  template is built, we decide what a successful outcome is for it (the
  measurable KPIs), and its eval tasks are graded on those.

## Builds on (v0.4.0 and after)

- The live model eval (`src/test/live.test.ts`): coding, research, and planning
  tasks; hidden acceptance tests; graders (`src/test/evalGraders.ts`) with
  regression tests for false positives; per-run cost, time, and privacy.
- Build-then-review candidates (`builder+reviewer`, `src/test/evalReview.ts`).
- Role routing (`nearAi.agent.roleModels`, `DEFAULT_ROLE_MODELS`, model tiers
  in `src/domain/agentDefaults.ts`).
- NEAR's model catalog with TEE/forwarded labels and pricing.

## Privacy constraints

- Fetching recommendations is a new outbound connection. It must send nothing
  about the user or their project (no project type, key, usage, or
  identifiers): fetch one public file for all project types and choose locally.
  List it in SECURITY.md.
- The recommendations file is signed; the extension verifies the signature and
  keeps the last good copy, falling back to the built-in defaults.
- No telemetry flows back. If we ever want field data to improve
  recommendations, that is a separate opt-in decision.
- A recommendation never lowers privacy below the user's setting (a TEE-only
  user is never recommended a forwarded model), the same rule sub-agents
  already follow.

## Open questions for the discuss phase

- The cost cap per evaluation round.
- How a new model is detected (polling NEAR's catalog) and how fast results
  must ship after it appears.
- Scoring: how the four measures combine, how many runs per task make a result
  trustworthy, and how much better a challenger must be (beyond run-to-run
  noise) to count as beating the user's setup.
- The success KPIs for each non-software project type, decided as its template
  is built.
- Whether a project can be more specific than its project type (e.g. language
  or framework), and how the extension infers that locally.
