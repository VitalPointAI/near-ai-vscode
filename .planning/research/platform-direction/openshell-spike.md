# OpenShell spike: an execution sandbox for the agent shell

Date: 2026-11-15. Approved by the owner on 2026-11-15. Read together with `openshell-analysis.md` (same folder). All supporting files (policies, DID drafts, test scripts, raw output) are in `openshell-spike/` next to this report. Raw logs there use `$SPIKE` for the scratch folder the spike ran in.

## Summary

| Goal | Result |
|---|---|
| 1. Shell in a sandbox on a copy of a project; key folder unreachable, including run-time-built paths, recursive walks and symlinks; normal work still possible; changes come back as a diff | **Pass** (20 of 20 escape cases blocked, the cases in `openshell-spike/tests/key-escape.sh`; edits, a node script and `npm start` worked; diff produced). One new risk found on the return path: downloads keep symlinks. |
| 2. Network egress: allowed host works, others refused | **Pass** (allowed GET works; POST to the same host, other hosts, raw IP, cloud metadata and a different binary are all refused, each with a logged reason) |

| 4. MCP rules are `unsupported`. |
| 5. Timings, resources, platforms, surprises | Done (below). Added GPU and arm64 section as requested by the coordinator. |

Bottom line: OpenShell does what the analysis said it would. The kernel boundary closes exactly the holes our text guard documents. It is fast enough per command (about 50 ms of overhead). Its gaps are about **our side of the integration**, not its enforcement: how a project copy goes in and how changes come back out safely, how a person approves, and how we package a gateway for users who do not run Linux.

Signatures: the release ships checksum files only, which come from the same place as the binaries. Telemetry: off before the first run with `OPENSHELL_TELEMETRY_ENABLED=false` on the gateway (the docs say the gateway passes this to sandbox supervisors). I also set `OPENSHELL_TELEMETRY_ENDPOINT` to an unreachable local address as a second guard.

Environment: Linux 7.0.0-43-generic x86_64, Landlock in the LSM list, cgroups v2, Podman 5.7.0 rootless with pasta networking, Node 24.22.2 in the workload image.

## 2. Setup steps (exact commands)

```sh
source $SPIKE/env.sh                     # PATH, XDG_* into the spike folder, telemetry off
podman system service --time=0 unix://$XDG_RUNTIME_DIR/nearai-os-spike/podman.sock &
openshell-gateway generate-certs --output-dir $SPIKE/pki --server-san 127.0.0.1 --server-san localhost
openshell-gateway config preflight --path $SPIKE/gateway.toml
openshell-gateway &                      # reads OPENSHELL_GATEWAY_CONFIG
# CLI registration: copy ca.crt, client tls.crt and tls.key into $XDG_CONFIG_HOME/openshell/gateways/nearai-spike/mtls/
openshell gateway add https://127.0.0.1:27670 --local --name nearai-spike
openshell status                         # Connected, Authenticated (mTLS transport), Version 0.1.8
```

Every heavy command ran under `systemd-run --user --scope -q -p MemoryMax=... -p MemorySwapMax=0 choom -n 1000 -- timeout ...`. The two long-running services (Podman API, gateway) used a 7200 s timeout instead of 900 s so they would outlive individual tests; sandboxes were also capped with `--memory 2Gi --cpu 2`.

Things that went wrong on the way (useful for the phase design):
1. The obvious socket path inside the scratch folder is longer than the 108-byte Unix socket limit (`path must be shorter than SUN_LEN`). Put sockets under `$XDG_RUNTIME_DIR`.
2. The first sandbox create could not see my local image because my Podman service and my `podman build` used different storage (I had changed `XDG_DATA_HOME` for one and not the other). Fixed by loading the image into the spike store.
3. A plaintext, unauthenticated local gateway starts, but the Podman driver refuses to launch sandboxes without the gateway JWT signing bundle ("Podman sandbox launch authentication is required"). So a local gateway effectively needs the PKI. That is good security, and something our installer must generate.

## 3. Goal 1: key folder unreachable, normal work possible, diff back

### Layout

- `project-live/`: a FAKE test project (git repo) with `.near-ai/state/keys/local.key` holding `FAKE-SPIKE-KEY-DO-NOT-USE:` plus random bytes, and `.near-ai/state/` in `.gitignore`.
- `agent-worktree/`: `git worktree add -b agent/run-1` of that project. A worktree never contains ignored files, so it has no `.near-ai/state`.
- `stage/`: `git archive HEAD` of the worktree, the exact set of tracked files. This is what was uploaded. No `.git` file goes in, so the sandbox does not even learn the host path of the repo.
- In the image, a second FAKE key at `/opt/nearai-decoy/.near-ai/state/keys/local.key`, readable by everyone (mode 644). This tests the **kernel** layer, not just absence: the file is really there, but `/opt` is not in the policy's file allowlist.

Policy (`openshell-spike/policies/run-policy.yaml`): workdir `/sandbox` read-write; `/usr /lib /lib64 /bin /etc /proc /dev/urandom` read-only; `/tmp /dev/null` read-write; `landlock: hard_requirement`; run as UID/GID 1000; one network rule (below). OpenShell added `/var/log` read-only on its own (its documented baseline when any network rule exists).

```sh
openshell sandbox create --name nearai-spike-1 --policy run-policy.yaml --memory 2Gi --cpu 2 \
  --no-auto-providers --upload $SPIKE/stage:/sandbox/project --detach --no-tty
openshell sandbox exec nearai-spike-1 --no-tty -- bash /tmp/key-escape.sh
```

Note: `--upload DIR:/sandbox/project` puts the folder at `/sandbox/project/stage`, not at `/sandbox/project`. I moved it inside the sandbox and re-ran everything; the results below are from the corrected layout (`logs/goal1-key-escape.txt` has both runs).

Container facts (from `podman inspect`): workload container `network=none`, user 1000:1000, no added capabilities, the common capabilities dropped, only volumes and the sandbox binary mounted. Supervisor container: host network, user 1000:1000, no added capabilities, no host paths mounted beyond its private volumes. No Docker or Podman socket inside either.

### Normal work on the copy

Inside the sandbox: `sed -i` edit of `src/index.js`, new `src/sum.js`, new `test.js`, `node test.js` printed `tests ok`, `npm start` printed the greeting. Then:

```sh
openshell sandbox download nearai-spike-1 /sandbox/project $SPIKE/result
rsync -a --exclude .git --exclude .near-ai/state $SPIKE/result/ $SPIKE/agent-worktree/
git -C $SPIKE/agent-worktree add -N . && git diff --stat
#  src/index.js | 2 +-   src/sum.js | 1 +   test.js | 2 ++   (3 files, 4 insertions, 1 deletion)
```

Full patch in `logs/goal1-diff.patch`.

### New risk found: the return path

`openshell sandbox download` **recreates symlinks exactly as the sandbox made them**, absolute or relative. I created `abs-link -> /etc/hostname` and `rel-link -> ../.near-ai/state/keys/local.key` inside the sandbox; both came back as symlinks on the host. Inside the sandbox they were harmless. Once applied to the real checkout, `rel-link` would point at the real key, and anything on the host that follows links (the editor, a build, our own context gathering, a later upload) could read it. The same applies to `.git/hooks`, `.vscode/tasks.json`, `package.json` scripts and executable bits: the sandbox can write anything into the copy, and the host trusts it when applying.

**The apply step must be treated as untrusted input**: compute the diff from regular files only, refuse or flag symlinks, special files and mode changes, refuse paths under protected locations (`src/domain/protectedPaths.ts` rules move here), and show the person the diff before applying. A `git diff --no-ext-diff` produced on the host from a host-side copy, then applied with `git apply` (which refuses to write through symlinks by default), is a reasonable base.

## 4. Goal 2: network egress

Policy rule (`run-policy.yaml`): `registry.npmjs.org:443`, `protocol: rest`, `access: read-only`, `enforcement: enforce`, binary `/usr/local/bin/node` only.

| Test (node `fetch` / `net.connect` inside the sandbox, `tests/egress.js`) | Result |
|---|---|
| E1 GET `https://registry.npmjs.org/left-pad` | HTTP 200 |
| E2 POST to the same allowed host | HTTP 403 `policy_denied`, rule named |
| E3 GET `https://example.com` | EACCES at connect |
| E4 GET `https://github.com` | EACCES at connect |
| E5 raw TCP to `1.1.1.1:443` | EACCES |
| E6 cloud metadata `169.254.169.254` | EACCES |
| E7 `127.0.0.1:8080` (a host service listens there) | ECONNREFUSED: the sandbox's loopback is its own, the host service is not reachable |
| E8 bash `/dev/tcp/registry.npmjs.org/443` (allowed host, wrong binary) | Permission denied |

No proxy environment variable was needed (`HTTPS_PROXY` unset): interception is transparent, through seccomp. Unapproved names resolve to synthetic `198.18.x.x` addresses and are refused at connect. Every decision is logged as an OCSF event naming the binary, host, rule and reason, for example:

```
NET:OPEN  [INFO] ALLOWED /usr/local/bin/node(0) -> registry.npmjs.org:443 [policy:npm_registry_read engine:opa]
HTTP:POST [MED]  DENIED POST https://registry.npmjs.org/-/v1/login [policy:npm_registry_read engine:l7] ...
NET:OPEN  [MED]  DENIED /usr/local/bin/node(0) -> example.com:443 [reason:transparent_tcp_policy_denied]
NET:OPEN  [MED]  DENIED /usr/bin/bash(0) -> registry.npmjs.org:443 [reason:transparent_tcp_policy_denied]
```

(`logs/goal2-ocsf-excerpt.txt`.) Note that to check methods and paths on HTTPS, the supervisor terminates TLS with its own per-sandbox CA, which the workload trusts. That is how L7 rules and credential injection work; it also means the supervisor sees request contents, which matters for how we describe privacy.

## 5. Goal 3: credential placeholder

No real secret was used. I started a tiny Node HTTP server on the host at `127.0.0.1:18555` that logs what arrives (`tests/echo-server.js`), wrote a custom provider profile `nearai-fake` (`policies/provider-nearai-fake.yaml`: credential `NEARAI_API_KEY`, bearer in `Authorization`, the only endpoint `host.openshell.internal:18555`, binary node), and created a provider with a generated fake value `FAKE-NEARAI-KEY-...`.

```sh
openshell profile import -f provider-nearai-fake.yaml
openshell provider create --name nearai-fake-1 --type nearai-fake --credential NEARAI_API_KEY="$FAKEKEY"
openshell sandbox create --name nearai-spike-2 --policy run-policy.yaml --provider nearai-fake-1 ...
```

| Inside the sandbox (`tests/cred.js`) | Result |
|---|---|
| C1 value of `$NEARAI_API_KEY` | `openshell:resolve:env:v11278428660970894216_NEARAI_API_KEY` |
| C2 does the environment contain the fake key anywhere | no (also checked from bash and `/proc/self/environ`) |
| C3 `Authorization: Bearer $NEARAI_API_KEY` to the bound endpoint | HTTP 200; the endpoint received `Bearer FAKE-NEARAI-KEY-...` |
| C4 placeholder in a POST body (body rewrite not enabled) | endpoint received the placeholder, not the key |
| C5 the same bearer header to `registry.npmjs.org` (allowed by network policy) | HTTP 403 `credential_endpoint_mismatch`, never forwarded |
| C6 placeholder moved into a query string on the bound endpoint | HTTP 403 `credential_placement_mismatch` |

What the endpoint logged is in `logs/goal3-endpoint-received.jsonl`. Two cautions for the design: the docs say responses are not scrubbed, so an approved endpoint that echoes the `Authorization` header back would hand the real key to the agent; bind credentials only to endpoints we trust. And `--credential KEY=value` puts the value on a command line (visible in `ps`); our integration should use the bare-key form (`--credential KEY`, read from the environment) or the API.

## 6. Goal 4: DID draft and containment proofs

### DID draft

Files: `openshell-spike/did/parent.did.json`, `child.did.json`, `widened-child.did.json`. They follow W3C DID Core (`@context`, `id`, `controller`, `verificationMethod`, `authentication`, `service`) and put our constraints in an extension member `agentGuardrails`. **Clearly marked DRAFT**: `did:near` is a placeholder method name, keys, signatures and the registry contract are dummies.

Shape of `agentGuardrails` (child shown):

```json
"agentGuardrails": {
  "version": "0-draft",
  "parent": "did:near:orchestrator.placeholder.near",
  "authority": {
    "network": { "hosts": ["registry.npmjs.org", "cloud-api.near.ai"] },
    "mcp": [ { "server": "mcp.docs.placeholder", "tools": ["search_docs"] } ],
    "send": [],
    "schedule": false,
    "skill.write": { "scope": [] },
    "spend": { "usd": 5.0, "period": "P1D" },
    "delegation": { "maxDepth": 1 },
    "expiry": "2026-11-22T00:00:00Z"
  },
  "sandbox": {
    "format": "openshell-policy/v1",
    "formatPinnedTo": "openshell 0.1.8",
    "policyRef": "child-sandbox.yaml",
    "policyHash": "sha256:a12d29a7...",
    "containmentProof": { "tool": "openshell-prover 0.1.8", "boundary": "parent.sandbox.policyHash", "result": "within_boundary required" }
  },
  "proof": { "type": "DataIntegrityProof-placeholder", "signedBy": "did:near:orchestrator.placeholder.near#key-1", "proofValue": "zDRAFT-NOT-SIGNED" }
}
```

The sandbox section is a **reference by hash** to an OpenShell policy file rather than inline YAML, so the chain anchor stays small and the policy can be stored off chain. Parent sandbox policy (`did/parent-sandbox.yaml`): files `/sandbox /tmp /dev/null` read-write and system paths read-only, `hard_requirement`, UID 1000, npm `read-write`, NEAR AI inference `GET /v1/models` and `POST /v1/chat/completions`. Child (`did/child-sandbox.yaml`): drops `/tmp` write, npm `read-only`, inference `POST /v1/chat/completions` only.

### Prover runs (`logs/goal4-prover.txt`)

`openshell-prover check <candidate> --boundary parent-sandbox.yaml`, each in 24 to 72 ms:

| Candidate | Change from the child | Result | Exit |
|---|---|---|---|
| `parent-sandbox.yaml` | (self) | `within_boundary` | 0 |
| `child-sandbox.yaml` | narrowed | **`within_boundary`** | 0 |
| `widened-net-host.yaml` | adds `github.com:443` full | **`exceeds_boundary`**, counterexample `host=github.com:443 method=GET path=/` | 1 |
| `widened-method.yaml` | npm `access: full` (parent is read-write) | **`exceeds_boundary`**, counterexample on `registry.npmjs.org` with a method outside the parent's set | 1 |
| `widened-binary.yaml` | rules for `/usr/bin/bash` instead of node | **`exceeds_boundary`**, counterexample `binary=/usr/bin/bash ... POST /v1/chat/completions` | 1 |
| `widened-landlock.yaml` | `best_effort` | **`exceeds_boundary`**, `landlock boundary=hard_requirement candidate=best_effort` | 1 |
| `widened-fs.yaml` | adds `/home` read-write | `unsupported`: "filesystem write containment for '/home' depends on sandbox path resolution" | 3 |
| `widened-fs-etc-write.yaml` | moves `/etc` from read-only to read-write | `unsupported` (same reason) | 3 |
| `narrowed-subpath.yaml` | `/sandbox/project` instead of `/sandbox` (a real narrowing) | `unsupported` (same reason) | 3 |
| `child-mcp.yaml` | adds an MCP rule | `unsupported`: "only L4 TCP and REST are modeled" | 3 |
| reverse: parent checked against child | | `exceeds_boundary` | 1 |

So: **for network, the widened child is rejected with a concrete counterexample. For files, any path that is not also listed in the parent comes back `unsupported`**, including a genuine narrowing to a subfolder. The docs say the prover compares filesystem rules path by path and refuses to reason about sub-paths because a symlink in the image could break the containment. That is a sound choice, but it means the filesystem vocabulary in our policies must be **a fixed set of canonical paths** (for example `/sandbox`, `/tmp`, system paths), with children only allowed to drop paths or turn read-write into read-only. Treat everything other than `within_boundary` as a reject, as the docs advise.

### Authority section check

The prover does not cover spend, send, schedule, skills, MCP tools, depth or expiry. I wrote a small draft verifier (`tests/verify-delegation.js`) that does what a delegation check would do at run admission: (1) re-hash each referenced policy file and compare with `policyHash`, (2) check the child's authority is a subset of the parent's (hosts, MCP server and tools, send channels, schedule, skill.write scope prefix, spend amount and period, depth strictly below the parent, expiry not later), (3) run the prover. Output (`logs/goal4-verify-delegation.txt`):

```
did:near:worker-1... under did:near:orchestrator...: ACCEPT (prover: within_boundary, ...)
did:near:worker-2... under did:near:orchestrator...: REJECT (prover: exceeds_boundary, ...)
  - authority: network host 'github.com' not granted by parent
  - authority: mcp tool on mcp.docs.placeholder 'delete_doc' not granted by parent
  - authority: send channel 'telegram:anyone' not granted by parent
  - authority: skill.write scope 'skills/**' outside parent
  - authority: spend 500/P1D exceeds parent 50/P30D
  - authority: delegation depth 2 not below parent 2
  - authority: expiry 2027-06-01T00:00:00Z after parent 2026-12-31T23:59:59Z
  - sandbox: prover exceeds_boundary :: {"domain":"network", "host":"github.com", ...}
```

Observations for the DID design:
- `authority.network.hosts` and the sandbox policy's hosts say the same thing twice. Either generate the sandbox network rules from the authority section, or check that they agree. I would generate.
- MCP over the network can be enforced by OpenShell (`protocol: mcp` with tool allowlists) but cannot be proven by it. Keep MCP tool containment in our own subset check, as the verifier does.
- Spend periods are not directly comparable (5 USD per day versus 50 USD per 30 days). The draft check requires the child amount and period both to be no larger, which is conservative. Budgets really need a running total held by the parent, not just a static comparison.

### Platforms for our users

| Where | Works? | Notes |
|---|---|---|
| Linux desktop, kernel 6.2+ with Landlock, Podman 5 or Docker 28+ | **Yes, shown here** with rootless Podman and no root. | Needs the gateway running as a user service and a local PKI. Docker works too but the gateway then talks to the Docker socket, which is root-equivalent; rootless Podman is the better default where available. |
| macOS Apple Silicon with Docker Desktop or Podman machine | Supported by OpenShell (kernel features run in the Linux VM). Not tested here. | Gateway binary exists for `aarch64-apple-darwin`. Intel Macs are not listed. |
| Windows | WSL 2 plus Docker Desktop is "experimental"; native MXC is on a separate branch and "not production-qualified". | Offer `container` or `host` backends, labelled. Prover has no Windows build. |
| code-server in Docker (our shared setup) | Possible, but only with the gateway **on the host**. | The code-server container must never get the Docker or Podman socket. Run the gateway on the host (rootless Podman), bind it to an address the code-server container can reach (for example the bridge address, or a Unix socket bind-mounted into the container, which is safe because it is the OpenShell API with mTLS, not the container runtime API), and give the extension a client certificate. The project copy then moves over the OpenShell upload API, not over a shared folder. The default listener on `127.0.0.1` is not reachable from inside the container, so this needs explicit configuration. |
| NEAR AI relay (server) | Best fit (Linux, already containerised). | Same rule: gateway beside the relay, never the runtime socket inside the relay container. |

### GPU and arm64 (requested by the coordinator; from docs and source, not tested on GPU hardware)

This host: `uname -m` = `x86_64`; `lspci` shows one GPU, `AMD/ATI Phoenix1` (an integrated Radeon); `/dev/kfd` and `/dev/dri/{card1,renderD128}` exist; no CDI specs (`/etc/cdi` and `/var/run/cdi` absent).

- **arm64 (NVIDIA GB10)**: supported. Linux arm64 is a listed platform for the CLI, gateway, prover and sandbox runtime, and the release ships `aarch64-unknown-linux-*` artifacts and multi-arch images (`docs/about/support-matrix.mdx`). The workload image must be arm64 too.
- **NVIDIA GPUs**: first-class. `openshell sandbox create --gpu [N]` selects NVIDIA CDI devices (`nvidia.com/gpu=...`) on Docker and Podman, which requires the NVIDIA Container Toolkit to have generated CDI specs on the host; Kubernetes uses `nvidia.com/gpu` limits; the MicroVM driver takes one GPU by PCI address (`gpu_device_ids`). When a GPU is requested, the sandbox runtime automatically adds the NVIDIA device nodes (`/dev/nvidiactl`, `/dev/nvidia-uvm`, `/dev/nvidia<N>`, ...) to the Landlock allowlist (`crates/openshell-sandbox/src/boundary_server.rs`, `enrich_gpu_filesystem_paths`). GPU access is opt-in per sandbox, so "only when policy allows" maps to whether our backend passes `--gpu`.
- **AMD GPUs (Strix Halo, ROCm/Vulkan)**: not first-class, but not blocked. Explicit CDI selectors are "not restricted to NVIDIA names" (`docs/how-it-works/sandboxes/overview.mdx`), and the Podman driver has a test accepting `amd.com/gpu=0` (`crates/openshell-driver-podman/src/container.rs`, `container_spec_accepts_non_nvidia_explicit_and_resolved_cdi_devices`). So with AMD's container toolkit generating CDI specs, `--gpu --driver-config-json '{"podman":{"cdi_devices":["amd.com/gpu=0"]}}'` should place `/dev/kfd` and `/dev/dri/renderD*` in the container. Gaps: (1) the automatic Landlock enrichment only knows NVIDIA and WSL device paths, so our policy must list `/dev/kfd` and `/dev/dri` (read-write) itself; (2) default `--gpu` selection (without explicit CDI IDs) only picks NVIDIA devices; (3) the workload user may need the `render` and `video` groups (there is code for GPU runtime groups, untested for AMD); (4) whether ROCm's ioctls pass the seccomp prelude is untested. **Needs a hardware test before we promise it.**
- **Pooled GPUs across linked boxes**: nothing in OpenShell does this. Each sandbox gets devices on its own host. Pooling would be a Kubernetes cluster spanning the boxes (OpenShell's Kubernetes driver, GPU scheduling by the cluster) or a model server on each box that sandboxes call over the network through an allowed endpoint (`host.openshell.internal` or a LAN host). The second is simpler and fits the network policy model.

### Surprises

1. **Downloads keep symlinks** (section 3). The biggest design finding.
2. **The prover cannot prove file-path narrowing** to sub-folders, and file widening returns `unsupported`, not `exceeds_boundary`. Both fail closed, but our policy compiler must use a fixed path vocabulary.
3. **`--upload DIR:/dest` nests the folder** (`/dest/DIR`), and outside a git work tree it uploads everything without `.gitignore` filtering (with a warning). Inside a git work tree it applies `.gitignore` by default, which happens to exclude `.near-ai/state` today; we should not rely on that and should build the copy ourselves (as with `git archive`).
4. **A local gateway is not "just a binary"**: it needs mTLS material and JWT signing keys before the Podman driver will launch anything, plus a container runtime socket on the host.
5. **The Podman driver resolves images through the Podman API's storage**, so the image the agent uses must be built or loaded into the same storage the gateway's Podman service sees.
6. **Sandbox loopback is private**: a dev server the agent starts is reachable only inside the sandbox (or through `openshell forward`/`service`), and host services are reachable only through `host.openshell.internal` with a policy rule. Good for safety, and a UX change for "run the dev server and open the browser".
7. **Unix socket path length** (108 bytes) bit immediately with our long scratch paths.
8. Network decisions resolve DNS inside the supervisor and hand the workload synthetic `198.18.x.x` addresses for unapproved names; tools that print resolved IPs will show odd addresses.

## 8. Recommendation for the execution-backend phase

**Adopt** (as an optional backend, as the analysis proposed):
1. An `executionBackend` setting with `host` (today), `container`, and `openshell`. With `openshell`, run the agent's shell commands through one sandbox per agent run, via the OpenShell API (TypeScript SDK or CLI), not `bash -c` on the host.
2. **Copy in, diff out**: build the copy from tracked files (`git archive` of a worktree, or of the working tree including uncommitted changes, never `.near-ai/state`, never `.git`), upload it, and on completion compute a diff on the host and show it for approval. The apply step must reject symlinks, special files, mode changes and protected paths. This is the part that needs the most care and tests.
3. **Policy generated from the agent's DID / team policy**: a fixed vocabulary of filesystem paths, network rules per binary with `enforcement: enforce`, `landlock: hard_requirement`, non-root UID. Pin the schema to the OpenShell version we ship.
4. **Credentials through providers**, never in the sandbox environment. Keep NEAR AI model calls in the extension where possible; use providers for tools that need a key (`npm publish`, `gh`), bound to exact endpoints and placements.
5. **The prover at delegation time**, plus our own subset check for the authority section (draft verifier in `tests/verify-delegation.js` shows the shape). Accept only `within_boundary`.
6. **OCSF events into our activity view**: the log lines already name binary, host, rule and reason, which is what the approval cards need to explain a block.

**Gaps we must build**: gateway lifecycle for users (install, PKI generation, user service, upgrades, telemetry off), the diff/apply guard, a UI that says which boundary is active, a dev-server/port story, image management (which image, built where, which tools inside), and Windows/Intel Mac fallbacks.

**Risks**: OpenShell is 0.1.x with weekly releases and some interfaces marked Experimental; pin a version, verify attestations, re-test on each bump. The gateway binary is large (113 MB) for an editor extension to download. AMD GPU support needs hardware testing. code-server deployments need a host-side gateway and careful network wiring. Supervisor TLS interception means request contents pass through the supervisor (local, but worth stating in SECURITY.md).

**Suggested next step**: a small integration spike inside the extension (behind a setting, Linux only) that runs one agent turn through the OpenShell API with the copy-in/diff-out flow and the apply guard, before planning the full phase.
