Agent Platform Direction

What to take from Hermes Agent, IronClaw and NVIDIA OpenShell so our agent teams work better, more efficiently and, where people want it, more autonomously, inside the DID trust and governance model we intend to build. Also: whether to fork IronClaw, how plugins should work, and how this fits the move to a product built on Eclipse Theia.

Based on three source-level reviews (shallow clones of each repository, read but never run) and on our own code on main and the relay branch.

Recommendation

Keep our TypeScript engine and build the governance layer into it. Do not fork IronClaw now. Take IronClaw's capability and authorization design, Hermes's best workflow ideas reshaped to pass a DID policy gate, and OpenShell as the sandbox that enforces policy outside the agent's process. Build the editor-independent parts now; they move to Theia unchanged. Ship the first Theia product as a container appliance, then a desktop app from the same code.

The owner's starting preference was to fork IronClaw and add Hermes and OpenShell to it. The reviews found that this would mean porting most of our product into Rust while IronClaw itself still lacks DIDs, a Teams channel and NEAR AI attestation checks. The same design fits our code at a fraction of the effort. A low-risk way to keep the option open is described below.

Not now

Fork IronClaw as our core

Rust, about 1.38 million lines in 61 crates. Means re-coding teams, GSD, approvals, privacy tiers, attestation and the spend ledger. Estimated 3 to 6 months plus permanent rebase cost.

Optional

IronClaw as a backend

Run upstream IronClaw unmodified behind its OpenAI-compatible Responses API, contribute upstream, fork only if upstream refuses something essential.

Recommended

Our engine, their designs

Capability manifests, restrict-only delegation and run contracts from IronClaw; scheduling and package lifecycle from Hermes; enforcement from OpenShell.

Avoid

Hermes plugins

Hermes's own docs say its plugin capabilities are a consent record, not a security boundary. They cannot carry DID constraints.

A sandbox runtime for any agent: a trusted supervisor outside, Landlock and seccomp inside, a network fence, and per-program network rules down to HTTP method and path. Trust and governance layers

Our plan in .planning/PROJECT.md: every agent gets a NEAR implicit account and a W3C DID carrying its limits, can never grant itself more than it was created with or delegated, only the orchestrator changes a DID and only with a person's delegated authority, and on-chain policy gates each action. None of the three projects has DIDs. Each fills a different layer:

Identity and delegationon chain (NEAR)

The DID chain from person to orchestrator to sub-agent to tool: policy hash, parent signature, expiry, revocation. Every delegation can only narrow: child equals parent intersected with the member's own limits.

Policy decisiononce per run, then local

At run start, verify the DID chain and revocation on chain and issue a short-lived lease. Every tool call inside the run passes one local gate, authorize(actorDid, capability, context), with a floor no mode or DID can override. If the chain is unreachable, a signed local copy is checked and the gate fails closed. Per-action checks never go on chain.

EnforcementOS sandbox + per-tool fence

An OpenShell-style sandbox loads only the policy whose hash matches the lease. The agent works on a copy of the project, so protected folders such as .near-ai/state/keys are simply absent. Egress allowlists and a credential broker apply here. IronClaw-style WASM isolation can be the inner fence for individual tools.

Auditsigned, hash-chained

Every grant, consent, delegation and decision goes into the signed event log in OCSF format, with its root anchored on chain from time to time.

Hard rules for anything we adopt

One gate for every tool call. No side doors for plugins, skills, hooks or schedules.
Delegation only narrows. Leaves are denied the tools that amplify authority.
Skill, memory and plugin text never grants authority.
Plugin and tool code never runs inside the extension or engine process.
Adding tools, servers or schedules is itself governed and never available to member agents.
Agents may propose new rules, schedules or skills. Only a person approves them.

Plugins for our teams

Use a hybrid. MCP servers, always out of process, plus our markdown team, agent and skill files remain the building blocks. A package adds a thin signed plugin.json in the cross-vendor Agent Plugins v1 layout (skills/, agents/, teams/, mcp.json) with a capabilities block that maps one-to-one onto DID constraints such as network{hosts}, mcp{server,tools}, send{channel}, schedule, skill.write{scope} and spend{usd}.

  • Enforced, not just consented to: the gate and the sandbox apply the capabilities block, the way IronClaw enforces its tool manifests.
  • Lifecycle from Hermes: packages install disabled, are pinned to a commit, are scanned on install, and need fresh consent when an update widens capabilities.
  • Not WASM as our tool format: MCP already covers tools; WASM stays an option for the inner fence.
  • Theia fit: Theia AI already reads agent.md agents, SKILL.md skills and MCP, so this format carries over.

What not to copy

In-process pluginsHermes default; any plugin bug or compromise owns the process.
Approvals offHermes YOLO mode and IronClaw's auto-approve default.
Free self-writesAgents writing skills, memory or cron jobs without a person's approval.
Checks skipped in containersHermes skips its dangerous-command check there.
Shared credential poolsChild agents must never inherit a parent's keys.
MCP sampling on by defaultLets a server drive the model.
Global policies that replaceOpenShell global policies override an agent's policy instead of narrowing it.
Audit-only enforcement and telemetryOpenShell defaults; both off in anything we ship.
Mounting the live checkoutOpenShell warns it bypasses the file policy; use a copy.
Docker socket in code-serverRoot-equivalent control of the host. Run the sandbox gateway on the host instead.

The relay

Keep building it. IronClaw has no Teams channel, dropped Signal after 1.x, and does not run our teams. Borrow IronClaw's channel manifest shape and its two-step setup: the operator configures a channel once, then each person pairs. The relay is the best fit for OpenShell (Linux, containerized, multi-tenant, workspaces map to tenants), and a sandbox should be required there once the relay runs tools. Phase 68 (PR #50) stands as built. Phase 69 planning is on hold until this direction is agreed.

Theia and how it installs

Theia is a sound base for a branded product: its own branding, browser and desktop forms from one codebase, Theia AI for agents, skills and MCP, and VS Code extension compatibility (v1.77 is current). Two caveats: the @nearai chat participant API is stubbed in Theia, and Theia stores AI API keys in clear text in settings, so we keep our own secret handling.

About 30 of our files import VS Code (28 of 126 in src/services, plus the webviews). The agent core, domain, GSD, MCP and relay code import nothing from VS Code and move as they are.

Now

Build priorities 1 and 2, the package format and the relay as editor-independent packages. Keep new UI in the current webviews small.

First Theia

A container appliance: Theia in the browser, the agent engine, the relay and an optional OpenShell gateway in one Compose stack, with optional GPU passthrough through the NVIDIA Container Toolkit. It replaces today's code-server setup, runs on any Linux machine with Docker or Podman, and can be loaded offline. The current VSIX can bridge the first release inside it.

Second

The desktop app from the same code, for people who want a local install. Rebuild Team Studio and chat as Theia widgets and agents. Add routines' UI and learned skills here.

If shared

When several people share one machine, Theia Cloud gives each person a container on Kubernetes. Until then, one container per person or per team is enough.

Throughout

Keep publishing the VS Code extension while the shared core makes it cheap.

Decisions needed

  1. Fork or not. Accept "our engine, their designs", or choose the IronClaw-as-backend experiment, or the full fork.
  2. Target hardware. Is it a shared server or appliance used by several people, or one machine per person? This decides whether Theia Cloud is needed.
  3. IronClaw upstream. Ask NEAR AI why main has been quiet since 10 September before depending on it in any form.
  4. OpenShell spike. One to two days on Linux: run the agent shell on a worktree copy inside OpenShell and confirm a run-time read of .near-ai/state/keys becomes impossible. Half a day more to draft a DID document with a sandbox section and run the prover on a parent and child pair.
  5. Relay scope. Resume Phase 69 with these designs folded in (capability manifest, run contracts, channel pairing), or re-plan v0.7.0 first.
