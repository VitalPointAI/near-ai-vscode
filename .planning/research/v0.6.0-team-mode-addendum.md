# Addendum Specification: Team Mode (multi-user, multi-agent coordination)

**Product:** Near AI for VSCode (`VitalPointAI/near-ai-vscode`)
**Baseline:** 0.4.8 (`main` at dd2f3d2)
**Proposed milestone:** v0.6.0 Team Mode, phases 25 to 32 (numbering continues from ROADMAP.md)
**Status:** Draft for owner review
**Date:** 2026-10-31

---

## 1. Purpose

Extend the extension from a single-developer harness into a team harness where several people, each running their own NEAR AI agents, work one project toward Open-GSD milestones and releases without colliding. The addendum covers:

1. Membership: invite people to a project, give them roles, remove them cleanly.
2. Shared plan of work: a live Kanban board derived from the GSD roadmap, phases and plans.
3. Automatic dispatch: the system works out what is ready, who should do it, and offers or assigns it.
4. Deconfliction: no two members or agents work the same item or the same files at the same time; duplicates are refused.
5. Integration: every member's and agent's output reaches the integration branch through one verified, reviewed merge path.
6. Economics: per-member token and dollar budgets, allocation and reallocation, hard caps at the provider, metrics.
7. The other things a multi-user, multi-agent system needs (section 13).

Out of scope: real-time co-editing of the same file (Live Share style), hosted SaaS operated by VitalPoint, mobile clients.

## 3. Key design decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | **Coordination state is an append-only, signed event log**, materialised locally into board state. | Every client can verify history; replay gives audit for free; no mutable shared record to fight over. |
| D2 | **Default transport is the project's own git remote** (orphan branch `near-ai/coordination`). An optional self-hosted relay (Phase 32) adds real-time push. | Zero new infrastructure for a small team; works anywhere the code already lives. A push of a descendant commit is an atomic compare-and-swap on the ref, which gives linearised claims. |
| D3 | **Claims are compare-and-swap on the log; first committed wins.** Leases carry a TTL and heartbeat. | Prevents duplicate work by construction rather than by convention. |
| D4 | **One branch and worktree per claim; nobody and no agent writes to the integration branch directly.** All code lands through the integration queue. | Fratricide becomes impossible at the git level; out-of-scope edits are caught at merge. |
| D5 | **Each member uses their own NEAR AI API key**, created in the team's NEAR workspace. Secrets never transit the coordination log. The lead sets a spend limit per key through NEAR's API. | Hard budget enforcement at the provider, not just in a client a member controls. Per-key usage gives authoritative per-member spend. |
| D6 | **Coordination log carries metadata only**: no prompts, source, diffs, tool output or secrets. | Preserves the UX-CONTRACT privacy boundary and keeps the branch small. |
| D7 | **The GSD files stay the plan of record; the log is the status of record.** `STATE.md` progress is regenerated from the log on the integration branch. | Removes the most common merge conflict (everyone editing STATE.md) while keeping GSD native. |
| D8 | **Team core lives in `src/domain/team/` and `src/team/` with no `vscode` imports.** | Testable with `node --test`; portable to other hosts (for example a future workbench or CLI) without rewrite. |
| D9 | **Team Mode is opt-in per project.** A project without `.planning/.near-ai/team.json` behaves exactly as 0.4.x. | No regression for solo users. |

## 4. Concepts and vocabulary

- **Team:** the set of people working one project. One team per project; ID `team-<hex32>`.
- **Member:** a human identity in the team. Has a signing key per device, a role, an availability state, skills, and an optional NEAR API key ID.
- **Agent:** an `AgentRun` started by a member. Agents never act on their own authority; every agent runs under a member and a claim.
- **Role:** `owner`, `lead`, `developer`, `reviewer`, `observer` (section 6.3).
- **Work item:** a card. Hierarchy: Milestone > Phase > Plan > Task. Plans are the default unit of claim; tasks are the unit of parallel agent work inside a plan.
- **Claim:** a member's exclusive right to work an item, with a branch, a worktree and a lease set.
- **Lease:** an exclusive, time-limited right to change a set of paths (globs) or a named resource (for example `integrator`, `schema:db`, `deps`).
- **Allocation:** a budget amount granted to a member (and optionally ring-fenced to a phase or plan).
- **Integration queue:** the ordered list of claims waiting to merge; processed by whoever holds the `integrator` lease.

### 5.2 Coordination log

**Event envelope** (JSON, one file per event, canonical JSON for signing):

```ts
interface TeamEvent<T extends TeamEventType = TeamEventType> {
  v: 1;
  id: string;              // evt-<ulid>
  teamId: string;
  type: T;
  lamport: number;         // max(seen)+1
  at: string;              // author clock, ISO; display only, never used for ordering
  author: string;          // memberId
  device: string;          // key fingerprint
  prev: string;            // id of the event this author last saw at the head (causal hint)
  body: TeamEventBody[T];
  sig: string;             // Ed25519 over canonical JSON without sig
}
```

**Ordering:** commit order on the coordination branch is the total order. Lamport is a tiebreak for relay transport and a sanity check.

**Validation on read (every client, every event):** signature valid; device key bound to author by a roster event earlier in the log; author's role at that log position permits the event (`decideTeamAction`); body schema valid; referenced entities exist. Invalid events are skipped and shown in a "Rejected events" diagnostics list with reason; they never change state.

**Snapshots:** every 500 events, the integrator writes `snapshots/<lamport>.json` (signed). New members load the latest snapshot plus later events.

**Event types (initial set):**

| Group | Types |
|---|---|
| Roster | `team.created`, `member.invited`, `member.joined`, `member.role-changed`, `member.removed`, `device.added`, `device.revoked`, `member.availability`, `member.skills` |
| Work | `item.imported`, `item.created`, `item.updated`, `item.estimated`, `item.blocked`, `item.unblocked`, `item.cancelled`, `item.reopened` |
| Claims | `claim.offered`, `claim.accepted`, `claim.declined`, `claim.taken`, `claim.heartbeat`, `claim.released`, `claim.handed-off`, `claim.expired`, `claim.progress` |
| Leases | `lease.granted`, `lease.extended`, `lease.requested`, `lease.released`, `lease.expired` |
| Integration | `integration.queued`, `integration.started`, `integration.verified`, `integration.failed`, `review.requested`, `review.submitted`, `integration.merged` |
| Budget | `budget.set`, `allocation.granted`, `allocation.revoked`, `allocation.requested`, `allocation.decided`, `spend.summary`, `spend.reconciled`, `budget.alert` |
| Collaboration | `comment.added`, `mention`, `handoff.note`, `decision.recorded` |
| Control | `team.stop`, `team.resume`, `policy.changed`, `snapshot.written` |

### 5.3 Git transport

- Branch: `near-ai/coordination` (orphan, configurable to a custom ref such as `refs/near-ai/coordination` for hosts that allow it). Layout: `events/<lamport 12-digit>-<eventId>.json`, `snapshots/`, `team.json` (genesis copy).
- **Append:** fetch the branch; validate the event against the materialised head (for example a claim is still free); commit the event file on top of the fetched head; `git push origin <commit>:refs/heads/near-ai/coordination` without force. Rejection (non-fast-forward) means someone appended first: fetch, re-materialise, re-validate, retry (max 5, jittered backoff). A claim that is no longer valid after re-validation is reported to the user as "taken by X", not retried.
- **Read:** poll every `nearAi.team.pollSeconds` (default 15 while a claim is active or the board is visible, 120 otherwise), plus immediate fetch after any local append and on window focus.
- Uses a dedicated bare mirror under extension global storage so coordination fetches never touch the user's working tree or index.
- Never force-pushes. Never rewrites history. Uses `GIT_TERMINAL_PROMPT=0` and the user's existing git credentials.
- Scale target: 25 members, 100 concurrent agents, 10 appends per minute sustained. Beyond that, use the relay.

### 5.4 Relay transport (Phase 32)

Self-hosted, zero-dependency `node:http` plus server-sent events, shipped as a container image. Same event format; the relay enforces append ordering and CAS on claim and lease keys, verifies signatures, and pushes events to connected clients. Clients still re-verify everything; a malicious relay can withhold but not forge. Borrow the threat model and malicious-relay test harness from paused Phase 21.

## 6. Feature specifications

### 6.1 Team creation and identity (TEAM)

- `NEAR AI: Enable Team Mode` on an initialised project: creates `team-<id>`, generates the owner's device key (Ed25519, private key in VS Code SecretStorage, never in settings or the workspace), writes `team.created` and `member.joined` (owner), creates the coordination branch, and commits `.planning/.near-ai/team.json` (team ID, coordination ref, transport, NEAR organization and workspace IDs, policy). `team.json` contains no secrets.
- A member may have several devices; each device key is bound by a `device.added` event signed by the member's existing device or by a lead.
- Member record: `memberId` (`mbr-<hex16>`), display name, git author email(s) for attribution, role, skills (free tags plus `role` names from agent teams), availability (`available`, `focus`, `away`, `offline`, with optional working hours and time zone), WIP limit, NEAR API key ID (not the key).

### 6.2 Invitations, joining, removal (TEAM)

**Invite (lead or owner):**
1. Choose name, email, role, initial allocation.
2. If the team has a NEAR organization configured and the lead has signed in (existing `reportingSignIn` session flow), call NEAR's "invite users to an organization by email" so the person gets org access for their own API key.
3. Write `member.invited` (email hash, role, allocation, expiry, single-use invite code hash).
4. Show an **invite bundle** to copy: repo URL, team ID, coordination ref, invite code. No secrets beyond the single-use code.

**Join (invitee):**
1. `NEAR AI: Join Team` and paste the bundle (or open the repo; the extension detects `team.json` and offers to join).
2. Generate device key; write `member.joined` carrying the invite code. The event is valid only if the code hash matches an unexpired, unused `member.invited`.
3. Accept the NEAR org invitation (deep link or in-extension accept via API), then create or select an API key in the team's NEAR workspace. Record the key ID in `member.joined` or a later `member.skills`/profile event; store the key in SecretStorage scoped to the project (existing `ProjectCredentialScope`).
4. Lead is notified to confirm (optional policy `requireLeadConfirmation`, default on). Until confirmed the member is `observer`.

**Remove:**
1. `member.removed` (lead/owner). All the member's claims are released to `ready` with their branches preserved; leases released; allocations revoked (unspent returns to the pool).
2. If configured, NEAR: remove org member and revoke the API key via API; set its spend limit to zero first so in-flight requests stop.
3. Devices revoked; later events signed by those keys are rejected.
4. Git remote access is outside the extension's control; the removal flow shows a checklist reminding the lead to remove repository access.

| View metrics (all members) | Y | Y | policy | policy | N |

| Create, edit, estimate items | Y | Y | Y (own phase drafts) | N | N |

| Assign or reassign others | Y | Y | N | N | N |
| Grant or revoke leases manually | Y | Y | N | N | N |
| Submit review | Y | Y | Y (not own work) | Y (not own work) | N |
| Approve out-of-scope merge | Y | Y | N | N | N |

`decideTeamAction(state, actorId, action)` in `domain/team/permissions.ts` is the single decision point and is applied both when writing and when validating every incoming event.

### 6.4 Work model and GSD integration (BOARD)

- `gsdImport.ts` reads `ROADMAP.md`, phase directories and `*-PLAN.md` frontmatter and produces a WorkItem graph:
  - Milestone and Phase items from ROADMAP; Plan items from PLAN files (`phase`, `plan`, `wave`, `depends_on`, `files_modified`, `estimate.tokens`, `requirements`, `must_haves`, `autonomous`); Task items from `<task>` blocks or the plan's task list.
  - Item IDs are stable and derived from GSD IDs (`plan:25-03`), so re-import is idempotent and updates rather than duplicates.
- Import runs when GSD planning commands finish (`/gsd-plan-phase`, `/gsd-phase`, etc.) on the integration branch, and on demand. Changes produce `item.imported` / `item.updated` events.
- Items can also be created directly on the board (bugs, chores, spikes) with type, description, scope globs and estimate; these are written back as GSD quick tasks when the item is done if `nearAi.team.writeQuickTasks` is on.
- **States:** `backlog` > `ready` > `claimed` > `in-progress` > `in-review` > `integrating` > `done`; plus `blocked` (flag with reason, any state before done) and `cancelled`.
- **Ready rule:** all `depends_on` done, estimate present, scope declared (files_modified or globs), no unresolved blocker, phase not frozen.
- **Milestone and release:** a milestone card shows progress (plans done / total, weighted by estimate), budget burn, open blockers and a **release readiness checklist**: all plans done, phase verifiers passed, no claims in flight, security scan clean (existing `securityScan.ts`), budget report generated. When ready, the lead runs `/gsd-complete-milestone` from the card; release notes are generated from done items with member and agent attribution.

### 6.5 Team Board (BOARD)

Webview view in the NEAR AI container, also openable as an editor panel.

- **Columns:** the states above, with WIP limits per column and per member (over-limit shows a warning badge and blocks new claims for that member when policy `enforceWip` is on).
- **Swimlanes:** by member (default), by phase, by milestone, or none.
- **Card face:** GSD ID and title, state, assignee avatar initials and agent count, estimate vs actual tokens and cost bar, lease scope summary, dependency count, blocked flag, review status, age in state.
- **Card detail:** description, `must_haves`, dependencies (graph), scope globs, lease holders, claim branch, agent runs (from orchestrator), spend breakdown, comments and decisions, history (events), handoff notes.
- **Interactions:** drag to move only along permitted transitions (permission-checked; illegal drops snap back with a reason). Claim, release, request review, block/unblock, hand off, comment, @mention. Keyboard operable; screen-reader labels; never colour-only (matches UX-CONTRACT).
- **Live updates:** the board re-materialises on every transport update and animates moves (respect reduced motion).
- **Filters:** mine, ready for me, blocked, over budget, by requirement ID, by phase.
- **Board header:** milestone progress, team spend today and to date against budget, active agents by member, integration queue length, team stop indicator.
- **Status bar:** `Team: 2 ready for you · 1 in review · $12.40/$40.00` (click opens the board). The existing GSD status line gains the active claim.

### 6.6 Dispatch and automatic assignment (ASSIGN)

`domain/team/dispatch.ts` is pure: given `TeamState` and a clock, it returns proposals.

**Eligibility filters (hard):**
1. Item is `ready`.
2. Member role permits the claim (reviewers only get review items).
3. Member availability is `available` (or `focus` for items already in their phase) and within working hours if set.
4. Member WIP below limit.
5. Member allocation headroom covers `estimate x safetyFactor` (default 1.25), unless the lead overrides.
6. No lease conflict with any active claim (section 6.7).
7. Separation of duties: a member never gets the review of their own work.

**Score (weights in team policy, defaults shown):**

```
score = 0.30*roleFit + 0.25*fileAffinity + 0.15*continuity + 0.15*capacity
      + 0.10*budgetHeadroom + 0.05*criticalPath - stalenessPenalty
```

- roleFit: overlap between item tags/requirements and member skills.
- fileAffinity: share of the item's scope the member touched in the last 30 days (git log on integration branch, by author email).
- continuity: member has done or is doing items in the same phase.
- capacity: 1 - WIP/limit.
- budgetHeadroom: clipped ratio of remaining allocation to estimate.
- criticalPath: item lies on the longest remaining dependency chain of the milestone.

**Modes** (`team.policy.dispatchMode`):
- `suggest`: proposals shown on the board only.
- `offer` (default): the top candidate gets a notification with Accept / Decline / Later; no answer within `offerTimeoutMinutes` (default 30) offers to the next candidate. Decline reasons feed scoring.
- `auto`: the item is claimed for the top candidate immediately; they are notified and can release.

**Next task:** `NEAR AI: Next Task` (and a board button) pulls the best eligible item for the caller, claims it, prepares the claim workspace, and opens a chat session pre-loaded with the plan, its `must_haves` and the GSD execute command. This is the primary flow for members who prefer pull over push.

**Agent dispatch inside a claim:** within a claimed plan, the member's lead agent (existing team or GSD executor) splits tasks across sub-agents. Each sub-agent gets a **sub-lease** that partitions the claim's lease set; two sub-agents in one claim cannot hold overlapping paths either. Waves from the plan are honoured: wave N+1 tasks start only when wave N completes.

**Re-dispatch triggers:** item becomes ready, claim released or expired, member availability changes, allocation changes, lease freed, integration failed and returned work.

### 6.7 Deconfliction: leases, scopes and duplicate prevention (CLAIM)

**Scope derivation:** a plan's lease set is derived from `files_modified` (exact paths) plus declared globs. Board-created items must declare scope before they become ready. Scopes are normalised (POSIX, repo-relative, no `..`).

**Overlap rule:** two lease sets conflict if any path or glob in one can match a path matched by the other (`leases.ts` implements glob-glob intersection conservatively: when undecidable, treat as conflict).

**Planning-time check:** when items are imported, the dispatcher computes the conflict graph of ready items. Conflicting items are never in flight at the same time; the board shows a "serialised with plan:25-04 (shared: src/services/chat.ts)" note. A lead can split scopes or add a dependency.

**Claim protocol:**
1. `claim.taken` (or `claim.accepted`) and `lease.granted` for the full lease set are appended in one event batch commit; the CAS push guarantees that two members racing for the same item or overlapping leases cannot both succeed.
2. A claim heartbeat (`claim.heartbeat`) is appended every `heartbeatMinutes` (default 10) while the member's client is open and the claim active; heartbeats are batched to limit log growth.
3. A claim with no heartbeat for `leaseTtlMinutes` (default 60) is `claim.expired` by any client's dispatcher; the branch is preserved and the item returns to `ready` with a "has prior work on branch X" note so the next claimant continues instead of restarting.

**Enforcement in the agent runtime (LeaseGuard):**
- `decidePermission` in `src/agent/permissions.ts` gains a lease check: `Write`, `Edit`, delete, rename and any file-writing tool targeting a path outside the run's lease set returns a `ToolError` that tells the agent the path is held by another claim or outside scope and how to request it.
- New agent tool `RequestLease { paths: string[]; reason: string }`: appends `lease.requested`; granted automatically if free and policy allows auto-extension, else routed to the lead.
- Every claim runs in its own worktree on its own branch (section 6.8), so shell commands that write outside the guard still only touch that branch. Integration enforces the same rule (section 6.9 step 2).

**Integration-owned hot spots:** paths in `team.policy.sharedPaths` (defaults: `package.json`, `package-lock.json`, lockfiles, `CHANGELOG.md`, `.planning/STATE.md`, `.planning/ROADMAP.md`, `.planning/REQUIREMENTS.md`) cannot be leased exclusively. Agents may edit them; integration applies merge strategies: union merge for CHANGELOG entries, regenerated content for STATE.md, dependency changes re-resolved by running the package manager on the integration head, and conflicts on others escalated to the lead.

**Named resource leases:** `integrator`, `deps`, `db-schema`, `release` and any custom names in policy. Used for work that is not file-shaped (migrations, version bumps).

**Duplicate prevention:**
- Same item: impossible by CAS (one active claim per item).
- Same work under a different card: when a card is created, compare normalised title tokens, requirement IDs and scope with open items; on overlap above threshold, require the creator to link, merge or confirm "distinct" with a reason (recorded).
- Same code produced twice: integration refuses a claim whose diff is already contained in the integration head (patch-id match) and marks it duplicate.

### 6.8 Claim workspaces (CLAIM)

- `claimWorkspace.ts` generalises `agent/worktree.ts`: branch `near-ai/<itemId>/<memberShort>`, based on the current integration head, worktree in extension storage (as today), opened in VS Code as an extra workspace folder or a new window per user choice.
- Sub-agents under a claim either share the claim worktree (when their sub-leases are disjoint, the default) or get nested worktrees branched from the claim branch (`isolation: worktree`), merged back into the claim branch by the lead agent.
- Commits carry trailers: `Near-Ai-Claim: <claimId>`, `Near-Ai-Item: <itemId>`, `Near-Ai-Agent: <agentId> (<model>)`, and `Co-authored-by:` for the member. These drive attribution and metrics and give an IP and audit trail of which model wrote what.
- Release or handoff keeps the branch; only `integration.merged` or explicit lead cleanup deletes it.

### 6.9 Integration pipeline (INTEG)

The client holding the `integrator` lease (leader election by lease CAS; any eligible client takes it over when the holder's lease expires) runs a sequential merge train:

1. **Rebase** the claim branch onto the current integration head in a scratch worktree. Conflict: return the claim to `in-progress` with the conflict file list; the claimant (or their agent) resolves.
2. **Scope check:** files changed must be within the claim's lease set plus shared paths. Out-of-scope changes require lead approval (shown with the diff stat) or are rejected.
3. **Duplicate check** (patch-id).
4. **Verify:** run `team.policy.verifyCommands` (default for this repo: `npm run lint`, `npm test`; e2e optional per policy) on the rebased tree; then run the GSD verifier against the plan's `must_haves` where the plan has them. Results recorded as `integration.verified` or `integration.failed` with a short summary (no raw output in the log; full output stays local and in the member's transcript).
5. **Review gate:** `review.requested` to a human reviewer or a reviewer agent run by a member other than the author, per policy (`reviewPolicy: human | agent | agent-then-human`, default `agent-then-human` for plans touching more than N files or security-sensitive paths). Review findings appear on the card.
6. **Merge:** fast-forward the integration branch to the verified rebased commit; push. If the push is rejected because the head moved, restart at step 1 for this claim.
7. **After merge:** append `integration.merged`; regenerate `.planning/STATE.md` progress from the log; update `estimation-calibration.json` with actual vs estimate; release leases; mark item `done`; trigger dispatch.

Semantic conflicts (each claim passes alone, combined head fails) are caught because each verification runs on the rebased tree, which includes everything merged before it.

Optional: if the project uses a hosted CI and PR flow, `integrationMode: pull-request` opens a PR per claim through the GitHub connector or `gh` and treats CI status and approvals as steps 4 and 5. Local merge train remains the default.

### 6.10 Budgets, allocation and token economics (BUDGET)

**Hierarchy:**

```
NEAR organization balance (read-only, from NEAR)
  └ Team budget (per period: monthly by default; also total for the milestone)
      ├ Milestone / phase ring-fences (optional)
      └ Member allocations (cumulative grants)
          └ Run limits (existing agent.maxRunCostUsd / maxRunTokens)
```

**Units:** budgets are held in nano-USD (matching NEAR billing and the existing ledger) and displayed in dollars; token views are derived using current model pricing. Allocations can also be expressed in tokens for a named model tier; the system converts at grant time and records the conversion.

**Operations (events):** `budget.set` (owner/lead), `allocation.granted` / `allocation.revoked` (lead, cannot exceed unallocated team budget), `allocation.requested` (member, with reason and item link), `allocation.decided` (lead). Unspent allocation policy per period: `rollover`, `return-to-pool` (default) or `expire`.

**Enforcement, three layers, the lowest wins:**
1. **Provider hard cap:** each member's NEAR API key has a spend limit set by the lead via `PATCH /v1/workspaces/{workspace_id}/api-keys/{key_id}/spend-limit` (nano-USD). The extension sets it to the member's cumulative granted allocation and raises it on each grant. Requires the lead's NEAR session (existing sign-in flow). If the team has no NEAR organization configured, this layer is absent and the board says so.
2. **Client pre-flight:** `outboundGuard` and the run budget check remaining member allocation (granted minus confirmed minus pending) before each request and before starting a run; a run's effective cap is `min(run limit, daily limit, member remaining, ring-fence remaining)`.
3. **Claim-level guard:** when a claim's spend reaches `estimate x overrunFactor` (default 1.5), the agent pauses at its next turn boundary and asks the member to continue, request more, or hand back.

**Accounting:**
- Every request is tagged (extended `SpendTag`: `teamId`, `memberId`, `claimId`, `workItemId`, plus existing `kind`, `runId`, `agentId`).
- Each client appends a signed `spend.summary` per claim at heartbeat cadence and on claim end: tokens in, cached, out; estimated, pending and confirmed nano-USD; request count. Aggregates only.
- **Authoritative reconciliation:** the lead's client (or integrator) periodically calls NEAR usage by API key (usage history per key, organisation usage summary with the reporting token) and appends `spend.reconciled` per member. Differences above `reconcileTolerance` (default 5%) flag the member's metrics with "unreconciled" and show both figures.

**Alerts:** at 50, 80 and 100% of member allocation, phase ring-fence and team budget: notification to the member and lead, card badge, `budget.alert` event. Forecast-to-complete per milestone: remaining estimate x member cost-per-estimate ratio vs remaining budget, shown on the milestone card.

**Model policy:** team policy lists allowed models and tiers per role (for example reviewers may not use the most expensive tier) and whether non-TEE routes are allowed at all. Enforced in `capabilityRouter`.

### 6.11 Metrics and analytics (METRIC)

Derived purely from the log, local ledger and git; no prompts or code.

**Per member:** tokens (in, cached, out), cost (confirmed, pending), allocation used %, items done, throughput per week, cycle time (claimed to done) and lead time (ready to done), time in review, rework rate (reopened or failed integration / done), integration first-pass rate, review findings received and given, estimate accuracy (actual / estimated tokens), cost per done estimate point, offers accepted / declined / timed out, active hours (from heartbeats, coarse).

**Per agent (by model and role):** runs, success rate, retries and stalls, tool denials (including lease denials, a signal of poor scoping), cost per completed task, reputation score (existing store).

**Per milestone and phase:** burn-up, budget burn vs plan, forecast completion date and cost, blocked time, critical path.

**Views:** a Team Metrics panel (tables plus sparklines; members see their own, leads see all, policy controls peer visibility) and CSV/JSON export (extends `usageExport.ts`). Metrics are for planning and coaching; the default view sorts by item and phase, not by person, and the spec deliberately excludes keystroke or screen activity tracking.

### 6.12 Collaboration and communication (COLLAB)

- Comments and decisions on cards (`comment.added`, `decision.recorded`), @mentions with notification, plain text only, size-limited (2 KB). Teammate text is untrusted input: when it reaches an agent it is wrapped by `untrusted.ts`, and agents never treat it as instructions.
- **Handoff:** `claim.handed-off` moves a claim (branch, leases, remaining allocation ring-fence) to another member with a structured note (`HandoffState`: what is done, what is next, open risks, verification status). The receiving member must accept.
- **Blockers and escalation:** blocking an item notifies the lead; blocked longer than `escalateAfterHours` re-notifies and highlights the card.
- **Approval routing:** approvals that exceed a member's role (out-of-scope merge, allocation increase, shell command classed as risky under `approve-risky` policy when the member is a developer and policy says so) can be routed to a lead's client as an approval request event; the lead answers from their board.
- **Notifications:** VS Code notifications for offers, mentions, review requests, failures, budget alerts; a digest mode to limit noise; per-member mute settings.

### 6.13 Shared context and memory (COLLAB)

- Project memory (`Remember`/`Recall`, context graph) gains scopes: `personal` (default for a member's agents, stored locally), `team` (shared; written only via approved proposal through `memoryApproval.ts`, committed to `.planning/.near-ai/team-memory/` on the integration branch through the normal pipeline).
- Agent teams: `.planning/.near-ai/team.md` stays the project agent team, versioned through integration. Personal agent teams stay in extension storage.
- GSD artifacts (`CONTEXT.md`, `RESEARCH.md`, `PLAN.md`, `SUMMARY.md`) are produced on claim branches and land through integration like code. Planning items (`/gsd-discuss-phase`, `/gsd-plan-phase`) are themselves board items with scope `.planning/phases/<phase>/**` so two people cannot plan the same phase at once.

### 6.14 Security, safety and audit (SEC)

- Device keys: Ed25519 via `node:crypto`; private keys in SecretStorage only; fingerprint shown in the member card. Key loss: another device or a lead re-binds a new device and revokes the old one.
- No API keys, tokens or session tokens are ever written to the coordination log, `team.json`, settings, transcripts or audit (extend the existing secret-move logic in `reportingToken.ts` to team fields).
- Team-wide stop: `team.stop` event; every client that sees it engages the local emergency stop, cancels runs at the next safe point, and refuses new runs until `team.resume` by a lead. Members can stop the team; only leads resume.
- Audit: all team events are mirrored as `AuditEvent`s with new types (`team-roster`, `claim`, `lease`, `integration`, `allocation`, `team-stop`) and member attribution.
- Prompt-injection boundary: card text, comments, review findings, handoff notes and branch names from others are untrusted data to agents.
- Least privilege: role default tool sets for agents (for example `observer` cannot start runs that write; `reviewer` agents get read and test tools only), enforced by combining role policy with the existing permission rules.
- Rejected-event diagnostics and a "verify log" command that replays and re-verifies the whole log.

### 6.15 Resilience and offline (CLAIM)

- Offline: local actions that need consensus (claim, lease, allocation) are disabled offline with a clear message; local work on an existing claim continues; heartbeats and spend summaries queue and flush on reconnect. If the claim expired while offline, the member is told and offered to re-claim (branch intact).
- Crash recovery: on startup, resume claims and runs held by this device (existing `resumableExecution.ts`), re-verify leases, reap orphan worktrees.
- Clock skew: ordering never uses wall clock; TTLs are measured as elapsed time since the commit timestamp of the last heartbeat as seen by the observer, with a skew allowance.
- Transport failure: exponential backoff, visible state in the status bar ("Team sync paused: remote unreachable"), no silent failure (address the CONCERNS.md swallowing pattern in all new code).

### Success criteria (abridged, per phase)

- **25:** Two VS Code instances on two clones share one coordination branch; an event appended by one is materialised identically by the other; a forged event (bad signature, unbound key, insufficient role) is rejected by both and listed in diagnostics; concurrent appends from both never lose an event.
- **26:** Invite, join and remove complete end-to-end against a fake NEAR API in tests and against a real NEAR organization in a manual check; no secret appears in any written file (canary test).

- **30:** A claim with an out-of-scope edit is held for lead approval; a semantic conflict (each passes alone, combined fails) is caught; a member's own agent cannot satisfy that member's review.

- **32:** Metrics match hand-computed fixtures; team stop from a developer halts all clients and only a lead resumes; injected instructions in a comment do not change agent behaviour (existing untrusted tests extended); relay passes the malicious-relay harness.

## 11. Testing strategy

- **Unit (`node --test`):** all of `src/domain/team/*` with property tests for materialisation (same events in, same state out, order of delivery irrelevant once committed), glob overlap (conservative: never reports disjoint when overlapping), dispatch determinism, budget arithmetic in integer nano-USD.
- **Transport tests:** a local bare repository with N simulated clients appending concurrently (child processes) to prove CAS correctness and no lost events.
- **Agent runtime tests:** extend `agentTools.test.ts` and `worktreeIsolation.test.ts` for LeaseGuard and claim workspaces.
- **Integration tests:** merge train against fixture repositories covering rebase conflict, scope violation, verify failure, semantic conflict, duplicate patch.
- **NEAR API:** fake server for org, invitation, workspace key, spend limit and usage endpoints (pattern from existing `fakeNear` tests); one opt-in live test behind an env flag, as `live.test.ts` does today.
- **E2E (`npm run test:e2e`):** a two-window scenario: enable, invite, join, claim, run a stub agent, integrate, see done on both boards.
- **Privacy canary:** run the full flow with canary strings in prompts, files and keys; assert none appears in the coordination branch, team.json, audit or settings.
